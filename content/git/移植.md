
# Cherry-pick 移植

**Cherry-pick 移植**（通常简称为 **Cherry-pick**）是 **Git 版本控制系统**中的一个核心操作。通俗来说，它的作用是：

**把某一个分支上的“特定几次提交（commits）”，像挑樱桃一样挑选出来，复制并粘贴到另一个分支上。**

---

### 1. 为什么要用 Cherry-pick？

在团队协作中，你经常会遇到这种情况：

- 你在 `develop` 分支上开发新功能，写了一个重要的 Bug 修复。
- 但线上 `main` 分支（生产环境）现在出了紧急问题，**不能**直接把整个 `develop` 合并过去（因为里面还有没测完的其他新功能）。
- 此时，你只需要把“修复 Bug 的那一个提交”单独放到 `main` 分支上。

**Cherry-pick 就是专门解决这个需求的。**

---

### 2. 核心逻辑（白话版）

假设你有两个分支：

- **分支 A**（比如 main）：当前稳定版本。
- **分支 B**（比如 feature）：有 10 个新提交，其中第 5 个提交是“修复了登录密码错误”。

**Cherry-pick 的操作流程：**

1. 切换到分支 A（`git checkout main`）。
2. 执行命令：`git cherry-pick <第5个提交的ID>`。
3. Git 会把第 5 个提交产生的**代码变动**（diff）取出来，在当前分支 A 上重新应用一遍，并生成一个**全新的提交**（但内容和原提交几乎一样）。

---

### 3. 对比“合并（Merge）”和“变基（Rebase）”

| 操作               | 特点                                     | 适用场景                                           |
| :----------------- | :--------------------------------------- | :------------------------------------------------- |
| **Merge（合并）**  | 把**整个分支**的所有提交一股脑拉过来。   | 常规功能开发完成，合并回主分支。                   |
| **Rebase（变基）** | 把整个分支的提交**挪个位置**，重写历史。 | 保持提交历史线性整洁。                             |
| **Cherry-pick**    | **只挑几个**想要的提交，不碰其他的。     | **紧急修复**、**版本回退后补丁**、跨分支复用代码。 |

---

### 4. 典型使用场景

- **紧急热修复（Hotfix）**：测试分支修好了 Bug，但发布分支等不及测完所有功能，只把 Bug 修复挑过去发版。
- **版本管理**：你在 `v1.0` 分支修了一个问题，想把同样的修改同步到正在开发的 `v2.0` 分支，但不想合并老代码。
- **丢弃错误提交**：不小心在错误的分支上写了代码，可以 Cherry-pick 到正确分支，然后删掉错误分支上的提交。

---

### 5. 常用命令示例

```bash
# 1. 切换到目标分支（要把提交拿过来放到这里）
git checkout main

# 2. 挑选一个提交（commit-id 可以去 git log 里复制）
git cherry-pick a1b2c3d4

# 3. 如果挑选多个连续的提交
git cherry-pick a1b2c3d4..e5f6g7h8

# 4. 如果发生代码冲突（最常见的问题）
# 手动解决冲突后，执行：
git add .
git cherry-pick --continue

# 5. 如果不想继续了，放弃这次 cherry-pick
git cherry-pick --abort
```

---

### 6. 重要注意事项（避坑指南）

1. **会产生新的 Commit ID**：虽然代码一样，但 Cherry-pick 过去的提交哈希值（ID）是全新的，和原来不一样。这会导致提交历史出现“重复”的修改记录。
2. **容易引发冲突**：如果目标分支的代码和原分支差异较大，应用补丁时会冲突，需要手工解决。
3. **不要滥用**：如果频繁 Cherry-pick 几十个提交，说明你的分支策略可能有问题。它适合“零星挑选”，不适合“大量同步”。大量同步应该用 Merge。
