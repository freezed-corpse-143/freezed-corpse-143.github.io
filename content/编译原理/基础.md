# 对齐

对齐（alignment）指一个数据的起始地址必须是某个数 `A` 的整数倍，`A` 就是对齐要求（alignment requirement）。

例如：
- `char` 对齐 1 字节：地址任意。
- `short`（2 字节）通常对齐 2：地址是 2 的倍数。
- `int`（4 字节）通常对齐 4：地址是 4 的倍数。
- `double`（8 字节）通常对齐 8：地址是 8 的倍数。
- 指针：32 位系统对齐 4，64 位系统对齐 8。

这些要求来自 CPU：**未对齐访问可能变慢，甚至触发异常**（如某些 ARM、SPARC、MIPS 架构）。

## 机器字长 vs 对齐边界

| 概念       | 含义                         | 例子                               |
| ---------- | ---------------------------- | ---------------------------------- |
| 机器字长   | CPU 一次自然处理的位数       | 32 位、64 位                       |
| 自然对齐   | 类型地址必须是其大小的倍数   | `int` 对齐 4，`double` 对齐 8      |
| 栈对齐     | 栈指针按字长或 16 字节对齐   | x86-64 SysV ABI 要求栈 16 字节对齐 |
| 结构体对齐 | 整体大小按最大成员对齐值补齐 | 含 `double` 的结构体整体对齐 8     |

所以：
- 在 32 位系统上，`double` 可能要求 8 字节对齐，**超过机器字长 4**。
- 在 64 位系统上，`int` 仍只要求 4 字节对齐，**小于机器字长 8**。
- 因此“按机器字长对齐”只是常见近似，不是严格规则。

## 为什么常按字长来

教材里画内存布局图时，为了简洁，常把方格画成**机器字大小**，因为：

1. 栈上的局部变量、参数、返回地址通常按字压栈。
2. 数组元素若是指针或 `int`，在 32 位系统上正好一字一个。
3. 字是 CPU 自然读写单位，按字画便于讲“一次访存读一个字”。

但这只是**示意图的简化**。真实结构体里会有填充字节（padding），比如：

```c
struct S {
    char  c;   // 1 字节
    int   i;   // 4 字节，前面补 3 字节
    char  d;   // 1 字节，后面补 3 字节使整体对齐 4
};
```

在 32 位系统上，`sizeof(struct S)` 通常是 12，而不是 1+4+1=6。方格图若按字画，就会显示成 3 个字，每个字里再细分字段和填充。

以 小端序为例

```text
高地址
┌──────┬──────┬──────┬──────┐ 0x1008
│ 0xBB │ 0x00 │ 0x00 │ 0x00 │  字[2]：偏移 8~11 
├──────┼──────┼──────┼──────┤ 0x1004
│ 0x78 │ 0x56 │ 0x34 │ 0x12 │  字[1]：偏移 4~7   
├──────┼──────┼──────┼──────┤ 0x1000
│ 0xAA │ 0x00 │ 0x00 │ 0x00 │  字[0]：偏移 0~3  
└──────┴──────┴──────┴──────┘
低地址

(d | padding | padding | padding)
(int i，LSB 在低地址)
(c | padding | padding | padding)
```

字内字节顺序（低地址->高地址）：
- 字 0: `AA | 00 | 00 | 00` -> `c` 后 3 字节填充
- 字 1：`78 | 56 | 34 | 12` -> 小端下 `i = 0x 12345678`
- 字 2：`BB | 00 | 00 | 00` -> `d` 后 3 字节尾部填充

# 大端序

big-Endian

规则：最高有效字节（MSB）放在最低地址。

```text
高地址
┌───────────────────┐ 0x1003
│       0x78        │  LSB  最低有效字节
├───────────────────┤ 0x1002
│       0x56        │
├───────────────────┤ 0x1001
│       0x34        │
├───────────────────┤ 0x1000
│       0x12        │  MSB  最高有效字节
└───────────────────┘
低地址
```

- 字节序列（低地址->高地址）：`12 34 56 78`
- 书写顺序：`0x 12 34 56 78`

优势：
- 快速判正负：符号位（最高位）固定在第一个字节，计算机只要读取第一个字节就能知道这个数的正负，无需知道数据的完整长度。
- 人类的可读性强：与书写顺序一致。
- 网络传输标准：TCP/IP 协议规定使用大端序作为“网络字节序”，确保不同架构的主机通信时有一个统一的解释标准。

# 小端序

Little-Endian

规则：最低有效字节（LSB）放在最低地址。

```text
高地址
┌───────────────────┐ 0x1003
│       0x12        │  MSB  最高有效字节
├───────────────────┤ 0x1002
│       0x34        │
├───────────────────┤ 0x1001
│       0x56        │
├───────────────────┤ 0x1000
│       0x78        │  LSB  最低有效字节
└───────────────────┘
低地址
```

- 字节序列（低地址->高地址）：`78 56 34 12`
- 书写顺序：`0x 12 34 56 78`

优势：

- 算术运算更顺畅：做加法或乘法时，通常需要从最低位开始计算并向高位进位。小端序让低位字节先被读到，便于计算机尽早开始运算，且多轮乘法的中间结果可以直接写入内存，无需频繁移位。
- 类型转换极简：如果有一个 32 位整数，但只需读取它的低 8 位或低 16 位，在小端序下，同一个内存地址直接当作 8 位或 16 位指针来用即可，读出来的恰好就是地位部分。在大端序下，则需要计算偏移量才能找到低位数据。
- 快速判奇偶：判读一个数是奇还是偶，只需看最低位。小端序把最低字节放在最前面，读第一个字节就能得出结论。

# 一个函数从源码到执行

前面的内容讲的是「数据在内存里怎么摆」。这一段换成「代码」：一个普通函数被编译成什么、放在内存哪一块、怎么被调用、怎么返回，以及 CPU 在这中间做了什么。

平台取 x86-64（System V ABI，Linux 默认）：

```c
int add(int a, int b)
{
    return a + b;
}

int compute(void)
{
    int x = 7;
    int y = add(x, 3);
    return y;
}
```

```bash
clang -c -O0 -o func.o func.c
objdump -d -r -M intel func.o
```

## 函数就是一段字节

`add` 的反汇编结果：

| 地址  | 字节              | 汇编                    | 作用             |
| ----- | ----------------- | ----------------------- | ---------------- |
| `0x00` | `55`             | `push rbp`              | 保存调用者的帧指针 |
| `0x01` | `48 89 e5`       | `mov rbp,rsp`           | 建立本函数的帧    |
| `0x04` | `89 7d fc`       | `mov [rbp-0x4],edi`     | 参数 a 落栈       |
| `0x07` | `89 75 f8`       | `mov [rbp-0x8],esi`     | 参数 b 落栈       |
| `0x0a` | `8b 45 fc`       | `mov eax,[rbp-0x4]`     | 读 a             |
| `0x0d` | `03 45 f8`       | `add eax,[rbp-0x8]`     | 加上 b           |
| `0x10` | `5d`             | `pop rbp`               | 恢复帧指针        |
| `0x11` | `c3`             | `ret`                   | 返回             |

整个函数是 18 个字节（`0x00`~`0x11`）。`add` 这个名字只是链接器标在 `0x00` 上的一个符号，运行时并不存在「函数对象」这种东西：**函数 = 起始地址 + 从这个地址开始的一串字节**。

指令是变长编码：`add` 里最短 1 字节（`55`、`5d`、`c3`），`compute` 里最长 7 字节（`c7 45 fc 07 00 00 00`），CPU 靠解码器的状态机逐条切开。

`compute` 的反汇编：

| 地址     | 字节                     | 汇编                  | 作用               |
| ------ | ---------------------- | ------------------- | ---------------- |
| `0x20` | `55`                   | `push rbp`          | 保存调用者的帧指针        |
| `0x21` | `48 89 e5`             | `mov rbp,rsp`       | 建立本函数的帧          |
| `0x24` | `48 83 ec 10`          | `sub rsp,0x10`      | 给局部变量留 16 字节     |
| `0x28` | `c7 45 fc 07 00 00 00` | `mov [rbp-0x4],0x7` | `x = 7`，一条写内存的指令 |
| `0x2f` | `8b 7d fc`             | `mov edi,[rbp-0x4]` | 第 1 个参数进 edi     |
| `0x32` | `be 03 00 00 00`       | `mov esi,0x3`       | 第 2 个参数进 esi     |
| `0x37` | `e8 00 00 00 00`       | `call add`          | 调用               |
| `0x3c` | `89 45 f8`             | `mov [rbp-0x8],eax` | `y = 返回值`        |
| `0x3f` | `8b 45 f8`             | `mov eax,[rbp-0x8]` | 读 y 作为返回值        |
| `0x42` | `48 83 c4 10`          | `add rsp,0x10`      | 释放局部变量空间         |
| `0x46` | `5d`                   | `pop rbp`           | 恢复帧指针            |
| `0x47` | `c3`                   | `ret`               | 返回               |

`0x37` 处的 `e8 00 00 00 00` 位移是 0，因为此时还不知道 `add` 最终会落在哪。目标文件里跟着一条重定位记录：

```text
37: e8 00 00 00 00   call 3c <compute+0x1c>
             38: R_X86_64_PLT32  add-0x4
```

链接器负责把这个 32 位相对位移填成 `add 的地址 - 下一条指令的地址`。所以**函数之间的连接发生在链接期，不是编译期**。

## 存在哪：.text 段

`objdump -h` 看目标文件的段表：

```text
Idx Name   Size      VMA     LMA     File off  Algn
  0 .text  00000048  0       0       00000040  2**4
           CONTENTS, ALLOC, LOAD, RELOC, READONLY, CODE
```

- `0x48` = 72 字节，正好装下 `add`（18 字节）+ 对齐填充 + `compute`（40 字节）。
- 属性 `READONLY, CODE`：装载后这段内存是**可读、可执行、不可写**。往函数地址写字节会触发访问违例。
- `VMA`/`LMA` 在目标文件里都是 0，真正的地址由链接器分配，再由装载器映射到进程地址空间。

两层地址要分清：

| 阶段     | 看到的东西                            |
| ------ | -------------------------------- |
| 源码     | 函数名 `add`                        |
| 目标文件   | `.text` 段内偏移 `0x00`，未解析的 call 位移 |
| 可执行文件  | 链接后的虚拟地址（如 `0x00401130`）         |
| 运行中的进程 | 装载器映射后的地址，可能因 ASLR 与文件里不同        |

装载时 `.text` 被映射成若干页（x86-64 常见 4 KiB 一页），多个函数的字节共享同一页；代码页进入 CPU 的指令缓存，数据页进入数据缓存。

## 怎么调用：call 只做两件事

调用前，调用者先按 ABI 把参数放进寄存器（System V 的整型参数顺序是 `rdi, rsi, rdx, rcx, r8, r9`）：

```asm
mov edi, [rbp-0x4]   ; 第 1 个参数
mov esi, 0x3         ; 第 2 个参数
call add
```

`call` 的语义可以拆成两条：

1. 把**下一条指令的地址**（`0x3c`）压到栈顶 —— 这就是返回地址；
2. 把 `rip` 设成 `add` 的地址。

`rip` 是 CPU 的指令指针，永远指向「下一条要执行的指令」。**改变控制流，本质上就是改 `rip`。**

进入 `add` 后，栈上的内容和寄存器状态如下（假设 `compute` 的 `rbp` 是 `0x7FFF00001000`）：

```text
高地址
0x7FFF00001000  ┌────────────────┐ ← compute 的 rbp
                │      ...       │
0x7FFF00000FFC  ├────────────────┤ x = 7
0x7FFF00000FF8  ├────────────────┤ y（此时还没写）
0x7FFF00000FF0  ├────────────────┤ ← compute 的 rsp（call 之前）
0x7FFF00000FE8  ├────────────────┤ 返回地址 0x3c
0x7FFF00000FE0  ├────────────────┤ 保存的 compute rbp  ← add 的 rbp / rsp
0x7FFF00000FDC  ├────────────────┤ a = 7
0x7FFF00000FD8  └────────────────┘ b = 3
低地址
```

`add` 开头的 `push rbp; mov rbp,rsp` 建立自己的帧：`rbp` 是帧基准，所有局部变量用 `[rbp-偏移]` 访问；返回地址固定在 `[rbp+8]`。

注意 `add` 没有 `sub rsp`：它是叶子函数，System V ABI 允许它直接使用 `rsp` 以下的 128 字节（red zone），这段空间不会被信号处理打断覆盖。

## 怎么返回：值在 eax，栈要还原

```asm
mov eax, [rbp-0x4]   ; a 读进 eax
add eax, [rbp-0x8]   ; 加上 b，结果就留在 eax
pop rbp              ; 恢复调用者的帧指针
ret                  ; 弹出返回地址到 rip
```

- **返回值放哪**：整型和指针放 `rax`（32 位用 `eax`），浮点放 `xmm0`，大结构体则通过隐藏指针由调用者提供空间。
- **`pop rbp`**：把 `[rsp]` 读进 `rbp`，`rsp += 8`。此时栈顶又回到返回地址。
- **`ret`**：把 `[rsp]` 读进 `rip`，`rsp += 8`。控制流回到 `compute` 的 `0x3c`。

回到调用者后，`eax` 里就是 10，`mov [rbp-0x8],eax` 把它写进 `y`，`add rsp,0x10` 把局部变量区域还回去。

`ret` 之后，那块栈内存还在，内容也没被擦掉，但已经「不属于」这个函数了 —— 返回局部变量地址会失效，原因就在这里：地址还有数值，只是那块空间随时会被下一次调用覆盖。

## 变量初始化到底做了什么

| 变量形式             | 初始化发生在    | 内存里是谁写的                        |
| ---------------- | --------- | ------------------------------ |
| `int x = 7;`（局部） | 每次进入函数    | 一条 `mov [rbp-4],7` 指令          |
| `int x;`（局部）     | **没有初始化** | 没有任何指令，读到的是上一次调用留下的值           |
| 全局 `int g = 7;`  | 装载时       | `.data` 段里直接存着字节 `07 00 00 00` |
| 全局 `int g;`      | 装载时       | 落在 `.bss`，文件里不占空间，装载器清零        |
| `"ABC"`（字符串字面量）  | 编译期       | 字节放在只读段 `.rodata`，指针指向它        |

两条容易混的结论：

1. **局部变量有初值 = 一条写内存的指令；没有初值 = 一条指令都没有。** 栈是复用的，所以「未初始化」不是 0，而是上一个函数留下的东西。
2. **全局变量的初值不需要任何指令。** 它躺在文件里，装载器把页面映射进进程，值天然就在；`.bss` 则连字节都不存，由操作系统映射零页来实现「初始为 0」。

## CPU 视角：取指、译码、执行

CPU 的执行循环可以简化成四步，`rip` 是唯一的游标：

```text
取指  ← 用 rip 去内存（实际会先查指令缓存）读指令字节
译码  ← 识别操作码和操作数，算出这条指令有多长
执行  ← ALU 运算 / 访存 / 跳转
写回  ← 结果写进寄存器或内存
rip = 下一条指令地址（跳转指令会改写它）
```

把 `add` 的 18 个字节代进去：

| 指令                  | CPU 实际做的事                            |
| ------------------- | ------------------------------------ |
| `push rbp`          | `rsp -= 8`，把 `rbp` 写入 `[rsp]`（一次写内存） |
| `mov rbp,rsp`       | 寄存器之间搬运，不访存                          |
| `mov [rbp-0x4],edi` | 算地址 `rbp-4`，把 `edi` 写进内存（一次写内存）      |
| `mov eax,[rbp-0x4]` | 算地址 `rbp-4`，从内存读 4 字节进 `eax`         |
| `add eax,[rbp-0x8]` | 读内存、ALU 相加、结果写回 `eax`                |
| `call`              | `rsp -= 8` 写返回地址，然后 `rip = 目标`       |
| `ret`               | 从 `[rsp]` 读地址写进 `rip`，`rsp += 8`     |

所以「函数调用」在硬件层面没有任何特殊待遇：它和加法、访存一样，只是一串普通的指令。不同之处仅在于 `call` 与 `ret` 会修改 `rip`。现代 CPU 靠返回地址预测（return stack）来避免 `ret` 造成的流水线停顿，这也是为什么 `ret` 在性能分析里常常被算成一次「间接跳转」。

## 同一份源码，两种实现

`-O2` 编译同一个文件：

```text
add:
  8d 04 37        lea eax,[rdi+rsi*1]
  c3              ret

compute:
  b8 0a 00 00 00  mov eax,0xa
  c3              ret
```

- `add` 从 18 字节变成 4 字节：参数不再落栈，直接 `lea` 一条算完。
- `compute` 里 `add(7,3)` 在编译期就算出 10，整个调用消失：没有栈帧、没有 `call`、没有局部变量、`y` 也不存在。

**汇编是某次编译的产物，不是语言的定义。** 讨论「这个函数在内存里长什么样」之前，必须先固定编译器和优化级别。

## 不同 ABI 的差异

同样是 x86-64，同一份 C 代码在 Windows 上生成的机器码不一样：

| 项目             | System V（Linux）           | Windows x64                      |
| ---------------- | --------------------------- | -------------------------------- |
| 整型参数寄存器    | `rdi rsi rdx rcx r8 r9`     | `rcx rdx r8 r9`                  |
| 返回值            | `rax`                       | `rax`                            |
| 参数在栈上的位置  | 被调者自己开帧后写 `[rbp-4]` | 写进调用者预留的 shadow space `[rbp+0x10]` |
| 调用者预留空间    | 无                          | 32 字节 shadow space             |
| `call` 时栈对齐   | 16 字节                     | 16 字节                          |

MinGW GCC 生成的 `add` 开头因此是：

```asm
push rbp
mov rbp,rsp
mov [rbp+0x10],ecx    ; 不是 [rbp-0x4]
mov [rbp+0x18],edx
```

ABI 是平台约定，不是语言语义。跨平台不支持「把某个平台的汇编背下来」，只支持「知道在哪一层找约定」。

## 验证方式

```bash
clang -c -O0 -o func.o func.c          # 生成目标文件
objdump -d -r -M intel func.o          # 反汇编 + 重定位
objdump -h func.o                      # 段表、属性、大小
gcc -O0 -S -masm=intel func.c          # 直接看汇编文本
gdb ./func                              # 运行时用 info registers / x/ 看真实栈
```

在调试器里 `break add` 之后执行 `info registers rbp rsp rip`，再 `x/8gx $rsp`，就能看到上面那张栈图上每一个格子的真实值。

# 类在内存里放在哪

先说结论：**类没有「一个位置」**。「类在代码段里怎么布局」这个问法本身就把几样东西混在了一起，它们分别落在不同的段：

| 东西                     | 实际位置               | 谁能改 |
| ---------------------- | ------------------ | --- |
| 成员函数的机器码               | `.text`（可执行）       | 否   |
| 虚函数表（vftable / vtable） | `.rdata`（只读数据）     | 否   |
| RTTI 类型描述              | `.rdata` / `.data` | 否   |
| 静态成员变量                 | `.data` / `.bss`   | 是   |
| 普通字段                   | **对象实例内部**（栈或堆）    | 是   |
| 模板实例化出的函数              | `.text`（每个类型一份）    | 否   |

所以「类」在二进制里被拆成了三部分：**一份代码、一份只读的索引表、N 份按字段排布的数据**。

下面的输出用 MSVC 19.51（x64）实际编译：

```cpp
struct Animal {
    int legs;
    virtual void speak();
    virtual void walk();
    virtual ~Animal();
    void breathe();                 // 非虚
};

struct Dog : Animal {
    int tail;
    void speak() override;
    virtual void fetch();
};

struct Robot {
    int battery;
    virtual void speak();
    virtual void charge();
};

struct Mutt : Dog, Robot {          // 多重继承
    void speak() override;
    void charge() override;
};
```

```bash
cl /EHsc /Od /c /Fa oop.cpp        # /Fa 输出汇编列表
dumpbin /nologo /symbols oop.obj
dumpbin /nologo /disasm:nobytes oop.obj
```

## 对象布局：字段 + 一个隐藏指针

运行时打印：

```text
sizeof(Animal)=16 sizeof(Dog)=24 sizeof(Robot)=16 sizeof(Mutt)=40
offsetof(Dog,legs)=8 offsetof(Dog,tail)=16
```

拆开看（同一偏移横向对比）：

| 偏移  | Animal (16) | Dog (24) | Mutt (40)      |
| --- | ----------- | -------- | -------------- |
| 0   | vfptr       | vfptr    | vfptr（Dog 表）   |
| 8   | legs        | legs     | legs           |
| 12  | padding     | padding  | padding        |
| 16  | —           | tail     | tail           |
| 20  | —           | padding  | padding        |
| 24  | —           | —        | vfptr（Robot 表） |
| 32  | —           | —        | battery        |
| 36  | —           | —        | padding        |

三点：

1. **`legs` 不在偏移 0**，因为对象开头被放了一个指向虚函数表的指针（`vfptr`，8 字节）。
2. 有虚函数 → 每个对象多 8 字节；没有虚函数的类（如 `struct P { int x; int y; };`）不付这个成本。
3. **多重继承时第二个基类子对象不在偏移 0**：`Robot` 部分从 24 开始，运行时实测 `diff=24`。

这个布局是 **ABI 约定**，不是语言标准：C++ 标准只说「要有虚分派」，没说虚表指针必须在开头。

## 虚函数表：放在 .rdata，对象里只存指针

编译器为每个**有多态行为的类**生成一张表。`Dog` 的表在汇编列表里是原样的：

```text
??_7Dog@@6B@ DQ FLAT:??_R4Dog@@6B@      ; vt[-1] RTTI Complete Object Locator
             DQ FLAT:?speak@Dog@@       ; vt[0] 覆盖了 Animal::speak
             DQ FLAT:?walk@Animal@@     ; vt[1] 没覆盖，仍指向基类
             DQ FLAT:??_EDog@@...       ; vt[2] 析构（deleting destructor）
             DQ FLAT:?fetch@Dog@@       ; vt[3] 新增的虚函数，追加在后面
```

符号表能直接看出它落在哪个段（`dumpbin /symbols` 原始行，已删去无关列）：

```text
0D7 00000000 SECT29 Static   | .rdata
    Section length   20, #relocs 4, selection 6 (pick largest)
0D9 00000008 SECT29 External | ??_7Animal@@6B@ (const Animal::`vftable')

0DA 00000000 SECT2A Static   | .rdata
    Section length   28, #relocs 5, selection 6 (pick largest)
0DC 00000008 SECT2A External | ??_7Dog@@6B@ (const Dog::`vftable')

0F5 00000000 SECT33 Static   | .rdata$r
0F7 00000000 SECT33 External | ??_R4Dog@@6B@ (const Dog::`RTTI Complete Object Locator')

0F8 00000000 SECT34 Static   | .data$rs
0FA 00000000 SECT34 External | ??_R0?AUDog@@@8 (struct Dog `RTTI Type Descriptor')
```

`Dog` 的表节长度是 `0x28` = 40 字节 = **5 个指针**（1 个 RTTI + 4 个函数），而符号值从 `+8` 开始，正好跳过 RTTI 槽。

- 表本身在 `.rdata`：**只读**。程序没法在运行时改虚函数表（除非刻意去改页保护）。
- 表里存的是函数地址，函数体本身在 `.text$mn`。
- 符号 `??_7Dog@@6B@` 的值是 `8`，不是 `0`：它指向**第一个函数指针**，RTTI 槽在它前面 8 字节，所以代码里写 `vftable[-1]` 才能拿到 RTTI。运行时验证：

```text
object  @ 000000F4B84FF810
vftable @ 00007FF66468A508
vt[-1]  = 00007FF664692AF8   (RTTI)
vt[ 0]  = 00007FF6646710C0   (speak)
vt[ 1]  = 00007FF664671030   (walk)
vt[ 2]  = 00007FF664671530   (destructor)
vt[ 3]  = 00007FF6646710F0   (fetch)
```

对象的前 8 字节就是 `00007FF66468A508`，即 `Dog::vftable` 的地址。

> 以上是 MSVC 的布局。GCC / Clang 用的是 Itanium C++ ABI，下标对不上：`vtable[0]` 是 offset-to-top（多重继承时用来找回对象起点），`vtable[1]` 是 typeinfo 指针，函数指针从 `vtable[2]` 开始；析构函数占**两个**槽（complete / deleting）。MSVC 没有 offset-to-top 槽，RTTI 放在表之前的 `[-1]`。所以「虚表第 0 项是 speak」这句话只有在指定 ABI 时才有意义。

## 虚调用与非虚调用：间接跳转 vs 直接跳转

同样的写法 `a->xxx()`，因为有 `virtual` 和没有 `virtual`，生成的机器码完全不同。

**虚函数**（`a->speak()`，`a` 的类型在编译期未知）：

```asm
; void call_speak(Animal *a) { a->speak(); }
mov rax, [rsp+30h]      ; rax = a
mov rax, [rax]          ; rax = a->vfptr            ← 第一次访存：取表
mov rcx, [rsp+30h]      ; rcx = this
call qword ptr [rax]    ; 间接调用 vftable[0]        ← 第二次访存：取函数地址
```

**非虚函数**（`a->breathe()`）：

```asm
; void call_breathe(Animal *a) { a->breathe(); }
mov rcx, [rsp+30h]      ; rcx = this
call ?breathe@Animal@@QEAAXXZ
```

差别的代价很清楚：

|            | 虚调用              | 非虚调用 |
| ---------- | ---------------- | ---- |
| 指令数        | 4 条              | 2 条  |
| 额外访存       | 2 次（读 vfptr、读表项） | 0 次  |
| 能否内联       | 不能（编译期不知道目标）     | 能    |
| 能否被 CPU 预测 | 间接跳转，靠 BTB 预测    | 直接跳转 |

顺带一个反例：把 `call_speak` 内联进 `main` 后，编译器**知道** `&d` 的静态类型是 `Dog`，`/O2` 会把它变成「先比较表项是不是 `Dog::speak`，相等就走直接调用，否则退回间接调用」，实测生成的是：

```asm
mov rax,[rsp+20h]
mov rdx,[rax]          ; rdx = vftable[0]
cmp rdx,rbx            ; rbx = &Dog::speak
je  ... 直接调用
...      call rdx      ; 不相等时退回间接调用
```

所以「虚函数一定慢」不是定律，取决于编译器能不能证明动态类型。

## 继承：偏移、表替换、thunk

**单继承**（`Dog : Animal`）就是父类子对象原封不动放在偏移 0，然后**覆盖表项**：

```text
Animal::vftable          Dog::vftable
[0] Animal::speak   →    [0] Dog::speak      ← 覆盖
[1] Animal::walk         [1] Animal::walk    ← 继承
[2] dtor                 [2] Dog dtor
                         [3] Dog::fetch      ← 追加
```

把 `Dog*` 转成 `Animal*` 不需要任何指针调整：基类子对象就在偏移 0，同一个地址可以直接用，差别只在两张表的内容不同。

**多重继承**（`Mutt : Dog, Robot`）就有两个非空子对象，于是需要两张表：

```text
??_7Mutt@@6BDog@@@      ; Mutt 中 Dog 部分的表（偏移 0）
  DQ ?speak@Mutt@@      ;   覆盖
  DQ ?walk@Animal@@
  DQ ??_EMutt@@
  DQ ?fetch@Dog@@

??_7Mutt@@6BRobot@@@    ; Mutt 中 Robot 部分的表（偏移 24）
  DQ ?speak@Mutt@@WBI@EAAXXZ   ← 不是函数本体，是调整器
  DQ ?charge@Mutt@@
```

关键是 `Robot` 那张表的 `speak` 槽：调用者传进来的 `this` 指向 **Robot 子对象**（偏移 24），但 `Mutt::speak` 要求 `this` 指向 **Mutt 开头**。于是编译器生成一个 thunk：

```asm
?speak@Mutt@@WBI@EAAXXZ ([thunk]:... Mutt::speak`adjustor{24}'):
  sub rcx, 18h          ; this -= 24
  jmp ?speak@Mutt@@UEAAXXZ
```

`0x18` 就是 24。**多重继承的地址调整不是抽象概念，就是一条 `sub`。**

## 泛型：单态化 vs 类型擦除

「泛型怎么实现」在不同语言里是两种完全不同的策略。

### C++ / Rust：每个类型生成一份代码（单态化）

```cpp
template <typename T>
T maxof(T a, T b) { return a > b ? a : b; }

int    use_int()    { return maxof(1, 2); }
double use_double() { return maxof(1.0, 2.0); }
```

符号表里是**两个独立的函数**：

```text
??$maxof@H@@YAHHH@Z (int __cdecl maxof<int>(int,int))          SECT4  .text$mn
??$maxof@N@@YANNN@Z (double __cdecl maxof<double>(double,double)) SECT5 .text$mn
```

反汇编也证实是两份完整代码，一份用 `mov/cmp/jle` 走整数，一份用 `movsd/comisd` 走浮点：

```asm
??$maxof@H@@YAHHH@Z:
  mov [rsp+10h],edx
  mov [rsp+8],ecx
  sub rsp,18h
  mov eax,[rsp+28h]
  cmp [rsp+20h],eax
  jle ...
  ...
  ret

??$maxof@N@@YANNN@Z:
  movsd [rsp+10h],xmm1
  movsd [rsp+8],xmm0
  sub rsp,18h
  movsd xmm0,[rsp+20h]
  comisd xmm0,[rsp+28h]
  ...
  ret
```

优点：零运行时开销，参数类型就是真实类型，能内联、能特化。
代价：**代码量随实例化数量线性增长**；`maxof` 用于 20 种类型就有 20 份机器码。

### Java / C#：擦除，只有一份代码

```java
class Box<T> {
    private T value;
    void set(T v) { this.value = v; }
    T get() { return value; }
}
```

`javap -c -p Box` 显示，方法签名还写着 `T`，但字节码里引用的类型全变成了 `Ljava/lang/Object;`：

```text
class Box<T> {
  private T value;

  void set(T);
    Code:
       0: aload_0
       1: aload_1
       2: putfield      #7                  // Field value:Ljava/lang/Object;
       5: return

  T get();
    Code:
       0: aload_0
       1: getfield      #7                  // Field value:Ljava/lang/Object;
       4: areturn
}
```

调用方被插入了强制转换：

```text
11: invokevirtual #12   // Method Box.set:(Ljava/lang/Object;)V
15: invokevirtual #16   // Method Box.get:()Ljava/lang/Object;
18: checkcast     #20   // class java/lang/String      ← 编译器补的类型检查
```

运行时反射也证实擦除是真的（`Box.class` 上看不到 `String`）：

```text
runtime class of value = java.lang.String
--- Box.class metadata ---
field  java.lang.Object value
method java.lang.Object get []
method void set [class java.lang.Object]
```

- 优点：所有类型共享一份代码，不含类型信息的目标文件更小。
- 代价：不能对 `T` 做 `new T()`、`T[]`、基本类型不装箱；每次取出都要 `checkcast`；`int` 走 `Integer` 需要装箱。

| 维度           | 单态化（C++ 模板 / Rust 泛型） | 擦除（Java 泛型 / C# 的引用类型） |
| -------------- | ------------------------------ | --------------------------------- |
| 代码份数       | 每个类型一份                   | 一份                              |
| 运行时类型信息 | 完整，可内联、可特化            | 丢失（只剩 `Object` + cast）      |
| 基本类型       | 直接使用真实类型                | 需要装箱                          |
| 二进制体积     | 膨胀                            | 稳定                              |
| 元数据里的类型   | 具体类型（`maxof<int>`）        | 只剩 `Object`                     |

## 反射：元数据从哪来

反射不是魔法，前提是**编译产物里保留了类型元数据**。

### C++：只有 RTTI，没有通用反射

启用 RTTI（默认开启）后，每个多态类会生成一整套结构：

```text
??_R4Dog@@6B@   RTTI Complete Object Locator   ; 虚表前 8 字节指向它
??_R0?AUDog@@@8 RTTI Type Descriptor           ; 类型描述符
??_R3Dog@@8     RTTI Class Hierarchy Descriptor
??_R2Dog@@8     RTTI Base Class Array          ; 基类数组
??_R1A@?0A@EA@Dog@@8 Base Class Descriptor at (0,-1,0,64)
```

这套东西只支持：

- `typeid(x)` → 拿到 `type_info`，比较类型是否相同；
- `dynamic_cast<T*>(p)` → 沿继承层次**向下转型**；
- `catch` 按类型匹配异常。

**没有**成员枚举、没有按名字调用方法、没有属性读写。语言层面就没提供，二进制里自然也没有。

代价：`-fno-rtti` 可以关掉，省下这些只读数据；关掉后 `typeid` 和 `dynamic_cast` 就不可用。

### Java：class 文件本身就是元数据表

`.class` 文件里有常量池、字段表、方法表、属性表；类加载时 JVM 把它们整理成运行时的 `Class` 对象，反射 API 只是读这张表：

```text
method java.lang.Object get []
method void set [class java.lang.Object]
```

这些信息不是「运行时推断」出来的，而是编译期就写进文件、加载时建好的索引。

| 能力                       | C++ RTTI            | Java 反射            |
| -------------------------- | ------------------- | -------------------- |
| 判断动态类型               | 是（`typeid`）      | 是                   |
| 安全向下转型               | 是（`dynamic_cast`） | 是（`instanceof`）   |
| 枚举字段 / 方法            | **否**              | 是                   |
| 按名字调用方法             | 否                  | 是                   |
| 访问私有成员               | 否                  | 是（`setAccessible`）|
| 元数据存放                 | `.rdata` 中的 RTTI  | class 文件 + JVM 内部结构 |

## 这些特性各自的成本

| 特性            | 内存成本                          | 运行成本                       |
| --------------- | --------------------------------- | ------------------------------ |
| 虚函数          | 每个对象 +8 字节，每个类一张表     | 两次额外访存 + 无法内联        |
| 单继承          | 无额外偏移                        | 无                             |
| 多重继承        | 第二个基类子对象在非零偏移         | 指针调整、thunk 跳转           |
| C++ 模板        | 每实例化一次 + 一份代码            | 0（类型是编译期常量）          |
| Java 泛型       | 无                                | `checkcast` + 可能的装箱       |
| RTTI / 反射     | 只读数据段中的元数据               | 查表 + 字符串比较              |

一句话总结：**代码在 `.text`，表在 `.rdata`，字段在对象里**。所谓「面向对象」在机器层面就是这三样东西加上几条 `mov`、`cmp`、`call`。
