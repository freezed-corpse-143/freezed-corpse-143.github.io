原子操作，就是在并发参与者看来，一次不可被拆开的操作。其他线程不能插入它的中间步骤，也不会观察到它只完成了一半的状态。

例如：

```text
普通自增：
读取 → 加 1 → 写回
```

两个线程可能读到同一个旧值，从而丢失一次更新。而原子自增把整个“读取、修改、写回”作为一个不可分割的操作。

但先区分三个层次：

| 层次     | 提供什么             | 示例                          |
| ------ | ---------------- | --------------------------- |
| CPU 硬件 | 原子指令及内存顺序机制      | 原子交换、CAS、原子加法               |
| 操作系统   | 基于硬件构建同步、等待与唤醒机制 | 互斥锁、信号量、futex 等             |
| 编程语言   | 向程序提供具有明确语义的接口   | C++ `std::atomic`、Rust 原子类型 |

操作系统提供的互斥锁，可以让**一段代码**互斥执行；CPU 原子指令通常作用于**有限大小的内存位置**。二者不是同一粒度。

### 1. 常见的原子操作有哪些

假设共享变量为 `x`：

| 操作                   | 含义               | 常见用途      |
| -------------------- | ---------------- | --------- |
| 原子读 `load`           | 完整读取一个值          | 读取状态、标志   |
| 原子写 `store`          | 完整写入一个值          | 发布状态、设置标志 |
| 原子交换 `exchange`      | 写入新值，并返回旧值       | 抢占标志、替换指针 |
| 比较并交换 `CAS`          | 当前值符合预期时才更新      | 条件更新、无锁算法 |
| 原子加减 `fetch_add/sub` | 更新数值，并返回旧值       | 计数器、分配编号  |
| 原子按位运算               | 原子地执行 AND、OR、XOR | 状态位设置和清除  |

这里“完整”还不足以代表全部语义：**与其他内存访问之间的顺序关系，也是使用原子操作时必须考虑的问题。**

### 2. 原子加法为什么能防止丢失更新

假设 `x = 10`，两个线程各增加 1。

普通读改写可能发生：

| 步骤 | 线程 A | 线程 B |
|---|---|---|
| 1 | 读取 10 | |
| 2 | | 读取 10 |
| 3 | 写回 11 | |
| 4 | | 写回 11 |

最终是 11。

如果两个线程都执行原子 `fetch_add(1)`，这两个操作会以某个顺序生效：

```text
第一次：10 → 11，返回 10
第二次：11 → 12，返回 11
```

最终为 12。哪个线程先完成不确定，但两次更新不会互相覆盖。

注意：**原子读取，再原子写回，并不等于原子自增。**

```cpp
// 两次独立的原子操作，仍然可能丢失更新
int old = x.load();
x.store(old + 1);

// 整个读改写是一个原子操作
x.fetch_add(1);
```

### 3. CAS：最重要的条件更新积木

CAS 是 Compare-And-Swap，比较并交换。其概念语义是：

```text
把下面整个过程作为一次原子操作：

如果 x == 预期值：
    x = 新值
    返回成功
否则：
    不修改 x
    返回失败
```

例如，要把库存从 1 改成 0：

```text
CAS(库存, 预期值=1, 新值=0)
```

两个线程同时尝试，最多只有一个成功：

| 线程 | 尝试 | 结果 |
|---|---|---|
| A | 库存等于 1，则改成 0 | 成功 |
| B | 库存等于 1，则改成 0 | 失败，因为当前已经是 0 |

这样就把之前分离的“检查”和“修改”合成了一次原子操作。

对于任意正库存，可以通过 CAS 重试：

```cpp
std::atomic<int> stock{10};

bool buy() {
    int current = stock.load();

    while (current > 0) {
        if (stock.compare_exchange_weak(current, current - 1)) {
            return true;
        }
        // 失败时，current 会更新为实际读到的值。
        // weak 也允许偶发的伪失败，因此放在循环中。
    }

    return false;
}
```

这里默认使用 C++ 的顺序一致性内存顺序，先把注意力放在算法本身。

**CAS 只检查比较瞬间的值。**如果值经历 `A → B → A`，CAS 不会自动知道中间发生过变化，这就是后续学习无锁结构时会遇到的 ABA 问题。

### 4. CPU 如何保证原子性

**不是简单地关闭当前核心的中断。**关闭本核中断，不能阻止其他核心访问共享内存。

在常见的多核系统中，对可缓存、满足要求的内存，CPU 可以通过缓存一致性协议取得目标缓存行的独占修改权限，并结合原子指令的执行机制，确保其他核心不能把冲突操作插进原子更新中间。

可以把它理解为：

> 多个核心竞争更新同一个位置时，硬件保证这些原子更新按照某个顺序生效。

具体指令因架构而异：

| 架构 | 典型机制 |
|---|---|
| x 86 | `LOCK` 前缀的读改写指令、内存形式的 `XCHG` 等 |
| ARM | 独占加载／存储指令对，以及部分架构支持的直接原子指令 |
| RISC-V | 支持相应扩展时的 LR/SC、AMO 等 |

**原子操作并不保证便宜。**多个核心频繁修改同一缓存行，仍然会产生争用和缓存行传递开销。

### 5. 操作系统在上面增加了什么

硬件原子操作能够判断“锁是否被我拿到”，但等待者还需要决定：

- 持续重试？
- 暂时让出 CPU？
- 进入睡眠，等待唤醒？

这些就是操作系统同步机制发挥作用的地方。

例如，很多互斥锁实现大致是：

```text
先通过原子操作尝试拿锁
    成功：进入临界区
    失败：短暂自旋，或进入操作系统等待
持有者解锁时，必要时唤醒等待者
```

Linux 的 futex 机制允许在用户态检查共享状态，并在需要时进入内核等待或唤醒。它的关键能力之一是**将检查指定值与进入等待连接起来**，避免“检查之后、睡眠之前，通知已经发生”导致的遗漏。

所以，**原子操作负责协调状态，操作系统还负责管理等待中的线程。**

### 6. 原子性不等于内存可见性和顺序全部解决

考虑：

```text
线程 A：
    写入 data
    设置 ready = true

线程 B：
    发现 ready == true
    读取 data
```

这里不仅要求 `ready` 的读写不可分割，还要求：

> B 看到“准备好了”时，也能安全地看到 A 先前写入的数据。

C++ 可以用 release/acquire 建立这个关系：

```cpp
int data = 0;
std::atomic<bool> ready{false};

// 线程 A
data = 42;
ready.store(true, std::memory_order_release);

// 线程 B
if (ready.load(std::memory_order_acquire)) {
    use(data);
}
```

在这个一次发布的例子中，如果 acquire 读取到了对应 release 写入的 `true`，就建立了所需的同步关系。还需保证发布后没有其他未同步的修改。

因此，要分开理解：

| 性质 | 回答的问题 |
|---|---|
| 原子性 | 这个操作会不会被其他参与者看到中间状态？ |
| 内存顺序与同步 | 看到这个状态时，其他相关读写有什么保证？ |
| 业务正确性 | 整个操作是否维护了业务规则？ |

**硬件原子操作是同步机制的基础积木。它能保护一次更新；要保护多个字段、一段流程和对象生命周期，还需要设计完整的同步协议。**
