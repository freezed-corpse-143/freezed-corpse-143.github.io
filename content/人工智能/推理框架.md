# 统一框架

 ```text
推理框架
├─ 接入面：HTTP / CLI / C API / Python API
├─ 请求面：模板、分词、参数校验、输入预处理
├─ 控制面：调度、批处理、生命周期、分布式协调
├─ 状态面：KV Cache、latent、RNG、前缀树、请求状态
├─ 数据面：模型 forward、计算图、算子、kernel
├─ 资源面：显存、内存、mmap、权重驻留、设备间传输
├─ 平台面：CUDA / ROCm / Metal / Vulkan / CPU 等
└─ 工件面
：模型格式、配置、权重解析、量化与转换
 ```

 四个项目的根本区别，不是“支持哪些模型”，而是把哪一层当作自己的核心抽象：

 - vLLM：以吞吐为中心的 LLM 请求调度器 + KV Cache 管理器。
 - SGLang：以共享前缀和复杂生成程序为中心的 状态感知调度器。
 - llama.cpp：以可移植、可嵌入为中心的 张量运行时 + 模型运行库。
 - stable-diffusion.cpp：以多组件生成流程为中心的 扩散管线编排器 + GGML 执行器。

“核心引擎”并不等于“无状态层”

 推理框架中真正接近无状态的部分是：

 ```text
输出 = 算子或模型前向（权重，只读输入，显式状态视图）
 ```

 例如：

 - GEMM、RMSNorm、RoPE、Attention kernel。
 - Transformer layer forward。
 - UNet/DiT/VAE 的单次 forward。
 - GGML 计算图执行。
 - logits processor 的部分纯函数操作。

 但完整推理引擎必然有状态：
 
| 状态     | LLM                          | Diffusion                    |
| :----- | :--------------------------- | :--------------------------- |
| 模型常驻状态 | 权重、量化参数                      | DiT/UNet、TE、VAE 权重           |
| 请求状态   | 已生成 token、停止条件               | 当前 latent、采样步、sigma          |
| 推理缓存   | KV Cache、前缀缓存                | conditioning、计算结果缓存          |
| 调度状态   | waiting/running、token budget | 当前阶段、组件驻留状态                  |
| 随机状态   | sampler RNG、历史 token         | 初始噪声、sampler RNG             |
| 运行时状态  | CUDA Graph、workspace         | graph workspace、runner cache |
推理核心引擎进行二分：

 - 计算内核层：尽可能无状态、输入输出明确。
 - 推理状态层：明确状态的所有者、生命周期、分配与回收策略。

## 请求接入层

负责把外部输入变成框架内部请求，不应承担核心计算。

| 框架 | 主要入口 | 职责 |
| :--- | :--- | :--- |
| vLLM | vllm/entrypoints/ | OpenAI API、离线 LLM API、请求解析、流式响应 |
| SGLang | python/sglang/srt/entrypoints/、TokenizerManager | HTTP/OpenAI API、tokenize、多模态处理、请求分发 |
| llama.cpp | tools/cli/、tools/server/、include/llama.h | CLI、HTTP server、C ABI |
| stable-diffusion.cpp | examples/cli/、examples/server/、include/stable-diffusion.h | 参数解析、图片输入输出、C API |
 重点：入口不是引擎。入口可以替换，内部请求模型应保持稳定。

## 模型工件与加载层

 四者都遵循相同流水线：

 ```text
定位模型
  → 解析元数据/配置
  → 识别模型架构
  → 建立 tensor 目录
  → 名称映射
  → 决定 dtype/量化/分片
  → 决定设备与驻留位置
  → 绑定到模型参数
  → warmup / graph capture
 ```

### vLLM

主要路径：

 - vllm/model_executor/model_loader/
 - vllm/model_executor/model_loader/default_loader.py
 - vllm/transformers_utils/
 - vllm/models/

 特点：

 - 以 Hugging Face 配置、tokenizer 和 checkpoint 生态为中心。
 - 默认加载器处理 safetensors/PyTorch 权重及权重迭代。
 - 另有 sharded state、tensorizer、远程/流式加载等路径。
 - 在模型初始化期间完成 TP 分片和量化布局，避免先把完整大模型加载到每个 GPU。
 - 模型类统一接收 VllmConfig，模型加载和执行配置耦合较深。

 入口可从 DefaultModelLoader 看起：

 - default_loader.py:50：加载器主体。
 - default_loader.py:254：权重迭代。
 - default_loader.py:468：权重装载。

### SGLang

主要路径：

 - python/sglang/srt/model_loader/loader.py
 - python/sglang/srt/model_loader/auto_loader.py
 - python/sglang/srt/model_loader/weight_utils.py

 当前加载格式包括：

 - safetensors、PyTorch .bin
 - sharded state
 - GGUF
 - Mistral native
 - layered loading
 - bitsandbytes
 - 对象存储流式加载
 - 远程实例权重传输

 对应文档：docs/docs/advanced_features/model_loading.mdx:8-100。

 SGLang 的加载层比“读文件”更宽：它已经覆盖权重更新、远程权重、RL 场景和运行中实例间传输。

### llama.cpp

 主要路径：

 - src/llama-model-loader.cpp
 - src/llama-model-loader.h
 - ggml/src/gguf.cpp
 - conversion/
 - convert_hf_to_gguf.py

 特点：

 - 运行时坚持使用 GGUF。
 - Hugging Face、PyTorch 等格式的复杂性主要放到离线转换阶段。
 - GGUF 同时保存模型元数据、tokenizer 元数据和 tensor。
 - loader 负责 mmap、分片文件、tensor 设备放置和量化类型读取。

 这是很重要的架构选择：

>  
>  vLLM/SGLang 把格式多样性吸收到运行时；
>  llama.cpp 把格式多样性推到转换工具，运行时只处理统一工件。
