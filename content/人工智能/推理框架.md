# 统一框架

 ```text
推理框架
├─ 接入面：HTTP / CLI / C API / Python API
├─ 请求面：模板、分词、参数校验、输入预处理
├─ 控制面：调度、批处理、生命周期、分布式协调
├─ 状态面：KV Cache、latent、RNG、前缀树、请求状态
├─ 数据面：模型 forward、计算图、算子、kernel
├─ 资源面：显存、内存、mmap、权重驻留、设备间传输
├─ 平台面：CUDA / ROCm / Metal / Vulkan / CPU 等
└─ 工件面
：模型格式、配置、权重解析、量化与转换
 ```

 四个项目的根本区别，不是“支持哪些模型”，而是把哪一层当作自己的核心抽象：

 - vLLM：以吞吐为中心的 LLM 请求调度器 + KV Cache 管理器。
 - SGLang：以共享前缀和复杂生成程序为中心的 状态感知调度器。
 - llama.cpp：以可移植、可嵌入为中心的 张量运行时 + 模型运行库。
 - stable-diffusion.cpp：以多组件生成流程为中心的 扩散管线编排器 + GGML 执行器。

“核心引擎”并不等于“无状态层”

 推理框架中真正接近无状态的部分是：

 ```text
输出 = 算子或模型前向（权重，只读输入，显式状态视图）
 ```

 例如：

 - GEMM、RMSNorm、RoPE、Attention kernel。
 - Transformer layer forward。
 - UNet/DiT/VAE 的单次 forward。
 - GGML 计算图执行。
 - logits processor 的部分纯函数操作。

 但完整推理引擎必然有状态：
 
| 状态     | LLM                          | Diffusion                    |
| :----- | :--------------------------- | :--------------------------- |
| 模型常驻状态 | 权重、量化参数                      | DiT/UNet、TE、VAE 权重           |
| 请求状态   | 已生成 token、停止条件               | 当前 latent、采样步、sigma          |
| 推理缓存   | KV Cache、前缀缓存                | conditioning、计算结果缓存          |
| 调度状态   | waiting/running、token budget | 当前阶段、组件驻留状态                  |
| 随机状态   | sampler RNG、历史 token         | 初始噪声、sampler RNG             |
| 运行时状态  | CUDA Graph、workspace         | graph workspace、runner cache |

推理核心引擎进行二分：

 - 计算内核层：尽可能无状态、输入输出明确。
 - 推理状态层：明确状态的所有者、生命周期、分配与回收策略。

## 请求接入层

负责把外部输入变成框架内部请求，不应承担核心计算。

| 框架 | 主要入口 | 职责 |
| :--- | :--- | :--- |
| vLLM | vllm/entrypoints/ | OpenAI API、离线 LLM API、请求解析、流式响应 |
| SGLang | python/sglang/srt/entrypoints/、TokenizerManager | HTTP/OpenAI API、tokenize、多模态处理、请求分发 |
| llama.cpp | tools/cli/、tools/server/、include/llama.h | CLI、HTTP server、C ABI |
| stable-diffusion.cpp | examples/cli/、examples/server/、include/stable-diffusion.h | 参数解析、图片输入输出、C API |

重点：入口不是引擎。入口可以替换，内部请求模型应保持稳定。

## 模型工件与加载层

 四者都遵循相同流水线：

 ```text
定位模型
  → 解析元数据/配置
  → 识别模型架构
  → 建立 tensor 目录
  → 名称映射
  → 决定 dtype/量化/分片
  → 决定设备与驻留位置
  → 绑定到模型参数
  → warmup / graph capture
 ```

### vLLM

主要路径：

 - vllm/model_executor/model_loader/
 - vllm/model_executor/model_loader/default_loader.py
 - vllm/transformers_utils/
 - vllm/models/

 特点：

 - 以 Hugging Face 配置、tokenizer 和 checkpoint 生态为中心。
 - 默认加载器处理 safetensors/PyTorch 权重及权重迭代。
 - 另有 sharded state、tensorizer、远程/流式加载等路径。
 - 在模型初始化期间完成 TP 分片和量化布局，避免先把完整大模型加载到每个 GPU。
 - 模型类统一接收 VllmConfig，模型加载和执行配置耦合较深。

 入口可从 DefaultModelLoader 看起：

 - default_loader.py:50：加载器主体。
 - default_loader.py:254：权重迭代。
 - default_loader.py:468：权重装载。

### SGLang

主要路径：

 - python/sglang/srt/model_loader/loader.py
 - python/sglang/srt/model_loader/auto_loader.py
 - python/sglang/srt/model_loader/weight_utils.py

 当前加载格式包括：

 - safetensors、PyTorch .bin
 - sharded state
 - GGUF
 - Mistral native
 - layered loading
 - bitsandbytes
 - 对象存储流式加载
 - 远程实例权重传输

 对应文档：docs/docs/advanced_features/model_loading.mdx:8-100。

 SGLang 的加载层比“读文件”更宽：它已经覆盖权重更新、远程权重、RL 场景和运行中实例间传输。

### llama.cpp

 主要路径：

 - src/llama-model-loader.cpp
 - src/llama-model-loader.h
 - ggml/src/gguf.cpp
 - conversion/
 - convert_hf_to_gguf.py

 特点：

 - 运行时坚持使用 GGUF。
 - Hugging Face、PyTorch 等格式的复杂性主要放到离线转换阶段。
 - GGUF 同时保存模型元数据、tokenizer 元数据和 tensor。
 - loader 负责 mmap、分片文件、tensor 设备放置和量化类型读取。

 这是很重要的架构选择：

>  
>  vLLM/SGLang 把格式多样性吸收到运行时；
>  llama.cpp 把格式多样性推到转换工具，运行时只处理统一工件。

### stable-diffusion.cpp

 主要路径：

 - src/model_loader.cpp
 - src/model_io/
 - src/name_conversion.cpp
 - src/model_manager.cpp

 当前 ModelLoader 明确支持：

 - GGUF：model_loader.cpp:260
 - safetensors：:288
 - safetensors index：:314
 - PyTorch legacy：:360
 - PyTorch zip：:388
 - Diffusers 目录：:416

 特点：

 - 从 tensor 名称和元数据推断 SD/Flux/DiT/VAE 等组件配置。
 - 使用名称转换层消化不同生态的权重命名。
 - ModelManager 不仅加载权重，还管理权重在 GPU、CPU、其他 GPU、磁盘之间的驻留。

## 控制面与推理状态层

### vllm：以 token budget 和 KV block 为核心

 核心循环非常清晰：

 ```python
scheduler_output = scheduler.schedule(...)
model_output = model_executor.execute_model(scheduler_output)
engine_outputs = scheduler.update_from_output(
    scheduler_output, model_output
)
 ```

 对应 vllm/v 1/engine/core.py:630-656。

 关键组件：

 - EngineCore：循环和组件编排。
 - Scheduler：决定每步运行哪些请求、每个请求运行多少 token。
 - KVCacheManager：分配和回收 KV block。
 - Executor：本地、多进程或 Ray 执行。
 - Worker：一个加速器进程。
 - GPUModelRunner：准备 tensor、执行模型、采样。
 - AttentionBackend：将逻辑 attention 映射到具体实现。

 核心问题不是“怎么调用模型”，而是：

> 在有限的 KV Cache 和 token budget 下，如何不断重组 batch，使 GPU 始终有工作。

### SGLang：以 Radix Tree 和 CPU/GPU 重叠为核心

 正常调度循环：

 ```text
ingest_requests
  → get_next_batch_to_run
  → run_batch
  → process_batch_result
 ```

 见 python/sglang/srt/managers/scheduler.py:1907-1937。

 重叠调度循环会把：

 - 上一批结果处理；
 - 当前批 GPU forward；
 - 下一批 CPU 调度准备；

 进行流水化，见 scheduler.py:1942-2008。

 关键组件：

 - TokenizerManager：请求输入、tokenize、IPC 分发、流式输出。
 - Scheduler：请求状态和 batch 构造。
 - RadixCache：共享前缀对应的 KV Cache。
 - HiCache：扩展到 GPU/CPU/外部存储层次。
 - TpModelWorker / ModelRunner：执行 forward 和采样。
 - attention backend：FlashInfer、FA、Triton、TRTLLM、AITER 等。

 它的核心问题是：

> 如何识别请求之间可共享的前缀状态，并让调度、缓存命中和 GPU 执行协同工作。

### llama.cpp：调用者拥有生成循环

 examples/simple/simple.cpp 展示了最小完整路径：

 ```text
llama_backend_init
  → llama_model_load_from_file
  → llama_tokenize
  → llama_init_from_model
  → llama_process / decode
  → llama_sampler_sample
  → token_to_piece
  → 下一轮
 ```

 这里没有一个类似 vLLM 的大型服务调度器。状态主要位于：

 - llama_model：只读模型状态。
 - llama_context：KV/序列/计算 workspace 等推理状态。
 - llama_sampler：采样历史和 RNG。
 - 调用者：控制生成循环、停止条件和输出。

 核心问题是：

> 如何用最小依赖，在不同硬件上可靠地执行一个量化模型。

### stable-diffusion.cpp：以阶段管线和采样步为核心

 图片生成主路径：

 ```text
请求规范化
  → 文本/图像 conditioning
  → 初始化或编码 latent
  → 构造 sigma/timestep 序列
  → 多步 denoise
  → VAE decode
  → image 输出
 ```

 关键位置：

 - src/pipeline/image.cpp:783：generate_image
 - src/pipeline/diffusion_engine.cpp:1842：conditioning
 - diffusion_engine.cpp:2251：核心 sample
 - diffusion_engine.cpp:2895：VAE decode
 - src/core/ggml_runner.cpp：GGML 计算图执行

 它的调度不是 LLM 的“跨请求 token 调度”，而是：

 - TE、Diffusion、VAE 等组件阶段切换；
 - 每一步 timestep/sigma 的循环；
 - 权重驻留、预取和释放；
 - 显存不足时 graph segmentation 或 VAE tiling。

# 平台适配应该拆成三层看

完整平台适配有三层：

## 能力发现与策略选择

 回答：

 - 当前是什么设备？
 - 支持哪些 dtype？
 - 选哪个 attention/backend？
 - block size、量化和显存策略是什么？

 实现：

 - vLLM：vllm/platforms/interface.py:135
 - SGLang：python/sglang/srt/platforms/
 - llama.cpp：GGML backend registry
 - stable-diffusion.cpp：SDBackendManager 和每组件 backend assignment

## 统一运行接口

 回答：

 - 如何分配 buffer？
 - 如何把 tensor 放到设备？
 - 如何提交计算图？
 - 如何同步、复制、查询显存？

 实现方式：

 - vLLM/SGLang：PyTorch device、distributed API、各类 backend 抽象。
 - llama.cpp/stable-diffusion.cpp：ggml_backend_t、ggml_backend_sched_t、buffer
   type。
## kernel 与构建适配

 - 最终执行 CUDA、HIP、Metal、Vulkan 还是 CPU SIMD？
 - kernel 是预编译、Triton JIT、Torch Compile 还是动态图？
 - 不同架构的编译产物怎么组织？

项目结构：

| 框架 | 平台实现 |
| :--- | :--- |
| vLLM | vllm/platforms/{cuda,rocm,cpu,tpu,xpu}.py，csrc/，Triton/FlashInfer 等 |
| SGLang | srt/platforms/、srt/hardware_backend/、大量 attention backend |
| llama.cpp | ggml/src/ggml-{cuda,metal,vulkan,sycl,...} |
| stable-diffusion.cpp | 复用 GGML backend，并在组件级指定 te/vae/diffusion 的执行设备 |
 stable-diffusion.cpp 还明确区分：

 - --backend：计算在哪里执行。
 - --params-backend：权重存在哪里。

 这是理解“计算设备”和“权重驻留设备不是同一个概念”的好案例。

# 切面层

 “切面层”不是主推理流程中的一个连续阶段，而是会穿过多个阶段的能力。

 ┌──────────┬──────────────────────────────────────────────┐
 │ 切面     │ 关注点                                       │
 ├──────────┼──────────────────────────────────────────────┤
 │ 配置     │ 模型、设备、并行、缓存、量化、采样参数       │
 ├──────────┼──────────────────────────────────────────────┤
 │ 可观测性 │ 日志、指标、trace、profiling、请求耗时       │
 ├──────────┼──────────────────────────────────────────────┤
 │ 内存治理 │ KV、workspace、mmap、权重驻留、offload       │
 ├──────────┼──────────────────────────────────────────────┤
 │ 分布式   │ TP/PP/DP/EP、collective、进程拓扑            │
 ├──────────┼──────────────────────────────────────────────┤
 │ 量化     │ 权重格式、加载转换、量化 kernel 选择         │
 ├──────────┼──────────────────────────────────────────────┤
 │ Adapter  │ LoRA、ControlNet、IP Adapter 等              │
 ├──────────┼──────────────────────────────────────────────┤
 │ 编译优化 │ CUDA Graph、Torch Compile、graph reuse       │
 ├──────────┼──────────────────────────────────────────────┤
 │ 生命周期 │ warmup、pause、sleep、取消、热更新、shutdown │
 ├──────────┼──────────────────────────────────────────────┤
 │ 容错     │ worker 异常、请求 abort、OOM 回退            │
 ├──────────┼──────────────────────────────────────────────┤
 │ 安全边界 │ remote code、模型文件解析、网络入口校验      │
 └──────────┴──────────────────────────────────────────────┘

 判断标准：
> 如果一个能力同时影响加载、调度、执行、缓存和输出，它通常是切面，不应塞进某个单一“engine”类里理解。

# I/O 层

 把所有 I/O 都放在一个分类里，会看不清性能瓶颈。

 1. 请求协议 I/O

 - HTTP、OpenAI API、CLI、C API。
 - JSON/SSE、图片上传、流式 token。

 2. 模型工件 I/O

 - Hugging Face 下载。
 - GGUF/safetensors/PyTorch 读取。
 - mmap、分片 checkpoint、对象存储。

 3. 进程与节点 I/O

 - vLLM API server 与 EngineCore 的 ZMQ。
 - worker IPC。
 - NCCL/RCCL collective。
 - SGLang prefill/decode 分离时的 KV 传输。
 - GGML RPC backend。

 4. 内存与设备 I/O

 - CPU → GPU 权重复制。
 - KV Cache offload。
 - GPU 间 tensor/KV 传输。
 - stable-diffusion.cpp 的参数预取和按段加载。

 5. 结果 I/O

 - token detokenize 和 SSE 推送。
 - latent preview。
 - VAE decode 后的 PNG/JPEG/WebP 编码。
 - 视频和音频封装。

 推理性能分析中，必须区分：

 ```text
算得慢
≠
模型读得慢
≠
CPU/GPU 拷贝慢
≠
跨进程传输慢
≠
客户端消费慢
 ```
