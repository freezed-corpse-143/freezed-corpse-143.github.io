# 约束驱动的技术元学习框架

版本：1.0  
日期：2026-10-28  
定位：一套用于理解、选择、验证和积累技术的开放框架，覆盖性能、容量、分布式协作、正确性与故障恢复。

> 技术的名字是知识的入口，约束与机制才是解释的核心。
>
> 学一项技术，就是理解它依赖什么假设、改变什么需求或能力、维护什么性质、付出什么代价，以及如何验证这些判断。

## 0. 一页使用法

面对一个新问题，依次填写：

1. **目标**：为谁优化什么？吞吐、延迟、尾延迟、能耗、成本还是恢复时间？
2. **性质**：哪些条件必须成立？精度、一致性、持久性、安全边界是什么？
3. **环境**：资源、拓扑、运行时、配额、共享干扰和故障域是什么？
4. **需求**：每个有效结果需要多少计算、搬运、驻留、交互和依赖等待？
5. **约束**：哪些条件限制了目标或威胁了性质？证据与替代解释是什么？
6. **机制**：候选技术改变了模型里的哪一项？会把成本转移到哪里？
7. **预测**：采用后，什么指标应变化？端到端收益上界是多少？
8. **验证**：测量、对照实验和故障注入是否支持预测？
9. **积累**：记录适用范围、失败案例和仍未解释的现象。

不要为了使用框架而填满所有表格。小问题只写目标、假设、预测、结果；复杂问题再逐层展开。

## 1. 核心原则

### 1.1 约束驱动，目标先行

瓶颈必须相对于目标、工作负载、系统边界和时间窗口定义。同一系统可能对吞吐受带宽限制，对单请求延迟受依赖限制，对扩容受协调限制。

“更快”“更可靠”都需要展开成可验收指标。平均值、P 99、最坏情况和故障期间表现不能相互替代。

### 1.2 现象、机制、约束分开记录

- 现象：GPU 带宽利用率低。
- 候选机制：独立访存不足，无法覆盖访问延迟。
- 候选约束：可用并发或依赖路径限制吞吐。
- 验证：在尽量保持字节数和计算量不变时增加独立工作，检查吞吐与等待是否改善。

单个计数器通常不足以完成因果判断。反复出现的相关性也需要排除替代解释。

### 1.3 技术与约束是多对多关系

一项技术可以同时缓解多项约束，也可能引入新约束。固定招法可用作入门索引，不能成为封闭分类。

技术无收益的原因包括：诊断错误、收益幅度太小、不在关键路径、附加成本抵消、联合约束、实现问题、测量失真，以及违反精度或正确性要求。

### 1.4 性能与稳健性共用推理流程，采用不同判据

性能关注需求如何超过能力，以及时间消耗在哪里。稳健性关注给定故障下，必须维持的性质是否仍然成立。

两者共享“假设—机制—预测—验证”，但不能全部压成一个利用率百分比。

### 1.5 所有结论都带适用域

至少标明：硬件与软件版本、工作负载、数据分布、运行阶段、缓存状态、并发度、精度要求、测量方式和故障模型。

“本项目 int 8 更慢”是一条有用的局部证据；“int 8 没用”是不受证据支持的推广。

## 2. 六层结构

| 层         | 内容                      | 主要产物      |
| --------- | ----------------------- | --------- |
| L 0 目标与性质 | 要优化的指标、必须保持的不变量、允许的退化   | 验收条件      |
| L 1 环境与资源 | 物理能力、有效资源、拓扑、配额、故障域     | 环境画像      |
| L 2 需求与结构 | 计算量、各级流量、工作集、依赖图、通信与副作用 | 工作负载模型    |
| L 3 约束与预测 | 生效约束、下界、敏感度、关键路径、故障传播   | 可证伪假设     |
| L 4 技术机制  | 改变需求、能力、结构或故障后果的方式      | 技术卡片与候选方案 |
| L 5 实现与证据 | 代码、部署参数、实验、恢复测试、结果与反例   | 可复现记录     |

这六层不是单向瀑布。新证据可以推翻需求估计、环境假设乃至目标选择。

## 3. 统一描述对象

### 3.1 目标与硬约束

把方案选择写成：

$$
\min_{\theta}\ J(\theta;w,e)
\quad\text{subject to}\quad
 g_i(\theta;w,e)\le 0,
\quad \mathcal{I}(\theta,f)=\mathrm{true}\ \forall f\in\mathcal{F}.
$$

- θ：实现与配置；w：工作负载；e：环境。
- J：一个主要目标，或明确权衡的多个目标。
- g：容量、成本、精度、延迟等限制。
- I：必须维持的性质；F：明确覆盖的故障集合。

公式是建模语言，不意味着所有软件性质都能被精确数值化或通过有限测试证明。故障测试只能为测试范围内的行为提供证据。

多目标没有明确权重时，记录 Pareto 取舍：哪些方案无法在不恶化其他目标的情况下继续改善。

### 3.2 资源的三个上限

| 上限      | 含义                      | 用途   |
| ------- | ----------------------- | ---- |
| 标称上限    | 产品规格或理论能力               | 粗略估计 |
| 可持续上限   | 匹配访问方式、指令类型、频率和功耗条件的校准值 | 性能建模 |
| 本任务有效预算 | 扣除共享竞争、配额、常驻开销后的可用能力    | 项目决策 |

不能简单用 L 0 与 L 1 相除产生通用绑定判据。必须把工作负载需求与同量纲、同作用域的能力比较。

### 3.3 需求向量

每个有效结果可以用以下项目描述：

$$
D=(F,\{Q_\ell\},M,\mathcal{G},N_{\mathrm{round}},N_{\mathrm{submit}},E).
$$

分别表示计算、各级数据流量、驻留需求、依赖图、通信轮次、提交次数、能量。该向量可以继续扩展；只纳入足以解释当前问题的变量。

区分逻辑工作与实际工作：有效 FLOP 与执行 FLOP、有效字节与传输字节、用户请求与包含重试的后端请求。

## 4. 约束分类：开放目录

| 类别     | 核心问题            | 证据线索                 | 机制方向               |
| ------ | --------------- | -------------------- | ------------------ |
| 计算吞吐   | 所需运算能否及时完成？     | 对应执行管线吞吐、指令组成        | 减少运算、改变算法、向量化、专用单元 |
| 数据带宽   | 必须传输的字节能否及时搬完？  | 各层实际流量与可持续吞吐         | 少搬、压缩、复用、增加通道      |
| 容量     | 必须同时存在的状态能否容纳？  | 驻留峰值、溢出、迁移和分页        | 分块、压缩、流式处理、卸载      |
| 延迟与依赖  | 哪些等待无法被覆盖？      | 依赖链、未隐藏等待、关键路径       | 独立工作、预取、流水、缩短依赖    |
| 并行覆盖   | 有多少可独立推进的工作？    | 任务数、尾波、负载偏斜          | 拆分、调度、工作窃取、减少串行段   |
| 访问结构   | 物理访问是否放大了逻辑需求？  | 扇区浪费、冲突、随机访问         | 合并、对齐、布局、索引与重排     |
| 缓存与局部性 | 重用能否发生，成本是否值得？  | 重用距离、miss 成本、回源与维护成本 | 分块、准入、淘汰、版本与刷新     |
| 提交与调度  | 工作是否及时抵达执行资源？   | 时间线空洞、提交速率、CPU 等待    | 批处理、graph、融合、流水    |
| 协调与顺序  | 多少步骤必须跨参与者共同决定？ | 串行轮次、锁等待、提交路径        | 分区所有权、减少全局协调、协议调整  |
| 功耗与热   | 预算是否压低了可持续能力？   | 功耗、温度、频率与吞吐联动        | 少搬、提高能效、调整工作点      |
| 过载与排队  | 到达需求是否超过可服务能力？  | 队长、排队时间、拒绝率、尾延迟      | 背压、准入、限流、扩容        |
| 故障与恢复  | 哪些部分失效会破坏性质？    | 故障注入、不变量与恢复结果        | 检测、隔离、冗余、日志、恢复     |
| 演进与兼容  | 部分升级或回滚是否仍可工作？  | 版本混用、协议与状态兼容测试       | 版本化、兼容窗口、分阶段迁移     |

这些类别允许重叠。例如缓存冲突同时属于访问结构，分页同时涉及容量、带宽和延迟。分类用于找到解释，不能代替解释。

## 5. 如何判断约束正在生效

### 5.1 速率：利用率、饱和与等待

$$
U_i=\frac{\text{实际服务速率}}{\text{匹配条件下的可持续服务速率}}.
$$

U 接近 1 是速率饱和的重要线索；还需观察是否有待处理工作、目标是否受到影响。低平均利用率不能排除短时、局部或依赖受限。

平均值至少明确作用域：设备、SM、分片、节点、阶段还是整个请求。

### 5.2 容量：工作集与溢出代价

$$
R_M=\frac{\text{需要驻留的工作集}}{\text{有效容量}}.
$$

缓存允许工作集超过容量，代价是 miss；显存溢出可能分页，也可能分配失败。越界行为由运行时与系统决定，不能一概而论。

### 5.3 延迟：关键路径与并发需求

$$
T\ge T_{\mathrm{critical\ path}}.
$$

稳态下 Little 定律为 N=XR：平均在途量等于吞吐乘平均停留时间。

若独立请求大小为 q，平均服务延迟为 τ，希望达到带宽 β，则在途请求数量需求的粗估为：

$$
N_{\mathrm{needed}}\gtrsim\frac{\beta\tau}{q}.
$$

实际还受请求合并、事务大小、队列容量、依赖关系及竞争影响。这是并发需求估计，不是 occupancy 的通用目标。

### 5.4 因果：局部敏感度与干预

对于吞吐目标 X，可定义：

$$
s_i=\frac{\partial\ln X}{\partial\ln C_i}.
$$

对延迟 T 可用负的对数导数。实际采用有限幅度对照实验估计，并记录误差、其他变量变化和适用区间。

单项干预无收益不能直接否认约束：可能存在联合约束、干预没有真正生效、范围太小或测量噪声。必要时设计二因素实验。

### 5.5 稳健性：性质与故障覆盖

为每个故障场景写出：触发点、损坏范围、检测方式、对外行为、允许损失、恢复流程和验收条件。

不要将“未观察到失败”直接等同于“已保证正确”。区分测试证据、协议证明、静态检查和运行时监测的覆盖范围。

## 6. 可复用的性能模型

### 6.1 分阶段 Roofline 与依赖下界

对一个阶段，理想化下界为：

$$
T_{\mathrm{stage}}\ge\max\left(\frac{F}{P},\left\{\frac{Q_\ell}{\beta_\ell}\right\},T_{\mathrm{critical\ path}}\right).
$$

P 与 β 使用匹配该任务的可持续能力。它不自动给出实际时间：不能重叠的成本要累加，可重叠部分仍可能因资源竞争而互相减速。

对整个系统，应沿依赖图计算关键路径，并检查共享资源需求；不能把所有阶段的下界简单取最大值。

### 6.2 Amdahl：先计算投入上限

若互不重叠的一部分占基线时间 f，局部加速 s，其他部分不变：

$$
S=\frac{1}{(1-f)+f/s}.
$$

若 f=5.7%，即使完全消除也只有约 1.060 倍；若 f=17%，最大约 1.205 倍。多流重叠时，先识别关键路径，不能直接用 kernel 时长总和占比代入。

### 6.3 批量解码：交叉点不等于最优点

假设每步读取权重 W，每条序列读取 Lk 的 KV；B 条序列各输出一个 token，忽略其他成本，且这些字节均经过建模的带宽层级：

$$
T_{\mathrm{step}}\approx\frac{W+BLk}{\beta},\qquad
X(B,L)\approx\frac{\beta B}{W+BLk}.
$$

权重流量与 KV 流量相等的位置：

$$
B_{\mathrm{cross}}=\frac{W}{Lk}.
$$

它是流量交叉点。在这里，吞吐只有渐近值的一半：

$$
X_\infty=\frac{\beta}{Lk},\qquad
\frac{X}{X_\infty}=\frac{B}{B+B_{\mathrm{cross}}}.
$$

达到比例 α 所需的理想批量为：

$$
B=\frac{\alpha}{1-\alpha}B_{\mathrm{cross}}.
$$

| 批量 | 渐近吞吐比例 |
|---|---:|
| B_cross | 50% |
| 4 B_cross | 80% |
| 9 B_cross | 90% |
| 19 B_cross | 95% |

容量限制估计：

$$
B_{\max}=\left\lfloor\frac{M_{\mathrm{budget}}-W-M_{\mathrm{fixed}}}{Lk+M_{\mathrm{per\ sequence}}}\right\rfloor.
$$

最终还要检查计算能力、单请求延迟、排队、请求供给、不同序列长度及分配粒度。跨请求共享、KV 压缩、滑动窗口和缓存驻留会改变需求模型。

### 6.4 比较两项技术：比较完整成本曲线

$$
T_j\approx H_j+\max\left(\frac{F_j}{P_j^{\mathrm{eff}}},\frac{Q_j}{\beta_j^{\mathrm{eff}}}\right).
$$

该式适用于可近似重叠的主计算与搬运部分；额外串行阶段单独累加。H 包含转换、补齐、提交与归约等适用成本。

算术强度跨过某条 Roofline 拐点，并不等于另一种实现必然更快。张量核、量化、压缩、融合都应比较完整曲线并检查精度。

### 6.5 功耗与能量分开

$$
E=\int P(t)\,dt.
$$

固定功耗下缩短时间可以节能，但瞬时功率可能不降。功耗贴上限不等于节能优化一定能提高吞吐；必须验证频率、时间和能量变化。

## 7. 缓存专章：缓存是用状态换重复工作

| 子约束 | 诊断重点 | 候选机制 | 需要验证的代价 |
|---|---|---|---|
| 容量 | 重用距离、工作集与 miss 成本 | 分块、压缩、分层、淘汰 | 管理成本与数据搬运 |
| 冲突 | 映射集合或分片是否偏斜 | 布局、padding、哈希 | 空间与寻址开销 |
| 一致性 | 失效、刷新、所有权转移 | 不可变数据、版本、分区所有权 | 陈旧读取与协调成本 |
| 填充 | 回源成本与集中失效 | 请求合并、预取、提前刷新、错峰 | 错误预取、回源放大 |
| 准入与污染 | 一次性访问是否挤出高价值数据 | 选择性缓存、绕过 | 分类与维护成本 |
| 净收益 | 查缓存是否比重算或回源还贵 | 调整粒度、移除无益缓存 | 序列化、锁、内存占用 |

粗略收益模型可写为：

$$
\Delta T\approx h\,C_{\mathrm{avoided}}-C_{\mathrm{lookup}}-C_{\mathrm{maintenance}}-C_{\mathrm{interference}}.
$$

各项必须使用一致的每请求口径；它是诊断近似，不能忽略并发与尾部成本。命中率高也可能没有净收益，流式低命中也未必需要修复。

## 8. 分布式专章：数据、轮次、顺序、偏斜、故障域

| 约束 | 需要建模的量 | 候选机制 |
|---|---|---|
| 通信量 | 每个结果的跨节点字节与经过的链路 | 分区、局部聚合、压缩、计算靠近数据 |
| 通信轮次 | 关键路径上的串行往返 | 批处理、减少交互、流水、提前执行 |
| 协调与顺序 | 全局决定的频率、范围与等待 | 分片、单一所有者、分层协调 |
| 负载偏斜 | 最忙分片、热点 key、最慢任务 | 重分区、热点拆分、工作窃取 |
| 尾部等待 | 扇出数量与完成规则 | 减少扇出、冗余请求、允许时返回部分结果 |
| 故障域 | 哪些组件可能相关失效 | 跨域放置、复制、纠删码 |
| 成员变化 | 重平衡流量、恢复时间、额外容量 | 增量迁移、限速、预留余量 |

集群平均空闲不能排除热点节点饱和；增加带宽不能消除必须串行等待的轮次。

放宽一致性是语义选择，必须先得到目标与性质层的允许。副本数增加也可能增加写入与协调成本。

冗余请求可能降低尾延迟，也可能放大过载。扩容与分片不能自动消除共享锁、中心协调或全局状态带来的限制。

## 9. 稳健性专章：检测、隔离、恢复与验证

### 9.1 明确故障模型

至少考虑是否覆盖：崩溃、超时、丢失、重复、乱序、网络分区、部分写入、位损坏、逻辑误写、资源耗尽、版本不兼容。任意恶意行为需要更强的独立故障模型，不能默认由普通崩溃恢复机制覆盖。

故障范围要包含相关性：一个机架失效、同一配置错误、所有副本复制同一个错误，并不等于若干独立节点随机失效。

### 9.2 从故障到机制

| 故障 | 需要的性质 | 机制族 | 常见遗漏 |
|---|---|---|---|
| 数据内容损坏 | 发现错误，避免静默传播 | 校验、哈希、语义检查 | 没有可信副本或重算路径 |
| 中途崩溃 | 能从已确认进度继续 | 检查点、日志、持久化中间结果 | 检查点依赖的外部状态已变 |
| 部分写入 | 对外可见状态满足不变量 | 事务、提交标记、原子发布 | 数据发布顺序与持久化顺序不匹配 |
| 重复请求或响应丢失 | 重试不重复副作用 | 幂等键、去重、结果记录 | 去重记录与副作用没有原子关联 |
| 局部变慢或失效 | 故障不扩散 | 超时、隔离、背压、熔断、降级 | 无限队列与重试放大 |
| 误改误删 | 恢复可信历史状态 | 版本、独立备份、恢复演练 | 错误已同步到所有在线副本 |

### 9.3 多阶段系统的检查点

每个阶段边界写清楚：

1. 输入与输出的版本、模式和完整性如何确认？
2. 哪些状态持久化，哪些需要重算？
3. 何时对外宣布完成？发布前崩溃会怎样？
4. 重放会不会重复产生外部副作用？
5. 上下游如何识别、隔离或拒绝损坏输出？
6. 恢复依赖哪些外部版本、密钥与元数据？
7. 在哪些位置注入故障，验收什么结果？

恢复时间目标 RTO 与恢复点目标 RPO 必须明确。检测不等于修复，复制不等于备份，检查点不等于可恢复。

## 10. 技术卡片：学习的最小单位

```yaml
id: tech.unique-name
name: 技术名称
status: hypothesis # hypothesis / supported / refuted / superseded
problem: 试图解决的具体问题
scope:
  workload: 输入形状、分布、并发、阶段
  environment: 硬件、运行时、版本、拓扑
  semantics: 精度、一致性、允许的退化
constraints: []
mechanism:
  reduces: []
  increases: []
  requires: []
predictions:
  mechanism_metrics: []
  end_to_end_metrics: []
  expected_ceiling: 未知
failure_modes: []
alternatives: []
evidence: []
open_questions: []
```

每张卡片至少能回答：为什么有效、何时无效、如何验证。不要只保存名字、用法和一张跑分图。

### 示例：算子融合

- 目标：缩短固定管线的端到端时间。
- 假设：中间结果写回与提交间隙占有可消除成本。
- 机制：减少中间流量与提交次数；可能增加寄存器占用、spill 和同步。
- 预测：对应流量或关键路径间隙下降；总体时间下降。
- 反例：流量已被缓存吸收、间隙不在关键路径，或资源压力抵消收益。
- 实验：相同输入与精度，比较流量、寄存器、spill、时间线和端到端分布。

## 11. 实验卡片：从观点变成证据

```markdown
### 实验：名称 / 日期

- 目标与验收条件：
- 当前假设：
- 竞争解释：
- 环境、工作负载、代码版本：
- 基线与唯一主要改动：
- 应变化的机制指标：
- 应变化的端到端指标与预期上界：
- 缓存、频率、功耗、内存与后台负载条件：
- 预热、同步、重复方式及计时边界：
- 结果分布与误差：
- 正确性与故障恢复检查：
- 结论：支持 / 否定 / 暂不确定
- 适用范围与下一步：
```

实验实践：

- 区分冷启动、稳态、热缓存、真实管线和微基准。
- 在目标环境验证；微基准只证明对应局部条件。
- 对比实验尽量交错运行，减少温度、频率和后台漂移影响。
- 报告中位数与所需分位数；重尾数据需要足够样本。
- 检查 profiler 的 replay、序列化及缓存处理是否改变了工作负载。
- 改变多个变量时，明确这是方案比较，不能直接归因于某一个因素。
- 没有收益也是结果；保存反例，避免未来重复试错。

## 12. 成长机制：稳定核心，开放扩展

### 12.1 三类知识分开维护

| 类型 | 内容 | 更新方式 |
|---|---|---|
| 稳定核心 | 目标、需求、机制、代价、证据、适用域 | 少量修改，保持一致语义 |
| 领域模块 | GPU、缓存、数据库、分布式、恢复等 | 随新领域扩展 |
| 项目实例 | 某配置下的测量、实现与失败记录 | 高频积累，保留版本 |

### 12.2 证据状态

- 待验证：只有机制解释或外部资料。
- 局部支持：一个明确条件下的实验成立。
- 多条件支持：不同输入、环境或重复实验支持。
- 存在反例：记录失效边界，缩小结论范围。
- 已替代：新模型解释更多现象，保留旧记录与替代理由。

这些是知识管理状态，不是严格统计置信等级。论文、官方文档、项目实测分别证明不同范围的事情，不能相互代替。

### 12.3 新增分类的规则

遇到无法解释的现象，先检查现有模型的粒度、阶段划分和假设。只有当新类别具有不同的机制、诊断方法或干预方式时，再增加类别。

新增条目至少包含：定义、可观测线索、竞争解释、候选机制、反例与来源。

### 12.4 知识应形成关系图

推荐关系：

- 技术 → 改变 → 需求或能力。
- 机制 → 缓解 / 加剧 → 约束。
- 技术 → 依赖 → 前提。
- 故障 → 威胁 → 性质。
- 实验 → 支持 / 反驳 → 假设。
- 项目结论 → 适用于 → 条件集合。

关系图可以先用 Markdown 链接与稳定 ID 实现，不必先建设知识管理软件。

### 12.5 学习进阶路径

1. 能描述一项技术的输入、输出和用途。
2. 能解释它改变的计算、数据、依赖或故障处理机制。
3. 能预测其收益条件、代价与失效范围。
4. 能用模型估算边界并设计证伪实验。
5. 能把机制迁移到不同领域，并指出迁移时改变的假设。

例如，GPU tile、数据库批处理、网络聚合都可能摊薄固定成本，但各自的容量、等待与语义限制不同。迁移的是机制，不能直接迁移参数。

## 13. 原项目案例的保存方式

以下数据来自讨论中的项目描述，未经本框架独立复测，应保存为案例而非普遍规律：

| 原始观察 | 建议保留的结论 | 待验证项 |
|---|---|---|
| 间隔占 prefill 约 5.7% | 固定基线下，若均可消除且不重叠，收益上界约 1.060 倍 | 间隔是否真由提交导致、是否在关键路径 |
| attention 只启动 2 个 block，occupancy 8.36% | 当前形状与实现可能缺乏并行覆盖 | 分块、拆分与归约的总成本 |
| int 8 实现变慢 | 当前完整路径的 int 8 方案无净收益 | 转换、指令、形状、误差与流量 |
| 累积进程与隔离测量差异很大 | 运行环境状态强烈影响结果 | 分页、迁移、分配与其他进程影响 |
| 负载频率低于名义频率 | 效率应使用匹配实际工作点的能力 | 指令路径、频率采样与可持续峰值 |
| 功耗长期接近 115 W | 功耗预算可能参与限制 | 改变工作点后吞吐与能量的敏感度 |

## 14. 常见误判检查

| 推断 | 需要补充的判断 |
|---|---|
| 利用率低，所以没有瓶颈 | 是否存在依赖、局部饱和、短时过载与供给不足？ |
| occupancy 高，所以性能好 | 是否存在足够 eligible 工作、有效执行与合理资源占用？ |
| 命中率高，所以缓存有效 | 避免的成本是否超过查询、维护与干扰成本？ |
| 分块更大，所以复用更好 | 并行覆盖、寄存器、同步与尾块损失如何变化？ |
| batch 到交叉点就是最优 | 吞吐仍有多少边际收益，延迟和容量允许到哪里？ |
| 资源贴上限，所以增加它必然有效 | 是否在关键路径，是否有联合约束？ |
| 有副本，所以能容忍损坏 | 副本是否独立、是否能识别可信版本、错误是否已传播？ |
| 加重试，所以更可靠 | 是否幂等、有限重试、退避，并且不会放大过载？ |
| 加机器，所以能扩展 | 中心协调、热点、重平衡与网络拓扑是否限制扩展？ |
| 测试通过，所以性质已被保证 | 测试覆盖了哪些故障、并发交错与状态空间？ |

## 15. 延伸资料与使用边界

以下是基础方法入口。本框架是这些方法与讨论建议的综合组织，并非声称全部分类或公式来自同一来源。

1. [Roofline 原始技术报告](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2008/EECS-2008-134.html)：连接计算需求、数据流量和机器能力。
2. [USE Method](https://www.brendangregg.com/usemethod.html)：按资源检查利用率、饱和与错误。
3. [TSA Method](https://www.brendangregg.com/tsamethod.html)：从线程状态与时间消耗分析等待。
4. [CUDA Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)：性能建模、Amdahl、访问、并发与资源取舍。
5. [Nsight Compute Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)：计数器解释、Roofline、等待与 profiling 条件。
6. [FlashAttention 原论文](https://arxiv.org/abs/2205.14135)：以存储层级间 IO 为设计对象的实例。
7. [CMU Performance Analysis 课程材料](https://www.cs.cmu.edu/afs/cs/academic/class/17654-f01/www/lecture/11.pdf)：Little 定律与性能分析。

后续新增分布式协议、存储或恢复方案时，应将相应原始论文、官方语义文档和项目实验挂到具体技术卡片，而非只在总表中增加名称。

## 16. 持续维护清单

每次遇到新技术或新问题，完成一次最小增量：

- 新增或修订一张技术卡片。
- 记录一个有效条件与一个失效条件。
- 保存一次有版本、有边界的实验。
- 把无法解释的结果留在开放问题中。
- 模型解释失败时修订模型，避免为了保住分类而忽略反例。

> 框架的成长，体现为预测更准确、适用边界更清楚、实验更能区分解释，以及跨领域迁移时更少依赖猜测。
