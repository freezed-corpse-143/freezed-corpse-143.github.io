# Dependency（依赖）

**定义**：如果模块 A 要完成工作必须用到模块 B，那么 A 依赖 B。

```java
class UserService {
    private MySQLUserRepository repo = new MySQLUserRepository(); // 依赖
}
```

问题：
- `UserService` 和 `MySQLUserRepository` **强耦合**
- 想换成 PostgreSQL、想 mock 测试，都很困难

# Dependency Graph（依赖图）

当依赖变多，就形成有向图：

```
UserService → UserRepository → DataSource → Driver
OrderService → UserService
```

要解决的问题：
- **循环依赖**（A→B→A）
- **传递依赖**（A 需要 B，B 又带来一堆 C、D）
- **版本冲突**（不同模块要不同版本的同一个库）

这就是 Maven / Gradle / npm 帮你解决的事。

# Dependency Inversion（依赖倒置原则，DIP）

Robert Martin 提出的 SOLID 中的 **D**：

> 高层模块不应依赖低层模块，二者都应依赖抽象。

**Before（高层依赖低层）**：
```
UserService ──→ MySQLUserRepository
```

**After（都依赖接口）**：
```
UserService ──→ UserRepository ←── MySQLUserRepository
                    ↑
                 抽象接口
```

关键点：**依赖方向被"倒置"了**——原本高层→低层的箭头，现在通过接口反转。这叫"倒置"，不是"依赖注入"。

# Inversion of Control（控制反转，IoC）

DIP 是**设计原则**，IoC 是**实现思想**。

> 传统：对象自己 `new` 依赖（自己控制）
> 反转：把"创建和组装依赖"的控制权交给外部框架

```java
// 传统：我控制
class UserService {
    private Repo repo = new MySQLRepo();
}

// IoC：别人控制
class UserService {
    private Repo repo;
    UserService(Repo repo) { this.repo = repo; } // 外部传进来
}
```

IoC 是一个**大概念**，实现方式有多种：
- 依赖注入（DI）
- 依赖查找（Service Locator）
- 事件驱动、模板方法等

# Dependency Injection（依赖注入，DI）

**IoC 最主流的实现方式**。三种注入形式：

| 方式        | 示例                            |
| ----------- | ------------------------------- |
| 构造器注入  | `new UserService(repo)`         |
| Setter 注入 | `service.setRepo(repo)`         |
| 字段注入    | `@Autowired private Repo repo;` |

好处：
- 解耦（面向接口）
- 可测试（注入 mock）
- 生命周期集中管理

# DI Container（依赖注入容器）

手动 `new` 太累，于是有了容器：**Spring、Guice、Dagger、Nest.js** 等。

容器负责：
1. **注册**：扫描/配置 Bean
2. **解析依赖图**：分析谁依赖谁
3. **实例化 + 注入**：按顺序创建并组装
4. **管理生命周期**：singleton / prototype / 作用域
5. **处理循环依赖**（如 Spring 三级缓存）

```java
@Configuration
class AppConfig {
    @Bean Repo repo() { return new MySQLRepo(); }
    @Bean UserService userService(Repo repo) { return new UserService(repo); }
}
```

容器把整张 **Dependency Graph** 自动搭起来。

# 逻辑链条

```
Dependency          → 一切从"我需要别人"开始
Dependency Graph    → 依赖多了就成图，需要管理
Dependency Inversion→ 设计原则：依赖抽象，打破耦合
Inversion of Control→ 设计思想：把控制权交出去
Dependency Injection→ 具体手段：从外部把依赖送进来
DI Container        → 工程化：让框架自动完成上面所有事
```

**一句话总结**：
> 从"对象自己 new 依赖"的硬编码，演进到"容器根据依赖图自动注入抽象"的自动化管理——这就是依赖管理的核心脉络。
