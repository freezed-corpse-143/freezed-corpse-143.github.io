
可以把一个现代错误体系理解成四个协作的部分：

> **错误类型告诉你“当前这件事怎么失败了”；语义映射控制模块之间知道多少；原因链解释“为什么失败”；恢复策略决定“接下来做什么”。**

我们用“提交订单”贯穿整个过程：订单服务调用库存服务，库存服务访问数据库，数据库连接超时。

# 一、局部的封闭错误集合：为一个接口定义失败契约

正常返回值是接口契约的一部分，错误也应该是。

例如：

```
预留库存(商品, 数量)
    成功 → 预留凭证
    失败 → 库存不足 | 商品不存在 | 库存服务不可用
```

这里的“封闭”表示：**对于当前版本的这个接口，调用者知道失败结果属于这些类别之一。**

数学上，它是一个有限的和类型：

$$ \operatorname{Result}(T,E)=\operatorname{Success}(T)\;|\;\operatorname{Failure}(E) $$

其中：

$$ E_{\text{库存}} = \text{库存不足} \;|\; \text{商品不存在} \;|\; \text{服务不可用} $$

每个分支还可以携带自己的数据：

```
库存不足 { 请求数量, 可用数量 }
商品不存在 { 商品编号 }
服务不可用 { 诊断信息 }
```

“局部”则表示：**接口只定义自己这一层的失败语义，不负责枚举整个系统所有可能的故障。**

库存接口的调用者通常不需要认识数据库锁、连接池、DNS、文件描述符等细节。它只需要知道是否缺货、商品是否存在、服务是否可用。

封闭集合也不是永远不能修改。它意味着修改公开错误分类属于接口演进，需要考虑调用者是否必须随之调整。

# 二、边界上的语义映射：把实现故障翻译成接口含义

数据库可能发生：

```
连接超时
连接被拒绝
连接池耗尽
数据库正在重启
```

库存模块可以把它们统一解释成：

```
库存服务不可用
```

这是一个多对一映射：

$$ f:E_{\text{数据库}}\rightarrow E_{\text{库存}} $$

接着，订单模块又把：

```
库存服务不可用
```

解释成：

```
订单暂时无法提交
```

得到另一个映射：

$$ g:E_{\text{库存}}\rightarrow E_{\text{订单}} $$

整个过程是映射的复合：

$$ E_{\text{数据库}} \xrightarrow{f} E_{\text{库存}} \xrightarrow{g} E_{\text{订单}} $$

**每跨过一个抽象边界，就重新回答一次：“这个失败对我提供的能力意味着什么？”**

这与正常结果的封装完全对称：

| 正常路径                   | 失败路径                   |
| -------------------------- | -------------------------- |
| 把数据库记录转换成库存对象 | 把数据库故障转换成库存错误 |
| 隐藏表结构和存储方式       | 隐藏连接方式和故障细节     |
| 对外提供稳定的数据契约     | 对外提供稳定的失败契约     |

但映射不能过度压缩。如果调用者需要在“库存不足”时减少数量，在“服务不可用”时稍后重试，就不能把两者都变成没有区别的“失败”。

可以用一个设计原则判断是否应该合并：

$$ f(e_1)=f(e_2) \quad\Longrightarrow\quad \text{调用者不需要仅凭这两者的区别采取不同动作} $$

这是设计目标：**保留决策所需的区别，隐藏实现造成的区别。**

也不必每调用一层函数就转换一次。只有抽象含义发生变化时，转换才有价值。

# 三、运行时原因链：语义被压缩，证据仍然保留

映射解决了接口膨胀，但也带来问题：

> 如果最终只剩“订单暂时无法提交”，如何排查数据库连接超时？

答案是：**公开分类可以转换，原始错误实例仍作为原因保留下来。**

这一次实际发生的错误可以表示成：

```
订单暂时无法提交
  操作：提交订单 #123
  原因：
    库存服务不可用
      操作：预留商品 A 的库存
      原因：
        数据库连接超时
          操作：连接库存数据库
          等待时间：2 秒
```

一个简化的数据模型是：

```
错误实例 {
    分类
    上下文
    原因：可选的另一个错误实例
}
```

这里要区分**类型**与**实例**：

- 类型描述“可能发生什么”：例如 `库存服务不可用`。
- 实例描述“这次发生了什么”：什么操作、什么资源、什么时间、什么原因。

因此，原因链是运行时数据，不需要把每一种可能的原因组合都定义成新类型。

还要区分原因链与调用栈：

| 信息  | 主要回答          |
| --- | ------------- |
| 调用栈 | 程序经过哪些函数到达这里？ |
| 原因链 | 哪个失败导致了哪个失败？  |

异步任务、跨进程调用中，调用栈可能断开，但逻辑原因仍然可以传递。

原因链也不一定严格是一条链。一次批量操作可能由多个子任务失败共同导致，此时可以保存多个原因，形成原因树；有共享原因时，概念上还可能形成图。

# 四、独立的恢复策略：错误描述事实，策略结合环境做决定

看到“数据库连接超时”，是否应该重试？

还不够信息：

- 这是读取库存，还是提交付款？
- 操作是否可能已经成功，只是响应没回来？
- 是否支持幂等键？
- 用户是否已经取消？
- 剩余时间够不够？
- 是否已经重试了五次？

所以恢复决策更适合写成：

$$ \pi(e,c)\rightarrow a $$

其中：

- \(e\)：错误及其携带的事实。
- \(c\)：操作上下文与当前状态。
- \(a\)：下一步动作。

例如：

```
动作 =
    向上传播
  | 重试
  | 使用备用服务
  | 返回缓存
  | 请求用户修改输入
  | 执行补偿
  | 终止操作
```

同样的错误，在不同场景下可以对应不同策略：

| 错误       | 上下文             | 决策                         |
| ---------- | ------------------ | ---------------------------- |
| 服务不可用 | 幂等读取，时间充足 | 有限重试                     |
| 服务不可用 | 用户已取消         | 停止                         |
| 响应超时   | 付款结果未知       | 查询交易状态，再决定后续动作 |
| 库存不足   | 用户正在结算       | 提示调整数量                 |

“独立”并不是指必须建立一个全局策略中心，而是指：**错误对象不应该把所有场景下的处理动作写死。** 策略可以属于调用者、业务流程或专门的协调器。

错误可以携带 `建议等待时间`、`结果是否确定` 等事实或提示，最终决策仍结合上下文产生。

另外，重试应该有明确的负责层。否则底层重试三次、服务层三次、业务层三次，一次请求可能放大成 $3^3=27$ 次尝试。

# 五、把四个部分放在一起

一次数据库连接超时，完整处理过程如下：

| 阶段       | 做什么                                   | 解决的问题   |
| ---------- | ---------------------------------------- | ------------ |
| 数据库模块 | 产生具体错误实例                         | 准确描述故障 |
| 库存边界   | 映射为“库存服务不可用”，保留原因         | 隔离实现细节 |
| 订单边界   | 映射为“订单暂时无法提交”，附加订单上下文 | 提供业务语义 |
| 流程协调者 | 根据幂等性、时间预算等选择动作           | 决定如何恢复 |
| 诊断出口   | 记录原因链和相关上下文                   | 支持排查     |

这里同时存在两种视角：

**处理视角：**

```
调用者主要看本层公开分类，作出稳定决策。
```

**诊断视角：**

```
排查者沿原因链深入，查看具体故障和上下文。
```

一般不应让业务调用者通过遍历原因链、识别某个数据库私有错误来决定业务行为。如果某个区别确实影响业务决策，就应该把它提升到公开错误契约中。

# 六、怎样实际设计一套错误体系

对每个模块依次回答四个问题：

1. **调用者需要区分哪些失败？**
   用这些区别定义局部错误集合。
2. **内部故障分别意味着什么？**
   定义从内部错误到公开错误的映射。
3. **为了排查这次失败，需要保留什么？**
   保存原因、操作、资源标识等上下文，并明确这些数据的生命周期。
4. **谁有足够的信息决定下一步？**
   把恢复策略放在能掌握幂等性、预算、取消状态和业务目标的那一层。

由此也能判断错误类型是否真的需要增加：**新的失败如果改变调用者的处理方式，就值得成为公开分类；如果只是解释这次为什么失败，通常属于原因或上下文。**
