**容量规划、性能工程与过载控制**。下面的分类是综合这些资料建立的分析框架，并非某个来源的固定分类。

**1. 首先补上目标：什么叫“系统承受住了”？**

“没有崩溃”远远不够。请求可能全部进入队列，却几个小时后才能完成；服务端显示成功，客户端却早已超时。

应该先定义用户可以感知的目标：

| 维度   | 需要回答的问题               | 示例                       |
| ------ | ---------------------------- | -------------------------- |
| 正确性 | 结果是否正确，是否重复执行？ | 支付不能重复扣款           |
| 延迟   | 多长时间内完成才有价值？     | 99% 的查询在 300 ms 内完成 |
| 可用性 | 有多少请求能够成功？         | 按约定口径统计成功比例     |
| 新鲜度 | 结果可以落后多久？           | 统计数据最多延迟 1 分钟    |
| 持久性 | 已确认接收的数据能否丢失？   | 已确认订单需要可靠保存     |
| 恢复性 | 故障解除后多久恢复？         | 积压在 10 分钟内消化       |
| 成本   | 满足上述目标需要多少资源？   | 每千次有效请求的资源成本   |

这对应 SLI/SLO 的思路：先定义衡量指标和服务目标，再判断容量、优化和保护措施是否有效。[Continuous Improvement To Get Reliability](https://sre.google/workbook/implementing-slos/?utm_source=chatgpt.com)

因此，真正值得优化的是：

$$ \text{有效吞吐} = \frac{\text{正确且在有效时间内完成的工作量}}{\text{时间}} $$

例如，每秒处理 10,000 次请求，但其中 8,000 次在客户端超时后才完成，实际价值可能很低。

**2. 规模分析之前，还需要“工作负载建模”**

只问“支持多少 QPS”不够。不同请求的资源成本可能相差几个数量级。Google SRE 专门指出，单纯依赖 QPS 建模容量可能产生误导，需要关注请求实际消耗的资源。[sre.google](https://sre.google/sre-book/handling-overload/?utm_source=chatgpt.com)

至少需要分析五个方面：

| 方面 | 关键变量                         | 为什么重要               |
| ---- | -------------------------------- | ------------------------ |
| 数量 | 请求速率、数据总量、连接数       | 决定总体规模             |
| 成本 | 每次 CPU 时间、内存、I/O、网络量 | 决定单位工作有多贵       |
| 分布 | 长尾、热点、大请求比例           | 平均值可能掩盖瓶颈       |
| 时间 | 突发、周期、持续时间             | 决定缓冲和扩容需求       |
| 关联 | 扇出、重试、缓存未命中           | 外部流量会放大成内部工作 |

例如，同样是每秒 1,000 个查询：

- 查缓存与扫描数据库的成本不同。
- 读取 10 行与读取 100 万行的成本不同。
- 均匀访问与集中访问同一个热点键的行为不同。
- 平稳到达与同一毫秒集中到达的排队情况不同。

**负载应当被看作带有成本和分布的工作集合。**

还有一个经常遗漏的维度：**数据规模增长会改变单位请求成本**。今天测出的容量，未必适用于一年后的索引、目录和数据库。

**3. 容量分析的基础：资源需求、排队与并发**

可以用三个互补模型理解系统。

第一，资源预算。对某项资源 $r$：

$$ D_r=\sum_i\lambda_i d_{i,r} $$

其中：

- $\lambda_i$：第 $i$ 类请求的到达速率。
- $d_{i,r}$：该类请求平均消耗的资源。
- $D_r$：单位时间内对该资源的总需求。

例如，每秒 2,000 个请求，每个消耗 3 ms CPU 时间：

$$ D_{\mathrm{CPU}}=2000\times0.003=6\text{ 核秒/秒} $$

这只是计算需求的估算，尚未包含系统开销、争用和容量余量。

第二，排队关系：

$$ L=\lambda W $$

在适用的稳定条件下，平均在途数量等于吞吐率乘以平均停留时间。**这里是在途数量，不只是正在执行的数量，也包括等待。**

第三，接近饱和后的非线性。以最简单的 M/M/1 排队模型为例：

$$ W=\frac{1}{\mu-\lambda} =\frac{1/\mu}{1-\rho}, \qquad \rho=\frac{\lambda}{\mu}<1 $$

它假设泊松到达、指数服务时间和单服务台，不能直接套用所有真实系统，但能说明一个重要规律：

> 资源越来越忙时，排队延迟可能加速上升，而不是线性上升。

因此，容量不是“CPU 能否达到 100%”，而是**在给定负载形态下，仍能满足服务目标的工作量**。

排查时可对每项资源检查利用率、饱和度、错误，即 USE 方法。尤其要看等待：总 CPU 不高，也可能存在单核、锁、连接池或单个分区的饱和。[brendangregg.com](https://www.brendangregg.com/usemethod.html?utm_source=chatgpt.com)

**4. 压力测试应该验证一片“运行范围”**

单次测出一个最大 QPS，并不能描述系统。

至少要分别改变：

| 测试变量     | 需要发现的问题                   |
| ------------ | -------------------------------- |
| 请求速率     | 吞吐拐点和过载表现               |
| 并发数量     | 线程、连接、内存与争用上限       |
| 数据规模     | 算法、索引和缓存是否随规模退化   |
| 请求组合     | 昂贵请求增加后容量如何变化       |
| 热点集中程度 | 单键、单分区是否提前饱和         |
| 持续时间     | 泄漏、积压、磁盘增长             |
| 可用容量     | 节点退出后是否仍满足目标         |
| 下游状态     | 慢响应、超时和失败是否向上游传播 |

还需要区分两类压测模型：

- **闭环模型**：固定数量的客户端完成一次操作后再开始下一次，适合模拟某些固定用户群行为。
- **开环模型**：按独立的到达计划产生工作，适合验证外部流量持续进入时的积压与过载。

若真实场景是持续外部到达，却使用“响应越慢、发送越少”的模型，可能低估延迟，这涉及 coordinated omission 问题。[Grafana k6 documentation](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/?utm_source=chatgpt.com)

测试应当继续覆盖超载区间及恢复阶段：保护是否生效，负载下降后能否恢复，而不只是寻找峰值。

**5. 运行时保护：你缺少的几个关键概念**

背压、卸压只是保护手段中的两部分。需要把它们和限流、并发控制、准入控制、熔断、降级区分开。

| 机制     | 控制什么               | 原理与作用                                   |
| -------- | ---------------------- | -------------------------------------------- |
| 限流     | 单位时间进入多少工作   | 通过速率预算限制流量，令牌桶可允许有限突发   |
| 并发控制 | 同时存在多少未完成工作 | 限制在途请求，保护内存、线程和连接           |
| 准入控制 | 当前工作是否值得接收   | 根据资源、优先级、成本和剩余时间决定是否放行 |
| 背压     | 上游的生产速度         | 把下游处理能力反向反馈给上游                 |
| 负载卸载 | 哪些工作不再处理       | 拒绝、丢弃或取消过量工作                     |
| 降级     | 每项工作执行多少内容   | 减少功能或结果精度，降低处理成本             |
| 熔断     | 是否继续调用异常依赖   | 暂停部分调用，并通过探测判断是否恢复         |
| 资源隔离 | 一类工作能影响多大范围 | 用独立队列、池、配额或实例限制故障传播       |

这里存在几个关键关系：

**限流不能替代并发控制。** 每秒请求数不变，但下游延迟变为原来的十倍，在途请求仍可能显著增加。

**熔断不能替代容量控制。** 它主要管理异常依赖的调用状态，无法保证健康服务不会被正常流量压垮。

**背压不能消除不可暂停的需求。** 用户持续发请求时，最终仍需要拒绝或其他取舍。

**负载卸载应尽可能在昂贵操作前发生。** AWS 将其目标概括为在过载中维持有效吞吐；拒绝请求本身也有成本，必须验证。[AWS Builder Center](https://builder.aws.com/content/3Eun1EEyX6p2e3VYNyRLSJzLuMV/using-load-shedding-to-avoid-overload?utm_source=chatgpt.com)

**6. 队列管理：需要管理“积压债务”**

日志队列是一个具体实例，更一般的问题是：**任何缓冲都会把当前处理不足转化为未来要偿还的工作。**

队列既能吸收短时突发，也可能显著延长故障恢复时间。AWS 对异步系统的分析强调：任务完成得太晚，即便最终执行成功，也可能失去业务价值。[builder.aws.com](https://builder.aws.com/content/3EuRcgkTP1MI0c7zM8W6HL3WIqA/avoiding-insurmountable-queue-backlogs?utm_source=chatgpt.com)

完整的队列设计需要回答：

| 问题           | 设计内容                     |
| -------------- | ---------------------------- |
| 能存多少？     | 条目上限、字节上限、磁盘配额 |
| 能等多久？     | 截止时间、TTL、最大排队时间  |
| 满了怎么办？   | 阻塞、拒绝、丢弃、持久化     |
| 谁先处理？     | FIFO、优先级、公平调度       |
| 失败怎么办？   | 有限重试、退避、死信或隔离   |
| 重复怎么办？   | 幂等、去重、重复检测         |
| 重启怎么办？   | 持久化、确认点、重放         |
| 如何判断恢复？ | 最老任务年龄、净消化速度     |

如果积压为 $Q$，处理能力为 $C$，新的到达速率为 $\lambda$，在速率近似恒定且 $C>\lambda$ 时：

$$ T_{\mathrm{drain}}\approx\frac{Q}{C-\lambda} $$

分母是**剩余处理能力**。只按 $Q/C$ 估算，会忽略恢复期间仍不断进入的新任务。

队列容量也不是越大越好。对近似同质的 FIFO 工作，可用

$$ Q_{\max}\approx C\,W_{q,\max} $$

粗略估算等待时间预算对应的队列规模，但真实系统还必须结合服务时间波动、字节数和尾延迟校准。

**7. 超时、取消和重试：控制工作生命周期**

这部分与你前面讨论的并发、恢复密切相关。

一次请求可能同时有三种状态：

> 客户端停止等待；服务端仍在计算；数据库已经提交。

所以：

- **超时不代表操作没有发生。**
- **取消信号不代表所有下游工作已经停止。**
- **重试不代表只是“再等一次”，它会创建额外工作。**

需要组合设计：

| 机制               | 作用                               |
| ------------------ | ---------------------------------- |
| 端到端截止时间     | 限制整条调用链可花费的总时间       |
| 下游时间预算       | 避免每一层都重新等待完整超时       |
| 取消传播           | 停止可安全中止的无效工作，释放资源 |
| 有限重试与重试预算 | 限制故障期间的额外工作             |
| 指数退避与随机抖动 | 减少同步重试形成的流量尖峰         |
| 幂等键和结果查询   | 应对结果未知时的重复提交           |

假设一条调用链有三层，每层最多尝试三次，在最坏的嵌套重试情况下，底层可能被调用 $3^3=27$ 次。应明确由哪层负责重试，并约束总体预算。AWS 的相关资料也强调了重试放大、幂等与抖动的重要性。[builder.aws.com](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter?utm_source=chatgpt.com)

**8. 隔离、公平性和调度：谁可以使用剩余容量？**

系统即使没有整体超载，也可能被某个租户、大任务或热点占满。

因此，还需要：

- **按租户配额**：防止单个调用方耗尽共享资源。
- **按工作类型隔离**：批处理不应占满交互查询的连接池。
- **按成本计费或调度**：昂贵请求不能简单按“一次请求”计量。
- **限制单项工作规模**：分页、分块、限制扫描范围。
- **优先级与公平调度**：保证核心请求，同时防止低优先级长期饥饿。

Google SRE 将按客户限制与资源成本建模作为过载管理的一部分。[sre.google](https://sre.google/sre-book/handling-overload/?utm_source=chatgpt.com)

一个值得牢记的区别是：**优先级决定先服务谁，隔离决定某类工作最多能伤害谁。** 两者通常需要配合。

**9. 扩缩容与阶梯管理：本质上是反馈控制**

“阶梯式管理”可以进一步拆成：

- **分级响应**：根据压力状态启用不同保护。
- **分层保护**：入口、服务、依赖和存储分别保护。
- **分时控制**：快速限流、较慢扩容、更慢的容量规划协同运行。

它们的时间尺度不同：

| 时间尺度         | 常见动作                     |
| ---------------- | ---------------------------- |
| 单次请求或毫秒级 | 准入、并发限制、取消、卸载   |
| 秒级             | 背压反馈、动态限额、熔断探测 |
| 分钟级           | 扩容、消费者调整、预热       |
| 更长周期         | 分片、架构优化、容量采购     |

这些控制存在测量和生效延迟，因此会出现振荡：扩容过多后缩容，缩容过快后再次扩容。滞回、稳定窗口、变化速率限制可以缓解这一问题；Kubernetes HPA 就提供扩缩容行为与稳定窗口配置。[Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/?utm_source=chatgpt.com)

还有一种容易遗漏的控制冲突：

> 卸载请求降低 CPU → 基于 CPU 的扩容看不到压力 → 系统持续拒绝请求。

AWS 明确讨论过这种相互作用。因此，扩容信号还需要考虑到达需求、拒绝量、积压等信息。[AWS Builder Center](https://builder.aws.com/content/3Eun1EEyX6p2e3VYNyRLSJzLuMV/using-load-shedding-to-avoid-overload?utm_source=chatgpt.com)

**10. 日志与可观测性：保护机制自己也要接受保护**

日志队列属于观测数据管道。它需要与业务管道一样接受容量和故障分析。

至少应区分：

| 数据     | 通常关注什么                   |
| -------- | ------------------------------ |
| 调试日志 | 可采样、聚合，限制数量与大小   |
| 错误日志 | 保留定位信息，避免重复错误刷屏 |
| 指标     | 控制标签基数和采集成本         |
| 链路追踪 | 根据预算和诊断需求采样         |
| 审计记录 | 明确持久性、完整性和访问要求   |

OpenTelemetry 的资料说明，内存发送队列会面临满载和进程退出导致的数据丢失；持久化队列能改善重启恢复，但仍受磁盘故障、空间和重试限制影响。[OpenTelemetry](https://opentelemetry.io/docs/collector/resiliency/?utm_source=chatgpt.com)

尤其要防止：

> 下游失败 → 错误日志暴增 → 日志占满 CPU、磁盘或内存 → 业务进一步变慢。

监控还必须区分到达量、放行量、拒绝量、完成量和有效完成量。成功请求延迟与快速拒绝延迟也应分别观察，否则大量快速拒绝可能让总体延迟指标看起来更好。

**11. 故障恢复：系统需要有“恢复容量”**

过载有两种主要来源：

$$ \text{需求增加} \qquad\text{或}\qquad \text{可用容量下降} $$

节点退出、缓存失效、磁盘变慢、部署回归，都可能在流量不变时造成过载。负载转移到剩余节点后，还可能形成级联故障。[Cascading Failures: Reducing System Outage](https://sre.google/sre-book/addressing-cascading-failures/?utm_source=chatgpt.com)

所以容量规划要覆盖：

- 故障后的剩余节点能否处理核心流量。
- 新节点和缓存预热期间能承接多少工作。
- 积压重放会不会挤占实时请求。
- 重试和恢复任务是否拥有独立预算。
- 扩容后会不会把共享数据库压垮。
- 保护解除是否需要逐步恢复。

**恢复本身也是负载。** 如果系统在正常状态下就没有余量，故障解除后未必能消化积压。

**12. 最终可采用的完整工作顺序**

| 步骤               | 主要产出                             |
| ------------------ | ------------------------------------ |
| 定义服务目标       | 延迟、正确性、可用性、恢复与成本目标 |
| 建立工作负载模型   | 请求类别、成本、分布、突发与放大关系 |
| 绘制资源和依赖关系 | CPU、内存、池、队列、热点与共享下游  |
| 估算容量和余量     | 正常、峰值、容量损失与恢复场景       |
| 建立观测           | 用户体验、资源饱和、队列、拒绝和重试 |
| 测量运行范围       | 数据规模、负载组合、长时间与故障测试 |
| 设置资源边界       | 单请求、并发、队列、重试、存储上限   |
| 配置保护与调度     | 背压、准入、卸载、降级、隔离和公平性 |
| 验证控制协同       | 扩容、熔断、限流是否互相干扰         |
| 验证恢复           | 预热、积压消化、渐进恢复和数据完整性 |

你原先的概念可以保留，但应补进一个更大的闭环：**先定义服务价值，再测量工作成本，约束所有积压与放大机制，最后验证系统在失去容量后仍能恢复。**
