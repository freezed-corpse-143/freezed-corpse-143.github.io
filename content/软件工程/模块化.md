# Module（模块）

- 语言级别的封装单位，通常对应一个源文件或一组源文件。
- 核心特征是**有明确的对外接口和隐藏的内部实现**（information hiding）。
- 例：Python 的 `.py` 文件、Java 的 `module-info.java`、Rust 的 `mod`。
- 关注点：**命名空间、可见性、依赖方向**

# Package（包）

- 比 module 更偏**分发与命名**的单位，语义在不同语言里不一致：
  - Java：`package` 是命名空间，`jar` 才是分发单位；
  - Python：`package` 是含 `__init__.py` 的目录；
  - npm/Go：`package` 既是命名空间也是分发单位。
- 关注点：**命名空间管理、可发布性**。

# Library（库）

- 可被其他代码**复用**的代码集合，强调"被依赖"的角色。
- 与 package 的区别：library 是**角色**，package 是**形态**。一个 library 可能由多个 package 组成。
- 关注点：**API 稳定性、版本兼容、复用价值**。

# Component（组件）

- 强调**可替换、可组合、有明确契约**的单元。可以是代码、二进制、甚至一个服务。
- 比 library 更强调**部署与替换的独立性**，是架构层面的词。
- 关注点：**契约、可替换性、组合**。

# Workspace（工作区）

- **开发时的组织单位**，把多个 package/module 放在一起协同开发。
- 例：Cargo workspace、npm workspaces、Bazel workspace。
- 关注点：**统一构建、共享依赖、原子提交**。

# Crate（包）

- Rust 特有的**编译与分发单位**，一个 crate 编译成一个 `.rlib` 或可执行文件。
- 一个 crate 内含多个 module；crate 是 module 的容器。
- 关注点：**编译单元、发布单元**。

# Assembly（程序集）

- .NET 的概念，是**部署与版本控制的最小单位**，通常对应一个 `.dll` 或 `.exe`。
- 包含 IL 代码、元数据、清单（manifest）。
- 关注点：**部署单元、版本绑定**。

# Project（项目）

- 最模糊的词，通常指**一次开发工作的组织容器**，可能包含多个 package/crate。
- 关注点：**人、时间、目标的组织**，不是技术边界。
# Service（服务）

- **运行时的能力提供者**，通过接口（通常是网络）对外提供服务。
- 关键：它有自己的**生命周期、部署、扩缩容**。
- 关注点：**运行时边界、SLA、独立部署**。

# Process（进程）

- **操作系统级别的隔离单位**，拥有独立地址空间。
- 是"逻辑边界"升级为"物理边界"的第一站。
- 关注点：**内存隔离、故障隔离、资源隔离**。

# 边界与隔离

```
Function → Type → Module → Package → Library
→ Component → Process → Service → Deployment Unit
```

这条链的本质是**"边界"从细到粗、从逻辑到物理的演化**：

| 层次            | 边界性质        | 隔离手段 |
| --------------- | --------------- | -------- |
| Function        | 调用边界        | 栈帧     |
| Type            | 数据+行为边界   | 类型系统 |
| Module          | 命名/可见性边界 | 编译器   |
| Package         | 分发边界        | 包管理器 |
| Library         | 复用边界        | 版本管理 |
| Component       | 契约边界        | 接口     |
| Process         | 内存边界        | OS       |
| Service         | 网络边界        | 网络协议 |
| Deployment Unit | 部署边界        | 编排系统 |

关键洞察：**越往下，隔离越强，但代价（延迟、复杂度、运维）也越大。**

# 边界升级

这是整个模块化学习中最核心的问题。判断依据可以归纳为几个信号：

## 升级信号（从逻辑边界 → 物理边界）

1. **故障隔离需求**
   - 一个模块崩溃不能拖垮整个系统 → 升级为 process。

2. **独立部署需求**
   - 不同团队要独立发版、不同节奏 → 升级为 service。

3. **独立扩缩容需求**
   - 某部分负载远高于其他部分 → 升级为 service。

4. **技术栈异构需求**
   - 不同部分要用不同语言/运行时 → 升级为 process/service。

5. **安全/权限边界**
   - 需要强隔离、审计、最小权限 → 升级为 process。

6. **组织边界（康威定律）**
   - 团队结构变了，边界要跟着变。

## 反向信号（不升级的理由）

- 延迟敏感：网络调用比函数调用慢几个数量级。
- 事务一致性：跨进程事务极其复杂。
- 运维成本：每个 service 都要监控、日志、CI/CD、on-call。
- 调试困难：分布式追踪比单步调试难得多。

## 核心原则

> **能在一个进程内解决的问题，不要用两个进程解决。**
> **能用模块边界解决的问题，不要用网络边界解决。**

升级边界是**用复杂度换隔离性**的交易，只有在隔离性带来的收益 > 复杂度成本时才值得。

## 微服务

> 微服务不是高级版代码组织方式，而是把逻辑边界升级为网络 + 进程 + 部署边界。

1. **微服务 = 模块化 + 分布式 + 独立部署**，三者缺一不可。
2. 如果只是"代码分模块"，那是 **Modular Monolith**，不是微服务。
3. 微服务的代价是**分布式系统的全部复杂度**：网络分区、最终一致性、服务发现、可观测性……

所以：

```
Modular Monolith  ← 先在这里把边界划对
      ↓
Plugin Architecture ← 学会运行时替换
      ↓
Multi-process      ← 学会进程隔离与 IPC
      ↓
Distributed System ← 学会网络、一致性、容错
      ↓
Microservices      ← 最后才是它
```

而 `Hello World → Kubernetes` 这条路径的问题在于：**跳过了所有边界演化的中间环节**，直接面对最复杂的运维形态，却没有建立起"为什么需要这些边界"的判断力。
