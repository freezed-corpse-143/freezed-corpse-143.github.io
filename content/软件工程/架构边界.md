# 回答的问题

| 分组            | 回答的核心问题               | 包含的概念                                          |
| ------------- | --------------------- | ---------------------------------------------- |
| **依赖方向 / 边界** | 代码依赖应该朝哪指？核心业务如何隔离外部？ | Layered、Hexagonal、Ports & Adapters、Onion、Clean |
| **组织维度**      | 按技术层切，还是按业务功能切？       | Layered vs Vertical Slice                      |
| **领域建模**      | 如何表达复杂业务规则？           | DDD                                            |
| **读写与消息**     | 如何分离读写？如何解耦组件间通信？     | CQRS、Event Driven                              |

注意第一组里的 5 个，其实**是同一个思想的渐进演化**，不是 5 个独立的东西。

# Layered Architecture（分层架构）

最传统的做法，按**技术职责**横向切层：

```
┌─────────────────────┐
│  Presentation (UI)  │
├─────────────────────┤
│  Application/Service│
├─────────────────────┤
│  Domain / Business  │
├─────────────────────┤
│  Persistence / Infra│   ← 依赖朝下
└─────────────────────┘
```

- **优点**：简单、直观、人人会。
- **问题**：**依赖方向指向基础设施**。业务层往往直接 import 数据库、ORM、HTTP 客户端，导致业务逻辑和框架绑死，无法脱离数据库测试，换框架要动核心代码。

Hexagonal / Onion / Clean 本质都是**对 Layered 的修正**：把依赖方向倒过来，让业务核心不依赖任何外部技术。

# Hexagonal Architecture / Ports & Adapters（六边形架构 / 端口适配器）

**这就是同一个东西的两个名字**（Alistair Cockburn 提出）。核心思想只有一句话：

> **核心业务不依赖外部，外部通过"端口"接入核心。**

```
                 ┌─────────────┐
 HTTP ─Adapter──►│             │◄──Adapter─ Database
 CLI ─Adapter───►│ Application │◄──Adapter─ Redis
 RPC ─Adapter───►│    Core     │◄──Adapter─ External API
                 │             │
                 └─────────────┘
        （驱动侧）              （被驱动侧）
```

几个关键点：

1. **Port（端口）= 接口**，定义在核心内部。分两种：
   - **Driving / Primary Port**：外部如何调用核心（如 `CreateOrderUseCase` 接口）
   - **Driven / Secondary Port**：核心如何调用外部（如 `OrderRepository` 接口）
2. **Adapter（适配器）= 实现**，在核心外部。把 HTTP 请求翻译成对 Primary Port 的调用；把 `OrderRepository` 接口翻译成 MySQL 调用。
3. **六边形的形状不重要**——画成六边只是想说"每一边都可以插适配器"，不是只有六个。

**收益**：核心可以脱离 HTTP、数据库独立测试；换数据库只换 Adapter；同一个核心可以同时暴露 HTTP、CLI、gRPC。

# Onion Architecture（洋葱架构）

Jeffrey Palermo 提出，**思想与 Hexagonal 相同，但用同心圆把"内部分层"画得更细**：

```
        ┌───────────────────────────┐
        │  Infrastructure / UI      │  ← 最外层：Adapter
        │  ┌─────────────────────┐  │
        │  │ Application Service │  │
        │  │  ┌───────────────┐  │  │
        │  │  │ Domain Model  │  │  │  ← 最内层：实体、领域服务
        │  │  └───────────────┘  │  │
        │  └─────────────────────┘  │
        └───────────────────────────┘
              依赖只能由外向内
```

- 比 Hexagonal 更强调**内部也分层**：Domain Model 最内，Application Service 次之，Infrastructure 最外。
- 规则：**外层可以依赖内层，内层绝不能依赖外层**。

# Clean Architecture（整洁架构）

Robert C. Martin（Uncle Bob）提出，**是把 Hexagonal + Onion + 一些其他思想综合后的"集大成版"**，也是最出名的一张图：

```
┌─────────────────────────────────────────┐
│  Frameworks & Drivers (outermost)       │
│  ┌───────────────────────────────────┐  │
│  │ Interface Adapters (Controllers,  │  │
│  │   Gateways, Presenters)           │  │
│  │  ┌─────────────────────────────┐  │  │
│  │  │ Use Cases (Application)     │  │  │
│  │  │  ┌───────────────────────┐  │  │  │
│  │  │  │ Entities (Domain)     │  │  │  │
│  │  │  └───────────────────────┘  │  │  │
│  │  └─────────────────────────────┘  │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
```

**The Dependency Rule（依赖规则）**：源码依赖只能由外向内。

三个概念的关系一句话总结：

> **Hexagonal ≈ Onion ≈ Clean**，都是"核心隔离、依赖倒置"。
> Hexagonal 强调**端口/适配器**（怎么接线）；
> Onion 强调**同心分层**（内部分几层）；
> Clean 强调**依赖规则 + 综合命名**（统一语言）。

实践中你几乎不会"只用其中一个"——它们说的是同一件事的不同侧面。

# Vertical Slice Architecture（垂直切片）

前面几个都是**横向切**（按技术层）。Vertical Slice 是**正交的另一维度**：按**业务功能**切。

```
横向分层：                垂直切片：
┌──────────────┐        ┌──────┬──────┬──────┐
│   UI 层      │        │Create│Cancel│Ship  │
├──────────────┤        │Order │Order │Order │
│  Service 层  │        │      │      │      │
├──────────────┤   vs   │ UI   │ UI   │ UI   │
│  Domain 层   │        │ +    │ +    │ +    │
├──────────────┤        │ Logic│ Logic│ Logic│
│  Infra 层    │        │ +    │ +    │ +    │
└──────────────┘        │ DB   │ DB   │ DB   │
                        └──────┴──────┴──────┘
```

- 每个"切片"（一个用例/功能）自带它的 UI、逻辑、数据访问，**端到端贯通**。
- 优点：加功能时只改一个文件夹，减少跨层牵动；适合需求频繁变化的业务系统。
- 与 Hexagonal/Clean **不冲突**：你可以在每个切片内部仍然用 Clean 的依赖规则。

**关键区别**：Layered 是"横向分层"，Vertical Slice 是"纵向切分"——这是**两个维度的正交选择**，不是互相替代。

# DDD（Domain-Driven Design，领域驱动设计）

DDD 不是分层方式，而是**关于如何建模复杂业务的方法论**。它回答的是"核心里面到底放什么"。

**战略设计**（大尺度）：
- **Ubiquitous Language**：业务和开发用同一套词
- **Bounded Context**：明确边界，同一个词在不同上下文含义不同
- **Context Map**：上下文之间的关系

**战术设计**（小尺度，落到代码）：
- **Entity / Value Object**：有身份 vs 不可变无身份
- **Aggregate / Aggregate Root**：一致性边界
- **Domain Event**：领域内发生的事
- **Repository**：聚合的持久化抽象（正好就是一个 Driven Port）
- **Domain Service / Factory**

**与前面架构的关系**：
- DDD 的 Entity/Aggregate/Repository 通常放在 Clean/Onion 的**最内层（Domain）**。
- DDD 的 Application Service 对应 Clean 的 **Use Case 层**。
- **Hexagonal 的 Port 常常就是 DDD 的 Repository 接口**——两者天然契合。

DDD 解决"**领域怎么建模**"，Clean/Hexagonal 解决"**代码怎么组织、依赖怎么指**"。二者正交且互补。

# CORS（Command Query Reponsibility Segregation）

不是分层，而是**读写职责分离**：

```
Command（写） ──► 领域模型 ──► 写库（规范化）
Query  （读） ──► 读模型   ──► 读库（为查询优化，可反规范化）
```

- 与 DDD 常搭配：写侧走聚合保证一致性，读侧直接查优化过的视图。
- 与 Event Driven 常搭配：写侧发事件，读侧订阅事件更新读模型（最终一致）。
- **注意**：CQRS 不等于"必须两个数据库"，最轻量可以只是代码层 Command/Query 方法分离。

# Event Driven Architecture (事件驱动架构)

组件之间通过**事件**而不是直接调用来通信：

```
Producer ──publish──► Event Bus ──► Consumer A
                                 └─► Consumer B
```

- 解耦：生产者不知道消费者是谁。
- 常见搭配：DDD 的 **Domain Event** → 发到总线 → 触发其他 Bounded Context 或更新 CQRS 读模型。
- 代价：最终一致性、调试更难、需要处理幂等/顺序/重放。

它解决的是"**组件之间怎么通信**"，与分层是正交维度。

# 正交维度图

```
                 ┌────────────────────────────────────┐
                 │  按什么维度组织代码？              │
                 │  ┌──────────┐  ┌─────────────────┐ │
   依赖方向 ────►│  │ 横向分层 │  │ 垂直切片        │ │
   （怎么指）    │  │ Layered  │  │ Vertical Slice  │ │
                 │  │ Hexagonal│  │                 │ │
                 │  │ Onion    │  │                 │ │
                 │  │ Clean    │  │                 │ │
                 │  └──────────┘  └─────────────────┘ │
                 └────────────────────────────────────┘
                          │
                          ▼
                 ┌────────────────────┐
                 │ 核心里面放什么？   │  DDD
                 │ （领域怎么建模）   │
                 └────────────────────┘
                          │
                          ▼
                 ┌────────────────────┐
                 │ 组件间怎么交互？   │  CQRS / EDA
                 │ （读写分离/事件）  │
                 └────────────────────┘
```

**一个真实的系统可以同时是**：

> Clean Architecture 定依赖方向 + DDD 建领域模型 + Vertical Slice 组织用例文件夹 + CQRS 分离读写 + Event Driven 做上下文间通信。

它们各管一摊，互不打架。
