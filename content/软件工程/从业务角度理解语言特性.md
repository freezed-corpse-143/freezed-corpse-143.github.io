适合初学者的顺序：先看业务遇到了什么问题，再看需要什么能力，最后选择语言特性。

先记住：语言特性提供工具，业务设计决定怎么使用工具。例如：所有权能约束内存访问，但“库存不能超卖”仍然需要设计完整操作。

下面以“订单系统”为贯穿例子，同时对照 C++与 Rust。

# 一、多态：同一种工作，存在不同实现

假设订单需要发送通知，有邮件、短信、站内信三种渠道。

真正要问的不是“这是业务层还是引擎层”，而是：

1. 调用时，编译器能不能知道具体实现？
2. 程序运行时，需不需要统一存放和选择不同实现？
3. 我们是否希望把全部合法类别列出来？

| 业务需求                        | 需要的能力 | C++                              | Rust                             | 主要代价             |
| --------------------------- | ----- | -------------------------------- | -------------------------------- | ---------------- |
| 一套算法适配多种类型，每次调用的具体类型编译期已知   | 静态多态  | 模板、Concepts                      | 泛型、trait bound                   | 可能增加编译时间和代码体积    |
| 根据配置、用户或运行状态选择实现；同一集合存放不同实现 | 动态多态  | 虚函数、接口基类                         | `dyn Trait`                      | 间接调用，以及部分优化机会减少  |
| 明确只有几种合法情况，新增一种时希望检查处理位置    | 封闭变体  | `std::variant`、`std::visit`      | `enum`、`match`                   | 新增变体通常需要修改相关处理逻辑 |
| 只需要传入一段行为，而不需要完整对象接口        | 可调用对象 | lambda、函数对象、模板回调、`std::function` | 闭包、`impl Fn`、泛型 `F: Fn`、`dyn Fn` | 取决于采用静态还是动态形式    |

**同一个通知需求，可以采用三种设计：**

| 设计                       | 含义                                 | 适用场景                           |
| -------------------------- | ------------------------------------ | ---------------------------------- |
| `Notifier<T>`              | 每个实例使用的通知器类型编译期确定   | 部署或组装时就确定渠道             |
| `Box<dyn Notifier>`        | 通过统一接口调用，具体实现运行时确定 | 根据配置选择渠道，管理异构渠道列表 |
| `enum NotificationChannel` | 合法渠道明确列为邮件、短信、站内信等 | 渠道种类属于业务模型，需要分别处理 |

这里有一个重要区别：

**泛型允许别人新增类型；`enum` 要求把类型列在定义里。**所以泛型并不等于“类型集合封闭”。

运行时条件也不一定需要 `dyn`。例如，`enum` 一样可以根据用户选择决定发送邮件还是短信。

# 二、扩展需求：你希望允许什么变化？

“开放扩展”需要进一步说明：谁来扩展，扩展后能不能重新编译？

| 业务需求                   | 设计方向             | 对应机制                           |
| ---------------------- | ---------------- | ------------------------------ |
| 外部开发者可以提供新实现，应用重新编译后使用 | 公开能力契约，允许外部实现    | C++ 模板/Concepts/虚接口；Rust trait |
| 一个运行中的程序需要处理不同实现       | 在运行时保留统一调用方式     | 虚函数、`dyn Trait`、类型擦除           |
| 全部合法种类由系统集中管理          | 显式定义变体集合         | `variant`、`enum`               |
| 安装新的动态库后即可增加插件         | 设计跨动态库的调用与生命周期协议 | 稳定 ABI、版本协议、句柄或函数表等            |

**虚函数和 `dyn Trait` 解决动态分发，但不自动解决插件兼容性。**

例如，“支付接口有多个实现”和“第三方支付插件可以独立编译、安装、升级”，是两个不同难度的问题。

# 三、依赖隔离：业务规则不要绑死在外部工具上

假设订单业务需要保存订单。它真正需要的是：

> 保存订单、查询订单，以及明确的失败语义。

它通常不需要知道 SQL 如何拼接、数据库连接如何建立。

| 业务需求                         | 设计思想                                   | C++ / Rust 中的实现方式                |
| -------------------------------- | ------------------------------------------ | -------------------------------------- |
| 更换数据库时，尽量不改订单规则   | 让业务依赖“存储能力”，具体数据库实现该能力 | 接口基类 / trait                       |
| 测试订单流程时，不启动真实数据库 | 注入测试实现                               | 构造参数、函数参数、泛型参数或动态接口 |
| 不同部署使用不同存储后端         | 把选择实现的工作放在组装位置               | 工厂函数、初始化代码、依赖注入         |
| 外部 SDK 经常变化                | 用适配器把外部接口转换为内部契约           | 普通类、`struct`、接口实现             |

这里需要分清两步：

- **接口设计**决定业务需要什么能力。
- **泛型或动态分发**决定具体实现怎样传给业务。

因此，**依赖倒置并不要求一定使用虚函数或 `dyn` **。使用泛型也能隔离业务与数据库实现。

此外，只有一个简单、稳定的实现时，也可以先直接调用，不必提前为每个类建立接口。

# 四、状态与不变量：让合法操作更容易，让非法状态更难出现

订单可能有金额、商品、支付状态等数据。业务要求：

- 金额不能为负；
- 已取消的订单不能支付；
- 已付款订单不能随意修改商品。

| 业务需求          | 需要的能力         | C++                             | Rust                  |
| ------------- | ------------- | ------------------------------- | --------------------- |
| 不允许外部随意修改关键字段 | 封装状态，通过方法执行操作 | `private` 成员、成员函数               | 私有字段、关联函数与方法          |
| 创建对象时就检查有效性   | 受控构造          | 构造函数、工厂函数                       | 返回 `Result` 的构造函数     |
| 区分订单的不同状态     | 显式状态模型        | `enum class`、`variant`          | `enum`                |
| 某些数据只在特定状态下存在 | 把状态与相应数据一起表达  | `variant<Paid, Cancelled, ...>` | 带数据的 `enum`           |
| 编译期限制某些操作顺序   | 用类型表示阶段       | 不同状态类型、模板                       | 不同状态类型、泛型，即 typestate |

例如，不要随意组合这些字段：

```
is_paid
is_cancelled
paid_at
```

否则容易出现“未付款，却有付款时间”等矛盾组合。可以改成：

```
enum OrderState {
    Pending,
    Paid { payment_id: String },
    Cancelled { reason: String },
}
```

这让部分非法组合无法直接表达。但“这个支付编号是否真实有效”，仍然需要业务校验。

**类和 `struct` 是承载状态的工具；聚合则是在决定哪些业务规则必须一起维护。**两者不能直接画等号。
