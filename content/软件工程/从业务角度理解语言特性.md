适合初学者的顺序：先看业务遇到了什么问题，再看需要什么能力，最后选择语言特性。

先记住：语言特性提供工具，业务设计决定怎么使用工具。例如：所有权能约束内存访问，但“库存不能超卖”仍然需要设计完整操作。

下面以“订单系统”为贯穿例子，同时对照 C++与 Rust。

# 一、多态：同一种工作，存在不同实现

假设订单需要发送通知，有邮件、短信、站内信三种渠道。

真正要问的不是“这是业务层还是引擎层”，而是：

1. 调用时，编译器能不能知道具体实现？
2. 程序运行时，需不需要统一存放和选择不同实现？
3. 我们是否希望把全部合法类别列出来？

| 业务需求                        | 需要的能力 | C++                              | Rust                             | 主要代价             |
| --------------------------- | ----- | -------------------------------- | -------------------------------- | ---------------- |
| 一套算法适配多种类型，每次调用的具体类型编译期已知   | 静态多态  | 模板、Concepts                      | 泛型、trait bound                   | 可能增加编译时间和代码体积    |
| 根据配置、用户或运行状态选择实现；同一集合存放不同实现 | 动态多态  | 虚函数、接口基类                         | `dyn Trait`                      | 间接调用，以及部分优化机会减少  |
| 明确只有几种合法情况，新增一种时希望检查处理位置    | 封闭变体  | `std::variant`、`std::visit`      | `enum`、`match`                   | 新增变体通常需要修改相关处理逻辑 |
| 只需要传入一段行为，而不需要完整对象接口        | 可调用对象 | lambda、函数对象、模板回调、`std::function` | 闭包、`impl Fn`、泛型 `F: Fn`、`dyn Fn` | 取决于采用静态还是动态形式    |

**同一个通知需求，可以采用三种设计：**

| 设计                       | 含义                                 | 适用场景                           |
| -------------------------- | ------------------------------------ | ---------------------------------- |
| `Notifier<T>`              | 每个实例使用的通知器类型编译期确定   | 部署或组装时就确定渠道             |
| `Box<dyn Notifier>`        | 通过统一接口调用，具体实现运行时确定 | 根据配置选择渠道，管理异构渠道列表 |
| `enum NotificationChannel` | 合法渠道明确列为邮件、短信、站内信等 | 渠道种类属于业务模型，需要分别处理 |

这里有一个重要区别：

**泛型允许别人新增类型；`enum` 要求把类型列在定义里。**所以泛型并不等于“类型集合封闭”。

运行时条件也不一定需要 `dyn`。例如，`enum` 一样可以根据用户选择决定发送邮件还是短信。

# 二、扩展需求：你希望允许什么变化？

“开放扩展”需要进一步说明：谁来扩展，扩展后能不能重新编译？

| 业务需求                   | 设计方向             | 对应机制                           |
| ---------------------- | ---------------- | ------------------------------ |
| 外部开发者可以提供新实现，应用重新编译后使用 | 公开能力契约，允许外部实现    | C++ 模板/Concepts/虚接口；Rust trait |
| 一个运行中的程序需要处理不同实现       | 在运行时保留统一调用方式     | 虚函数、`dyn Trait`、类型擦除           |
| 全部合法种类由系统集中管理          | 显式定义变体集合         | `variant`、`enum`               |
| 安装新的动态库后即可增加插件         | 设计跨动态库的调用与生命周期协议 | 稳定 ABI、版本协议、句柄或函数表等            |

**虚函数和 `dyn Trait` 解决动态分发，但不自动解决插件兼容性。**

例如，“支付接口有多个实现”和“第三方支付插件可以独立编译、安装、升级”，是两个不同难度的问题。

# 三、依赖隔离：业务规则不要绑死在外部工具上

假设订单业务需要保存订单。它真正需要的是：

> 保存订单、查询订单，以及明确的失败语义。

它通常不需要知道 SQL 如何拼接、数据库连接如何建立。

| 业务需求                         | 设计思想                                   | C++ / Rust 中的实现方式                |
| -------------------------------- | ------------------------------------------ | -------------------------------------- |
| 更换数据库时，尽量不改订单规则   | 让业务依赖“存储能力”，具体数据库实现该能力 | 接口基类 / trait                       |
| 测试订单流程时，不启动真实数据库 | 注入测试实现                               | 构造参数、函数参数、泛型参数或动态接口 |
| 不同部署使用不同存储后端         | 把选择实现的工作放在组装位置               | 工厂函数、初始化代码、依赖注入         |
| 外部 SDK 经常变化                | 用适配器把外部接口转换为内部契约           | 普通类、`struct`、接口实现             |

这里需要分清两步：

- **接口设计**决定业务需要什么能力。
- **泛型或动态分发**决定具体实现怎样传给业务。

因此，**依赖倒置并不要求一定使用虚函数或 `dyn` **。使用泛型也能隔离业务与数据库实现。

此外，只有一个简单、稳定的实现时，也可以先直接调用，不必提前为每个类建立接口。

# 四、状态与不变量：让合法操作更容易，让非法状态更难出现

订单可能有金额、商品、支付状态等数据。业务要求：

- 金额不能为负；
- 已取消的订单不能支付；
- 已付款订单不能随意修改商品。

| 业务需求          | 需要的能力         | C++                             | Rust                  |
| ------------- | ------------- | ------------------------------- | --------------------- |
| 不允许外部随意修改关键字段 | 封装状态，通过方法执行操作 | `private` 成员、成员函数               | 私有字段、关联函数与方法          |
| 创建对象时就检查有效性   | 受控构造          | 构造函数、工厂函数                       | 返回 `Result` 的构造函数     |
| 区分订单的不同状态     | 显式状态模型        | `enum class`、`variant`          | `enum`                |
| 某些数据只在特定状态下存在 | 把状态与相应数据一起表达  | `variant<Paid, Cancelled, ...>` | 带数据的 `enum`           |
| 编译期限制某些操作顺序   | 用类型表示阶段       | 不同状态类型、模板                       | 不同状态类型、泛型，即 typestate |

例如，不要随意组合这些字段：

```
is_paid
is_cancelled
paid_at
```

否则容易出现“未付款，却有付款时间”等矛盾组合。可以改成：

```
enum OrderState {
    Pending,
    Paid { payment_id: String },
    Cancelled { reason: String },
}
```

这让部分非法组合无法直接表达。但“这个支付编号是否真实有效”，仍然需要业务校验。

**类和 `struct` 是承载状态的工具；聚合则是在决定哪些业务规则必须一起维护。**两者不能直接画等号。

# 五、所有权与生命周期：谁负责让对象活着？

这部分首先处理资源管理问题，例如订单对象、缓存、连接、文件等。

| 业务需求              | 所有权含义      | C++                   | Rust                 |
| ----------------- | ---------- | --------------------- | -------------------- |
| 某个对象由一个地方负责管理     | 独占所有权      | 值成员、`unique_ptr`      | 值字段、`Box`            |
| 临时读取对象，不接管生命周期    | 只读借用       | `const T&`            | `&T`                 |
| 临时修改对象            | 可写访问       | `T&`，约束主要靠设计          | `&mut T`，由借用规则约束     |
| 同一线程里多个对象共同持有数据   | 共享所有权      | `shared_ptr`          | `Rc`                 |
| 多线程共同持有数据         | 可跨线程的共享所有权 | `shared_ptr`，对象访问另需同步 | `Arc`，对象访问仍需满足线程安全约束 |
| 建立反向关系，同时避免引用计数循环 | 弱引用        | `weak_ptr`            | `Weak`               |

注意两个区别：

**第一，共享所有权不等于允许随意并发修改。** `shared_ptr`、`Arc` 解决的是“对象什么时候销毁”，对象内部的数据访问仍需要额外约束。

**第二，业务关联不一定要使用内存引用。**例如订单关联用户，在很多系统里存储 `UserId` 比长期持有一个用户对象更合适。

# 六、并发与一致性：安全访问之后，还要保证操作正确

假设库存只剩一件，两个人同时下单。

这里存在不同层次的问题：

| 业务问题                                   | 需要什么保证     | 常见机制                                                     |
| ------------------------------------------ | ---------------- | ------------------------------------------------------------ |
| 多线程不能无同步地冲突访问同一内存         | 防止数据竞争     | Rust 所有权、`Send` / `Sync`，配合同步类型；C++ 正确使用同步机制 |
| “检查库存”和“扣库存”不能被其他操作穿插破坏 | 保护完整操作     | 锁、原子条件更新等                                           |
| 多条数据库修改要一起成功或失败             | 持久化事务一致性 | 数据库事务、约束、隔离级别                                   |
| 重试支付请求不能重复扣款                   | 幂等性           | 幂等键、唯一约束、状态检查                                   |
| 多个服务之间最终保持业务一致               | 跨服务协调       | 事件、重试、补偿、Outbox 等设计                              |

所以：

> **没有数据竞争，只说明内存访问符合规则；不代表库存一定不会超卖。**

Rust 可以帮助你检查第一层，但后面几层仍需要业务和存储设计。C++ 与 Rust 都会使用锁、原子操作和事务。

# 七、错误处理：失败是什么、由谁处理？

订单系统中，“余额不足”“支付超时”“程序内部状态损坏”需要不同的处理策略。

| 业务需求              | 设计方向        | C++                 | Rust                   |
| ----------------- | ----------- | ------------------- | ---------------------- |
| 调用可能失败，需要把失败交给调用者 | 用可传播的失败结果表达 | `std::expected`、异常等 | `Result<T, E>`         |
| 只表示有没有值，不需要解释失败原因 | 可选值         | `std::optional`     | `Option<T>`            |
| 当前层无法处理，交给上层      | 错误传播        | 返回错误、异常传播           | `?`                    |
| 将底层失败转换为业务语义      | 边界错误映射      | 自定义错误类型、异常转换        | 自定义错误枚举、显式转换、`From` 等  |
| 保留排障信息            | 原因链与上下文     | 嵌套异常或错误对象           | `Error::source`、上下文包装等 |
| 内部出现不应存在的状态       | 按故障策略处理     | 断言、异常、终止等           | 断言、panic 或返回错误等        |

例如：

```
数据库连接失败
    ↓ 存储层转换
订单暂时无法保存
    ↓ 接口层决定
返回“服务暂时不可用”，记录原因，按策略重试
```

需要记住：

- `?` 是**传播**，不是恢复。
- C++ 异常不要求每一层显式处理。
- `noexcept` 表示异常不能逃出函数，不表示函数不能业务失败。
- 是否重试，要看操作是否幂等、失败是否暂时性等，不能只看错误使用哪种语法。

# 八、边界隐藏：你到底想隐藏什么？

“隐藏实现”至少包含三种不同需求。

| 业务或工程需求                     | 要建立的边界   | 对应技术                                                     |
| ---------------------------------- | -------------- | ------------------------------------------------------------ |
| 外部代码不能随意访问内部细节       | 可见性边界     | C++ `private`；Rust 模块、`pub(crate)` 等                    |
| 修改实现后，尽量少重新编译其他代码 | 编译依赖边界   | C++ 前置声明、Pimpl；Rust 合理划分 crate、控制泛型实现暴露等 |
| 升级动态库后，旧程序仍能调用       | 二进制兼容边界 | 稳定 ABI、布局与调用约定、版本协议                           |

**Rust 模块可见性不能替代 C++ Pimpl 的全部作用；Pimpl 本身也不能自动保证一切 ABI 兼容。**

初学时，可以先学会可见性和模块组织，再逐步接触编译边界与 ABI。

# 九、性能：根据实际成本选择，而不是根据“层名”选择

| 实际需求或瓶颈                       | 可能有帮助的技术                 | 需要留意                                 |
| ------------------------------------ | -------------------------------- | ---------------------------------------- |
| 很小的函数被极高频调用，分发成本明显 | 泛型、模板、静态分发             | 编译时间与代码膨胀                       |
| 大量不同类型导致重复生成很多代码     | 动态分发、提取非泛型公共逻辑     | 间接调用与内联限制                       |
| 封闭的几种类型需要统一处理           | `enum`、`variant`                | 对象大小受最大变体影响，分支成本需要测量 |
| 数据访问占主要时间                   | 连续存储、布局优化、减少指针追踪 | 改变分发方式可能帮助有限                 |
| 主要时间花在网络和数据库             | 批处理、缓存、减少往返、并发控制 | 应先定位主要等待来源                     |

因此，“泛型下沉、dyn 上浮”可以是一种项目经验，但不是普遍规则。

**业务代码也可以用泛型，引擎代码也可以用动态分发。关键是这个具体边界需要什么。**

# 十、最终速查表

以后遇到需求，可以直接从左向右查：

| 我遇到的需求                             | 优先理解的技术                         |
| ---------------------------------------- | -------------------------------------- |
| 一套算法用于多种类型，调用类型编译期确定 | 模板 / 泛型                            |
| 运行时通过统一接口处理不同实现           | 虚函数 / `dyn Trait`                   |
| 明确列出全部合法状态或事件               | `variant` / `enum`                     |
| 允许调用者提供一段行为                   | lambda / 闭包 / 回调                   |
| 换数据库、SDK 时尽量不动业务规则         | 接口、适配器、依赖倒置                 |
| 不允许外部绕过规则修改数据               | 封装、受控构造、业务方法               |
| 明确谁拥有资源、谁临时使用               | 所有权、智能指针、借用                 |
| 多线程共享数据                           | `Send` / `Sync`、锁、原子操作            |
| 多步操作必须共同保持正确                 | 临界区、事务、一致性协议               |
| 失败需要被识别、传播或恢复               | 错误类型、`Result` / `expected` / 异常 |
| 内部实现变化不应广泛影响调用者           | 可见性、模块、编译依赖隔离             |
| 独立编译的组件需要长期兼容               | ABI、版本与生命周期协议                |
| 热点太慢或程序体积太大                   | 性能测量，再选择分发、布局和实例化策略 |

学习时，建议按这个顺序推进：**值与函数 → 封装与状态 → 所有权与借用 → 泛型与 trait/接口 → 动态分发与变体 → 错误边界 → 并发与事务 → 编译边界与 ABI。**每学一项，都用一个具体问题检验自己：“它帮我约束了什么，又有哪些正确性仍需要我自己设计？”
