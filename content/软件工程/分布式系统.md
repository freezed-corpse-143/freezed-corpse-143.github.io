分布式系统 = 多台计算机通过网络协作，对外表现为一个整体。由于网络不可靠、机器会故障、时钟不同步，所以需要一整套机制来保证系统正确、稳定、可恢复。

# Idempotency（幂等性）

**定义**：同一操作执行一次或多次，对系统状态的影响相同。

**为什么重要**：分布式系统中请求可能重复（超时重试、消息重投），如果操作不幂等，就会产生重复扣款、重复下单等问题。

**实现方式**：
- 唯一请求 ID（去重表）
- 数据库唯一约束
- 状态机（只允许从 A → B，重复执行无效）

**例子**：`DELETE /user/123` 是幂等的；`POST /orders`（无去重）不是。

# Retry（重试）

**定义**：操作失败后重新发起，以应对**瞬时故障**（网络抖动、临时过载）。

**关键点**：
- 必须配合**幂等性**，否则会重复副作用
- 需要**退避策略**（Exponential Backoff + Jitter），避免重试风暴
- 需要**重试上限**，否则会放大故障

**反模式**：无限制立即重试 → 雪崩。

# Timeout（超时）

**定义**：等待某个操作的最长时间，超过则放弃或报错。

**为什么重要**：没有超时，线程/连接会被永久占用，导致资源耗尽。

**难点**：
- 超时不等于失败——对方可能已成功，只是响应没回来（所以需要幂等）
- 超时时间要合理：太短误判，太长失去保护

# Circuit Breaker（断路器）

**定义**：当对某个依赖的失败率超过阈值时，**快速失败**，不再发起调用，给下游恢复时间。

**三种状态**：
- **Closed**：正常放行
- **Open**：直接拒绝，快速失败
- **Half-Open**：放少量请求试探，成功则关闭，失败则继续打开

**作用**：防止故障级联（Cascading Failure），是**熔断**的核心。

# Backpressure（背压）

**定义**：当消费者处理不过来时，向上游施加压力，让其**减速或暂停**，而不是无限缓冲。

**对比**：
- 无背压：队列无限增长 → 内存爆掉 → 崩溃
- 有背压：生产者被限速，系统保持稳定

**实现**：Reactive Streams、TCP 流控、消息队列的消费者拉取模式（pull-based）。


# Consistency（一致性）

**定义**：多个副本/节点之间数据的同步程度。

**常见模型**（从强到弱）：
- **强一致（Linearizability）**：读到的永远是最新写入
- **顺序一致**：所有节点看到相同顺序
- **因果一致**：有因果关系的操作保序
- **最终一致**：停止写入后，副本最终收敛

**理论基石**：CAP 定理（一致性、可用性、分区容忍三者不可兼得）。

# Transaction（事务）

**定义**：一组操作要么全部成功，要么全部失败（ACID）。

**分布式事务的难点**：跨多个节点/服务，无法用单机锁和本地事务。

**常见方案**：
- **2 PC/3 PC**：强一致但阻塞、性能差
- **TCC**（Try-Confirm-Cancel）：业务层面的补偿
- **Saga**：长事务拆成多个本地事务 + 补偿

# Saga（saga 模式）

**定义**：把一个长事务拆成多个**本地事务**，每个步骤都有对应的**补偿操作**。任一步失败，就反向执行已成功步骤的补偿。

**两种编排方式**：
- **Choreography（编排）**：各服务通过事件互相触发
- **Orchestration（编制）**：有一个中心协调器

**特点**：最终一致，无全局锁，适合微服务长流程（如订单→支付→库存→物流）。

**缺点**：补偿逻辑复杂，无法保证隔离性。

# Outbox（发件箱模式）

**定义**：解决**数据库写入**与**消息发送**的原子性问题。

**问题**：写库成功但发消息失败，或反之，导致数据不一致。

**方案**：
1. 在同一个本地事务中，把业务数据和"待发消息"写入 **Outbox 表**
2. 另一个进程/CDC 读取 Outbox 表并发送消息
3. 发送成功后标记已发送

**保证**：至少一次投递 + 消费端幂等 = 效果上的一致性。

# Consensus（共识）

**定义**：多个节点对某个值/状态达成一致，即使有节点故障。

**经典算法**：
- **Paxos**：理论奠基，难实现
- **Raft**：易理解，广泛用于 etcd、TiKV
- **ZAB**：ZooKeeper 使用
- **PBFT**：拜占庭容错（可容忍恶意节点）

**用途**：选主、日志复制、分布式锁、配置管理。

**理论边界**：FLP 不可能定理——在异步网络中，即使只有一个故障节点，也无法保证既终止又一致。

# Failure Model（故障模型）

**定义**：描述系统可能发生哪些故障，是设计容错机制的前提。

**常见分类**：
- **Crash-stop**：节点崩溃后永久停止
- **Crash-recovery**：崩溃后可重启（需持久化状态）
- **Omission**：消息丢失
- **Timing**：消息延迟无上界（异步）
- **Byzantine（拜占庭）**：节点可能发送错误/恶意信息

**意义**：不同故障模型对应不同的算法和保证。比如 Raft 假设非拜占庭故障；PBFT 处理拜占庭故障。


# 关系

```
Failure Model  ← 决定系统要应对什么
      │
      ├── Timeout ──→ Retry ──→ Idempotency
      │                │
      │                └──→ Circuit Breaker ──→ Backpressure
      │
      ├── Consistency ──→ Consensus
      │        │
      │        └──→ Transaction ──→ Saga
      │                        │
      │                        └──→ Outbox
```

- **Failure Model** 是基础假设，决定其他机制的设计。
- **Timeout + Retry + Idempotency** 是处理瞬时故障的铁三角。
- **Circuit Breaker + Backpressure** 防止故障扩散。
- **Consistency + Consensus** 解决多副本一致。
- **Transaction / Saga / Outbox** 解决跨服务数据一致性。
