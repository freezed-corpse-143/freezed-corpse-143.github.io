# Entity（实体）

**定义**：具有唯一标识符（Identity）的领域对象，其身份贯穿整个生命周期，即使属性发生变化，仍然是同一个对象。

**关键特征**：
- 有唯一 ID（如用户 ID、订单号）
- 可变性：属性可以改变
- 相等性基于 ID，而非属性值

**例子**：
```java
class User {
    private UserId id;      // 唯一标识
    private String name;    // 可变属性
    private String email;
}
```
两个 `User` 只要 `id` 相同，就是同一个用户，哪怕名字改了。

# Value Object（值对象）

**定义**：没有唯一标识符，通过属性值来定义的对象。它是**不可变**的。

**关键特征**：
- 无 ID
- 不可变（Immutable）
- 相等性基于所有属性值
- 通常用于描述、度量或量化

**例子**：
```java
class Money {
    private final BigDecimal amount;
    private final Currency currency;
}
```
`Money(100, USD)` 和另一个 `Money(100, USD)` 是相等的，可以互相替换。`Address`、`DateRange`、`Color` 也是典型值对象。

# Aggregate（聚合）

**定义**：一组相关对象的集群，作为数据修改的单元。每个聚合有一个**聚合根（Aggregate Root）**，是外部访问的唯一入口。

**关键特征**：
- 聚合根是 Entity
- 聚合内保证一致性（事务边界）
- 外部只能通过聚合根访问内部对象
- 一次事务只修改一个聚合

**例子**：
```
Order (聚合根)
 ├── OrderItem (实体/值对象)
 └── ShippingAddress (值对象)
```
要修改 `OrderItem`，必须通过 `Order` 来进行。`Order` 是整个聚合的一致性边界。

# Domain Service（领域服务）

**定义**：当某个操作/业务逻辑不属于任何单个 Entity 或 Value Object 时，将其放在领域服务中。

**关键特征**：
- 无状态
- 表达领域概念（用通用语言命名）
- 协调多个领域对象
- 不包含基础设施逻辑

**例子**：
```java
class TransferService {
    void transfer(Account from, Account to, Money amount) {
        from.debit(amount);
        to.credit(amount);
    }
}
```
转账涉及两个账户，不属于任何单个 Account，因此放在领域服务中。

# Repository（仓储）

**定义**：提供对聚合的持久化和查询访问，像集合一样操作领域对象，屏蔽底层存储细节。

**关键特征**：
- 以聚合为单位（通常一个聚合根一个 Repository）
- 接口在领域层，实现在基础设施层
- 只处理聚合根
- 提供类似集合的 API：`add`、`remove`、`findById`

**例子**：
```java
interface OrderRepository {
    Order findById(OrderId id);
    void save(Order order);
    void remove(Order order);
}
```

# Domain Event（领域事件）

**定义**：领域中发生的、对业务有意义的事情。表示"已发生"的事实。

**关键特征**：
- 用过去时命名（如 `OrderPlaced`、`PaymentReceived`）
- 不可变
- 用于解耦不同聚合/限界上下文
- 支持最终一致性

**例子**：
```java
class OrderPlaced {
    private final OrderId orderId;
    private final Instant occurredAt;
}
```
订单创建后发布此事件，库存、通知等系统可订阅处理。

# Bouned Context（限界上下文）

**定义**：一个显式的边界，在这个边界内，某个特定的领域模型被定义并适用。同一个词在不同上下文中可能有不同含义。

**关键特征**：
- 是 DDD 战略设计的核心
- 每个上下文有自己的通用语言（Ubiquitous Language）
- 一个上下文内模型保持一致
- 不同上下文可以有不同模型

**例子**：
- "客户"在**销售上下文**中是"买家"，有购买历史
- "客户"在**客服上下文**中是"工单提交人"，有联系方式
- 同一个词，不同的模型，分属不同限界上下文

# Context Mapping（上下文映射）

**定义**：描述多个限界上下文之间如何集成与协作的模式。

**常见模式**：

| 模式                             | 说明                           |
| ------------------------------ | ---------------------------- |
| **Shared Kernel**              | 两个上下文共享一小部分模型                |
| **Customer/Supplier**          | 下游依赖上游，上游按下游需求调整             |
| **Conformist**                 | 下游直接遵从上游模型，不做适配              |
| **Anticorruption Layer (ACL)** | 下游建防腐层，隔离上游模型污染              |
| **Open Host Service**          | 上游提供公开协议/API 供多方使用           |
| **Published Language**         | 用共享的、文档化的语言交互（如 JSON Schema） |
| **Partnership**                | 两个上下文紧密协作，共同演进               |
| **Separate Ways**              | 无集成，各自独立                     |

**例子**：
```
[订单上下文] ---ACL---> [支付上下文]
[库存上下文] ---OHS---> [多个下游]
```

# 关系图

```
Bounded Context（边界）
 ├── Aggregate（一致性边界）
 │    ├── Entity（聚合根/内部实体）
 │    └── Value Object（不可变描述）
 ├── Domain Service（跨对象逻辑）
 ├── Repository（持久化聚合）
 └── Domain Event（发布业务事实）

Context Mapping（上下文之间的关系）
```

**战略设计**：Bounded Context、Context Mapping  
**战术设计**：Entity、Value Object、Aggregate、Domain Service、Repository、Domain Event
