真正要系统掌握现代代码架构，关键不是背几十个 Pattern，而是建立一张从 **语言机制 → 代码组织 → 模块设计 → 架构 → 运行时部署** 的统一地图。

建议把它当成一套“内功体系”来学：

> **类型表达约束 → 抽象变化 → 管理依赖 → 划分边界 → 组织模块 → 控制副作用 → 设计运行时 → 演化大型系统**

最终达到一个目标：

> 给你一个陌生需求，你能自然推导出：
> **类型怎么定义 → interface/trait 怎么划 → 模块怎么拆 → dependency 怎么走 → 文件放哪里 → package/crate/project 怎么组织 → 进程怎么划 → 服务怎么部署。**

# 总地图

建议以后看到任何所谓“最佳实践”，先问：

**它到底解决哪一层的问题？**

| 层                | 核心问题               | 典型知识                                          |
| ----------------- | ---------------------- | ------------------------------------------------- |
| L 1 类型与数据建模 | 什么状态是合法的？     | Type System、ADT、Generics、Phantom Type、Newtype |
| L 2 抽象           | 哪些东西应该统一？     | Interface、Trait、Protocol、Polymorphism          |
| L 3 依赖           | 谁依赖谁？             | DI、DIP、IoC、Dependency Graph                    |
| L 4 行为组织       | 一个功能内部怎么组织？ | Strategy、State、Command、Pipeline、Middleware    |
| L 5 模块           | 代码边界在哪里？       | Module、Package、Component、Encapsulation         |
| L 6 架构           | 整个程序如何划分？     | Layered、Hexagonal、Clean、Vertical Slice         |
| L 7 并发与运行时   | 程序怎么执行？         | Async、Actor、CSP、Event Loop、Thread Pool        |
| L 8 物理/部署架构  | 程序最终怎么存在？     | Monolith、Modular Monolith、Microservices、Plugin |

其中：

**L 1–L 4 是代码“心法”。**

**L 5–L 6 是软件架构。**

**L 7–L 8 是系统架构。**

# 类型系统 - 让非法状态无法表达

很多程序设计问题，本质上不是：

> 怎么写代码？

而是：

> **怎么定义数据，使错误代码根本写不出来？**

这就是现代 Type-driven Design。

例如最初可能写：

```text
User
    id: string
    status: string
```

然后代码里到处：

```text
if status == "active"
if status == "pending"
if status == "banned"
```

更好的模型是：

```text
UserStatus =
    Pending
    | Active
    | Banned
```

进一步：

```text
User =
    PendingUser
    | ActiveUser
    | BannedUser
```

于是：

```text
activate(PendingUser) -> ActiveUser
```

而不是：

```text
activate(User) -> bool
```

这就是一个非常重要的思想：

> **状态机可以编码进类型系统。**

这一阶段重点学：

```text
Type System
├── Primitive / Composite Types
├── Product Type
├── Sum Type
├── Algebraic Data Types
├── Enum / Tagged Union
├── Pattern Matching
├── Generic
├── Generic Constraint
├── Trait / Typeclass
├── Associated Type
├── Newtype
├── Phantom Type
├── Option / Maybe
├── Result / Either
├── Null Safety
├── Variance
├── Subtyping
└── Type State
```

尤其要理解一个公式：

```text
struct / record ≈ AND

enum / union ≈ OR
```

例如：

```text
User = {
    name: Name,
    age: Age
}
```

就是：

```text
Name AND Age
```

而：

```text
Payment =
    Card(CardInfo)
    | Paypal(PaypalInfo)
```

就是：

```text
Card OR Paypal
```

这之后你会开始发现：

**数据结构本身就是业务逻辑。**

# 泛型与抽象 - 找出“变化”和“不变”

泛型不能简单理解为：

> `List<T>`。

真正重要的是：

> **把算法中的不变量，与数据类型中的变量分开。**

例如：

```text
sort(User[])
sort(Product[])
sort<Order[])
```

逐渐抽象成：

```text
sort<T>(items, comparator)
```

这里：

```text
不变：
    sorting algorithm

变化：
    T
    comparison rule
```

这是几乎所有架构模式共同的核心：

> **Separate what changes from what stays the same.**

你之后学 Strategy：

```text
PaymentService
       │
       ▼
PaymentStrategy
   ├── Stripe
   ├── Paypal
   └── Crypto
```

其实还是同一思想：

```text
不变：
Payment workflow

变化：
Payment implementation
```

所以应该把这些一起学：

```text
Generics
Polymorphism
Interface
Trait
Protocol
Typeclass
Strategy Pattern
Template Method
Higher-order Function
Closure
Composition
```

你会发现 OO、FP、Rust Trait、Go Interface、Haskell Typeclass 其实在解决大量相同问题，只是表达机制不同。
