真正要系统掌握现代代码架构，关键不是背几十个 Pattern，而是建立一张从 **语言机制 → 代码组织 → 模块设计 → 架构 → 运行时部署** 的统一地图。

建议把它当成一套“内功体系”来学：

> **类型表达约束 → 抽象变化 → 管理依赖 → 划分边界 → 组织模块 → 控制副作用 → 设计运行时 → 演化大型系统**

最终达到一个目标：

> 给你一个陌生需求，你能自然推导出：
> **类型怎么定义 → interface/trait 怎么划 → 模块怎么拆 → dependency 怎么走 → 文件放哪里 → package/crate/project 怎么组织 → 进程怎么划 → 服务怎么部署。**

# 总地图

建议以后看到任何所谓“最佳实践”，先问：

**它到底解决哪一层的问题？**

| 层                | 核心问题               | 典型知识                                          |
| ----------------- | ---------------------- | ------------------------------------------------- |
| L 1 类型与数据建模 | 什么状态是合法的？     | Type System、ADT、Generics、Phantom Type、Newtype |
| L 2 抽象           | 哪些东西应该统一？     | Interface、Trait、Protocol、Polymorphism          |
| L 3 依赖           | 谁依赖谁？             | DI、DIP、IoC、Dependency Graph                    |
| L 4 行为组织       | 一个功能内部怎么组织？ | Strategy、State、Command、Pipeline、Middleware    |
| L 5 模块           | 代码边界在哪里？       | Module、Package、Component、Encapsulation         |
| L 6 架构           | 整个程序如何划分？     | Layered、Hexagonal、Clean、Vertical Slice         |
| L 7 并发与运行时   | 程序怎么执行？         | Async、Actor、CSP、Event Loop、Thread Pool        |
| L 8 物理/部署架构  | 程序最终怎么存在？     | Monolith、Modular Monolith、Microservices、Plugin |

其中：

**L 1–L 4 是代码“心法”。**

**L 5–L 6 是软件架构。**

**L 7–L 8 是系统架构。**

# 类型系统 - 让非法状态无法表达

很多程序设计问题，本质上不是：

> 怎么写代码？

而是：

> **怎么定义数据，使错误代码根本写不出来？**

这就是现代 Type-driven Design。

例如最初可能写：

```text
User
    id: string
    status: string
```

然后代码里到处：

```text
if status == "active"
if status == "pending"
if status == "banned"
```

更好的模型是：

```text
UserStatus =
    Pending
    | Active
    | Banned
```

进一步：

```text
User =
    PendingUser
    | ActiveUser
    | BannedUser
```

于是：

```text
activate(PendingUser) -> ActiveUser
```

而不是：

```text
activate(User) -> bool
```

这就是一个非常重要的思想：

> **状态机可以编码进类型系统。**

这一阶段重点学：

```text
Type System
├── Primitive / Composite Types
├── Product Type
├── Sum Type
├── Algebraic Data Types
├── Enum / Tagged Union
├── Pattern Matching
├── Generic
├── Generic Constraint
├── Trait / Typeclass
├── Associated Type
├── Newtype
├── Phantom Type
├── Option / Maybe
├── Result / Either
├── Null Safety
├── Variance
├── Subtyping
└── Type State
```

尤其要理解一个公式：

```text
struct / record ≈ AND

enum / union ≈ OR
```

例如：

```text
User = {
    name: Name,
    age: Age
}
```

就是：

```text
Name AND Age
```

而：

```text
Payment =
    Card(CardInfo)
    | Paypal(PaypalInfo)
```

就是：

```text
Card OR Paypal
```

这之后你会开始发现：

**数据结构本身就是业务逻辑。**

# 泛型与抽象 - 找出“变化”和“不变”

泛型不能简单理解为：

> `List<T>`。

真正重要的是：

> **把算法中的不变量，与数据类型中的变量分开。**

例如：

```text
sort(User[])
sort(Product[])
sort<Order[])
```

逐渐抽象成：

```text
sort<T>(items, comparator)
```

这里：

```text
不变：
    sorting algorithm

变化：
    T
    comparison rule
```

这是几乎所有架构模式共同的核心：

> **Separate what changes from what stays the same.**

你之后学 Strategy：

```text
PaymentService
       │
       ▼
PaymentStrategy
   ├── Stripe
   ├── Paypal
   └── Crypto
```

其实还是同一思想：

```text
不变：
Payment workflow

变化：
Payment implementation
```

所以应该把这些一起学：

```text
Generics
Polymorphism
Interface
Trait
Protocol
Typeclass
Strategy Pattern
Template Method
Higher-order Function
Closure
Composition
```

你会发现 OO、FP、Rust Trait、Go Interface、Haskell Typeclass 其实在解决大量相同问题，只是表达机制不同。

# Composition - 现代架构的基本功

传统 OO 教程特别喜欢：

```text
Inheritance
```

现代工程更应该熟悉：

> **Composition over inheritance**

例如不要：

```text
Animal
 └── Bird
      └── FlyingBird
```

而考虑能力组合：

```text
Bird
 ├── FlyBehavior
 ├── EatBehavior
 └── MoveBehavior
```

然后：

```text
Bird = Data + FlyBehavior + MoveBehavior
```

进一步你会遇到：

```text
Decorator
Adapter
Middleware
Pipeline
Plugin
Capability
Mixin
Extension
```

它们背后大量都是：

> **Composition。**

所以看到：

```text
A(B(C(D(x))))
```

不要只把它看成函数调用。

这可能就是一个完整的软件架构。

例如 HTTP：

```text
Request
  ↓
Logging
  ↓
Authentication
  ↓
Authorization
  ↓
RateLimit
  ↓
Handler
```

这就是：

```text
Pipeline + Composition
```

# 依赖管理

你提到 Dependency Injection，这非常重要，但不要从 DI Framework 开始学。

先理解：

```text
Dependency
        ↓
Dependency Graph
        ↓
Dependency Inversion
        ↓
Inversion of Control
        ↓
Dependency Injection
        ↓
DI Container
```

假设：

```text
OrderService
     ↓
PostgresOrderRepository
```

业务代码直接依赖 PostgreSQL。

改变为：

```text
             OrderRepository
                  ▲
                  │
OrderService      │
                  │
         PostgresRepository
```

逻辑关系变成：

```text
Business
   ↓
Abstraction
   ↑
Infrastructure
```

这就是 Dependency Inversion。

DI 只是解决：

> 那运行时到底是谁把 `PostgresRepository` 塞进去？

例如：

```text
repo = PostgresRepository(db)

service = OrderService(repo)

server = HttpServer(service)
```

这几行代码非常重要。

它叫：

> **Composition Root**

建议你以后特别关注这个概念。

一个成熟项目往往可以理解为：

```text
             main()
               │
       Composition Root
               │
      ┌────────┼────────┐
      ▼        ▼        ▼
    Service   Repo    Adapter
      │        │
      └────┬───┘
           ▼
       Application
```

`main()` 的一个核心职责就是：

> **构建 dependency graph。**

# 副作用边界 - 现代架构的贡献

这一层很多 OO 开发者容易缺失。

程序可以粗略分成：

```
Pure Logic
+
Side Effects
```

Side Effects 包括：

```
Database
Filesystem
Network
Clock
Random
Environment
Process
UI
```

理想状态：

```
        Side Effects

 HTTP ─────┐
 DB ───────┤
 File ─────┤
           ▼
      ┌──────────┐
      │Pure Core │
      └──────────┘
           ▲
 Clock ────┤
 Random ───┤
 Config ───┘
```

也就是：

> **Functional Core, Imperative Shell**

例如不要：

```
calculate_price():
    user = db.get_user()
    now = datetime.now()
    config = env.get(...)
    ...
```

而是：

```
calculate_price(
    user,
    current_time,
    pricing_policy
) -> Price
```

外围负责：

```
user = db.get_user()
time = clock.now()

price = calculate_price(user, time, policy)
```

这样核心业务逻辑：

```
无 DB
无网络
无环境变量
无时间
```

测试会异常简单。

这套思想与 Clean Architecture / Hexagonal Architecture 最终会汇合。

# Architecture Boundary - 进入架构

现在再学习：

```
Layered Architecture
Hexagonal Architecture
Ports & Adapters
Onion Architecture
Clean Architecture
Vertical Slice Architecture
DDD
CQRS
Event Driven Architecture
```

不要把这些当成八种互斥架构。

它们是在回答不同问题。

例如 Hexagonal Architecture 的核心其实极其简单：

```
                 ┌─────────────┐
 HTTP ─Adapter──►│             │◄──Adapter─ Database
 CLI ─Adapter───►│ Application │◄──Adapter─ Redis
 RPC ─Adapter───►│    Core     │◄──Adapter─ External API
                 │             │
                 └─────────────┘
```

Application 不应该知道：

```
HTTP
Postgres
Redis
Kafka
```

它只知道：

```
Port
```

于是：

```
HTTP       = inbound adapter
CLI        = inbound adapter

Postgres   = outbound adapter
Redis      = outbound adapter
OpenAI API = outbound adapter
```

突然你会发现：

> Adapter Pattern + Dependency Inversion + DI + Module Boundary

组合起来就是：

> **Hexagonal Architecture。**

这就是为什么我不建议先背“架构”。

架构其实是基础设计原则的大规模组合。

# 目录结构 - 逻辑设计如何映射到物理设计

这是你特别问到的地方，而且非常重要。

初学者经常写：

```
src/
├── controllers/
├── services/
├── repositories/
├── models/
├── utils/
└── interfaces/
```

这是：

> **按技术角色分目录。**

规模小没问题，但系统大以后容易变成：

```
services/
    87 files

models/
    143 files

utils/
    219 files
```

一个功能散落整个项目。

现代大型项目越来越值得掌握：

> **Package by Feature / Vertical Slice**

例如：

```
src/

users/
    domain/
    application/
    infrastructure/
    api/

orders/
    domain/
    application/
    infrastructure/
    api/

payments/
    domain/
    application/
    infrastructure/
    api/
```

进一步：

```
orders/
├── domain/
│   ├── order
│   ├── order_id
│   ├── order_status
│   └── repository
│
├── application/
│   ├── create_order
│   ├── cancel_order
│   └── query_order
│
├── adapters/
│   ├── postgres
│   └── kafka
│
└── api/
    ├── http
    └── grpc
```

这时：

```
逻辑边界
     ↓
module boundary
     ↓
package boundary
     ↓
directory boundary
```

开始对齐。

这叫：

> **Screaming Architecture**

看目录就应该大致知道：

> 这个软件是干什么的。

而不是只能知道：

> 它用了 Controller 和 Service。
