# 普通调用（Direct Call/Prcedure Call）

最传统的程序交互方式：A 直接调用 B 的方法，**同步阻塞**，调用者知道被调用者是谁，并等待返回值。

```
orderService.pay(orderId)  // 直接调用，等待结果
```

特点：简单直接，但耦合度高、难以扩展、难以异步。

# Pipeline（管道）

把处理过程拆成**一串依次执行的阶段（Stage）**，前一个阶段的输出是后一个阶段的输入。类似工厂流水线。

```
请求 → [鉴权] → [限流] → [日志] → [业务处理] → 响应
```

典型例子：ASP.NET Core Middleware Pipeline、Unix pipe、CI/CD Pipeline。

# Event（事件）

**"某件事已经发生了"** 的通知，是过去式的事实描述。

- 例：`OrderCreated`、`PaymentCompleted`、`UserRegistered`
- 特点：**一对多**、发布者不关心谁接收、通常不可变
- 是 Event-Driven Architecture 的核心

# Message（消息）

一个更宽泛的概念，泛指在系统间传递的数据单元。Event、Command、Query 本质上都是 Message 的不同语义形式。

# Command（命令）

**"请做某事"** 的指令，是祈使句，有明确的接收者和意图。

- 例：`CreateOrder`、`PayOrder`、`ShipOrder`
- 特点：**一对一**、可以失败/拒绝、通常改变状态
- 与 Event 的区别：Command 是"我要你做"，Event 是"我已经做了"

# Query（查询）

**"请告诉我某事"** 的请求，只读，不改变状态。

- 例：`GetOrderById`、`ListUnpaidOrders`
- 是 CQRS 中与 Command 相对的另一半

# Actor（演员 / Actor 模型）

并发计算模型。每个 Actor 是一个**独立的计算单元**，拥有：
- 私有状态（不可被外部直接访问）
- 邮箱（Mailbox，接收消息队列）
- 行为（收到消息后如何处理）

Actor 之间**只通过发消息通信**，不共享内存。天然支持并发和分布式。

代表：Erlang/Elixir、Akka、Orleans。

# State Machine（状态机）

系统在**有限个状态**之间，根据**事件**进行**确定的转移**。

```
Created --Pay--> Paid --Ship--> Shipped --Deliver--> Delivered
```

三要素：
- **State（状态）**：Created / Paid / Shipped / Delivered
- **Event（事件）**：Pay / Ship / Deliver
- **Transition（转移）**：状态 + 事件 → 新状态

作用：把复杂的业务规则显式化，避免"状态混乱"。

# Reactive Stream（响应式流）

处理**异步数据流**+**背压（Backpressure）**的规范。

核心接口（Java Reactive Streams）：
- `Publisher`：生产者
- `Subscriber`：消费者
- `Subscription`：订阅关系
- `Processor`：既是订阅者又是发布者

背压：当下游处理不过来时，可以告诉上游"慢点发"，避免压垮。

代表：RxJava、Reactor、Akka Streams。

# 进阶学习层

| 概念                       | 一句话解释                                                                           |
| ------------------------ | ------------------------------------------------------------------------------- |
| **Observer**             | 观察者模式：对象状态变化时自动通知依赖它的观察者                                                        |
| **Pub/Sub**              | 发布订阅：发布者和订阅者通过中间人（Broker）解耦，比 Observer 更松                                       |
| **Event Bus**            | 事件总线：系统内事件的中转站，组件通过它收发事件                                                        |
| **Command**              | 见上，封装"请求做某事"                                                                    |
| **Mediator**             | 中介者模式：用一个中介对象协调多个对象之间的交互，减少耦合                                                   |
| **Pipeline**             | 见上                                                                              |
| **Middleware**           | 中间件：在请求处理链中插入的可复用处理单元                                                           |
| **Actor Model**          | 见上                                                                              |
| **CSP**                  | Communicating Sequential Processes：通过 Channel 通信的并发模型（Go 的 goroutine + channel） |
| **State Machine**        | 见上                                                                              |
| **Reactive Programming** | 响应式编程：以数据流和变化传播为核心的编程范式                                                         |
| **Event Sourcing**       | 事件溯源：不存当前状态，而是存所有事件，状态由事件重放得出                                                   |
| **CQRS**                 | 命令查询职责分离：写模型和读模型分开                                                              |
# 关系

```
                     ┌─────────────── 消息通信层 ───────────────┐
                     │                                          │
  普通调用 ──→ Command / Query / Event  ──→ Message ──→ Pub/Sub / Event Bus
                     │                                          │
                     ↓                                          ↓
              Pipeline / Middleware                    Actor Model / CSP
                     │                                          │
                     └──────────────→ 业务建模 ←────────────────┘
                                       │
                          State Machine / Event Sourcing / CQRS
                                       │
                                 Reactive Stream
```

**学习路径建议：**

1. **先懂同步**：普通调用 → Pipeline / Middleware
2. **再懂解耦**：Observer → Pub/Sub → Event Bus
3. **再懂语义**：Command / Query / Event 的区别（CQRS 的根基）
4. **再懂并发**：Actor Model vs CSP（两种哲学）
5. **再懂建模**：State Machine → Event Sourcing → CQRS
6. **最后懂流**：Reactive Stream / 背压

你的状态机示例正是 **State Machine** 的经典用法——电商订单的生命周期管理。理解它之后，配合 Event Sourcing（把每次状态转移记录为事件）和 CQRS（订单写入用状态机、查询用读模型），就能搭建出健壮的领域系统。
