
可以把要求整理成下面这张检查表。

| 维度             | 需要回答的问题              | 典型要求                            |
| -------------- | -------------------- | ------------------------------- |
| **1. 契约与正确性**  | 代码承诺做什么？什么情况下不接受请求？  | 输入范围、输出含义、前置条件、后置条件、不变量、错误语义    |
| **2. 边界与异常输入** | 空值、极值、重复、乱序、非法数据会怎样？ | 边界检查、长度限制、编码校验、溢出处理、明确拒绝非法输入    |
| **3. 时间与空间成本** | 数据量增长后还能运行吗？         | 复杂度、内存上限、分配次数、I/O 次数、大数据下的退化行为  |
| **4. 资源生命周期**  | 资源由谁申请、谁释放？          | 文件、连接、锁、线程、定时器的可靠释放；部分初始化失败后的清理 |
| **5. 并发安全**    | 多个操作同时发生会怎样？         | 数据竞争、死锁、锁顺序、原子性、可见性、并发数量限制      |
| **6. 中断与恢复**   | 在任意执行阶段停止，会留下什么状态？   | 取消、超时、优雅退出、事务、检查点、重启恢复、崩溃一致性    |
| **7. 故障处理**    | 依赖失败、网络断开、磁盘满了怎么办？   | 错误分类、有限重试、退避、降级、故障隔离            |
| **8. 重复与一致性**  | 请求重复执行、只完成一半怎么办？     | 幂等、去重、事务边界、补偿、顺序保证、一致性模型        |
| **9. 容量与过载保护** | 请求超过处理能力时会怎样？        | 有界队列、背压、限流、负载拒绝、并发上限            |
| **10. 安全与隐私**  | 输入和调用者是否可信？          | 身份认证、权限校验、注入防护、秘密管理、日志脱敏        |
| **11. 可观测性**   | 出问题后，能知道哪里坏了吗？       | 结构化日志、指标、追踪、关联 ID、可操作的告警        |
| **12. 可测试性**   | 如何证明行为符合契约？          | 单元测试、集成测试、边界测试、故障注入、并发与性能测试     |
| **13. 可维护性**   | 修改一个功能会影响多少地方？       | 清晰命名、职责划分、显式依赖、模块边界、关键决策说明      |
| **14. 兼容与演进**  | 新旧版本同时运行会怎样？         | API 兼容、数据格式兼容、数据库迁移、配置版本、回滚策略   |
| **15. 部署与运维**  | 能否安全上线、启动、停止和回退？     | 配置校验、健康检查、就绪检查、灰度发布、部署与恢复说明     |

这里有几个很重要的细化。

**第一，“处理所有输入”不代表接受所有输入。**

真正的要求是：**对所有可能进入系统的输入，都有定义明确、成本可控的行为。**

例如一个排序接口，可以规定：

- 仅接受整数数组。
- 最多一百万个元素。
- 空数组返回空数组。
- 类型不符或超过限制，返回明确错误。
- 不允许因为恶意输入无限分配内存。

你不需要为无限大的输入提供正常结果，但必须知道它如何被拒绝。除了输入值，还要考虑**操作序列**：重复调用、先关闭再写入、初始化失败后再次初始化，都是边界。

**第二，复杂度只是性能的一部分，还要有资源预算。**

`O(n)` 并不自动意味着适合生产：如果每个元素都发起一次网络请求，或者 `n` 没有上限，仍然可能拖垮服务。

实际需要明确：

- 一次请求最多消耗多少时间、内存、连接和线程？
- 等待外部依赖是否有超时？
- 队列、缓存、重试次数是否有上限？
- 系统达到容量极限后，是排队、拒绝，还是降低服务质量？

**第三，“随时中断与恢复”要先定义中断模型。**

|中断类型|应对重点|
|---|---|
|用户取消、任务取消|在安全位置响应取消，释放资源，明确是否已产生效果|
|操作超时|区分“停止等待”和“实际操作已停止”|
|进程正常退出|停止接收新任务，处理或移交正在执行的任务|
|进程被强杀、机器掉电|依赖事务、持久化日志、原子更新或检查点恢复|
|网络断开|处理“对方可能已成功，但我没收到结果”的不确定状态|

**清理代码无法保证在强杀或掉电时执行。** 因此，崩溃恢复必须靠持久化机制与状态设计。

比如支付请求超时：不能直接推断“扣款失败”，然后换一个请求重新扣款。需要使用幂等键、查询交易状态等机制，处理结果不确定的情况。

**第四，要定义失败后允许留下什么状态。**

这是生产级代码经常缺失的一层：

- **失败后不产生改变**：例如校验不通过，数据保持原样。
- **失败后保持合法状态**：操作可能部分完成，但系统不变量仍成立。
- **失败后可以恢复**：记录进度，重启后继续或补偿。
- **失败后需要人工介入**：保留足够证据，并明确告警与修复方式。

不能只写“捕获异常”，还要说明捕获之后系统处于什么状态。

你可以对每个重要函数、模块或任务，依次问这八个问题：

1. **正常情况下，它保证什么？**
2. **输入非法、边界异常或调用顺序错误时，会怎样？**
3. **重复执行或并发执行，会怎样？**
4. **依赖失败或执行到一半中断，会留下什么？**
5. **时间、内存和其他资源有没有上限？**
6. **失败后如何发现、定位和恢复？**
7. **如何验证这些保证？**
8. **以后升级或修改时，如何保持兼容？**

**生产级的核心是：在明确的运行环境与故障假设下，行为有契约、成本有边界、失败可控制、问题可定位、变化可验证。** 不同项目需要的强度不同：纯计算函数重点关注正确性与成本，文件工具需要关注崩溃一致性，支付服务则必须进一步明确幂等与交易一致性。
