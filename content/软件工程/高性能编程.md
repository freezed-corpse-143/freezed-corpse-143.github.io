# 泛型单态化

泛型单态化（Generic Monomorphization）是编程语言实现泛型的一种编译期策略：**编译器在编译时为每一组实际使用的具体类型参数，分别生成一份独立的、类型确定的代码副本**。

它主要出现在 Rust、C++（模板实例化）等语言中，与 Java 的“类型擦除”、Go 早期的“字典/装箱”等方案形成对比。

Rust 的泛型默认就是单态化。这也解释了为什么：

- `Vec<T>` 对 `Vec<i32>` 和 `Vec<String>` 会生成不同的机器码；
- 泛型函数通常不会带来运行时性能损失；
- 大量使用泛型会导致编译产物变大，有时需要用 `dyn Trait` 来换取代码体积和编译速度。

简单说，**泛型单态化就是用编译期代码复制，换取运行期零开销的一种泛型实现策略**。
## 核心含义

以 Rust 为例：

```rust
fn identity<T>(x: T) -> T {
    x
}

fn main() {
    let a = identity(1i32);      // 生成 identity::<i32>
    let b = identity("hello");   // 生成 identity::<&str>
}
```

编译器看到 `identity` 被 `i32` 和 `&str` 各用了一次，就会生成两个具体函数，类似：

```rust
fn identity_i32(x: i32) -> i32 { x }
fn identity_str(x: &str) -> &str { x }
```

泛型参数 `T` 在生成的代码里已经被替换成具体类型，运行时不存在“泛型”这回事。

## 名称由来

“单态”（monomorphic）与“多态”（polymorphic）相对：

- **多态**：一份代码可以处理多种类型。
- **单态化**：把多态代码在编译期展开成多份只处理单一具体类型的代码。

所以泛型函数在源码层面是多态的，但编译产物里是多个单态函数。

## 主要优点

1. **零运行时开销**  
   类型在编译期确定，不需要虚表查找、类型装箱、运行时类型判断，性能与手写具体类型代码基本一致。

2. **利于内联和优化**  
   编译器知道确切类型，可以做针对性的内联、常量传播、SIMD 等优化。

3. **类型安全**  
   所有类型检查在编译期完成，不依赖运行时。

## 主要代价

1. **代码膨胀**  
   每种类型组合都会生成一份代码。如果泛型被很多类型使用，二进制体积会明显增大。

2. **编译时间变长**  
   需要为每个实例化生成并优化代码。

3. **无法用于动态类型场景**  
   不能在运行时才决定类型参数；需要动态分发时，通常要配合 trait object / 虚函数。

## 与其他泛型实现方式对比

| 方式    | 代表语言        | 运行时开销    | 代码体积 | 动态分发                 |
| ----- | ----------- | -------- | ---- | -------------------- |
| 单态化   | Rust、C++    | 几乎为零     | 可能膨胀 | 需 trait object / 虚函数 |
| 类型擦除  | Java、Kotlin | 有装箱/检查开销 | 小    | 支持                   |
| 字典传递  | Swift、Go 泛型 | 有一定开销    | 较小   | 部分支持                 |
| 运行时特化 | 部分 JIT      | 可变       | 较小   | 支持                   |

# 染色问题

## 网络与路由调度

在交换网络（如路由器、Clos 网络、片上网络）中，多个输入端口同时想把数据发往多个输出端口。但内部链路、中间模块、缓冲区是有限的，不可能所有请求同时通过。于是需要决定：**哪些请求可以同一时刻并行传输，哪些必须排队等待。**

染色在这里的作用，是把"会互相冲突的请求"标记成不同颜色，同色请求可以并行，异色请求必须错开时间。

难点：

1. **冲突关系动态变化**：请求矩阵每时每刻都在变，染色方案不能一劳永逸，必须快速重算。
2. **颜色数量有限**：内部模块数、时间槽数是硬件固定的，颜色太多意味着要串行很多轮，吞吐下降。
3. **在线决策**：调度器必须在极短时间内（纳秒级）做出决定，不能跑一个慢速的全局优化算法。
4. **公平性**：如果总是优先某些颜色的请求，其他请求可能被饿死。
5. **多级网络**：Clos 网络有多级中间模块，每一级都要染色，级与级之间的颜色要协调，否则会阻塞。

核心矛盾：并行度最大化 vs. 调度延迟最小化 vs. 硬件资源固定。
## 寄存器分配

编译器把程序翻译成汇编时，程序里可能有成百上千个变量，但 CPU 寄存器只有几十个甚至十几个。必须决定：**哪些变量放在寄存器里，哪些溢出到内存，哪些变量可以共用同一个寄存器。**

染色在这里的作用，是把"不能共用寄存器"的变量（即同时活跃的变量）标成不同颜色，每种颜色对应一个寄存器。

难点：

1. **冲突图规模大**：大型程序可能有几万个变量，冲突图非常大，精确求解最优染色是 NP 难问题。
2. **活跃范围重叠判断**：两个变量是否冲突，取决于它们是否在同一时刻都"活着"。控制流复杂时，精确判断活跃范围本身就很耗时。
3. **溢出代价**：寄存器不够时，必须把某些变量放到内存。选哪些变量溢出，直接影响程序性能。溢出选择不好，可能让热循环里的变量反复读写内存。
4. **拷贝指令消除**：程序中大量 `a = b` 这类拷贝，理想情况是让 a 和 b 共用寄存器。但合并两个变量可能让冲突图变得更复杂，反而导致更多溢出。
5. **寄存器类别限制**：有些指令只能用特定寄存器（如乘法、浮点），染色时还要考虑寄存器类别，不是简单的"颜色够不够"。
6. **编译时间**：编译器不能花几小时分配寄存器，必须在合理时间内给出一个"足够好"的方案。

**核心矛盾**：寄存器数量有限 vs. 变量数量多 vs. 溢出代价 vs. 编译速度。
## 并行与分布式调度

在并行计算或分布式系统中，有很多任务需要执行，任务之间有依赖关系或资源冲突。需要决定：**哪些任务可以同时执行，哪些必须等待，任务分配到哪个处理器/节点上。**

染色在这里的作用，是把任务按"能否并行"分层或分组，同色任务并行，异色任务按顺序执行。

难点：

1. **依赖关系复杂**：任务之间可能是 DAG（有向无环图），也可能有环（需要特殊处理）。依赖关系决定了哪些任务必须串行。
2. **负载均衡**：同色任务数量可能不均匀，有的颜色任务多，有的少。如果简单按颜色调度，可能导致某些处理器忙死、某些闲死。
3. **通信开销**：分布式系统中，不同节点上的任务如果同色并行，它们之间可能需要通信。通信延迟可能比计算本身还大，染色时必须考虑把通信密集的任务放在同一节点。
4. **动态性**：任务执行时间不确定，有的任务可能突然变慢，原本的染色方案可能不再均衡。
5. **容错**：分布式系统中节点可能失效，染色方案必须考虑失效后的重新调度。
6. **可扩展性**：任务数量可能从几十个到几百万个，染色算法必须能扩展到大规模。

**核心矛盾**：并行度最大化 vs. 负载均衡 vs. 通信开销最小化 vs. 动态适应。
## 事务内存与并发控制

在事务内存（STM）或数据库并发控制中，多个事务同时读写共享数据。如果两个事务访问同一数据且至少有一个是写，就会冲突。需要决定：**哪些事务可以并行提交，哪些必须回滚或串行执行。**

染色在这里的作用，是把事务按冲突关系标成不同颜色，同色事务无冲突可并行，异色事务需要协调。

难点：

1. **冲突不可预知**：事务在提交之前，往往不知道它会读写哪些数据。只能边执行边检测冲突，染色方案必须动态调整。
2. **回滚代价**：如果两个事务冲突，通常要回滚其中一个。回滚意味着之前的工作白做，代价可能很高。染色策略要尽量减少回滚。
3. **饥饿问题**：如果总是回滚同一个事务，它可能永远无法提交。染色必须考虑公平性。
4. **假冲突**：两个事务可能访问同一缓存行但不同变量，硬件层面会误判为冲突。染色时要把这种假冲突也考虑进去，否则并行度会大幅下降。
5. **长事务 vs. 短事务**：长事务持有资源时间长，容易和很多事务冲突。短事务频繁提交，冲突检测开销大。染色策略要区分对待。
6. **串行化正确性**：染色方案必须保证最终结果等价于某个串行执行顺序，否则数据会不一致。
7. **分布式事务**：跨节点的事务冲突检测需要网络通信，延迟高，染色方案必须容忍网络分区和延迟。

**核心矛盾**：并行度最大化 vs. 回滚代价最小化 vs. 串行化正确性 vs. 公平性。

## 关系对比

| 角度               | 染色对象 | 核心难点                     | 核心矛盾                   |
| ------------------ | -------- | ---------------------------- | -------------------------- |
| 网络与路由调度     | 传输请求 | 在线快速决策、硬件资源固定   | 并行度 vs. 延迟            |
| 寄存器分配         | 变量     | NP 难、溢出代价、寄存器类别  | 寄存器有限 vs. 变量多      |
| 并行与分布式调度   | 任务     | 依赖复杂、负载均衡、通信开销 | 并行度 vs. 均衡 vs. 通信   |
| 事务内存与并发控制 | 事务     | 冲突不可预知、回滚代价、饥饿 | 并行度 vs. 正确性 vs. 公平 |
