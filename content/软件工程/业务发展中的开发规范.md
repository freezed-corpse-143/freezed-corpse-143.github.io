## 1. 框架：用业务风险驱动工程规范

### 1.1 核心思想

业务发展会改变系统承担的责任：从计算结果正确，到真实数据不丢失，再到多人独立协作、大规模持续运行，以及最终完成迁移和退役。

开发规范的作用，是把这些责任转换成明确约束、可执行流程和可验证证据。

**业务目标 → 失败后果 → 关键约束 → 工程措施 → 验证证据 → 运行反馈。**

例如：

| 业务变化 | 新增风险 | 应增加的工程能力 | 验证证据 |
|---|---|---|---|
| 内部演示开始服务真实用户 | 错误影响用户，数据开始有价值 | 权限、备份、发布恢复、故障负责人 | 授权测试、恢复演练、发布记录 |
| 请求量增加 | 队列积压、连接耗尽、尾延迟恶化 | 容量测量、并发限制、背压 | 代表性负载报告、资源上限 |
| 多团队分别发布 | 版本错配、接口语义不一致 | 兼容窗口、契约检查、所有权 | 混合版本测试、消费者迁移记录 |
| 开始处理资金 | 重复操作、账实不一致 | 幂等、并发约束、审计、对账 | 重复与中断测试、对账结果 |

### 1.2 三种坐标，不能混为一谈

- **发展阶段**：业务承担了哪些责任。
- **工程主线**：正确性、数据、交付等能力如何持续建设。
- **风险等级**：某次变更需要多强的验证和保护。

阶段不是瀑布流程。同一产品的新功能可能仍在验证假设，而支付模块已经需要严格生产治理。小团队也可能承担高风险，大团队中的低风险文案修改则可以走轻量流程。

### 1.3 如何使用本文

1. 选择当前模块或业务链路，而不是笼统评价整个公司。
2. 判断它承担的阶段责任及本次变更风险。
3. 从八条主线中找出相关约束。
4. 为约束指定实现办法、证据与负责人。
5. 在上线与事故反馈后重新评估。

规范中的“必须”表示被团队采纳后不可无记录跳过；“建议”允许结合上下文裁剪。本文中的检查表是起点，不应全部机械变成审批步骤。

## 2. 七个业务发展阶段

### 2.1 阶段一：单模块——建立行为边界

**核心矛盾：实现功能与控制局部复杂度。**

目标是让别人可以理解、使用、修改和验证这一项能力。

#### 最低规范

- 写明模块职责、非职责及公开入口。
- 定义输入范围、输出含义、业务不变量和失败行为。
- 明确副作用：是否写文件、修改共享状态、发起网络请求。
- 明确资源所有权：谁创建、谁持有、谁关闭。
- 名称表达业务语义；注释解释原因、约束和取舍。
- 在信任边界校验外部输入；内部通过类型、断言和构造约束维护不变量。
- 不吞掉错误；在适当边界翻译错误并保留内部原因。
- 不强求每个函数“一眼读完”，优先保持职责内聚和控制流清晰。
- 对输入规模可能增长的算法，说明时间、空间复杂度及实际限制。

#### 验收信号

- [ ] 核心规则、边界值和失败路径有针对性验证。
- [ ] 非法输入不会留下半完成的业务状态。
- [ ] 使用者无需阅读全部内部实现即可正确调用。
- [ ] 资源生命周期和共享状态归属明确。

**产物**：简短 README、接口说明、核心测试。小模块可以将它们合并，不要求独立文档目录。

### 2.2 阶段二：MVP——验证业务假设

**核心矛盾：学习速度与试错损失。**

目标是证明业务值得继续投入，而不只是证明软件能运行。

#### 最低规范

- 定义目标用户、待验证假设、成功指标与停止条件。
- 区分功能验收与假设验证：按钮可用不代表用户有需求。
- 限制试用人群、数据范围、调用额度和外部副作用。
- 保留关键行为、失败和业务结果的观测能力。
- 环境配置外置；密钥独立管理，不能以配置外置代替密钥保护。
- 临时代码登记负责人、风险与替换触发条件，不能只留 TODO。
- 对外接口按实际消费方承诺稳定范围，避免为尚未验证的业务冻结过多设计。
- 一旦涉及真实资金、敏感数据或公开网络暴露，提前引入相应生产规范。

#### 验收信号

- [ ] 能判断假设成立、失败或证据不足。
- [ ] 试验失败后的用户和数据影响在可接受范围内。
- [ ] 临时方案的继续使用条件明确。
- [ ] 能复现部署，并知道如何停止试验。

**产物**：一页假设说明、验收样例、指标定义、技术债记录。

### 2.3 阶段三：首次生产——承担真实后果

**核心矛盾：快速上线与用户、数据风险。**

目标是让系统可以被负责地运行。

#### 最低规范

- 构建步骤、依赖、配置及发布物可追溯；关键版本锁定。
- 启动时验证必要配置，对无法安全运行的配置及时失败。
- 就绪与存活检查具有明确语义；避免把非核心依赖短暂故障变成无限重启。
- 关键路径有日志、指标和可行动告警。
- 明确业务与技术负责人、故障联系和止损操作。
- 数据有备份策略、恢复步骤和至少一次实际恢复验证。
- 发布前明确回退、关闭功能或前向修复方案。
- 权限、密钥、敏感数据和发布权限满足最低保护要求。

#### 验收信号

- [ ] 接近生产的环境可以完成部署、冒烟与恢复验证。
- [ ] 关键问题能够被发现、归属和止损。
- [ ] 恢复后检查业务状态，而不只检查进程启动。
- [ ] 发布产物能够关联到源码、依赖和配置版本。

**产物**：上线清单、运行手册、恢复记录、负责人信息。

### 2.4 阶段四：持续增长——约束变化与负载

**核心矛盾：需求、流量和数据增长与系统承载力。**

#### 最低规范

- 按业务责任和变化原因组织模块，建立依赖约束。
- 测量响应时间、吞吐、错误率、积压及资源占用。
- 识别热点、共享资源、关键依赖与最先耗尽的容量。
- 请求体、分页、并发、队列、缓存和批次规模都有适当上限。
- 写入明确并发控制、重复提交和重试语义。
- 数据迁移兼顾新旧代码共存、分批回填与结果核对。
- 缓存定义陈旧容忍度、失效与重建行为。
- 限流、降级与背压依据核心业务优先级设计。
- 优先优化有证据的问题；流量增长不自动意味着需要微服务。

#### 验收信号

- [ ] 能解释下一轮增长首先受哪项约束限制。
- [ ] 超载行为可预测，不会无限排队直至整体失效。
- [ ] 迁移可以暂停、继续，并检查遗漏和重复。
- [ ] 重复、并发和失败注入不会破坏关键业务不变量。

**产物**：容量评估、迁移计划、关键架构决策、负载与一致性验证记录。

### 2.5 阶段五：多人多团队——支持独立演进

**核心矛盾：并行开发与集成协调成本。**

#### 最低规范

- 模块、接口、数据和生产故障有明确所有者。
- 结构化契约与实现同步检查；语义约束另外说明。
- 对独立演进的边界设置适当契约与兼容性测试。
- 明确支持版本、升级顺序、弃用期限与迁移责任。
- 不依赖“客户端与服务端恰好同时升级”的假设。
- 共享基础设施有接入边界和升级机制，避免无限共享内部实现。
- 对常见路径提供可复用脚手架、流水线和文档，减少重复劳动。
- 允许有理由的例外，记录风险与重新评估时间。

#### 验收信号

- [ ] 常规变更无需所有团队同步发布。
- [ ] 消费方知道如何验证升级以及何时必须迁移。
- [ ] 交接后能够找到维护人、运行方式和历史决策。
- [ ] 集成问题可以定位到具体契约与责任边界。

**产物**：所有权清单、契约、弃用公告、接入说明和必要的兼容检查。

### 2.6 阶段六：规模运营——管理可靠性与成本

**核心矛盾：功能收益、故障风险与单位成本。**

#### 最低规范

- 用用户可感知的指标制定服务等级目标（SLO）。
- 根据可靠性表现决定发布节奏与修复优先级。
- 发布逐步扩大影响范围，并定义暂停条件。
- 重要依赖、容量、数据恢复和故障转移定期验证。
- 事故复盘关注触发条件、防线缺口、发现和恢复过程。
- 按业务量归集成本，关注每订单、每次推理等单位成本。
- 持续处理重复手工操作、无效告警和运维负担。

#### 验收信号

- [ ] 用户体验目标与实际表现可对照。
- [ ] 故障改进项有负责人、期限和验证证据。
- [ ] 降本没有把费用转移为不可接受的延迟、故障或人工负担。
- [ ] 演练能够证明恢复能力，并暴露实际限制。

**产物**：SLO、发布策略、复盘与演练记录、成本看板。

### 2.7 阶段七：迁移与退役——结束旧系统责任

**核心矛盾：替换收益与历史兼容、数据责任。**

#### 最低规范

- 盘点调用方、定时任务、消息消费者、凭证和依赖。
- 数据迁移定义数量、金额、关系及抽样内容等校验方法。
- 明确切换条件、回退窗口和旧系统停止写入的时间。
- 弃用有期限、联系人与消费者迁移状态。
- 回收权限、域名、证书、实例、存储及第三方订阅。
- 处理历史数据保留、删除和必要的审计记录。

#### 验收信号

- [ ] 在合理观察窗口内确认旧路径没有业务调用。
- [ ] 迁移数据和业务结果完成核对。
- [ ] 遗留任务与资源已经退出，费用停止产生。
- [ ] 留存数据可按约定访问，到期可按约定处置。

## 3. 八条贯穿全程的工程主线

### 3.1 需求与正确性：定义“做对”的含义

需求应覆盖以下内容：

| 维度 | 需要回答的问题 |
|---|---|
| 目标与非目标 | 解决谁的什么问题？哪些情况暂不支持？ |
| 前置条件 | 哪些身份、状态、数据条件下允许执行？ |
| 不变量 | 哪些关系在任何合法执行后都必须成立？ |
| 状态转换 | 哪些迁移允许、拒绝或需要人工介入？ |
| 完成语义 | 成功代表接收、持久化、执行完毕还是外部确认？ |
| 失败语义 | 哪些失败确定无效果，哪些可能已有副作用？ |
| 质量预算 | 可接受的延迟、资源、数据损失和恢复时间是多少？ |
| 验收证据 | 用哪些样例、测试、演练证明？ |

外部输入校验与业务正确性分开考虑。格式正确的金额也可能超出可退款余额；身份已经认证的用户也可能无权操作该订单。

### 3.2 代码与架构：控制变更传播

#### 组织原则

- 把经常一起变化的内容放在一起，把不同变化原因隔离。
- 文件是物理组织单位，模块是职责、接口与封装单位。
- 显式依赖优于隐藏全局状态；依赖注入可以手动完成，不要求引入框架。
- 业务规则应有清晰归属，避免在多个入口各写一份。
- 抽象应对应真实变化、测试隔离或边界要求，不要求每个类都有接口。
- 共享代码前确认语义相同；外观类似不代表应长期共用。

#### 调用方向与依赖方向

运行时可能发生“应用服务调用数据库适配器”；源码可以由应用核心定义存储接口、基础设施实现该接口。这样核心逻辑无需依赖具体数据库。

依赖倒置是可选设计手段，不是所有项目必须完整套用四层目录。判断依据是变化成本、隔离需要和团队理解成本。[1]

#### 评审问题

- 新增一种业务规则需要修改哪些位置，为什么？
- 替换外部服务是否会迫使核心规则变化？
- 哪个模块拥有共享状态，谁可以修改？
- 当前拆分是否减少理解和变更成本，还是增加了跳转与胶水代码？

### 3.3 契约与协作：规定行为和演进责任

#### 契约六个维度

| 维度 | 示例内容 |
|---|---|
| 数据 | 类型、单位、货币、精度、时区、默认值、缺失值 |
| 行为 | 前置条件、副作用、重复提交、排序和分页语义 |
| 时间 | 超时、截止时间、异步完成时限、数据新鲜度 |
| 失败 | 错误分类、可否重试、结果未知、查询方式 |
| 演进 | 兼容范围、弃用期限、版本支持窗口 |
| 责任 | 提供者、消费者、维护人、故障与迁移责任 |

OpenAPI、Protobuf、Schema 可以作为结构化契约的权威来源；权限与业务行为仍需说明和验证。代码生成减少重复维护，不能自动证明语义正确。

#### 兼容性检查

- **编码兼容**：旧数据能否解析，新字段是否被拒绝或忽略。
- **源码兼容**：消费者重新生成、编译后是否正常。
- **行为兼容**：默认值、排序、权限、校验强度和错误语义是否改变。
- **运行兼容**：滚动升级和回退期间，新旧版本是否能共存。

“字段只增不删”不足以保证兼容。删除 Protobuf 字段后应保留编号；不同编码格式的演进规则也可能不同。[2]

#### 错误契约

局部可以使用封闭错误集合；跨边界将内部错误映射为稳定业务语义。内部保留原因链，对外提供必要错误码、关联标识和处理建议，不暴露内部堆栈或密钥。

恢复策略独立于错误名称：同一种网络错误，在只读查询、资金扣款和后台同步中可能需要不同处理。

### 3.4 数据与并发：保护真实状态

#### 基础要求

- 用数据库约束、事务、版本检查或合适的并发协议维护关键不变量。
- 不把“先查再写”默认当成原子操作。
- 明确事务覆盖范围；外部 API 通常不属于本地数据库事务。
- 识别写数据库与发消息之间的失败窗口，按需要采用事务发件箱等方式，并处理重复投递。
- 消费者明确重复、乱序、迟到和无法处理的消息策略。
- 批处理和回填记录进度，支持安全重跑，并核对结果。

#### 迁移规范

优先考虑“扩展—迁移—收缩”：增加兼容结构，迁移与验证数据，切换读写，确认旧版本退出后清理旧结构。[3]

每次迁移说明：数据量、锁与负载影响、执行权限、新旧版本兼容、分批策略、暂停与恢复、校验方式和故障处置。

**有恢复方案不等于所有迁移都有逆向脚本。** 不可逆变更需明确备份恢复、前向修复或人工修复的条件；数据库恢复还要考虑迁移后新增业务数据的保留。

#### 缓存规范

说明权威数据源、可接受陈旧时间、缓存键与租户隔离、容量与淘汰、失效方式、冷启动、热点失效以及缓存不可用时的行为。避免缓存故障把全部请求同时转移到已经没有余量的数据库。

### 3.5 故障与恢复：覆盖部分完成和结果未知

| 状态 | 典型处置 |
|---|---|
| 确定未执行 | 修正条件或按策略重试 |
| 已执行但响应丢失 | 查询结果、凭业务标识去重 |
| 执行结果未知 | 保留未知状态，通过查询、回调或对账收敛 |
| 部分执行 | 继续、补偿、隔离或人工介入 |
| 状态疑似损坏 | 停止传播、校验、定位和修复 |
| 依赖过载 | 限并发、背压、拒绝或降级 |

#### 超时与重试

- 远程调用明确连接、请求及整体截止时间。
- 总时间预算包括排队、重试、退避和必要清理。
- 只重试适合重试的失败；限制次数和总预算。
- 使用适当退避与抖动，避免多层重复重试。
- 超时不代表没有副作用；幂等与结果查询必须匹配业务语义。[4]
- 熔断和隔离按故障模式引入，并考虑探测恢复和状态复杂度。

#### 中断与资源

- 取消等待和取消实际业务执行分别定义。
- 关闭时停止接收新工作，限时排空或保存任务状态。
- 锁、文件、连接等使用语言提供的生命周期机制。
- RAII、with、finally 不能保证断电或强制终止时执行业务清理。
- 可恢复工作应依赖持久化状态、原子提交与重启恢复。
- 工作队列、并发、内存、临时文件、重试和日志增长均有上限。

#### 恢复目标

- **RTO**：发生中断后，目标多久恢复业务。
- **RPO**：目标最多允许丢失多长时间窗口的数据。

目标需覆盖恢复后校验、重新接入流量和业务追平。备份成功不是恢复能力的充分证据。

### 3.6 安全与供应链：保护数据和发布边界

安全工作按暴露面和损失后果逐步增强，并纳入现有开发流程。NIST SSDF 提供了将安全实践嵌入开发生命周期的框架。[5]

- 认证与授权分别实现；检查对象级、角色级和租户级权限。
- 最小权限用于人员、服务身份、数据库与流水线。
- 密钥不进入源码、日志、镜像和普通配置样例；支持轮换与撤销。
- 对不可信输入考虑注入、路径、文件、URL 和反序列化风险。
- 敏感数据限制收集、展示、访问、保留与导出。
- 依赖明确来源和版本，高风险漏洞有评估与修复责任。
- 构建产物可追溯；发布权限与生产凭证受到保护。
- 日志用于排障，审计用于追溯关键操作；二者分别规定访问和保留要求。

### 3.7 验证、发布与可观测性：提供可操作证据

#### 按风险选测试

| 风险 | 优先手段 | 关注点 |
|---|---|---|
| 计算与业务规则 | 单元测试、性质测试 | 不变量和边界 |
| 数据库与消息行为 | 集成测试 | 事务、约束、投递与消费 |
| 独立发布接口 | 契约与兼容测试 | 混合版本和语义 |
| 核心用户旅程 | 少量端到端测试 | 从入口到业务结果 |
| 并发和中断 | 并发测试、故障注入 | 关键失败窗口 |
| 容量与成本 | 代表性负载测试 | 尾延迟、资源、积压、单位成本 |
| 恢复与迁移 | 演练和对账 | 数据正确、业务恢复 |

覆盖率用于发现盲区，不能单独证明正确性。测试应验证可观察行为与风险，避免只复述内部实现。

#### 发布约束

每次重要发布回答：发布什么、谁负责、影响谁、如何观察、何时扩大、何时停止、如何恢复。

代码、配置、特性开关、数据库迁移和依赖升级都可能改变生产行为。小范围发布需选择代表性用户和指标，并考虑共享数据库等无法被流量隔离的影响。[6]

#### 可观测性约束

- 日志解释事件，指标展示趋势，追踪定位跨组件路径，审计记录关键操作。
- 用关联标识连接一次业务操作；避免敏感数据和无界高基数标签。
- 告警对应用户影响、明确行动和责任人。
- 业务指标与技术指标互证：HTTP 成功率正常，不代表退款已经到账。
- 观测系统故障时有基本排障办法，观测本身也有资源预算。

### 3.8 性能、成本与技术债：持续管理预算

#### 性能

早期定义可行性预算，持续测量，按瓶颈深入优化。明确负载模型、输入分布、并发、环境和测试时长；记录优化前后用户指标及资源变化。

缓存、批处理、异步化、并行和索引都附带约束：异步化可能引入积压，批处理可能增加等待，并行可能增加争用，索引可能增加写入与存储成本。

#### 成本

按业务单位核算，同时观察总成本：

> 单位业务成本 = 约定范围内的总成本 ÷ 对应有效业务量。

定义计算范围与时间窗口，纳入计算、存储、网络、第三方调用和必要运维成本。流量变化会影响单位成本，比较时应说明负载与利用率差异。

#### 技术债

债务记录包含当前代价、未来风险、影响范围、负责人、偿还触发条件和继续接受的理由。临时方案升级为长期方案时，要补齐维护责任；已经无影响的债务可以关闭。

用用户体验目标约束优化。在规模运营阶段，可借助 SLO 与错误预算协调发布和可靠性投入；阈值和动作由团队结合业务制定。[7]

## 4. 按风险选择规范强度

### 4.1 评估维度

评估损失程度、影响范围、可逆性、可检测性、数据与权限敏感度、外部副作用、并发复杂度及新旧版本共存时间。

不建议简单加总成一个分数后自动放行。某个严重风险就可能决定必须采用更强措施。

### 4.2 参考分级

| 等级 | 示例 | 建议最低证据 |
|---|---|---|
| 低 | 无行为变化的文案、局部展示调整 | 相关静态检查或人工预览 |
| 中 | 普通流程或内部接口调整 | 相关自动测试、评审、发布观察与恢复办法 |
| 高 | 权限、资金、共享状态、大数据迁移 | 不变量验证、并发与失败测试、演练、受控发布、专人观察 |
| 关键 | 大范围不可逆删除、核心账务切换 | 独立复核、分阶段执行、隔离验证、恢复与数据核对、明确决策责任 |

这些等级是本文的参考约定，不是行业统一分级。团队需结合自身业务校准。

### 4.3 不应按阶段延后的底线

涉及真实风险时，业务不变量、资源上限、权限、密钥保护、关键数据恢复和外部副作用处理不能仅因“还在 MVP”而省略。流程形式可以轻量，责任不能缺失。

## 5. 将规范落到日常交付流程

| 环节 | 核心问题 | 最小证据 |
|---|---|---|
| 需求澄清 | 正确结果和失败后果是什么？ | 验收样例、不变量、范围 |
| 方案设计 | 状态、依赖和失败窗口在哪里？ | 状态说明、风险、关键决策 |
| 实现评审 | 实现是否维护约束？ | 代码与相关验证 |
| 发布准备 | 能否发现问题并止损？ | 观察指标、恢复步骤、负责人 |
| 上线观察 | 用户结果是否符合预期？ | 业务与技术指标 |
| 后续复盘 | 哪项风险或假设需要调整？ | 改进项与债务更新 |

### 5.1 基础交付检查表

- [ ] 目标、非目标和验收样例明确。
- [ ] 业务状态与关键不变量明确。
- [ ] 失败、重复、并发与中断按风险评估。
- [ ] 数据、权限和资源影响已检查。
- [ ] 接口与数据演进考虑实际消费者和旧版本。
- [ ] 验证覆盖本次变化及关键失败窗口。
- [ ] 发布物、配置和相关迁移可追溯。
- [ ] 观察、停止和恢复方式明确。
- [ ] 所有人与运行责任明确。
- [ ] 不适用项说明原因，而不是补造形式化文档。

### 5.2 自动化优先级

先自动化高频、确定性、容易漏掉的检查：格式、类型、核心测试、契约差异、构建和配置校验。业务语义、风险取舍和无法还原的生产后果仍需人工判断。

规范数量增加前，先检查现有规范能否自动执行、是否减少真实问题、是否存在更简单的办法。

## 6. 退款业务贯穿示例

### 6.1 业务契约

- 退款只能由有权主体针对可退款订单发起。
- 金额使用明确货币和最小货币单位，避免模糊精度。
- 成功退款加上仍占用额度的在途退款，不得超过可退金额。
- 同一退款意图具有稳定业务标识，重复请求返回同一操作结果。
- 相同幂等键但参数不同的请求应明确拒绝。
- “已受理”和“已退款”分别表达，结果未知不能当作确定失败。

### 6.2 状态设计

可采用：已创建、处理中、成功、确定失败、待核查。待核查通过外部查询、可信回调和对账逐步收敛。

进入处理中时如何占用额度、确定失败时何时释放额度、迟到成功如何处理，需要与支付渠道实际能力一致。不能只依据本地超时释放额度。

### 6.3 关键失败窗口

| 窗口 | 风险 | 防护与证据 |
|---|---|---|
| 两个请求同时检查余额 | 同时通过导致超退 | 原子额度占用、事务或版本控制；并发验证 |
| 本地持久化后、外部调用前崩溃 | 操作长期停滞 | 持久任务状态、恢复扫描；重启验证 |
| 外部成功后、记录结果前崩溃 | 重试重复退款 | 渠道幂等标识或查询能力；故障注入与对账 |
| 回调重复或乱序 | 错误覆盖终态 | 验签、去重、状态迁移规则；回调测试 |
| 退款记录写入但消息未发送 | 后续业务遗漏 | 可靠发布机制与消费去重；一致性核查 |

这些措施不能自动提供跨任意外部系统的“恰好一次”。如果渠道缺少幂等或查询能力，应明确剩余风险与人工核查路径。

### 6.4 随阶段增加责任

| 阶段 | 新增重点 |
|---|---|
| 单模块 | 金额计算、状态和权限规则 |
| MVP | 沙箱或受限额度、业务假设、试验止损 |
| 首次生产 | 真实渠道、审计、恢复、资金对账 |
| 增长 | 并发额度、积压、渠道限额、重试预算 |
| 多团队 | 订单与财务契约、版本演进、责任归属 |
| 规模运营 | 到账时延目标、异常对账率、单位处理成本 |
| 退役 | 在途退款收敛、历史凭证、旧回调与凭证处理 |

## 8. 学习路线与框架演进

### 8.1 面向初学者的实践顺序

| 学习步 | 练习任务 | 掌握信号 |
|---|---|---|
| 1. 行为契约 | 写一个金额计算模块 | 能表达不变量并验证边界 |
| 2. 外部边界 | 增加文件、数据库或网络操作 | 能说明失败、副作用与资源生命周期 |
| 3. 安全交付 | 部署一个小服务 | 能发布、观察并恢复 |
| 4. 并发与数据 | 增加重复提交和并发写入 | 不变量在竞争和中断后仍成立 |
| 5. 协作演进 | 分离提供方和消费者 | 能验证混合版本与弃用流程 |
| 6. 运行治理 | 制造过载、依赖超时和恢复 | 能定位瓶颈并限制影响 |
| 7. 迁移退役 | 替换旧字段或旧服务 | 能完成数据核对与旧资源退出 |

每次只增加一类主要风险。先理解机制和失败窗口，再选择框架或基础设施。

### 8.2 定期评估问题

- 当前最可能造成不可接受损失的风险是什么？
- 哪些规范已经产生证据，哪些只停留在文档？
- 哪些检查可以自动化或合并？
- 哪些流程成本已经超过它降低的风险？
- 新事故、业务变化或团队变化带来了什么新约束？
- 原有假设失效后，哪条规范需要修改或删除？

成熟度应由“能够控制哪些风险”描述，不宜仅统计文档数、微服务数、测试覆盖率或工具数量。

### 8.3 持续扩展方式

对新领域沿用同一分析方法。例如 GPU 推理服务需要额外关注显存上限、批处理等待、请求取消、设备故障与模型切换；桌面客户端需要关注安装更新、离线、配置迁移和崩溃恢复。

扩展时新增领域约束及验证证据，并连接到已有主线，避免为每项技术重新发明整套生命周期。

## 9. 术语与参考资料

### 9.1 术语

| 术语 | 含义 |
|---|---|
| 业务不变量 | 合法执行过程中必须维护的业务关系 |
| 幂等 | 按约定重复执行不会产生额外业务效果；需明确作用范围和有效期 |
| 背压 | 下游通过限制或信号约束上游生产速度，防止无界积压 |
| SLI | 服务等级指标，例如有效请求在目标时间内完成的比例 |
| SLO | 对 SLI 设定的目标及统计窗口 |
| 错误预算 | 在目标窗口和口径下允许的不可靠程度 |
| ADR | 记录重要架构选择及其背景和后果 |
| RTO / RPO | 目标恢复时间 / 目标可接受数据损失时间窗口 |
| 金丝雀发布 | 先对有限范围发布，依据观测判断是否继续扩大 |
| 事务发件箱 | 将业务写入与待发布事件放入同一本地事务，再可靠发布；仍需处理重复 |
