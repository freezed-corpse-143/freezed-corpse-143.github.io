学习元编程，最适合从**“程序如何表示，以及程序如何被另一个程序处理”**入手，再把 C++、Rust、Zig、Python 的机制放到这个框架中。这样学到的是可迁移的原理。
可以用下面这个抽象模型贯穿整个学习过程：

$$
\boxed{
\text{元程序 }M
+
\text{程序描述 }P
+
\text{配置 }C
\;\longrightarrow\;
\text{分析结果或新程序 }P'
}
$$

例如，序列化生成器读取类型定义 $P$，结合命名规则 $C$，生成序列化实现 $P'$。

这里的“程序描述”可以是源码、语法树、类型信息、数据库 Schema，甚至运行时的类和函数对象。

# 一、先建立五个分析维度

以后遇到任何一种元编程机制，都用这五个问题分析：

| 维度     | 核心问题         | 典型选项                   |
| ------ | ------------ | ---------------------- |
| **对象** | 它处理什么？       | 文本、语法树、类型、函数、模块、Schema |
| **时机** | 它什么时候执行？     | 构建前、预处理、编译期、加载期、运行期    |
| **能力** | 它可以做什么？      | 检查、计算、选择、生成、修改         |
| **边界** | 它能看到和改变哪些信息？ | 当前表达式、类型字段、模块、整个程序     |
| **保证** | 变换后如何保证正确？   | 语法检查、类型检查、语义约束、测试      |

例如：

- C 宏：处理 Token，在预处理阶段展开，主要保证展开结果最终能通过编译。
- Rust 过程宏：处理 Token 流，在编译期间生成代码；它并不直接拥有编译器完整的类型信息。
- Python 反射：处理运行时对象，在运行期检查属性和调用关系。

**执行在编译期，不代表拥有全部编译期信息。**“什么时候执行”和“能看见什么”必须分开理解。

# 二、第一层：程序的表示

目标是理解：**代码不是只有字符串这一种形态。**

```text
源码文本 → Token → AST → 类型化表示 → IR → 机器代码
```

| 表示 | 保留的信息 | 适合的操作 |
|---|---|---|
| 文本 | 字符、格式、注释 | 模板填充、简单生成 |
| Token | 关键字、标识符、运算符 | 宏展开、词法级处理 |
| AST（抽象语法树） | 表达式、声明、嵌套结构 | 结构化检查和代码变换 |
| 类型化表示 | 语法结构及类型、符号等信息 | 类型驱动分析和变换 |
| IR（中间表示） | 更适合计算分析的操作与控制流 | 优化、降低到目标平台 |
| 运行时对象 | 实际的类、函数、属性等 | 反射、动态组合、行为修改 |

这一层重点学习：

- 语法与语义有什么区别。
- 标识符如何绑定到变量、函数和类型。
- 作用域和名字解析如何工作。
- AST 为什么比字符串替换可靠。
- 为什么有些变换必须等到类型信息出现以后。

**练习：**把 `a + b * 2` 表示为树，然后将其中所有整数常量乘以 10。分别用字符串替换和 AST 变换思考，会出现哪些区别。

# 三、第二层：阶段与执行时间

目标是理解：**一段逻辑放在哪个阶段执行，会改变它能使用的信息以及产生的成本。**

可以区分：

$$
\text{构建阶段}
\rightarrow
\text{编译阶段}
\rightarrow
\text{加载阶段}
\rightarrow
\text{运行阶段}
$$

学习三个核心概念：

| 概念    | 含义           | 示例            |
| ----- | ------------ | ------------- |
| 编译期计算 | 提前算出某个值      | 计算常量查找表       |
| 代码生成  | 产生新的程序结构     | 生成序列化函数       |
| 特化    | 根据已知条件得到专用实现 | 针对固定类型或参数生成实现 |

这三者可以组合，但不能混为一谈。**编译期计算不一定是元编程**，普通常量表达式求值也可能只是提前计算。

进一步学习**部分求值（Partial Evaluation）**：

给定：

$$
f(x,y)
$$

若 $x=a$ 已知，可以提前处理与 $a$ 有关的部分，得到：

$$
f_a(y)=f(a,y)
$$

输出 $f_a$ 是一个保留未知输入 $y$ 的专用程序。

**练习：**实现一个幂函数。比较“运行时传入指数”和“提前知道指数为 3”时，可以生成怎样不同的实现。

# 四、第三层：元编程的基本操作

目标是把各种语言机制归纳成少量通用操作。

| 操作  | 抽象含义         | 常见用途       |
| --- | ------------ | ---------- |
| 检查  | 获取程序结构的信息    | 枚举字段、检查注解  |
| 计算  | 根据已有信息计算结果   | 计算布局、生成查找表 |
| 选择  | 按条件选择实现      | 根据类型能力选择算法 |
| 构造  | 创建新的程序结构     | 创建类、函数、表达式 |
| 变换  | 修改已有程序结构     | 插入日志、重写调用  |
| 组合  | 将多个结构或行为拼接起来 | 包装函数、组合接口  |

这里需要区分几个经常混用的术语：

- **内省（Introspection）**：检查程序自身的结构。
- **反射（Reflection）**：术语边界因语言而异，通常涵盖对程序结构的检查，部分系统还支持修改。
- **宏**：按规则展开或变换代码的机制。
- **代码生成**：生成代码这一行为，可以由宏、编译器或外部工具完成。
- **泛型**：表达适用于多种类型的逻辑，可以与元编程结合。
- **装饰器**：包装或转换被装饰对象的机制；是否属于元编程，取决于具体用途。

**练习：**围绕一个函数，分别实现“检查参数”“包装调用并计时”“生成一个新函数”。观察三者处理的对象和执行时机。

# 五、第四层：类型驱动的元编程

目标是理解：**类型既能约束程序，也能成为生成程序的输入。**

按下面的顺序学习：

1. **参数化**：将具体类型替换成类型参数。
2. **约束**：要求类型具备某些能力。
3. **类型计算**：从输入类型推导输出类型。
4. **实现选择**：根据类型或能力选择实现。
5. **结构生成**：根据类型的字段或变体生成代码。

例如：

$$
\text{字段描述}
\longrightarrow
\text{序列化实现}
$$

或者：

$$
(T,\text{是否支持连续存储})
\longrightarrow
\text{选定的处理算法}
$$

需要掌握的知识：

- 参数化多态与特设多态。
- Trait、Concept、接口等能力约束。
- 类型推导与类型检查。
- 类型层面的递归和条件计算。
- 实例化、单态化与代码体积的关系。

**特别注意：拥有类型参数，不等于能枚举该类型的字段。**泛型能力与结构反射能力是两个不同维度。

**练习：**设计一个通用输出函数：对于具有指定能力的类型使用专用输出方式，否则使用默认方式。再思考：如果要自动输出全部字段，还缺少什么信息？

# 六、第五层：正确性与组合能力

这一层决定你能否从“写得出来”进入“工程上可靠”。

元编程至少需要处理以下问题：

| 问题 | 典型失败 | 需要学习的机制 |
|---|---|---|
| 名字绑定 | 生成的变量意外覆盖用户变量 | 卫生宏、作用域、符号身份 |
| 求值次数 | 参数表达式意外执行多次 | 暂存值、求值策略 |
| 类型正确性 | 生成了不满足类型约束的代码 | 类型检查、约束传播 |
| 语义正确性 | 代码能编译，但行为改变 | 明确变换前后的语义关系 |
| 阶段正确性 | 编译期依赖运行期才存在的值 | 阶段分离、跨阶段规则 |
| 可组合性 | 两个宏或包装器互相干扰 | 明确输入输出契约 |
| 可诊断性 | 错误只指向大量生成代码 | 源位置映射、清晰错误信息 |

例如，一个看似简单的宏：

```c
#define SQUARE(x) ((x) * (x))
```

调用：

```c
SQUARE(i++)
```

会将参数展开两次，并引入求值副作用问题。这里要学习的不是“宏语法”，而是**变换是否保留了调用者预期的求值语义**。

对于优化类变换，常见目标可以写为：

$$
\operatorname{Behavior}(T(P))
=
\operatorname{Behavior}(P)
$$

对于序列化生成等增加功能的变换，则应检查生成程序是否满足指定契约，不能简单要求与原程序完全等价。

**练习：**为一个计时包装器明确规定：参数求值几次、异常如何传播、返回值如何保留、嵌套包装如何工作。

# 第六层：工程成本与使用边界

目标是学会判断：**这件事是否值得用元编程，以及应该放在哪个阶段。**

比较以下成本：

$$
\text{开发成本}
+
\text{构建成本}
+
\text{运行成本}
+
\text{诊断与维护成本}
$$

典型取舍包括：

- 提前生成专用实现，可以降低运行时分派成本，但可能增加编译时间和代码体积。
- 动态反射提供灵活性，但把部分检查推迟到了运行时。
- 外部生成器便于查看输出，但需要管理输入、生成文件和构建依赖。
- 隐式生成减少重复代码，但可能降低程序行为的可见性。

选择机制时，依次问：

1. 普通函数、组合或泛型能否表达？
2. 是否必须读取程序结构？
3. 必要信息最早在哪个阶段可用？
4. 生成结果是否容易检查和调试？
5. 重复工作是否足够多，值得承担额外复杂度？
# 八、用同一个项目贯穿学习

建议采用一个**“类型描述 → 序列化器”**项目，逐步提升抽象层次。

| 阶段 | 实现内容 | 验证的知识 |
|---|---|---|
| 1 | 手写几个类型的序列化函数 | 识别重复模式 |
| 2 | 提取公共函数和泛型逻辑 | 普通抽象的能力边界 |
| 3 | 用字段 Schema 生成源码 | 外部代码生成 |
| 4 | 解析和变换 AST | 程序的结构化表示 |
| 5 | 用语言内置机制生成实现 | 宏、类型信息、阶段 |
| 6 | 用运行时反射构建序列化器 | 动态结构处理 |
| 7 | 加入嵌套类型、可选字段和错误诊断 | 递归、组合、工程可靠性 |

每一步都记录同样五项：**输入、输出、执行阶段、可用信息、正确性契约。**

语言实践可以选择：用 Python 理解动态对象与反射，用 Rust 理解语法变换与生成，用 C++ 或 Zig 深入类型计算和编译期执行。无需一开始同时学习全部语言。

完成这套框架后，你应当能看到一种元编程机制，就判断出：**它操作哪一层程序表示，依赖哪些信息，在哪个阶段运行，生成什么，以及如何验证它。**
