并发 Bug 的排查，核心是：**找出哪些操作访问同一份状态、它们必须满足什么顺序，以及实际执行如何破坏了这个顺序。**

它比普通 Bug 难，是因为输入不只包括函数参数，还包括**线程调度、内存可见性、异步完成顺序和故障发生时机**。同一份代码、同一组参数，也可能得到不同结果。

可以建立一个完整的分析流程：

**定义正确性 → 列出共享状态 → 建立操作时序 → 检查同步关系 → 构造错误交错 → 用工具捕获 → 固定回归用例。**

## 1. 先明确：你要抓的是哪一种错误

“并发 Bug”不等于“多个线程同时写一个变量”。

| 类型                  | 问题是什么                     | 典型表现                      |
| ------------------- | ------------------------- | ------------------------- |
| 数据竞争 Data race      | 多个线程无充分同步地访问同一内存位置，至少一个是写 | 随机值、崩溃、编译优化后异常            |
| 逻辑竞态 Race condition | 结果依赖操作时序，某些时序违反业务规则       | 重复扣款、重复初始化、超卖             |
| 原子性违反               | 应当整体完成的多步操作被插入其他操作        | 检查通过后，实际执行条件已改变           |
| 顺序违反                | 必须先发生的操作实际没有先发生           | 初始化前使用、释放后访问              |
| 死锁                  | 多个参与者互相等待，无法继续            | 请求永久卡住                    |
| 活锁、饥饿               | 系统在运行，但某些操作始终无法取得进展       | CPU 忙但无产出、个别请求长期等待        |
| 生命周期错误              | 任务仍在访问对象，对象已经销毁或被复用       | use-after-free、取消后回调访问旧对象 |

**数据竞争和逻辑竞态必须分开。**

例如，余额的每次读取和写入都加了锁，但“检查余额 → 扣款”没有放在同一个临界区，仍然可能超额扣款。

反过来，即使程序只有一个线程，多个异步任务在 `await` 前后交错，也可能产生逻辑竞态。

## 2. 第一步：先写“什么情况绝对不能发生”

不要一开始就盯着锁。先明确系统的**不变量**，也就是执行过程中必须持续成立的条件。

例如：

| 场景     | 不变量或正确性要求            |
| ------ | -------------------- |
| 账户转账   | 一次成功转账前后，总余额保持不变     |
| 库存扣减   | 库存不小于 0；成功订单数不超过可售数量 |
| 单次初始化  | 初始化结果只能在完成后对其他线程可见   |
| 任务队列   | 每个已接收任务最终按约定完成或取消    |
| 对象生命周期 | 销毁前，所有访问者已经退出或失去访问能力 |
| 缓存刷新   | 旧版本结果不能覆盖已经发布的新版本结果  |

还要写清楚**进展要求**：例如“拿不到资源可以失败返回，但不能无限等待”。

这一步的作用是把“偶尔不对劲”变成可判断的错误：

> 不是“两个请求碰巧重叠了”，而是“两个请求重叠时，同一张优惠券被成功使用了两次”。

## 3. 第二步：画出共享状态和访问者

对每份共享状态，至少回答以下问题：

| 问题 | 需要记录的内容 |
|---|---|
| 谁访问它？ | 线程、异步任务、回调、后台工作线程 |
| 谁修改它？ | 所有写入路径，包括错误处理和清理 |
| 谁负责同步？ | 哪把锁、原子操作、消息队列或事务 |
| 哪些字段必须一起变化？ | 例如 `余额 + 交易记录`、`指针 + 长度` |
| 谁负责销毁？ | 谁释放，如何确认其他访问者已经结束 |
| 是否存在绕过路径？ | 无锁读、调试接口、超时处理、取消回调 |

特别要警惕：

**同一份数据在不同路径上由不同的锁“保护”。**

```text
路径 A：拿 lockA → 修改 state
路径 B：拿 lockB → 修改 state
```

两把锁各自正常工作，但它们没有形成对 `state` 的共同保护。

还有一种更隐蔽的情况：容器本身线程安全，但容器里的对象不是；或者每个字段都安全，但字段组合没有一致性保证。

## 4. 第三步：把代码拆成真正的并发步骤

源码中的一行，不一定是一个不可分割操作。

例如：

```cpp
counter++;
```

可以从概念上拆为：

```text
读取 counter
计算 counter + 1
写回 counter
```

如果普通共享变量在 C++ 中这样被并发读写且没有同步，可能构成数据竞争，程序行为未定义；上面的拆解只是帮助理解，不能把它当成所有实际执行的完整描述。

再看一个**没有数据竞争、但仍然有逻辑竞态**的例子：

```cpp
std::atomic<int> stock{1};

bool buy() {
    if (stock.load() > 0) {
        stock.fetch_sub(1);
        return true;
    }
    return false;
}
```

每一次原子访问都合法，但整个购买操作不具备原子性：

| 步骤 | 线程 A | 线程 B | 库存 |
|---|---|---|---:|
| 1 | 读取，发现库存为 1 | | 1 |
| 2 | | 读取，发现库存为 1 | 1 |
| 3 | 原子减 1，返回成功 | | 0 |
| 4 | | 原子减 1，返回成功 | -1 |

**原子变量只能保证相应原子操作的语义，不能自动保证一段业务流程正确。**

修复方向可以是：

- 用同一把锁包住“检查 + 扣减”。
- 用 CAS 循环实现有条件扣减。
- 对数据库库存，用满足条件的原子更新，并检查受影响行数。

关键是找到整个操作的**生效点**：系统究竟在哪一个瞬间决定“这次购买成功”。

## 5. 第四步：建立 happens-before，而不是凭时间猜测

并发分析中，一个重要工具是 **happens-before，先行发生关系**。

它描述的是由语言和同步机制保证的执行顺序、内存可见性关系，不能简单理解成“日志时间戳更早”。

例如，针对同一把互斥锁：

```text
线程 A：
拿锁 → 写入状态 → 解锁

线程 B：
随后成功拿到这把锁 → 读取状态
```

锁建立了必要的同步关系。

分析时要问：

> 线程 A 发布了数据，线程 B 依靠什么同步机制确认数据已经发布，并能安全读取？

常见答案包括互斥锁、线程启动与等待、具有相应语义的原子操作，以及语言或库明确规定的消息传递机制。

下面这些通常不能替代正确同步：

- “A 应该比 B 快。”
- “我已经等了 100 毫秒。”
- “日志显示 A 先输出。”
- “这个变量加了 `volatile`。”——在 C/C++ 中，它不能代替线程同步。
- “在我的机器上一直正常。”

分析时可以把事件视为图中的节点，把**线程内部顺序和同步保证**画成边。两个冲突访问之间如果缺少必要的顺序约束，就要继续检查是否构成数据竞争或逻辑错误。

## 6. 真正排查时，怎样提高命中率

### 6.1 先按症状缩小范围

| 症状        | 优先检查                   |
| --------- | ---------------------- |
| 偶发崩溃、内存损坏 | 数据竞争、越界、释放后访问、对象复用     |
| 结果偶尔错误    | 检查与执行分离、丢失更新、旧结果覆盖新结果  |
| 永久卡住      | 锁循环、通知遗漏、等待条件不可能满足     |
| 仅高负载发生    | 队列积压、资源耗尽、超时与取消交错      |
| 仅退出时发生    | 后台任务未退出、析构顺序、回调访问已释放对象 |
| 开启日志后消失   | 时序敏感问题；日志改变了调度和同步行为    |

这些只是入口，不能仅凭症状确定原因。

### 6.2 把随机交错变成可控交错

普通压力测试是“多运行，等撞上”；更有效的方法是**主动控制关键事件的顺序**。

例如，要复现上面的库存错误：

1. 线程 A 检查库存后，在测试屏障处等待。
2. 线程 B 也检查库存，进入同一个屏障。
3. 两个线程都检查完成后，再放行扣减。
4. 断言成功次数和最终库存。

这样可以稳定构造：

```text
A 检查 → B 检查 → A 扣减 → B 扣减
```

常用手段包括：

- 在关键步骤加入测试专用屏障、事件或调度钩子。
- 控制网络响应、数据库返回和异步回调的完成顺序。
- 在取消、超时、关闭、重试等边界注入故障。
- 用随机延迟和 `yield` 扩大交错范围，并记录随机种子。

**随机种子通常只能复现注入策略，不能保证操作系统调度完全相同。** 想严格复现，需要进一步控制或记录调度和外部事件。

不要把增加 `sleep` 当成修复。它最多帮助暴露或暂时掩盖问题。

### 6.3 记录能还原因果关系的日志

只记录：

```text
开始操作
操作完成
```

通常不够。更有用的是记录：

```text
任务 ID、线程 ID、对象 ID
操作类型、阶段
读到的版本、准备提交的版本
取消请求、取消确认、实际退出
锁等待、锁获取、锁释放
```

例如，排查旧响应覆盖新响应：

```text
request=41 query=A start
request=42 query=B start
request=42 result=B commit
request=41 result=A commit
```

这里问题很清楚：**请求发出顺序和结果提交顺序不一致，而提交时没有判断结果是否过期。**

日志也会扰动调度；日志中的时间先后不能单独证明内存同步关系。

## 7. 工具分别能抓什么

工具应当分层使用：

| 工具类型                       | 擅长发现                | 局限                     |
| -------------------------- | ------------------- | ---------------------- |
| 数据竞争检测器，如 ThreadSanitizer  | 实际执行路径中的未同步内存冲突     | 不能证明没有逻辑竞态；没执行到的路径可能漏掉 |
| 内存错误检测器，如 AddressSanitizer | 释放后访问、越界等           | 不直接判断业务并发规则            |
| 调试器线程栈、线程转储                | 死锁、阻塞、异常现场          | 单个快照难以说明整个过程           |
| 调度与性能追踪                    | 锁竞争、线程等待、任务迁移、长时间停顿 | 需要结合正确性要求分析            |
| 系统化调度测试、模型检查               | 枚举或探索多种交错，生成反例      | 受模型范围、状态空间和运行环境限制      |
| 应用级历史校验                    | 请求历史是否符合业务对象的顺序语义   | 需要准确的规格和完整的事件记录        |

要记住：

**检测器报告“没有数据竞争”，不等于系统并发逻辑正确。压力测试通过，也不等于所有交错都正确。**

## 8. 死锁要用另一套分析视角

排查死锁，核心是建立**等待关系**：

| 线程  | 已持有  | 正等待  |
| --- | ---- | ---- |
| A   | 锁 L1 | 锁 L2 |
| B   | 锁 L2 | 锁 L1 |

它形成等待环。

但等待的对象不一定是锁，也可能是：

- 主线程等待工作线程退出，工作线程等待主线程处理回调。
- 线程持锁等待任务完成，而任务也需要这把锁。
- 消费者等待消息，生产者已经退出。
- 队列已满，发送者等待空位，但接收者正在等待发送者结束。

实际卡住时，先抓取**所有相关线程的栈和等待对象**；必要时连续抓取几次，判断是完全不动、缓慢推进，还是持续重试。

修复也不能只靠“换成递归锁”或“加超时”。要消除等待环、调整资源获取顺序，或重新安排任务依赖。

## 9. 修复后，要同时验证三件事

一个并发修复需要回答：

1. **安全性**：原来的错误交错是否已经被禁止，或者即使出现也不会破坏不变量？
2. **进展性**：是否引入死锁、饥饿、无限重试或无法结束的取消？
3. **代价**：锁范围扩大后，是否造成不可接受的等待、吞吐下降或尾延迟？

比较可靠的验证组合是：

- 原始反例能够稳定复现，修复后通过。
- 检查相关路径中的数据竞争和内存错误。
- 覆盖失败、取消、超时、关闭等生命周期边界。
- 根据改动范围，再做适量压力测试和性能检查。

尤其要避免：修复正常路径，却遗漏异常退出时没有解锁、没有通知或没有完成状态转换。

## 10. 可以直接使用的分析模板

每次遇到并发问题，按下面七项写：

```text
1. 正确性要求：
   哪个不变量被破坏？哪个任务无法取得进展？

2. 参与者：
   哪些线程、任务、回调参与？

3. 共享状态：
   哪些内存、对象、数据库记录或外部资源被共同访问？

4. 同步与生命周期：
   用什么建立顺序、可见性和存活保证？

5. 最小反例：
   A1 → B1 → B2 → A2，具体怎样导致错误？

6. 修复机制：
   哪个同步边、原子操作、版本检查或状态转换消除了反例？

7. 验证：
   怎样稳定重现旧错误，并验证修复后的安全性和进展性？
```

对你正在做的解析库，也可以用这套方法分析：如果一个 `JsonDocument` 被多个任务共享，就要分别检查**节点访问、Arena 分配、文档销毁**的并发规则。即使节点已经只读，另一个线程提前销毁文档，仍然会破坏所有节点和字符串引用的有效性。
