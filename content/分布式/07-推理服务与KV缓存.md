# 推理服务与 KV 缓存：从训练吞吐到用户延迟

[返回总览](./分布式大模型.md)

## 一次请求的两个阶段

用户发来提示词后，**Prefill** 一次处理输入 token，建立各层注意力需要的 KV cache，并生成第一个输出 token；随后 **Decode** 逐步生成新 token，每步读取已有缓存并写入新 token 的 K/V。

Prefill 通常更容易利用矩阵计算；Decode 在常见批量与硬件配置下常受权重/KV 读取带宽限制，但不能把“Prefill 必定计算受限、Decode 必定带宽受限”当作无条件定律。

**KV cache** 是已处理 token 的 key/value，不是模型权重。上下文越长、并发请求越多，占用显存通常越大；保留它可避免每生成一个 token 都重算全部历史上下文。

## 服务端调度什么

- **Batching**：把多个请求合在一起运行以提高吞吐；静态批次要等请求一起结束，持续批处理可在生成过程中加入或移出请求。
- **PagedAttention / 分页式 KV 管理**：以块管理缓存，减少因不同请求长度造成的分配浪费；不是减少模型权重大小。
- **Prefix caching**：复用相同前缀已经算出的 KV；前缀不相同则无法直接复用。
- **Speculative decoding**：先提出候选 token，再由目标模型验证；只有验证通过的结果才作为目标模型输出，收益取决于接受率和验证开销。
- **Prefill/Decode 分离**：将两个阶段分到不同资源池，利于各自调度，但 KV 传输也有成本。

训练往往首先衡量单位时间处理多少 token；在线服务还要衡量首 token 延迟（TTFT）、后续 token 延迟、吞吐和成本。**SLO** 是约定的服务目标，例如一定比例请求的延迟上限；提高批量吞吐不应无视等待队列中的用户。
