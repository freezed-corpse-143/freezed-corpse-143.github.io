# 推理服务与 KV 缓存：从训练吞吐到用户延迟

[返回总览](./分布式大模型.md)

## 一次请求的两个阶段

用户发来提示词后，**Prefill** 一次处理输入 token，建立各层注意力需要的 KV cache，并生成第一个输出 token；随后 **Decode** 逐步生成新 token，每步读取已有缓存并写入新 token 的 K/V。

Prefill 通常更容易利用矩阵计算；Decode 在常见批量与硬件配置下常受权重/KV 读取带宽限制，但不能把“Prefill 必定计算受限、Decode 必定带宽受限”当作无条件定律。

**KV cache** 是已处理 token 的 key/value，不是模型权重。上下文越长、并发请求越多，占用显存通常越大；保留它可避免每生成一个 token 都重算全部历史上下文。

## 服务端调度什么

- **Batching**：把多个请求合在一起运行以提高吞吐；静态批次要等请求一起结束，持续批处理可在生成过程中加入或移出请求。
- **PagedAttention / 分页式 KV 管理**：以块管理缓存，减少因不同请求长度造成的分配浪费；不是减少模型权重大小。
- **Prefix caching**：复用相同前缀已经算出的 KV；前缀不相同则无法直接复用。
- **Speculative decoding**：先提出候选 token，再由目标模型验证；只有验证通过的结果才作为目标模型输出，收益取决于接受率和验证开销。
- **Prefill/Decode 分离**：将两个阶段分到不同资源池，利于各自调度，但 KV 传输也有成本。

训练往往首先衡量单位时间处理多少 token；在线服务还要衡量首 token 延迟（TTFT）、后续 token 延迟、吞吐和成本。**SLO** 是约定的服务目标，例如一定比例请求的延迟上限；提高批量吞吐不应无视等待队列中的用户。

## 动态组批与持续批处理有什么区别

假设请求 A 要生成 2 个 token，B 要生成 20 个 token。如果固定批次一直等两者都结束，A 完成后留下的计算位置无法及时给新请求 C 用。**Dynamic batching（动态组批）**根据当前队列在运行时把请求组合成批次，而不是事先固定成员；**continuous batching（持续/迭代级批处理）**更进一步，在生成的迭代之间让已完成的请求离开、新请求加入。各实现对两种叫法可能有交叠，关键是看**何时允许批次成员改变**。

组得太小，GPU 工作不饱和；为凑大批次等太久，用户首 token 延迟（TTFT）上升。调度器要在吞吐、排队时间和显存容量之间取舍，而不是无限制把请求塞进一批。

## KV cache 占满显存怎么办

**KV cache management** 管的是当前请求和可复用前缀的缓存块：请求生成越长，每步还要为新 token 分配空间；上文的分页式管理使块分配更灵活，却不意味着容量无限。**KV cache eviction（淘汰）**指空间紧张时释放已缓存的内容：

- 已结束请求的缓存可以释放；不再有人引用的共享前缀缓存也可按策略淘汰，下次相同前缀到来就重新计算，失去缓存带来的加速。
- 正在生成的请求若丢失历史 KV，不能假装历史从未存在而继续解码；必须保留、迁移到其他存储再取回，或从仍可用的输入重新计算。资源仍不足时，应限流、排队或按服务策略中止请求。

所以“前缀缓存淘汰”主要损失命中率，“活动请求缓存淘汰”还涉及结果正确性与恢复开销。

## 推理也需要模型并行吗

需要时与训练共享“拆哪里”的思路，但推理通常不存训练梯度和优化器状态（[并行方式详解](./01-显存与模型并行.md)）：

- **TP**：同一层权重放不进单卡时跨卡切分，每生成一次 token 都可能等待层内通信；不能只看参数是否放得下。
- **PP**：不同设备负责不同层，请求的激活依次经过多个阶段；批量不足时某些阶段会等待，单请求延迟也受跨阶段传输影响。
- **EP**：MoE 专家分布到多卡，推理时按路由结果把 token 发给目标专家再取回；热门专家和 All-to-All 依旧可能成为瓶颈。

如果单卡放得下且能达到延迟目标，多个**独立模型副本**并行接收不同请求通常比拆一个请求更简单；只有显存或吞吐需求需要时再跨卡拆模型。Prefill/Decode 分离则是按**请求阶段**放置计算，与按权重/层/专家拆模型不是同一维度。
