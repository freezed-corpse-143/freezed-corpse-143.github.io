# 计算与利用率：为什么 GPU 会空等

[返回总览](./分布式大模型.md)

## 算得多不等于算得快

训练计算量随模型参数量和训练 token 数增加；粗略估算常写作 $\text{FLOPs}\propto P\times T$，其中 $P$ 是参数数，$T$ 是训练 token 数。这是工作量估算，不是每一步的精确耗时公式。

一个训练 step 包括取数据、前向、反向、跨卡同步、更新参数。若某张卡做完计算却要等最慢的卡完成同步，额外算力并不会自动缩短这一步。

## 三个容易混淆的量

- **GPU utilization（设备忙碌率）**：设备在采样窗口内是否忙；忙于低效小算子也可能很高。
- **吞吐量**：单位时间处理的训练 token 或样本数；比较时要固定模型、序列长度等工作负载。
- **MFU（模型 FLOPs 利用率）**：模型有效计算的估算 FLOPs/s 除以所用硬件的理论峰值 FLOPs/s；依赖统计口径和硬件精度峰值，不能直接与设备忙碌率画等号。

## 看一次慢 step

假设一个 step 中计算用 60 ms，通信与等待用 40 ms，那么总时间至少约 100 ms；即便将计算缩短到 30 ms，若其余部分不变，总时间也只降到约 70 ms。实际执行可重叠通信和计算，因此各项耗时不能总是直接相加。

排查时先看 step 时间，再区分计算、通信、数据读取、流水线空泡与检查点写入。**目标不是让监控图上的 GPU 忙碌率好看，而是让同一工作负载完成得更快。**

## GPU 到底在等什么

一次训练 step 不只是矩阵乘法。CPU/数据加载进程先从存储读取样本并整理成批次（**data pipeline**）；GPU 执行前向与反向时会调用许多计算程序；分布式进程之间还要交换张量。监控中出现空档，可按下面的现象定位，而不是一律归咎于 GPU 太慢：

| 术语 | 在等什么或花时间做什么 |
| --- | --- |
| CPU / 数据 I/O | CPU 解码、预处理或存储读取没跟上，GPU 暂时拿不到下一批数据 |
| Kernel launch | CPU/运行时把一次 GPU 计算任务提交给设备的启动过程；许多极短的小算子可能让启动开销显眼 |
| PCIe / NVLink / 网络 | 参数、梯度或激活在相应链路上传输；慢链路或拥塞让计算等待数据 |
| NCCL | GPU 间集体通信库正在组织或执行同步；等待的原因可能是链路慢，也可能是其他进程尚未到达同一通信操作 |
| Pipeline stage / bubble | 当前流水线阶段没有待处理的微批次，发生空泡；见[流水线阶段与空泡](./01-显存与模型并行.md) |
| Checkpoint | 将可恢复的训练状态写到存储；同步写入会影响 step，异步写入也会竞争带宽或内存 |

**Kernel（GPU 内核）**是一段在 GPU 上执行的计算程序，例如矩阵乘法或逐元素运算；**kernel launch** 是提交该程序运行，不等于开始一个新操作系统进程，更不是启动整个模型。如果一次计算很短、启动次数很多，可通过算子融合或批量化减少相对开销；如果真正瓶颈是跨节点网络，这样做帮助有限。
