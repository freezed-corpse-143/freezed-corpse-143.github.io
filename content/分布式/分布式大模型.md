一个很重要的认识是：

> **大规模 LLM 系统的核心问题，不只是“如何把模型分到很多 GPU 上”，而是如何把一个巨大的计算任务映射到一个异构、昂贵、通信受限、会故障、性能动态变化的分布式机器上，并长期维持高吞吐和高利用率。**

# 模型过大：Memory Wall

这是最直接的问题。

假设一个模型有 $P$ 个参数，BF 16 参数本身大约需要：

$$ 2P\ \text{bytes} $$

但训练时远远不止参数：

$$ \text{Memory} = \text{Parameters} +\text{Gradients} +\text{Optimizer States} +\text{Activations} +\text{Buffers} $$

例如 Adam 通常还需要维护一阶、二阶动量以及可能的 FP 32 master weights。

所以一个 100 B 模型：

$$ 100B\times2B = 200GB $$

仅仅权重就已经无法放进单张 GPU。

训练内存更可能达到 **TB 级**。

于是产生第一组技术：

**模型怎么拆？**

$$ \boxed{ DP,\ TP,\ PP,\ CP/SP,\ EP,\ ZeRO/FSDP } $$

也就是：

- Data Parallelism
- Tensor Parallelism
- Pipeline Parallelism
- Context / Sequence Parallelism
- Expert Parallelism
- ZeRO / Fully Sharded Data Parallel

这是你以后学习分布式 LLM 的第一条主线：

> **Parallelism Strategy。**

# 计算很贵：Compute Wall

即使模型能装下，计算量也巨大。

Transformer 训练粗略可以理解成：

$$ \text{Training FLOPs} \propto N_{\text{parameters}} \times N_{\text{tokens}} $$

例如一个大模型训练可能需要：

$$ 10^{24}\sim10^{26}\ \text{FLOPs} $$

所以问题变成：

> 如何让几千、几万张 GPU 尽可能一直做有效计算？

这里出现一个非常重要的指标：

$$ \boxed{\text{MFU — Model FLOPs Utilization}} $$

理想状态：

```
GPU:

████████████████████████████
compute compute compute compute
```

现实：

```
GPU:

██████░░███░░░░██████░░██░░
compute wait comm wait compute
```

GPU 可能大量时间在等待：

- 数据
- NCCL
- CPU
- PCIe
- NVLink
- 网络
- pipeline stage
- checkpoint
- kernel launch

因此：

> **GPU utilization ≠ GPU useful utilization**

GPU 显示 100% utilization，也不意味着 MFU 很高。

# 通信比计算重要

现代 GPU 计算增长非常快，但跨设备通信没有同比例增长。

一个节点内部可能是：

```
GPU ─ NVLink ─ GPU
 │              │
NVSwitch      NVSwitch
 │              │
GPU ─ NVLink ─ GPU
```

速度可能达到数百 GB/s。

但跨节点变成：

```
GPU
 │
PCIe
 │
NIC
 │
InfiniBand / RoCE
 │
Switch
 │
NIC
 │
GPU
```

再跨数据中心：

```
Datacenter A
     │
 WAN
     │
Datacenter B
```

延迟、带宽可能差几个数量级。

于是：

$$ T_{\text{step}} = T_{\text{compute}} + T_{\text{communication}} + T_{\text{bubble}} + T_{\text{I/O}} + T_{\text{sync}} $$

真正优化目标不是单纯提高 FLOPS，而是：

$$ \boxed{\min T_{\text{step}}} $$

这也是为什么你之后必须理解：

- AllReduce
- AllGather
- ReduceScatter
- All-to-All
- Broadcast
- Ring
- Tree
- Hierarchical Collective
- NCCL
- RDMA
- GPUDirect RDMA
- InfiniBand / RoCE

尤其 MoE 带来了非常典型的：

$$ \boxed{\text{All-to-All bottleneck}} $$

# 物理机器是异构的：Heterogeneity



$$ \text{heterogeneity} = \begin{cases} GPU\\ CPU\\ Memory\\ Network\\ Topology\\ Software\\ Geography \end{cases} $$

比如一个集群可能同时存在：

```
H100 80GB
H200 141GB
B200
A100 80GB
A100 40GB
```

甚至节点内部：

```
Node A
8 × H100
NVSwitch

Node B
8 × A100
PCIe

Node C
4 × H100
```

如果简单同步训练：

```
Fast GPU: ████████ wait wait wait
Slow GPU: ██████████████████
```

整个系统速度由：

$$ \boxed{\text{slowest worker}} $$

决定。

这叫 **straggler problem**。

因此异构调度本身就是一个巨大研究领域。

甚至：

$$ Latency(GPU_i,GPU_j) $$

因此逻辑并行策略：

> **通信最密集的并行维度放到最快的物理连接上。**

$$ \boxed{ \text{Logical Parallelism} \rightarrow \text{Physical Topology Mapping} } $$

# 系统会坏：Failure Wall

$$ \boxed{\text{Fault Tolerance}} $$

当 GPU 数量很少：

> GPU 坏掉是异常。

当 GPU 数量达到 10,000：

> **GPU 坏掉是正常系统状态。**

假设单节点平均故障间隔 MTBF 为：

$$ 10000\text{ hours} $$

如果有 10,000 个节点，粗略理解，整个集群发生某个故障的时间尺度可能已经接近：

$$ \frac{10000}{10000} \approx 1\text{ hour} $$

所以大规模训练不能假设：

```
start
↓
train 3 months
↓
finish
```

而应该假设：

```
train
 ↓
failure
 ↓
recover
 ↓
train
 ↓
failure
 ↓
recover
 ↓
...
```

因此需要：

- Checkpoint
- Distributed checkpoint
- Incremental checkpoint
- Async checkpoint
- Elastic training
- Worker replacement
- Optimizer-state recovery
- RNG-state recovery
- Data-loader state recovery

目标从：

> 不发生故障

变成：

> **故障发生时尽量少损失训练进度。**

于是有一个很漂亮的系统问题：

$$ \boxed{ \text{Checkpoint Frequency} \leftrightarrow \text{Checkpoint Cost} \leftrightarrow \text{Failure Probability} } $$

checkpoint 太频繁 → 浪费大量 I/O。

checkpoint 太少 → 一次故障损失几个小时训练。

# 训练本身的数学故障

这和机器坏掉完全不同。

比如：

```
Loss
 │
 │          ╱
 │        ╱
 │      ╱
 │____╱
 └──────────── step
```

可能出现：

- loss spike
- NaN
- gradient explosion
- optimizer instability
- numerical overflow
- corrupted batch
- bad data shard

这时候：

> 机器全部正常，但训练已经废了。

所以训练系统还需要：

$$ \boxed{\text{Training Health Monitoring}} $$

监控：

- loss
- gradient norm
- activation norm
- learning rate
- NaN / Inf
- GPU error
- throughput
- MFU
- communication latency

甚至自动：

```
detect anomaly
      ↓
identify bad step
      ↓
rollback checkpoint
      ↓
skip corrupted data
      ↓
resume training
```

这已经接近一个**自治分布式系统**。

# 推理的新问题：Serving Wall

训练主要追求：

$$ \boxed{\text{Throughput}} $$

而在线推理同时关注：

$$ \boxed{ Latency + Throughput + Cost + SLO } $$

例如用户请求：

```
Request
   ↓
Prefill
   ↓
Decode
   ↓
Token
   ↓
Token
   ↓
Token
```

这里最大的特点是：

**Prefill 和 Decode 完全不同。**

Prefill：

$$ \text{Compute-bound} $$

Decode：

$$ \text{Memory-bandwidth-bound} $$

同时还有一个巨大问题：

$$ \boxed{\text{KV Cache}} $$

于是推理系统需要处理：

- Continuous batching
- Dynamic batching
- PagedAttention
- KV cache management
- KV cache eviction
- Prefix caching
- Speculative decoding
- Tensor Parallel
- Pipeline Parallel
- Expert Parallel
- Prefill/Decode disaggregation

最终变成：

```
    Requests
           │
       Scheduler
           │
   ┌───────┴──────┐
   │              │
Prefill Pool   Decode Pool
   │              │
GPU GPU        GPU GPU GPU
```

因此 **LLM Training Systems** 和 **LLM Serving Systems** 到后面其实是两个很大的研究方向。

# 重新组织方向

你原来的观察可以形成这样一张完整地图：

```
                Large Scale LLM Systems
                         │
        ┌────────────────┼────────────────┐
        │                │                │
      Model           Hardware         Cluster
        │                │                │
   Huge Model       GPU/CPU/NIC      Thousands GPUs
        │                │                │
        ▼                ▼                ▼
 Parallelism       Heterogeneity     Fault Tolerance
 DP/TP/PP/EP       GPU/Network       Checkpoint
 ZeRO/FSDP         Topology          Elasticity
        │                │                │
        └───────────┬────┴────────────────┘
                    │
                Communication
                    │
         NCCL / RDMA / Collective
                    │
                    ▼
                Scheduling
                    │
        Placement / Load Balance
        Straggler / Utilization
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       Training             Serving
          │                   │
    Loss Stability       KV Cache
    Checkpoint           Batching
    Optimizer            Latency
    Data Pipeline        Throughput
```

你可以把整个领域记成一个非常简单的公式：

$$ \boxed{ \text{LLM Systems} = \text{Parallelism} + \text{Communication} + \text{Memory} + \text{Scheduling} + \text{Fault Tolerance} + \text{Numerical Stability} } $$

然后分别在 **Training** 和 **Inference** 两个场景中研究它们。
