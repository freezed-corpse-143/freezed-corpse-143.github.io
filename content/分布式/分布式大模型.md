一个很重要的认识是：

> **大规模 LLM 系统的核心问题，不只是“如何把模型分到很多 GPU 上”，而是如何把一个巨大的计算任务映射到一个异构、昂贵、通信受限、会故障、性能动态变化的分布式机器上，并长期维持高吞吐和高利用率。**

# 模型过大：Memory Wall

这是最直接的问题。

假设一个模型有 $P$ 个参数，BF 16 参数本身大约需要：

$$ 2P\ \text{bytes} $$

但训练时远远不止参数：

$$ \text{Memory} = \text{Parameters} +\text{Gradients} +\text{Optimizer States} +\text{Activations} +\text{Buffers} $$

例如 Adam 通常还需要维护一阶、二阶动量以及可能的 FP 32 master weights。

所以一个 100 B 模型：

$$ 100B\times2B = 200GB $$

仅仅权重就已经无法放进单张 GPU。

训练内存更可能达到 **TB 级**。

于是产生第一组技术：

**模型怎么拆？**

$$ \boxed{ DP,\ TP,\ PP,\ CP/SP,\ EP,\ ZeRO/FSDP } $$

也就是：

- Data Parallelism
- Tensor Parallelism
- Pipeline Parallelism
- Context / Sequence Parallelism
- Expert Parallelism
- ZeRO / Fully Sharded Data Parallel

这是你以后学习分布式 LLM 的第一条主线：

> **Parallelism Strategy。**

# 计算很贵：Compute Wall

即使模型能装下，计算量也巨大。

Transformer 训练粗略可以理解成：

$$ \text{Training FLOPs} \propto N_{\text{parameters}} \times N_{\text{tokens}} $$

例如一个大模型训练可能需要：

$$ 10^{24}\sim10^{26}\ \text{FLOPs} $$

所以问题变成：

> 如何让几千、几万张 GPU 尽可能一直做有效计算？

这里出现一个非常重要的指标：

$$ \boxed{\text{MFU — Model FLOPs Utilization}} $$

理想状态：

```
GPU:

████████████████████████████
compute compute compute compute
```

现实：

```
GPU:

██████░░███░░░░██████░░██░░
compute wait comm wait compute
```

GPU 可能大量时间在等待：

- 数据
- NCCL
- CPU
- PCIe
- NVLink
- 网络
- pipeline stage
- checkpoint
- kernel launch

因此：

> **GPU utilization ≠ GPU useful utilization**

GPU 显示 100% utilization，也不意味着 MFU 很高。

# 通信比计算重要

现代 GPU 计算增长非常快，但跨设备通信没有同比例增长。

一个节点内部可能是：

```
GPU ─ NVLink ─ GPU
 │              │
NVSwitch      NVSwitch
 │              │
GPU ─ NVLink ─ GPU
```

速度可能达到数百 GB/s。

但跨节点变成：

```
GPU
 │
PCIe
 │
NIC
 │
InfiniBand / RoCE
 │
Switch
 │
NIC
 │
GPU
```

再跨数据中心：

```
Datacenter A
     │
 WAN
     │
Datacenter B
```

延迟、带宽可能差几个数量级。

于是：

$$ T_{\text{step}} = T_{\text{compute}} + T_{\text{communication}} + T_{\text{bubble}} + T_{\text{I/O}} + T_{\text{sync}} $$

真正优化目标不是单纯提高 FLOPS，而是：

$$ \boxed{\min T_{\text{step}}} $$

这也是为什么你之后必须理解：

- AllReduce
- AllGather
- ReduceScatter
- All-to-All
- Broadcast
- Ring
- Tree
- Hierarchical Collective
- NCCL
- RDMA
- GPUDirect RDMA
- InfiniBand / RoCE

尤其 MoE 带来了非常典型的：

$$ \boxed{\text{All-to-All bottleneck}} $$

# 物理机器是异构的：Heterogeneity



$$ \text{heterogeneity} = \begin{cases} GPU\\ CPU\\ Memory\\ Network\\ Topology\\ Software\\ Geography \end{cases} $$

比如一个集群可能同时存在：

```
H100 80GB
H200 141GB
B200
A100 80GB
A100 40GB
```

甚至节点内部：

```

```

如果简单同步训练：

```
Fast GPU: ████████ wait wait wait
Slow GPU: ██████████████████
```

整个系统速度由：

$$ \boxed{\text{slowest worker}} $$

决定。

这叫 **straggler problem**。

因此异构调度本身就是一个巨大研究领域。

# 系统不可靠：Reliability / Failure Wall

> **大规模系统中的 failure 是跨越硬件、通信、软件、数值状态和训练语义的多层异常。**

随着训练规模从几十张 GPU 扩展到几千甚至几万张 GPU，我们不能再假设底层系统始终正确。

系统可能发生的异常大致可以分成四层：

## Fail-stop：显式硬件/节点故障

这是最容易理解的一类：

```
GPU failure
CPU failure
DRAM failure
NIC failure
SSD failure
Power failure
Switch failure
Node crash
```

例如某张 GPU 直接掉卡：

```
GPU 0 ─ GPU 1 ─ GPU 2 ─ GPU 3
                  X
                failed
```

对于同步分布式训练：

$$ \text{step}_{t} = \operatorname{Sync}(GPU_0,\ldots,GPU_N) $$

只要其中一个 participant 消失，collective communication 就可能无法继续。

这类故障通常具有一个好处：

$$ \boxed{\text{Failure is explicit}} $$

系统知道“出问题了”。

因此主要解决：

- failure detection
- worker eviction
- worker replacement
- communicator reconstruction
- elastic membership
- checkpoint recovery
- job rescheduling

## Communication Failure：通信系统异常

机器本身可能没有坏，但**机器之间的连接出了问题**。

例如：

```
GPU ─ NIC ─ Switch ─ Switch ─ NIC ─ GPU
       │       │
       X       X
```

可能出现：

- packet loss
- link failure
- congestion
- timeout
- RDMA error
- NIC reset
- switch failure
- routing change
- collective hang

甚至并不完全断开，而只是：

$$ Bandwidth: 400Gbps \rightarrow 80Gbps $$

于是一个 worker 没有死亡，却突然成为 straggler：

```
GPU 0 ████████
GPU 1 ████████
GPU 2 ████████████████████
       ↑
   slow network
```

因此通信故障又可以区分：

$$ \boxed{ \text{Hard Failure} \quad vs \quad \text{Performance Degradation} } $$

后者尤其难处理，因为系统**还能运行，只是运行得越来越差**。

## Detected Numerical Failure：显式数值异常

第三类非常重要：

> **硬件没有坏，程序也没有 crash，但训练数学状态已经异常。**

例如：

$$ \text{Loss}=3.2 \rightarrow3.0 \rightarrow2.9 \rightarrow \boxed{\mathrm{NaN}} $$

或者：

$$ \|\nabla L\| \rightarrow \infty $$

包括：

- NaN / Inf
- FP overflow / underflow
- gradient explosion
- loss spike
- optimizer instability
- numerical instability
- corrupted activation
- bad training batch

这种情况下：

```
GPU      ✓
Network  ✓
Process  ✓
NCCL     ✓

Training ✗
```

所以传统分布式系统意义上的 **fault tolerance 并不够**。

还必须有：

$$ \boxed{\text{Training-state fault detection}} $$

例如监控：

$$ L_t,\quad \|\nabla L_t\|,\quad \|W_t\|,\quad \|A_t\| $$

检测异常之后：

```
detect anomaly
      ↓
locate bad step
      ↓
rollback
      ↓
possibly skip bad data
      ↓
restore optimizer / RNG / dataloader
      ↓
resume
```

## Silent Data Corruption：隐式错误

这可能是最危险的一类。

硬件没有报告错误：

```
GPU      ✓
CPU      ✓
NIC      ✓
NCCL     ✓
Process  ✓
Loss     看起来也正常
```

但某个地方：

$$ 0 \rightarrow 1 $$

发生了一个 bit flip。

例如原本某个浮点数：

$$ x=0.03125 $$

由于 memory、interconnect、GPU computation 等路径上的 silent error，最终得到：

$$ \tilde{x}=0.03174 $$

系统没有 crash，甚至 loss 在短期内可能仍然正常。

于是：

```
correct state
     │
     │ silent corruption
     ▼
corrupted state
     │
     ▼
forward
     │
     ▼
backward
     │
     ▼
optimizer
     │
     ▼
corruption propagates
```

这类问题一般可以放在：

$$ \boxed{\text{SDC — Silent Data Corruption}} $$

这个概念下理解。

来源可能包括：

- DRAM / HBM bit flip
- arithmetic error
- transient hardware fault
- corrupted communication
- DMA / PCIe / network path error
- storage corruption
- software bug

其中一些错误能被 ECC、CRC、协议校验等发现。

真正麻烦的是：

$$ \boxed{\text{undetected corruption}} $$

因为系统可能继续训练数小时甚至数天。

## 总结

因此，我们可以把“大规模训练 Failure”重新画成：

```
                    System Failure
                          │
       ┌──────────────────┼──────────────────┐
       │                  │                  │
   Hardware          Communication       Numerical
       │                  │                  │
 GPU/CPU/HBM         NIC/Switch          NaN / Inf
 Node/SSD            RDMA/NCCL           Loss spike
 Power               Congestion          Divergence
       │                  │                  │
       └──────────────────┼──────────────────┘
                          │
                   Silent Failure
                          │
                    Bit corruption
                    Silent compute
                    Silent comm.
                    State corruption
```

|                        | **Detected**                       | **Undetected / Silent**     |
| ---------------------- | ---------------------------------- | --------------------------- |
| **Hardware**           | GPU crash、ECC uncorrectable error | silent bit flip             |
| **Communication**      | timeout、link down、NCCL error     | corrupted message           |
| **Numerical**          | NaN、Inf、loss explosion           | subtle numerical corruption |
| **Training semantics** | 明显 divergence                    | 模型质量悄悄下降            |

## 重新理解 Checkpoint

之前我们说：

$$ \text{Checkpoint Frequency} \leftrightarrow \text{Checkpoint Cost} \leftrightarrow \text{Failure Probability} $$

其实还不够。

真实问题更接近：

$$ \boxed{ \text{Recovery} = f( \text{Detection Latency}, \text{Checkpoint Interval}, \text{Checkpoint Cost}, \text{Failure Type}, \text{Corruption Propagation} ) } $$

比如：

```
t0        t1        t2        t3        t4
│---------│---------│---------│---------│
CKPT      CKPT      CKPT      CKPT      detect
                     ↑
                  corruption
```

如果 $t_2$ 发生 silent corruption，直到 $t_4$ 才发现，那么：

> ** $t_3$ 的 checkpoint 可能本身已经被污染。**

所以并不是简单：

> 出问题 → 读取最近 checkpoint。

而是：

> **首先判断最近哪个 checkpoint 是可信的。**

这就把问题从普通的 **Fault Tolerance** 推到了更广义的：

$$ \boxed{ \textbf{Reliability + Resilience + Correctness} } $$

我认为这是更适合我们后续学习的框架。下一步如果继续深入这一章，值得专门拆解 **“Detect → Localize → Contain → Recover → Resume”** 这条完整容错流水线，因为 checkpoint、elastic training、冗余计算、ECC/CRC、健康监控、自动 rollback 等技术都可以自然挂到这五个阶段下面。

# 训练本身的数学故障

这和机器坏掉完全不同。

比如：

```
Loss
 │
 │          ╱
 │        ╱
 │      ╱
 │____╱
 └──────────── step
```

可能出现：

- loss spike
- NaN
- gradient explosion
- optimizer instability
- numerical overflow
- corrupted batch
- bad data shard

这时候：

> 机器全部正常，但训练已经废了。

所以训练系统还需要：

$$ \boxed{\text{Training Health Monitoring}} $$

监控：

- loss
- gradient norm
- activation norm
- learning rate
- NaN / Inf
- GPU error
- throughput
- MFU
- communication latency

甚至自动：

```
detect anomaly
      ↓
identify bad step
      ↓
rollback checkpoint
      ↓
skip corrupted data
      ↓
resume training
```

这已经接近一个**自治分布式系统**。

# 推理的新问题：Serving Wall

训练主要追求：

$$ \boxed{\text{Throughput}} $$

而在线推理同时关注：

$$ \boxed{ Latency + Throughput + Cost + SLO } $$

例如用户请求：

```
Request
   ↓
Prefill
   ↓
Decode
   ↓
Token
   ↓
Token
   ↓
Token
```

这里最大的特点是：

**Prefill 和 Decode 完全不同。**

Prefill：

$$ \text{Compute-bound} $$

Decode：

$$ \text{Memory-bandwidth-bound} $$

同时还有一个巨大问题：

$$ \boxed{\text{KV Cache}} $$

于是推理系统需要处理：

- Continuous batching
- Dynamic batching
- PagedAttention
- KV cache management
- KV cache eviction
- Prefix caching
- Speculative decoding
- Tensor Parallel
- Pipeline Parallel
- Expert Parallel
- Prefill/Decode disaggregation

最终变成：

```
        Requests
           │
       Scheduler
           │
   ┌───────┴──────┐
   │              │
Prefill Pool   Decode Pool
   │              │
GPU GPU        GPU GPU GPU
```

因此 **LLM Training Systems** 和 **LLM Serving Systems** 到后面其实是两个很大的研究方向。
