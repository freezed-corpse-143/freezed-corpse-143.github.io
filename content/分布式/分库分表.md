
# 分库分表
## 一、为什么要分库分表

核心原因只有一个：**单机数据库的容量和性能存在物理上限**。具体表现为：

### 1. 单表数据量过大
- MySQL 单表在几百万到千万级时，B+ 树索引层级变深，查询和写入性能明显下降。
- 数据文件过大，备份、DDL（如加字段）耗时极长，甚至锁表。

### 2. 单库磁盘/连接数瓶颈
- 单机磁盘容量有限，无法无限存储。
- 数据库连接数有限（如 MySQL 默认 151），高并发下连接成为稀缺资源。
- 单机 CPU、内存、IO 都有天花板，垂直升级（换更强的机器）成本高且终有极限。

### 3. 读写压力集中
- 所有请求打到同一个库，热点数据竞争激烈，锁冲突严重。

分库分表就是把数据按某种规则拆到多个库、多个表中，让每个节点只承担一部分数据和流量，从而突破单机限制。

**拆分的两个维度：**
- **垂直拆分**：按业务或字段拆。比如用户库、订单库分开；把不常用的大字段拆到扩展表。
- **水平拆分**：按数据行拆。比如订单表按用户 ID 取模拆成 16 张表。

---

## 二、分库分表后怎么查询

这是分库分表最核心的难点。查询方式取决于**查询条件是否包含分片键**。

### 1. 带分片键查询（最理想）
如果查询条件里包含分片键（如 `user_id`），中间件或应用可以直接路由到对应的库和表。

```sql
-- 分片键是 user_id，取模 16
SELECT * FROM order_08 WHERE user_id = 12345;
```

这是效率最高的方式，只访问一个节点。

### 2. 不带分片键查询（最麻烦）
如果查询条件没有分片键，比如按 `order_no` 或 `create_time` 查，就不知道该去哪个分片。常见解决方案：

**（1）冗余分片键 / 基因法**
在订单表里冗余一份 `user_id`，并让 `order_no` 的生成规则中“基因”包含 `user_id` 的取模值。这样即使按 `order_no` 查，也能解析出分片位置。

**（2）建立映射表 / 索引表**
单独建一张“查询条件 → 分片键”的映射表。比如 `order_no → user_id`，先查映射表拿到 `user_id`，再路由到具体分片。

**（3）异构索引（搜索引擎）**
把数据同步到 Elasticsearch、ClickHouse 等，复杂查询走搜索引擎，再回表拿详情。这是大厂常用方案。

**（4）广播查询 + 内存归并**
如果无法路由，只能把查询发到所有分片，再由中间件合并结果。性能差，只适合低频或小数据量场景。

```sql
-- 中间件会把这条 SQL 发到所有 16 个分片，再归并排序
SELECT * FROM order WHERE create_time > '2024-01-01' ORDER BY create_time LIMIT 10;
```

### 3. 分页、排序、聚合的难点
- **深度分页**：`LIMIT 100000, 10` 在每个分片都要扫大量数据再归并，性能极差。通常限制最大页数，或用游标（`WHERE id > last_id`）替代。
- **跨分片排序**：各分片返回 Top N，中间件再归并出全局 Top N。
- **跨分片聚合**：`COUNT`、`SUM`、`GROUP BY` 都要在各分片先算，再二次聚合。

### 4. 常用中间件
- **ShardingSphere**（Apache）：JDBC 和 Proxy 两种模式，国内使用广泛。
- **MyCat**：基于 Proxy 的数据库中间件。
- **Vitess**：YouTube 开源，Kubernetes 友好。
- **应用层分片**：自己写路由逻辑，灵活但维护成本高。

---

## 三、关键原则

1. **能不分就不分**：先考虑索引优化、读写分离、缓存、归档冷数据。分库分表是最后手段。
2. **分片键选择决定成败**：要选查询最频繁、分布均匀的字段，避免热点。
3. **尽量让查询带分片键**：这是设计分片方案时的核心约束。
4. **接受妥协**：分库分表后，跨分片事务、全局唯一 ID、跨分片查询都会变复杂，需要额外方案（如 Seata、雪花算法、ES）。

# 雪花算法

雪花算法（Snowflake）是 Twitter 开源的一种**分布式全局唯一 ID 生成算法**。在分库分表场景里，它常被用来解决“多个分片如何生成不冲突的主键”这个问题。

## 一、为什么需要它

分库分表后，传统的自增主键行不通了：

- 每个分片各自自增，会产生重复 ID。
- 用 UUID 虽然不重复，但**无序**、**占空间大**（36 字符）、**索引效率差**（随机写入导致 B+ 树频繁分裂）。

雪花算法要同时满足：**全局唯一、趋势递增、高性能、不依赖中心节点**。

## 二、ID 结构

雪花算法生成一个 **64 位长整型（long）**，结构如下：

```
0 | 0000000000 0000000000 0000000000 0000000000 0 | 00000 | 00000 | 000000000000
↑ |                   41 位时间戳                 | 5 位  | 5 位  |   12 位序列号
符号位(1位，恒为0)                                数据中心  机器
```

各段含义：

| 部分        | 位数 | 作用                          |
| ----------- | ---- | ----------------------------- |
| 符号位      | 1    | 恒为 0，保证正数              |
| 时间戳      | 41   | 毫秒级时间戳，可用约 69 年    |
| 数据中心 ID | 5    | 最多 32 个数据中心            |
| 机器 ID     | 5    | 每个数据中心最多 32 台机器    |
| 序列号      | 12   | 同一毫秒内最多生成 4096 个 ID |

**核心思路**：把“时间 + 机器标识 + 同一毫秒内的序号”拼在一起。因为时间在自增、机器各不相同、同毫秒靠序号区分，所以整体不会重复。

## 三、工作流程

生成 ID 时：

1. 取当前毫秒时间戳。
2. 如果和上次相同，序列号 +1；如果序列号溢出（超过 4096），就等待下一毫秒。
3. 如果时间戳比上次大，序列号归零。
4. 如果时钟回拨（时间倒退），则抛异常或等待恢复。
5. 把各段按位左移、或运算拼成最终 ID。

```java
// 简化逻辑
long id = ((timestamp - twepoch) << 22)
        | (datacenterId << 17)
        | (workerId << 12)
        | sequence;
```

## 四、优点

- **全局唯一**：机器 ID 不同，时间+序列保证不冲突。
- **趋势递增**：高位是时间戳，整体随时间增大，对 MySQL 聚簇索引友好，写入性能好。
- **高性能**：本地生成，单机每秒可产生几十万个 ID，无网络开销。
- **轻量**：不依赖数据库、Redis 等中心服务。

## 五、缺点与坑

1. **依赖系统时钟**：时钟回拨会导致 ID 重复或服务不可用。生产环境需要 NTP 同步，并做回拨检测（等待或报警）。
2. **机器 ID 分配**：5+5 位只支持 1024 个节点，需要一套机器 ID 管理机制（如 Zookeeper、配置中心）。
3. **ID 较长**：64 位 long 比自增 int 占空间大，但对现代系统通常可接受。
4. **不是严格递增**：只是趋势递增，不同机器同一毫秒的 ID 大小不保证有序。

## 六、在分库分表中的应用

雪花算法生成的 ID 天然适合做分片键：

- **全局唯一**，不用担心跨分片冲突。
- **趋势递增**，写入时新数据集中在索引尾部，减少页分裂。
- 可以**从 ID 中解析出时间**，方便按时间范围查询或归档。

不过要注意：如果直接用雪花 ID 取模分片，因为低位是序列号，分布还算均匀；但如果按时间范围查询，仍可能跨多个分片。

## 七、常见替代/改进方案

- **百度 UidGenerator**：基于雪花思想，用 RingBuffer 预生成，性能更高。
- **美团 Leaf**：提供号段模式和雪花模式，号段模式依赖数据库但更简单。
- **滴滴 TinyId**：号段模式，依赖数据库。
- **Redis INCR**：简单，但依赖 Redis，且 ID 连续可预测。
- **数据库号段**：一次取一批 ID 缓存在内存，减少数据库压力。

总的来说，雪花算法是分布式 ID 的经典方案，核心是“时间戳 + 机器标识 + 序列号”的组合。实际使用时，重点要解决好**时钟回拨**和**机器 ID 分配**这两个工程问题。
