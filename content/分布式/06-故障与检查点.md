# 故障与检查点：训练中断后如何接着跑

[返回总览](./分布式大模型.md)

## 先分清故障是否看得见

- **显式停止**：GPU 掉卡、节点断电或进程崩溃。同步通信的参与者消失后，其他进程也可能停住或报错。
- **通信异常**：链路断开会超时；带宽下降则可能只表现为某个进程越来越慢。
- **数值异常**：进程都活着，但 loss 出现 NaN/Inf、梯度爆炸；继续更新参数可能使模型失效。
- **静默数据损坏 SDC**：状态被错误地改变却未立即报错；ECC/校验能发现部分错误，但不能保证发现全部错误。仅观察 loss 正常不能证明训练状态正确。

这些维度会交叉：一次硬件错误可能以通信超时或数值异常的形式暴露。

## 看得见的故障：链路与训练数值

**通信硬故障**如网卡（NIC）重置、链路断开、RDMA 报错，可能导致通信超时或 **collective hang（集体通信卡住）**：同步操作要等参与者，某个进程未进入或无法完成通信，其他进程也继续不了。**性能退化**如拥塞、丢包重传或路由变化，可能没有立刻报错，却把某个进程变成慢节点；丢包不自动等于结果悄悄被改写，网络协议可能检测并重传。先区分“不能继续”与“仍在继续但变慢”。

**数值故障**发生在计算结果而不一定是硬件掉线。浮点数 **overflow（上溢）**指结果超出可表示范围，可能得到 Inf；**underflow（下溢）**指非零小值小到无法按当前精度表示，可能变为零或精度显著下降。反向得到的梯度异常大称**梯度爆炸**；**loss spike** 是损失突然上升，不一定已经是 NaN，也不意味着每次波动都是故障。坏训练批次或数据分片、被损坏的激活、不稳定的优化器更新都可能是诱因，不能只靠一个 loss 值判定原因。

可一起观察 loss、**梯度范数**（梯度整体大小）、**权重范数**（参数整体大小）、**激活范数**（中间输出整体大小）、学习率以及 NaN/Inf 出现的步数；“范数”在这里是把一组数汇总成大小指标，而不是直接证明这组数都正确。硬件和程序都正常时，也可能只有模型质量悄悄变差，属于训练语义层面的异常。

## Checkpoint 究竟要存什么

为了尽量从同一步继续训练，检查点不仅要有模型权重，通常还要保存优化器状态、训练进度、随机数状态，以及能恢复数据读取位置所需的信息；具体取决于训练实现。仅恢复权重可能导致学习率、样本顺序或优化器动量变化。

完整恢复路径：**发现异常 → 定位受影响步骤 → 判断检查点可信度 → 恢复训练状态 → 重建通信/进程组（若需要）→ 继续并观察结果**。例如 t2 发生未检测到的损坏，到 t4 才发现，t3 写下的检查点可能已被污染；不能机械地读取最新文件。

检查点写得越频繁，重算损失越少，却占用更多存储和 I/O 时间。先确认实际故障频率、写入耗时与可接受回退量，再决定间隔。弹性训练指进程成员变化后还能重组继续工作，但不自动保证损坏的数据或状态被修复。

## Checkpoint 与 activation checkpointing 不是一回事

这里的 **checkpoint（训练检查点）**是把某一步的训练状态持久化到可靠存储，以便进程崩溃后重新加载。若每 100 步保存一次，训练在第 250 步中断，通常需要从第 200 步的可信检查点继续，并重算其后的工作。分布式保存时各进程分片必须对应同一个一致的训练状态；不完整或已受污染的检查点不能因为“最新”就直接使用。

另一个常见术语 **activation checkpointing（激活检查点/重计算）**虽然也叫 checkpoint，却是前向传播时少存部分中间激活，反向传播时重新计算以节省显存；**它本身不会把模型状态写盘，也不能用于故障恢复**。前者用存储空间和写入时间换取故障后少重跑，后者用更多计算换取训练时更少激活显存。

**故障检测**是发现进程消失、通信超时或数值异常；**定位**是判断从哪一步开始出错；**隔离/重建**是停用有问题的进程、重建通信组；**恢复**是读取可信训练状态。节点故障通常容易检测，但没有检查点或没有可恢复的数据进度时，重启程序并不等于无损续训。

## 静默损坏为什么难发现

**DRAM** 是主机内存，**HBM** 是 GPU 上的高带宽显存；存储或传输中出现 **bit flip（位翻转）**、计算错误或软件错误，可能改变权重、激活或梯度。**DMA（直接内存访问）**是设备无需 CPU 逐字搬运数据的传输方式；PCIe、网卡、存储等路径上的错误也可能影响数据。**ECC** 用冗余校验位检测/纠正部分内存错误，**CRC** 用校验值检测部分传输/存储错误；它们覆盖的路径和错误类型不同，能检测一些错误但不能保证发现全部错误。真正的 SDC 是错误已经进入训练状态，却没有及时被检测出来。

若受损参数参与后续前向、反向和优化器更新，污染可能扩散。**检测延迟**是错误发生到发现之间的时间：这段期间保存的多个 checkpoint 都可能不可信。对可疑检查点要结合写入完整性、训练指标和错误发生时间判断，不是只按文件时间挑最新的。

## 从发现到续训：每一步在做什么

| 动作 | 新手可以怎样理解 |
| --- | --- |
| Detect / Localize | 通过进程报错、超时或数值监测发现问题，定位哪个节点、通信组、数据批次或训练步异常 |
| Contain / worker eviction | 暂停受影响作业并把失效进程移出本轮参与集合，避免其继续写坏状态 |
| Worker replacement / job rescheduling | 在可用节点重新拉起工作进程，必要时把任务放到别的机器 |
| Communicator reconstruction | 参与者变了，重新建立进程组/集体通信关系；只读回权重不能让旧通信自动恢复 |
| Recover / Resume | 选择可信 checkpoint，恢复模型、优化器、数据进度等，再继续并核对指标 |

**Elastic membership（弹性成员变更）**是训练框架允许参与进程集合改变并重组；具体能否在 GPU 数量变化后维持相同的有效批次、学习率和分片布局，要看实现，并不自动保证无损。无论是否弹性，若确认某一批数据损坏才考虑跳过该批；仅因 loss 升高就跳过数据，可能掩盖真正的错误。
