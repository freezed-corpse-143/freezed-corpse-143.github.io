# 关系定位法

一句话：

> 理解一个项目的正确顺序不是"读它"，而是**先确定它在关系网中的坐标，再读它的实现**。因为同一个实现在不同坐标下意义完全不同。

它是 [`并行学习法.md`](./并行学习法.md) 的单项目版本：并行学习法处理"一类系统"，关系定位法处理"一个项目"。参考样式来自 [`github项目/flashinfer.md`](../github项目/flashinfer.md)。

---

# 零、先把"程序是什么"这个问题答对

因为方法论完全由这个答案决定。

**问题**：马克思说"人的本质是一切社会关系的总和"。那程序是什么？是一堆需求与算法的总和吗？

三个递进的答案：

## 答案一（多数人停在这）

```text
程序 = 需求 + 算法 + 实现
```

这是**静态清单式**的定义。它的致命缺陷：它无法解释"为什么这么写"。

拿 FlashInfer 举例。这三个事实都是真的，但都没用：

- 它提供 attention kernel
- 它用 CUDA / CUTLASS
- 它支持 Paged KV Cache

它们解释不了："为什么 FlashInfer 要把自己拆成 `flashinfer-python` / `flashinfer-cubin` / `flashinfer-jit-cache` / `flashinfer-jit-cache-provider` 四个发布包？"（见 [实例](#十实例flashinfer-全流程走一遍)）

## 答案二（好一点）

```text
程序 = 一组约束下的可行解
```

有了取舍感。但还是没说清**约束从哪来**。

## 答案三（可操作的）

```text
程序 = 它所处关系的总和
```

一个程序里**每一个非平凡设计**，其直接原因都是下面三种之一：

| 关系 | 形式 | 例 |
| :--- | :--- | :--- |
| **上游约束** | 它必须适配谁 | 必须兼容 Paged KV Cache 的内存布局，所以 attention kernel 的签名长成那样 |
| **下游契约** | 谁依赖它的什么保证 | vLLM/SGLang 依赖它"同一个 API 在不同 backend 上语义一致"，所以才有 backend 抽象 |
| **演化包袱** | 上一版怎么写的 | 两个 minor 版本才能删废弃 API，所以代码里留着 deprecated 路径 |

**推论（这就是整套方法）**：

1. **定位先于阅读。** 先回答"它站在哪"，再读"它怎么写"。
2. **"它为什么不是 X"比"它是什么"信息量大。** 差异——尤其与竞品的差异——是唯一能暴露设计取舍的证据。
3. **关系会变，所以要看历史。** release notes / deprecation 记录 / 架构迁移 PR，是"哪些关系变了"的直接证据。

## 一条高价值的判据

> 任取一个让你费解的设计，问：它属于上游约束、下游契约、还是演化包袱？
> **三者都解释不了**，那它多半是"作者偏好"或"未清理的技术债"。
>
> 这个结论本身就是重要发现，不是理解失败——它意味着**你找到了这个项目的可改进点**。

这条判据把"理解"和"维护"接了起来，见 [Q6](#q6-怎么优化和维护它)。

# 一、核心思想（五条）

## 1. 关系是有限可枚举的

"定位"听起来像玄学。不是。一个项目**只有四种**对外关系：

```text
        ┌──────────────── 历史 ────────────────┐
        │  它替换了什么？要被什么替换？          │
        ▼                                      ▼
   [ 上游 ] ──依赖──▶ ┌──────────┐ ──被消费──▶ [ 下游 ]
   它站在谁的肩膀上     │  项目 X  │              谁靠它活着
                      └──────────┘
                            ▲
                            │ 竞争 / 分道扬镳
                      [ 横向 ] 竞品 / 姊妹项目
```

四种关系对应四个固定的调研动作，工作量是**有界**的。

## 2. 定位的产出是一句话，不是一个图

做完定位，你应该能填满这个句子：

```text
<项目> 依赖 <上游> 提供 <C>，
       为 <下游> 提供 <E>，
       替代了 <F>，
       与 <竞品 G> 在 <H> 上分道扬镳。
```

填不满，说明定位没做完——通常缺的是"与竞品分道扬镳在哪"这一格，因为它最费事、也最有价值。

## 3. 先问"为什么需要它"，再问"它是什么"

顺序反了就会读成 README 摘要。

因为"它是什么"的答案会被官方文案污染（营销化的能力清单），而"为什么需要它"必须靠你自己推：

```text
如果没有它 → 谁最痛苦 → 痛在哪 → 它填的是哪个洞
```

这个推演出来的答案，比 README 的第一段更接近真相。

## 4. 内容要切两刀：垂直面 + 横切面

只看垂直面（模块树）会漏掉一半的工程量；只看横切面会没有骨架。

| 刀 | 切法 | 得到 |
| :--- | :--- | :--- |
| **垂直面** | 自顶向下逐层分解 | 类型 → 实体 → 模块 → 应用 |
| **横切面** | 穿过所有层的能力 | 日志 / 异常 / 配置 / 资源 / 并发 / 缓存 / 安全 / 生命周期 |

**判据**：一个能力如果同时影响多个垂直层，它就是横切面，不该塞进某个单一模块里理解。

（这条判据与 [并行学习法](./并行学习法.md) 里"切面"的判据是同一条。）

## 5. 边界是定位的产物，不是独立的一问

初学者常把"边界"当成一个额外问题：*"它有什么限制？"*

不是。**边界不是"再查一遍"，而是"关系的补集"。**

```text
上游依赖  →  划出「能力边界」：哪些必须自己做，哪些可以借
上游约束  →  划出「设备与环境边界」：必须在什么环境下运行
下游契约  →  划出「职责边界」：该做什么、不该做什么
横向竞品  →  划出「能力边界（相对）」：我有什么它没有、反之
历史包袱  →  划出「兼容边界」：什么不能改、要等几个版本

关系定了 → 边界自动落地
关系没定 → 边界只能靠猜（猜出来的边界通常是营销话术的复述）
```

**推论**：不要在读完定位之后再单独问"它的边界在哪"，而是在 [Q2](#q2-它在体系中的位置) 的每一条关系上顺手记下边界。定位和边界是同一个动作的两个输出。

完整展开与六种边界的清单见 [第三节的「边界」](#边界关系的补集)。

**另一条同样重要的推论**：边界要**从外侧核对**。项目自己声明的限制有营销偏差，而**下游的工程量是诚实的**——下游补的那一层，就是上游的边界。取证方法见 [边界从哪一侧看](#边界从哪一侧看内侧声明-vs-外侧证据)。

# 二、七问：顺序即逻辑

七问的顺序不是随意的，它遵守三条排序原则：

```text
由外到内：先确定边界，再进入内部
由因到果：先问为什么存在，再问是什么
由静到动：先问是什么，再问怎么用、怎么改
```

| # | 问题 | 一句话 | 产出物 | 典型耗时 |
| :--- | :--- | :--- | :--- | :--- |
| **Q0** | 它是什么类别的**东西**？ | 一句话定位 + 反例边界 | 一句话 + "它不是什么"三条 | 10 min |
| **Q1** | 它解决**什么问题**？谁在什么**场景**下遇到？ | 问题陈述 | 痛点 → 场景 → 触发条件 | 20 min |
| **Q2** | 它在**体系中的位置**？上下游是谁？ | 关系定位 | 一张栈图 + 四种关系表 | 30 min |
| **Q3** | 它**为什么出现**？竞品没解决什么？ | 因果定位 | 竞品对照表 + 三个"为什么不是" | 30 min |
| **Q4** | 它的**内容**是什么？ | 结构分解 | 垂直面 4 层 + 横切面清单 | 60 min |
| **Q5** | 怎么**用它**？ | 上手 | 最小可用 + 典型场景 + 接口地图 | 30 min |
| **Q6** | 怎么**优化和维护**它？ | 演进 | 反馈闭环 + 迭代点 + 特化边界 | 30 min |

前四问（Q0–Q3）做完就可以对外讲清楚这个项目了，占 40% 时间产生 70% 的理解。Q4 是重活。Q5/Q6 决定你是"知道它"还是"能用它"。

## Q0 它是什么类别的**东西**？

### 问什么

```text
它是库 / 框架 / 编译器 / 运行时 / 服务 / 规范 / 工具链 里的哪一种？
它最像什么？（用一个已知物做类比）
```

### 为什么先问这个

因为类别决定了**它的成熟度模型、使用者身份、以及"好"的标准**。

- 库的"好"= 快 + API 稳
- 框架的"好"= 表达力 + 生态
- 编译器的"好"= 覆盖率 + 生成代码质量
- 服务的"好"= 吞吐 + 延迟 + 可用性

搞错类别，后面的评价体系全错。把 FlashInfer 当"推理框架"来评价（问它怎么处理 HTTP 请求），是典型的类别错误。

### 动作

1. 读官方定位句（README 第一段 / docs 首段），逐字抄下来。
2. **写出三条"它不是什么"**。这一条比"它是什么"更有信息量，因为它直接划出边界。
3. 找一个已知物做类比："可以把它理解成 ___"。

### 产出示例（FlashInfer）

```text
它是什么：专门为 LLM 推理/Serving 提供高性能 GPU 算子的基础设施库
           （官方定位句：High-Performance GPU Kernels for Inference，README.md:8）
它不是什么：
  · 不是一个完整的 LLM Serving 系统 —— 不做 HTTP API / 请求队列 / 模型调度
  · 不是一个编译器 —— 虽然自述是 "library and kernel generator"，但不做通用 IR/schedule 搜索
  · 不是 FlashAttention —— 后者是算法/Kernel 家族，前者是覆盖整条 inference 的 Kernel Library
类比：可以把它理解成 "LLM 推理的算子标准库 + 调度器"
```

### 不合格的答案

> "FlashInfer 是一个高性能的 LLM 推理加速库。"

没有类别边界、没有"不是什么"、没有类比 = 等于没说。

## Q1 它解决**什么问题**？谁在什么**场景**下遇到？

### 问什么

```text
在它出现之前，谁在做这件事？怎么做？痛在哪？
这个痛在什么场景下才会发作？（什么条件下不痛？）
```

**第二问是关键且最常被跳过。**"什么条件下不痛"决定了这个项目的适用边界。

### 动作：反推法

不要读它宣称解决什么，而是**倒推它不解决什么情况下最舒服**：

```text
痛点 → 触发条件 → 触发条件的反例
```

### 产出示例（FlashInfer）

| 痛点 | 触发条件 | 反例（不需要 FlashInfer） |
| :--- | :--- | :--- |
| 用小算子拼 attention 会产生大量 kernel launch + HBM 搬运 | 请求长度不一 + KV Cache 分页 + continuous batching | 固定长度、单请求、离线批处理 |
| 通用 PyTorch op 不适合 decode 阶段的 GPU occupancy | decode 时 batch 大、每请求只算 1 个 token | prefill 主导、算力密集型负载 |
| 上层框架要自己拼 sampling 流程 | 需要 top-k/top-p/min-p 融合 | 贪心解码 |

**倒推出的一般规律**：

> FlashInfer 的适用边界 = **serving 场景**（长度不一、batch 混合、KV 分页）。
> 离线、定长、单请求的场景，它的复杂度收益大幅下降。

这个结论比"它给 LLM 推理加速"有用得多——它告诉了你**什么时候不要用它**。

## Q5 怎么**用它**？

### 问什么

```text
最小可用路径是什么？（复制粘贴就能跑）
典型场景的三段代码是什么？
接口地图在哪？（不是逐个 API，而是"我要做 X 该看哪个模块"）
```

### 三段式

| 段 | 内容 | 判据 |
| :--- | :--- | :--- |
| **最小可用** | 一段能跑的代码 | 自己跑过，不是抄 README |
| **典型场景** | 2–3 个真实用法 | 来自 `examples/` 或 `tests/`，不是 docs 里的玩具 |
| **接口地图** | "要做 X → 看模块 Y" 的对照表 | 用**任务**索引，不用 API 名索引 |

### 为什么接口地图要按任务索引

因为你的记忆是任务导向的："我要做一个 paged attention" 比 "`BatchPrefillWithPagedKVCacheWrapper` 怎么用" 更容易想起来。

产出示例（FlashInfer，形式）：

```text
我要做 prefill attention        → flashinfer/attention/
我要做 MoE                      → flashinfer/fused_moe/, flashinfer/moe_ep/
我要做采样                      → flashinfer/logits_processor/, cake_sampling*
我要调 kernel 选择              → flashinfer/autotuner/, tuning_configs/
我要看为什么这么慢              → flashinfer/profiler/, flashinfer/trace/
我要离线编译                    → flashinfer/aot.py
```

**注意**：这张表的每一行都必须来自你实际打开过的目录，不能来自目录名猜测。

### 一个高价值动作：找"入口的入口"

```text
python -m <package>            # 有没有 CLI？
<package>/__main__.py          # 有的话，这是作者认为的"最常用路径"
```

作者写 `__main__.py` 的地方，就是他心里"用户第一件事想干的事"。FlashInfer 有 `flashinfer/__main__.py`（38 KB）和 `docs/cli.rst`——这说明它把"环境诊断/编译缓存管理"当成用户的第一步。

## Q6 怎么**优化和维护**它？

展开在 [第六节](#六q6-深入四种演进动作)。

一句话版：

```text
四种动作：反馈错误（闭环） / 迭代优化（数据驱动） / 场景特化（什么时候 fork）
          / 复用技术（哪些能搬走）
```

判定"这个项目好不好维护"的最快方法：**看它的仓库里有没有维护制度化的产物**。

| 看什么 | 说明什么 |
| :--- | :--- |
| `deprecation` / `migration` / `upgrade` 类文档 | 有机会做破坏性变更，且有纪律 |
| `experimental/` 目录 + `experimental.rst` | 有"未定型的场景特化"的隔离区 |
| `autotuning` / `profiler` / `benchmarks` | 性能迭代是数据驱动的 |
| `code_review_guidance.md` | 协作规范成文 |
| 异常类的层次结构 | 错误是可分类、可处理的，不是字符串 |

FlashInfer 五项全中（见 [实例](#十实例flashinfer-全流程走一遍)）。这是"成熟项目"的指纹。

# 三、Q2 深入：四种关系（以位置定位）

这是整套方法的核心。**四种关系 = 四个有界的调研动作**，做完就能填出那句定位句。

## 关系一 · 上游：它站在谁的肩膀上

### 动作

读依赖清单（`pyproject.toml` / `requirements.txt` / `3rdparty/` / `gitmodules`），按**物理层次**重排，而不是按字母排序：

```text
硬件
 └─ 驱动 / 运行时        （CUDA Runtime、libcuda、NVSHMEM）
     └─ 编译器 / 工具链   （nvcc、Triton、CUTLASS、CuTe DSL）
         └─ 库             （cuDNN、cuBLAS、FlashAttention）
             └─ 框架        （PyTorch）
                 └─ 本项目
```

### 判据（很重要）

> 如果它的核心能力**能由上游直接提供**，那它是"薄包装/调度层"；
> 如果**不能**，那它是"真实现"。

FlashInfer 是**两者都有**——这正是它被误读的地方：它自己写 kernel，同时又能把 `FlashAttention-2/3`、`cuDNN`、`CUTLASS`、`TensorRT-LLM` 当 backend 调。所以它既是实现在，也是调度层。

### 产出

一张依赖栈图 + 一句话："上游里，哪些是**硬依赖**，哪些是**可选 backend**。"

## 关系二 · 下游：谁靠它活着

### 动作

```text
1. 谁 import 它？（搜索生态：上游框架的依赖清单、集成目录）
2. 官方 docs 里有没有 "used by" / "integrations" 章节？
3. 有没有专门的适配层？（例如 3rdparty 反向集成、plugin）
4. 它在哪些框架的版本发布里被提到？
```

### 为什么必须做这一步

因为**下游决定了它的 API 契约强度**。

- 下游是脚本 → API 可以随便改
- 下游是长期服务框架 → API 必须保证两三个版本兼容

FlashInfer 的 `deprecation_survey_v0.7.0.md` 里明确写着"FlashInfer guarantees a deprecated public API for **two minor releases**"——这个承诺不是自己定的，**是被 vLLM/SGLang 这类下游逼出来的**。

**这是"关系决定设计"最漂亮的证据**：一个"允许删废弃 API 的期限"这个看起来纯粹是内部的规则，它的直接原因在外部关系里。

### 产出

"它服务于谁 + 因此它必须保证什么"。

## 关系三 · 横向：同一问题的其他解

### 动作

1. 列出 3–5 个同类项目。
2. 建一张**能力矩阵**（行=能力，列=项目），只用"有/无/部分"标注。
3. 找出**分道扬镳的那一格**：不是能力多寡之差，而是**路线之差**。

### 判据

> 如果找不出"分道扬镳点"，两种可能：要么你选错了竞品（它们其实不是竞品），要么你还没读懂。

判断两者哪个成立的方法：问"它们能互相替换吗"。能互相替换的才是竞品。FlashInfer 与 MC 类似的 kernel 库能替换；与 FlashAttention **不完全能**——前者包含后者。这种情况下关系是"包含/分层"，不是"竞争"，应该画成嵌套图而不是对照表。

### 产出

能力矩阵 + 一句"它与 X 在 Y 上分道扬镳"。

同时产出**三类关系图**：

```text
竞争   ：可互相替换，取舍不同        → 对照表
包含   ：A 是 B 的一个子集/一层       → 嵌套图
分层   ：A 与 B 在不同层，不构成竞争   → 栈图
```

把包含关系误判成竞争关系，是最常见的定位错误。

## 关系四 · 历史：它替换了什么，又要被什么替换

### 动作

```text
1. 读 CHANGELOG / releases / 迁移文档 / deprecation 记录
2. 找"它替换了什么"—— 这解释它为什么存在
3. 找"它现在往哪走"—— 这解释哪些模块是活的、哪些是化石
```

### 为什么这一问能省钱

因为**它告诉你哪些代码可以不用读**。

一个项目里通常有 30% 是历史包袱（向后兼容层、废弃路径、迁移适配）。读之前先通过历史定位把它们圈出来，能省大量时间。

### 产出

"它替代了 F，正被 G 侵蚀 / 正在吸收 G 的能力"，以及一份**"不必读清单"**。

## 边界：关系的补集

四种关系做完，边界就自动出来了。对照表：

| 关系 | 划出的边界 | 取证方式 |
| :--- | :--- | :--- |
| 上游依赖 | **能力边界**（哪些必须自己做） | 依赖清单 + "核心能力能否由上游直接提供" |
| 上游约束 | **设备与环境边界** | 官方支持矩阵 + 环境类异常 |
| 下游契约 | **职责边界** | 下游怎么用它 + 官方兼容承诺 |
| 横向竞品 | **能力边界（相对）** | 竞品对照表 |
| 历史 | **兼容边界** | deprecation 记录 |

### 六种边界：可复用清单

分析任何项目都按这个清单过一遍，缺哪条就问哪条：

| # | 边界 | 问题 | 主要来源 |
| :--- | :--- | :--- | :--- |
| 1 | **能力边界** | 能做什么、明确不做什么 | 上游依赖 + 横向竞品 |
| 2 | **职责边界** | 该做什么（不由它做的是什么） | 下游契约 |
| 3 | **场景边界** | 在什么负载形态下才划算 | 痛点结构 |
| 4 | **设备与环境边界** | 能在什么硬件/软件上跑，哪些特性受限 | 平台矩阵 |
| 5 | **性能边界** | 多大规模才值得用（小规模时反而更慢） | 开销结构（编译 / launch / dispatch） |
| 6 | **兼容边界** | 什么不能改、要等几个版本 | 历史 + 下游契约 |

**第 3 条和第 5 条最容易漏**，而它们恰好是决策时最有用的两条：

- 场景边界 = **什么时候不要用它**（比"它擅长什么"有用得多）
- 性能边界 = **规模多小就不划算**（编译开销 / 启动开销压过收益的临界点）

场景边界的取证方式是**反推**：

```text
痛点 → 触发条件 → 反例
```

反例就是它的场景边界。任何"痛点"都对应一个"痛不起来"的条件。

### 边界从哪一侧看：内侧声明 vs 外侧证据

```text
从内侧看（它自己说的）：
  README 的限制说明、docs 的 caveat、异常类型
  → 有营销偏差。作者会弱化限制、强调能力

从外侧看（关系推出来的）：
  下游自己补了什么、包了什么、搬了什么
  → 没有偏差。下游的工程量是诚实的
```

**两侧都要看，但结论以外部为准。**

### 一条强启发式

> **下游自己写的那一层，就是上游的边界。**
> 下游写得越厚、分得越细、越需要 vendored 代码，说明上游的边界越硬。

可操作版本——**去下游仓库里数一数**：

```bash
# 在下游项目里
grep -rln "<上游项目名>" <下游源码目录> | wc -l
```

然后读这些文件**长什么样**，每类形态指向一种边界：

| 下游的形态 | 上游的哪种边界被暴露 |
| :--- | :--- |
| 每个领域一个适配文件 | 能力边界：上游的"统一 API"统一在接口层，实现层是分叉的，选型由下游做 |
| 同一功能有多个并列实现 | 能力边界（更硬）：多条路线并存，上游没收敛 |
| 调优/预热/生命周期管理在下游 | 职责边界：上游提供设施，不决定策略——谁决定"什么时候值得花时间"，谁掌握调度权 |
| 下游出现 vendored / forked 代码 | 兼容边界被打破：上游不肯改，或改动的节奏跟不上 |
| 一大批参数 hook / 配置桥接 | 配置边界：上游暴露旋钮，下游决定旋钮怎么被用户映射 |

**反向也能用**：

```text
下游很薄、只 import 几个符号   → 上游边界清晰、API 收敛 → 成熟
下游很厚、每个领域一个适配层  → 上游边界模糊、接口未定型 → 早期
下游出现 vendored 代码        → 边界与需求已发生硬冲突 → 要么上游被撼动，要么会被替换
```

**这比看版本号更能判断一个库处在生命周期的哪个阶段。**

### 落地动作

做完 Q2，除了那句定位句，还要产出：

```text
【六种边界】逐条写"是/不是 + 证据"
  能力边界：
  职责边界：
  场景边界：（含 2 条以上反例）
  设备与环境边界：
  性能边界：
  兼容边界：

【外侧核对】下游是谁、下游补了多厚的一层、暴露出哪些边界
```

## 关系定位检查表

做完四种关系，逐项自检：

| # | 检查 | 不合格 |
| :--- | :--- | :--- |
| 1 | 依赖栈画出物理层次了吗 | 只是把依赖清单抄了一遍 |
| 2 | 核心能力是由上游提供还是自己实现 | 说不清，全归功于"用了 CUTLASS" |
| 3 | 下游是谁、因此它承诺了什么 | 说不出 API 兼容承诺的来源 |
| 4 | 竞品是"竞争/包含/分层"中的哪一种 | 一律当竞争对手列 |
| 5 | 分道扬镳点在哪一格 | 只写出了能力多寡 |
| 6 | 它替换了什么、要被什么替换 | 完全没看历史 |
| 7 | 有没有产出"不必读清单" | 打算全读 |
| 8 | **六种边界**逐条有答案吗 | 只能用"它很快"这类话描述能力边界 |
| 9 | **场景边界**有没有给出反例 | 说不出"什么时候不需要它" |
| 10 | **性能边界**有没有金额（多大的规模才划算） | 说不出编译/启动开销压过收益的临界点 |
| 11 | 边界是否**从外侧核对**过 | 只抄 README 的限制说明 |
| 12 | 有没有数过**下游的适配层有多厚** | 没去下游仓库看过 |

# 四、Q4 深入：垂直面与横切面两把刀

## 第一刀 · 垂直面：四层分解

自顶向下，每一层问一个**固定的问题**：

| 层 | 问什么 | 具体怎么看 | 判据 |
| :--- | :--- | :--- | :--- |
| **类型层** | 它对外承诺了哪几种"东西的存在"？ | 读对外导出的**概念名**，不是逐个类 | 能用一句话说出它的"名词体系" |
| **实体层** | 这些类型的具体实现者是谁？ | 找命名里的实体词（`Wrapper` / `Plan` / `Engine` / `Scheduler`） | 能说出每个概念有几个实现 |
| **模块层** | 实体如何组织成子系统？ | 看目录树 + `__init__.py` 的**导出意图** | 能按目录画出子系统图 |
| **应用层** | 子系统如何组合成"用户能用的东西"？ | 看 `examples/`、`tests/`、上层框架的集成代码 | 能说出 2–3 个端到端用法 |

### 为什么"类型层"要读导出意图而不是类列表

因为 `__init__.py` 里 `X as X` 这种**显式重导出**是作者的**承诺清单**——他在这里划定了"这是我们的公开名词体系"。

FlashInfer 的 `flashinfer/__init__.py` 就是这种风格，逐行 `X as X`。

### 产出示例（FlashInfer 的类型层与实体层）

只读命名就能得到一份**高信息量的判断**：

```text
类型层（对外名词体系）：
  Wrapper  ——  一次"工作负载形态"的适配器
  Plan     ——  一次执行的事前规划
  以及 per-op 的函数式 API（norm / rope / sampling / activation）

实体层（Wrapper 的实例）：
  BatchPrefillWithPagedKVCacheWrapper
  BatchDecodeWithPagedKVCacheWrapper              flashinfer/decode.py:967
  CUDAGraphBatchDecodeWithPagedKVCacheWrapper     flashinfer/decode.py:2977
  MultiLevelCascadeAttentionWrapper               flashinfer/cascade.py:226
  BatchPODWithPagedKVCacheWrapper                 flashinfer/pod.py:61
```

**从这两层就能读出这个项目的骨架**：

| 命名模式 | 说明什么关系 |
| :--- | :--- |
| `XxxWithPagedKVCacheWrapper` | 上游约束：必须适配分页 KV Cache 的内存布局 |
| `CUDAGraph...Wrapper`（子类） | 上游约束升级为**类型**：CUDA Graph 捕获期不能用某些操作，这个约束被编码进类名与继承 |
| `...WithSharedPrefixWrapper`（cascade） | 下游场景特化：前缀共享 |
| `...PODWith...` | 下游场景特化：prefill/decode 解耦 |
| `Plan / _LaunchPlan` | 时间优化：把决策从运行期提到事前 |

**这就是"内容是什么"的真正答案**：不是一张能力清单，而是**一组被关系塑造出来的名词**。

### 模块层的一个深刀法：看发布边界

目录树告诉你代码怎么分；**发布包**告诉你作者认为"什么应该一起走"。

FlashInfer 把自己拆成四个发布包：

```text
flashinfer-python            主代码（含 kernel 生成器）
flashinfer-cubin             预编译的 cubin
flashinfer-jit-cache         运行期 JIT 编译结果的缓存
flashinfer-jit-cache-provider 缓存的提供者（可服务化/共享）
```

这一刀切出的问题意识是：**"编译产物如何分发"**。这是很多库根本不会想到的一层，也是判断"这个项目有没有认真做工程化"的好指标。

一条可复用的判据：

> 看**发布边界**（几个包、几个 artifact），比看目录树更能看出作者认为的模块边界。

## 第二刀 · 横切面：十类能力

横切面 = 穿过所有垂直层的能力。逐类扫一遍，每类只问一个问题：

| # | 横切面 | 只问这一句 | FlashInfer 的证据 |
| :--- | :--- | :--- | :--- |
| 1 | **配置** | 配置从哪来？环境变量 / 文件 / 代码？ | `FLASHINFER_LOGLEVEL`、`FLASHINFER_LOGDEST`、`FLASHINFER_JIT_CACHE_PROVIDER_ARCH` |
| 2 | **可观测性** | 有日志/指标/trace 吗？关掉时有开销吗？ | `flashinfer/api_logging.py`（2700+ 行）、`@flashinfer_api` 装饰器（`:2400`）、`docs/logging.rst`、`flashinfer/trace/` + `trace_apply/` |
| 3 | **异常管理** | 错误是分类的，还是字符串？ | `flashinfer/utils.py:83-95` 的 `GPUArchitectureError` / `LibraryError` / `BackendSupportedError`，加上按子系统细分的 `CudnnCaptureUnsafeError`、`MissingJITCacheError`、`DAResourceLeaseConflict` |
| 4 | **资源治理** | 显存/workspace/流 谁管？超了怎么办？ | `CudnnWorkspaceTooSmallInCaptureError`（把"资源不足"做成可识别的异常） |
| 5 | **并发模型** | 线程/进程/流/派发 的模型是什么？ | `csrc/*/` 里的多流、NVSHMEM 通信 |
| 6 | **缓存** | 缓存什么？key 是什么？什么时候失效？ | `autotune_cache.py`、`flashinfer-jit-cache` |
| 7 | **序列化/持久化** | 有没有落盘格式？版本兼容吗？ | JIT 缓存与 cubin 的产物格式 |
| 8 | **校验/安全** | 输入在哪校验？非法输入怎么处理？ | `flashinfer/logits_processor/validators.py` + `legalization.py` |
| 9 | **生命周期** | 创建/热身/销毁/复用 的阶段是什么？ | `Plan` 的预规划、CUDA Graph 捕获期约束 |
| 10 | **兼容性** | 跨 GPU 架构/版本怎么兼容？ | `experimental/`、废弃策略、`BackendSupportedError` |

### 为什么异常管理这一格特别值钱

**异常类的名字是"作者认为会出现哪些坏情况"的清单。**这是一个免费获得的失败模式目录。

看 FlashInfer 的 `CudnnCaptureUnsafeError` 系列就明白：作者把"CUDA Graph 捕获期"当作一个**环境约束维度**，把在这个环境下不安全的行为做成了一类异常。你由此学到：*"CUDA Graph 捕获期间，有些工作和流捕获不兼容"*——这是领域知识，而且是白拿的。

一个可复用的动作：

```text
grep -rn "^class .*Error\|^class .*Exception" <repo> | sort
```

五分钟，得到一份领域失败模式清单。

## 两把刀合起来：十字扫描

单切一刀会漏。正确用法是**十字**：

```text
选一个端到端的业务动作（例："跑一次 decode attention"）
  │
  ├─ 纵向：它经过哪几层？（类型 → 实体 → 模块 → 应用）
  │
  └─ 横向：每一层上，有哪些切面能力插进来？
             （日志？异常？缓存？资源？生命周期？）
```

**十字扫描的产出就是"这个项目的完整心智模型"**：纵向给了骨架，横向给了肌肉。

# 五、Q3 深入：竞品三问

"它为什么出现"这个问题，用**三个"为什么不是"**来回答。每一个都在切掉一片空间，剩下的就是它的位置。

## 问一：为什么不是竞品 A？

```text
A 的做法：____
A 解决不了：____（要具体到场景，不能是"性能不够好"）
本项目补上的：____
```

**例（FlashInfer vs 直接用 PyTorch 拼算子）**：

> PyTorch 的做法：`q @ k.T` → softmax → `@ v`，逐 op 调用。
> 解决不了的：请求长度不一时，KV Cache 分页 + continuous batching + prefill/decode 混合导致大量 kernel launch、中间 tensor 和 HBM 搬运；decode 阶段每请求只算 1 个 token，GPU occupancy 极低。
> 补上的：把"LLM serving 特有的负载形态"直接做成特化 kernel。

注意"解决不了"必须落到**具体场景**上。"PyTorch 慢"不是答案，"decode 阶段的 occupancy 低"才是。

## 问二：为什么不是更底层的技术？

它明明可以用 CUDA/Triton 直接写，为什么还要封装一层？

**答案通常是"抽象层次的选择"**——它在赌：*这一类问题会反复出现，值得固化成一个抽象*。

判据：**如果它的抽象能被两行代码替代，说明抽象层次选错了；如果每次用都要写 500 行，说明抽象得太薄**。

## 问三：为什么不是更上层的框架？

它为什么不干脆做成一个完整的 serving 系统？

**答案通常是"职责边界"**——它选择只做一件可以被别人依赖的事。

判据：**它的接口是否不依赖某个特定上游框架**。如果它 import 了 vLLM，那它就不是"库"，是"vLLM 的一部分"。

这条判据直接量化了 [关系二](#关系二--下游谁靠它活着) 里说的"下游契约"。

## 产出：竞品对照表

| | 本项目 | 竞品 A | 竞品 B | 更底层做法 | 更上层框架 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 解决什么 | | | | | |
| 不解决什么 | | | | | |
| 抽象层次 | | | | | |
| 谁依赖它 | | | | | |
| 分道扬镳点 | — | | | | |

**"不解决什么"这一列才是最有价值的**——因为它同时是它的边界和它的护城河。

# 六、Q6 深入：四种演进动作

从"理解"走向"能用/能改"，需要四种能力。

## 动作一 · 反馈错误：建立分层定位闭环

错误来了不要直接读代码，先**定位它在哪一层**：

```text
现象
 │
 ├─ 输入层 ？   → 参数/形状/dtype 校验，看 validators
 ├─ 配置层 ？   → 环境变量 / 选项组合，看 config 与 docs
 ├─ 环境层 ？   → GPU 架构 / 驱动 / CUDA 版本，看 BackendSupportedError 类异常
 ├─ 算法层 ？   → 数值/精度/边界，看 tests 与 reference 实现
 ├─ 资源层 ？   → 显存 / workspace / 流，看资源类异常
 └─ 编译层 ？   → JIT 产物 / cubin / 缓存，看 jit/ 与 cache
```

**这一步能省掉 80% 的无效 debug**。而且它和 [Q2 的四种关系](#三q2-深入四种关系以位置定位) 是同一张地图的两种用法：定位理解用关系，定位故障用层。

**可复用的动作**：项目里已有的异常分类（`grep "^class .*Error"`）**就是它自己提供的分层定位表**。优先用项目自己的分类，别自创一套。

## 动作二 · 迭代优化：让数据说话

```text
基线 → 度量 → 假设 → 改动 → 复测
```

判据：

- 有没有**现成的度量入口**？（`benchmarks/`、`profiler/`、`tests/` 里的性能测试）
- 有没有**自动调优设施**？（`autotuner/`、`tuning_configs/`、`autotuning.rst`）

有自动调优设施的项目，意味着**作者已经把"性能是搜出来的，不是想出来的"制度化**了。这是判断项目成熟度的强信号。

**注意区分**：可调参数（tuning knobs）≠ 可优化点（optimization targets）。前者是作者给你的旋钮，后者是你需要自己找的。前者看 `tuning_configs/`，后者看 `profiler/`。

## 动作三 · 场景特化：什么时候 fork，什么时候包装

这是最需要判断力的动作。三条路：

| 路径 | 适用 | 代价 |
| :--- | :--- | :--- |
| **外层包装** | 只改调用方式，不动内部 | 最便宜，但受限于原接口的表达力 |
| **提 PR 回上游** | 改动对所有人都有价值 | 需要说服力 + 等待周期 |
| **Fork** | 改动与上游路线冲突，或上游不接受（许可证/评审） | 必须自己承担跟随上游的成本 |

**决策依据来自 Q2 的关系定位**：

```text
我的改动会不会破坏"下游契约"？
  会  → 不可能被接受，考虑 fork 或外层包装
  不会 → 提 PR
我的改动是"上游约束"导致的吗？
  是 → 上游一变你就得改，别 fork，做薄适配层
```

**一个好信号**：如果项目里有 `experimental/` 目录和 `experimental.rst`，说明**作者已经建好了"场景特化"的隔离区**——你的特化需求大概率应该先放那里，而不是直接改核心。

## 动作四 · 复用技术：把可迁移的东西抽出来

最后一步，把项目里学到的东西**分成三类**：

| 类别 | 处理 |
| :--- | :--- |
| **领域通用**（换任何同类项目都成立） | 写进自己的知识库，这是最值钱的产出 |
| **项目特有**（只在这个架构下成立） | 记住即可，别当规律用 |
| **技术技巧**（与领域无关的工程手法） | 直接搬到别的项目 |

判断技巧是否"与领域无关"的测试：

> 这条技巧**能不能换一个完全不同的系统复述出来**？
> 能 → 它是通用工程手法（如"编译产物独立发布"、"异常名字即失败清单"）
> 不能 → 它是领域知识

**这一步是整个方法论的收口**，也是它和 [并行学习法](./并行学习法.md) 的接口：并行学习法产出"领域不变量 + 设计空间"，关系定位法产出"通用工程手法 + 领域知识"，两者合起来才是完整的知识资产。

# 七、工作流

## 时间盒（总计约 4.5 小时）

```text
Q0 定位          10 min   ─┐
Q1 问题与场景     20 min    │  阶段一：讲得清（60 min）
Q2 四种关系 + 边界 40 min    │
Q3 竞品三问       30 min   ─┘
Q4 内容分解       60 min      阶段二：画得出（60 min）
Q5 使用           30 min   ─┐
Q6 演进           30 min   ─┘  阶段三：用得上（60 min）

写文档收口        30 min
```

**阶段一的 60 分钟是杠杆最高的**。做完就能对外讲清楚这个项目、也能说清它的边界，而且已经能判断"我要不要深入"。

Q2 里多出的 10 分钟专门给边界——**六种边界逐条填 + 去下游仓库数一遍适配层**。这 10 分钟是整份工作里唯一无法由自己仓库完成的部分。

## 每步的"够用即停"信号

不要追求完美，每一步都有明确的停手条件：

| 步 | 停手条件 |
| :--- | :--- |
| Q0 | 能说出三条"它不是什么" |
| Q1 | 能说出两个"不需要它的场景" |
| Q2 | 能填满那句定位句（四要素全齐） |
| Q3 | 每个竞品都写出了"不解决什么" |
| Q4 | 四层都能举出具体名称；十类横切面都有"有/无"的结论 |
| Q5 | 有一份自己跑过的最小示例 + 一张按任务索引的接口地图 |
| Q6 | 能说出三种特化路径的选择依据 |

## 强制纪律

1. **每条结论必须落到具体位置**（`path:line` 或模块名）。写不出位置 = 没验证 = 是猜测。
2. **区分"官方宣称"与"我观察到的"**。前者加引号注明来源，后者必须能指出证据。
3. **Q4 之前不许打开源码文件**（除了 `README` / `docs/index` / `pyproject`）。先建外框，再进内部——顺序反了会被细节淹没。

# 八、验收标准

做完之后逐项自检：

| # | 检查 | 不合格的样子 |
| :--- | :--- | :--- |
| 1 | 能不能用一句话说清"它是什么类别 + 不是什么" | 只能说"它是一个高性能 XX 库" |
| 2 | 能不能说出"什么时候**不该**用它" | 说不出适用边界 |
| 3 | 定位句四要素是否填满 | 缺"与竞品在哪分道扬镳" |
| 4 | 竞品关系是否分对了（竞争/包含/分层） | 一律当竞争对手 |
| 5 | 垂直四层是否都能举例 | 只说得出模块层（目录树） |
| 6 | 横切面是否扫过，而不是只看了主流程 | 完全没提日志/异常/缓存/生命周期 |
| 7 | 是否有一份**自己跑过**的最小示例 | 只抄了 README 的代码 |
| 8 | 接口地图是否按任务索引 | 按 API 字母序排列 |
| 9 | 是否产出了"不必读清单" | 打算全读 |
| 10 | 是否把学到的技术分成了"通用/领域/项目特有" | 全部混在一起 |
| 11 | **六种边界**是否逐条有答案 | 边界只复述了 README 的限制说明 |
| 12 | **场景边界**是否给出反例 | 说不出"什么时候不该用它"（第 2 项的具体化） |
| 13 | **性能边界**是否有临界点 | 只说"它比 X 快"，没有"规模多小就不划算" |
| 14 | 边界是否**从外侧**核对过 | 没看过下游仓库，没数过下游的适配层 |

第 6 项是最容易漏的，也是区分"读过"和"读懂"的分水岭：**能不能说出这个项目的异常体系**，几乎是"有没有真读进去"的单点测试。

第 11–14 项是同一件事的四个侧面：**边界只能从关系里推，且必须用外侧证据核对**。只抄 README 的限制说明，等于把营销话术当结论。

# 九、反模式

| 反模式 | 表现 | 修正 |
| :--- | :--- | :--- |
| **从 README 开始顺读** | 读了 20 分钟还在看"特性列表" | 先做 Q2 定位，再读 |
| **把能力清单当内容** | Q4 产出一张"支持 A/B/C/D"的表 | 换成垂直四层分解 |
| **只看纵向不看横向** | 目录树画得很漂亮，说不出日志怎么开 | 十字扫描 |
| **把"包含"当"竞争"** | 说 FlashInfer 和 FlashAttention 是竞品 | 画嵌套图 |
| **问"它是什么"不问"为什么需要它"** | 复述官方文案 | 用反推法（痛点→触发条件→反例） |
| **忽略历史** | 读了一堆废弃代码 | 先读 CHANGELOG / deprecation |
| **不区分宣称与观察** | 把营销话术当事实 | 每条结论标来源 |
| **Q5 只抄 README** | 示例跑不起来 | 自己跑一遍 |
| **追求读完** | 卡在 30% 放弃 | 用时间盒 + 停手条件 |
| **不产出可复用物** | 读完就忘 | 必须产出：定位句 / 接口地图 / 通用手法 / 提问清单 |
| **边界只抄自述** | 边界 = README 的"限制"一节 | 边界从关系推，用下游适配层核对 |
| **边界当成独立问题** | 定位做完再单独去"查限制" | 在 Q2 的每条关系上顺手记边界 |
| **只写能力不写反例** | 场景边界写成"它适合高并发场景" | 必须给出"什么时候不该用它" |

## 一个特别值得警惕的陷阱

```text
把"实现细节"当成"领域规律"
```

例：看到 FlashInfer 用 `Wrapper` 命名，就总结"LLM kernel 库应该用 Wrapper"。

**检验方法**：换一个同类项目，这个名字还成立吗？换一个领域呢？

- 换项目不成立、换领域也不成立 → 项目特有，记住即可
- 换项目成立、换领域不成立 → 领域知识
- 换领域也成立 → 通用工程手法（"用 Wrapper 适配外部工作负载形态"确实属于这一类）

这一步是 [动作四](#动作四--复用技术把可迁移的东西抽出来) 的实操检验。

下面补齐 Q1 的缺口、Q4 的两把刀、Q5、Q6。

## Q1 补：什么时候**不**需要 FlashInfer

反推法（痛点 → 触发条件 → 反例）：

| 触发条件 | 反例（不需要它） |
| :--- | :--- |
| 请求长度不一 + KV Cache 分页 | 离线批处理、定长输入 |
| continuous batching + prefill/decode 混合 | 单请求、纯 prefill |
| decode 阶段每请求 1 token、GPU occupancy 低 | 计算密集型 prefill 主导 |
| 需要 top-k/top-p/min-p 融合采样 | 贪心解码 |

→ **适用边界 = serving 场景。** 离线/定长/单请求场景，它的复杂度收益显著下降。

## Q2 补：横向关系分对了没有

flashinfer.md 已经正确区分了两种：

```text
与 FlashAttention ：包含关系（FlashInfer 把 FA-2/3 当一个 backend）
与 TVM           ：分层关系（编译器基础设施 vs 领域 kernel 库）
```

第 1 条尤其值得学：它明确写了"这两个非常容易混淆"，然后**画了嵌套图而不是对照表**——这正是 [关系三](#关系三--横向同一问题的其他解) 里"包含 ≠ 竞争"的正确处理。

## Q4 补：垂直四层

```text
实体层：BatchDecodeWithPagedKVCacheWrapper        flashinfer/decode.py:967
        CUDAGraphBatchDecodeWithPagedKVCacheWrapper  flashinfer/decode.py:2977

        norm/ quantization/ comm/ mamba/ kda_kernels/ logits_processor/ …）
```

**读法示范**（这一步才叫做"理解内容"，而不是"列能力"）：

| # | 横切面 | 证据 |


**注意最后一行**：`__main__.py` 的存在本身就是一个高信息量的发现——它说明这个项目的痛点不只是"kernel 慢"，还有"**装不上/编不出/缓存对不上**"。

# 十一、与并行学习法的关系

两套方法不是替代，是**互补的正交方向**：

| | [并行学习法](./并行学习法.md) | 关系定位法 |
| :--- | :--- | :--- |
| 对象 | 一类系统的 N 个实现 | 一个项目 |
| 手段 | 并排填表，找共性与差异 | 向外看关系，向内切两刀 |
| 核心产出 | 领域不变量 + 设计空间 | 定位句 + 接口地图 + 通用手法 |
| 回答 | "这个领域里什么是必然的" | "这个东西是什么、怎么用、怎么改" |
| 时间尺度 | 一周级 | 半天级 |

**配合用法**：

```text
关系定位法（半天）→ 判断"这个项目值不值得深读"
        ↓ 值得
并行学习法（一周）→ 把它和同类项目并排，读出整个领域
        ↓
回到关系定位法 → 用并行学习得到的"设计空间"重新定位每个项目
```

**两次实战已经形成闭环**：

- 先用 [并行学习法](./并行学习法.md) 处理了四个推理框架（vLLM/SGLang/llama.cpp/stable-diffusion.cpp）和两个 kernel DSL（Triton/TileLang）
- 而 vLLM/SGLang 正是 FlashInfer 的**下游**
- 于是：并行学习给出了"推理框架这一层在做什么"，关系定位给出了"FlashInfer 在下游契约下必须保证什么"

**这才是这两套方法合起来的力量**：单看 FlashInfer，你不知道它为什么要保证两个 minor 版本的 API 兼容；看过 vLLM/SGLang 之后，这个约束自动有了来源。

反过来说：**只做关系定位不做并行学习，你的"关系"是猜的**——因为关系网的另一端你并不了解。

# 十二、提问清单模板

可直接复制使用。每问后面留空，答不出来就是没读到。

## Q0 定位（10 min）

```text
它是什么类别的"东西"？（库/框架/编译器/运行时/服务/规范/工具链）
官方定位句（逐字抄，注明出处）：
它不是什么（三条，最重要）：
  1.
  2.
  3.
类比：可以把它理解成 ____
```

## Q1 问题与场景（20 min）

```text
在它出现之前，谁在做这件事？怎么做？痛在哪？

痛点：
触发条件：                    ← 什么条件下才发作？
反例（不需要它的场景）：        ← 关键，决定适用边界
```

## Q2 关系定位（30 min）

```text
上游（依赖栈，按物理层次重排）：
  硬件 → 驱动 → 编译器/工具链 → 库 → 框架 → 本项目

  核心能力由上游提供，还是自己实现？      ← 薄包装 or 真实现？
  硬依赖 vs 可选 backend：

下游（谁靠它活着）：
  谁 import 它：
  官方承诺了哪些保证（兼容性/语义一致性）：
  这些承诺是被谁逼出来的？

横向（竞品/姊妹）：
  候选：
  关系是 竞争 / 包含 / 分层？（三选一，别一律当竞争）
  分道扬镳的那一格：

历史：
  它替换了：
  它要被什么替换：
  不必读清单（废弃/兼容层）：

【定位句】____ 依赖 ____ 提供 ____，为 ____ 提供 ____，
```

# 一句话总结

```text
程序是它所处关系的总和。
所以：先定位，后阅读。
      向外看四种关系（上游 / 下游 / 横向 / 历史），
      向内切两刀（垂直四层 / 横向十类），
      向前走两步（怎么用 / 怎么改）。

边界不是第五个问题，它是这段关系的补集：
  上游给能力边界，下游给职责边界，
  竞品给相对边界，历史给兼容边界。
  ——所以边界不可能在自己仓库里读全，必须去下游数。

定位的产出不是"我知道了"，而是四件可复用的东西：
  一句定位句、一张接口地图、一份边界清单、一份"什么是通用的"分类。
```
