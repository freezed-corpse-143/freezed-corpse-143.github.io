# 并行学习法

一句话：

> 当你要学的不是"一个系统"而是"一类系统"时，**不要逐个读**，而是把它们并排放进同一张表——先逼出共性，再读出差异，最后定位各自的核心技术。

它是 [`经验之谈.md` 的「类预训练」元学习法](../经验之谈.md) 在"一类系统"这个场景下的具体执行器。

---

# 它解决什么问题

逐个读项目的三个病：

| 病 | 症状 | 后果 |
| :--- | :--- | :--- |
| README 摘要化 | 读完能复述每个项目的介绍，但说不出它们的差别 | 知识是 N 份孤立的目录，不是一张地图 |
| 局部最优 | 以为某个项目的做法"就是标准答案" | 把实现细节误当成领域不变量 |
| 没有对照组 | 无法判断"这里为什么这样设计" | 只能记住结论，无法迁移和判断 |

并行学习的本质是：

```text
同一个问题的 N 个不同实现
= 关于这个问题的 N 个对照解
= 一场天然的消融实验（ablation）
```

单看一个项目，你看到的是"一个答案"。
并排看 N 个，你看到的是**答案背后的设计空间**——哪些格子所有实现都填满了（领域不变量），哪些格子各填各的（自由选择），哪些格子只有一家填得漂亮（核心技术）。

这三类格子的区分，才是学习的真正产出。

## 为什么它比"多读几个项目"有效

呼应「类预训练」法里的那条元原则：

```text
学习速度 ≈ 单位时间内接触的高质量样本密度
```

并行学习把样本密度的分母直接改掉了：

```text
逐个读：  样本 = N 个项目                    （N 个不相干的样本）
并行读：  样本 = N 个项目 × M 个维度          （N×M 个可比较的单元）
```

而且这 N×M 个单元不是随机采样的——**每一个单元都自带 N-1 个对照组**。同样是"读了 4 个项目"，逐个读得到 4 个印象，并行读得到 4×8 = 32 个带对照的判断。

# 核心思想（六条）

## 1. 学习单位是"维度"，不是"项目"

这是整套方法的第一性改变。

```text
错误的心智模型：          正确的心智模型：
  ├─ 项目 A                  ├─ 维度 1 ── A / B / C / D
  ├─ 项目 B        →         ├─ 维度 2 ── A / B / C / D
  ├─ 项目 C                  ├─ 维度 3 ── A / B / C / D
  └─ 项目 D                  └─ 维度 4 ── A / B / C / D
```

前者是图书馆的目录，后者是坐标系。**只有坐标系里的位置才能比较、才能内插、才能外推。**

## 2. 共性先于差异

先问"所有实现都必须解决什么"，再问"它们怎么解决"。

共性 = **领域不变量**。它告诉你：这个领域里有哪些事是无论如何都躲不掉的。这是最可迁移的知识——换一个新系统，这些格子照样存在。

在推理框架的例子里，共性抽象出来是三件事：

```text
语义正确性：正确解析模型、构图、管理状态、产生结果
资源调度：  让权重、缓存、请求和计算适配有限的内存与设备
时间优化：  减少空转、复制、重复计算和调度间隙
```

在 kernel 编译器（Triton / TileLang）的例子里，收敛到了结构相同的三件事：

```text
语义正确性：正确地把 Python 语义翻成 IR，再翻成机器语义
硬件映射：  把"块"和"tile"映射到 warp / shared / MMA / TMA
时间优化：  减少空转、减少搬运、搬运与计算重叠、减少编译时间
```

对照一下真正的重合度（不要夸大成"完全一样"）：

| | 推理框架 | kernel 编译器 | |
| :--- | :--- | :--- | :--- |
| 1 | 语义正确性 | 语义正确性 | **逐字相同** |
| 2 | 资源调度 | 硬件映射 | 领域特化（都是"第 2 层把抽象落到物理"） |
| 3 | 时间优化 | 时间优化 | **逐字相同** |

**两个完全不同的领域，第 1 条和第 3 条逐字相同，第 2 条是同一个位置的领域特化**——这本身就是这条方法有效的证据。而且它提示了一个更强的猜想：任何计算系统都逃不掉"正确性 / 落到物理 / 省时间"这三件事，第 2 条的内容随领域变，位置不变。

## 3. 差异即设计空间

每一处差异都不要记成"A 是这样、B 是那样"，而要翻译成：

```text
这是一个设计选项
  选项甲（A 采取）：擅长 __，代价是 __
  选项乙（B 采取）：擅长 __，代价是 __
  选择由什么决定：___
```

例：

> 模型格式多样性由谁吸收？
> - vLLM/SGLang：**运行时**吸收（支持 HF/safetensors/多格式/远程加载）
> - llama.cpp：**转换工具**吸收，运行时只认 GGUF
> - 选择由什么决定：**是否要做服务化的多模型平台**。运行时吸收=灵活但复杂；工具期吸收=运行时简单但接入受限。

这样记下来的差异才是可迁移的——遇到新系统时你能直接问"它选的是哪一边，为什么"。

## 4. 抽象即"面"，面必须正交且可迁移

统一框架不是目录树，是**职责切面**。

一张合格的面清单要满足：

| 判据 | 说明 |
| :--- | :--- |
| 正交 | 一个能力只属于一个面，不重叠 |
| 完备 | 每个项目在每个面上都有答案，不存在"其他/不适用"格 |
| 可迁移 | 换一个同类系统，这套面基本还能用（只改内容不改骨架） |
| 可容纳 N+1 | 下一个同类项目能直接插进来变成新的一列 |

## 5. 四问检验：状态 / 决策 / 资源 / 隔离层

每读到一个类、一个模块、一个设计，问同样四个问题：

```text
它管理什么状态？
它作出什么决策？
它消耗什么资源？
它把什么不稳定性隔离在了哪一层？
```

配套的判据（来自推理框架实践）：

> 如果一个能力同时影响加载、调度、执行、缓存和输出，它就是**切面**，不该塞进某个单一 engine 类里理解。

这条判据比"读源码"有用得多——它让你能一眼识别出哪些是主流程阶段，哪些是横切能力。

## 6. 抽象会变，骨架不变

这是最值得记住的一条元观察。

两次实践里"面"的具体名字并不一样。把两份文档的统一框架树按**骨架槽位**对齐（两列都是各自文档里的原文名）：

| 骨架槽位 | 推理框架.md | TileLang与Triton.md |
| :--- | :--- | :--- |
| 接入 | **接入面**：HTTP / CLI / C API / Python API | **接入面**：Python API / `@jit` / 显式 compile / AOT / CLI |
| 前置处理 | **请求面**：模板、分词、参数校验 | **前端语言层**：DSL 构件（block、tile、内存空间、循环原语） |
| 表示与转换 | **工件面**：模型格式、配置、权重解析、量化转换 | **前端降级面**：Python AST → 前端 IR（TTIR / TIRX） |
| 控制 | **控制面**：调度、批处理、生命周期、分布式协调 | **编译控制面**：pass 流水线、布局推导、流水线规划、调优搜索 |
| 状态 | **状态面**：KV Cache、latent、RNG、前缀树 | 并入控制面（编译缓存 / autotune 状态）——**没有请求状态** |
| 计算 | **数据面**：模型 forward、计算图、算子、kernel | **数据面**：IR → 目标源码 → 机器码 |
| 资源 | **资源面**：显存、内存、mmap、权重驻留 | 并入控制面（shared/寄存器分配）——**没有运行时资源争夺** |
| 平台 | **平台面**：CUDA / ROCm / Metal / Vulkan / CPU | **平台面**：CUDA / HIP / Metal / CPU / WebGPU / Ascend |
| 运行时 | 并入控制面 + 资源面 | **运行时面**：kernel 句柄、launch、缓存、profiler、解释执行 |
| 产物 | 隐式（API 响应） | **产物面**：cubin / hsaco、生成的 C/CUDA 源码、AOT 宿主 |

但**底层骨架是同一条**：

```text
接入 → 表示 → 控制 → 状态 → 计算 → 资源 → 平台 → 产物
                            ＋ 贯穿全部层的切面
```

一个诚实的观察：**第二列不是第一列的改名，而是按"这个领域有什么"重新分布的**。kernel 编译器没有"请求"，于是"状态面"和"资源面"塌进了控制面，同时长出了新的一格"运行时面"（launch + 缓存 + profiler），因为编译产物需要一个独立的运行环节。**槽位会重组，但骨架上的槽位一个都没丢。**

这才是"可迁移"的准确含义：不是把面原样搬过去，而是**知道槽位序列，然后按新领域重新划边**。

看懂这一点之后，学任何一个新的计算系统，你都能先把这个骨架默写出来，再往里填这个系统特有的内容。**这就是"元学习"相对于"学会一个框架"的全部意义。**

# 与「类预训练」元学习法的关系

并行学习法不是另一套方法论，它是对「类预训练」四阶段中**前两阶段的执行器**：

| 类预训练阶段 | LLM 类比 | 并行学习法做什么 |
| :--- | :--- | :--- |
| Pattern Exposure | Pretraining | **提供高密度采样器**：把"读 N 个项目"变成"读 N×M 个带对照的单元" |
| Constraint Alignment | SFT | **提供对齐目标**：仿写的不是某个项目，而是"所有项目都填满的那张共性表" |
| Feedback Optimization | RL | 不涉及。必须靠真项目、真 bug、真性能压测 |
| Self-Evolution | Self-play | 不涉及。但共性骨架会变成你提出新设计的坐标系 |

关键在第二阶段：**模仿的对象不该是"某个优秀项目"，而该是"共性表的交集"**。

初学者的问题不是没有创意，是"不知道什么叫好"。并排读之后，"好"有了可操作的定义：

```text
好 = 在共性表的每一个格子里
    都没有交出明显更差的答案
    （而不是"在某一个格子里特别巧"）
```

# 步骤

八个步骤，S1–S3 是"建表"，S4–S6 是"读表"，S7–S8 是"收口"。

## S0 选对象

**输入**：一个想搞懂的领域。
**判据**：

| 要求 | 说明 |
| :--- | :--- |
| 同一问题域 | 它们必须都在回答同一个问题。vLLM 和 llama.cpp 都在回答"怎么跑 LLM" |
| 实现路径不同 | 差异要有信息量。四个都是 PyTorch 重写版就没意义了 |
| N ∈ [2, 5] | N=1 没有对照；N=2 只能读出"A/B 二选一"；N≥6 填表成本爆炸 |
| 有源码可读 | 能给出 `file:line` 级锚点，而不是只看官方博客 |

**产出**：`(对象列表, 它们的共同问题一句话)`

## S1 划面（不看代码）

**这一步刻意不看代码。**先凭对领域的已有认知，把"任何这类系统都必须处理的事"列出来。

**动作**：拿上文的骨架当骨架，逐个改写成该领域的具体名字。

```text
接入 → 表示 → 控制 → 状态 → 计算 → 资源 → 平台 → 产物 ＋ 切面
```

例（推理框架 → kernel 编译器）：

| 骨架 | 推理框架 | kernel 编译器 |
| :--- | :--- | :--- |
| 表示 | 模型工件与加载层 | 前端语言层 + 前端降级面 |
| 控制 | 调度与推理状态层 | 编译控制面 |
| 产物 | — | 产物面（cubin/PTX/生成源码） |

**判据**：划完之后自问"如果有一个第 N+1 个同类项目，它能被这几条面装下吗？"

**产出**：面清单（8–12 条）。

## S2 建统一框架树

把面排成一个层级树，标出层与层之间的数据流。

这一棵树的形态和目标文档一致：

```text
<领域名>
├─ 接入面：外部怎么进来
├─ 表示面：内部用什么表示
├─ 控制面：谁决定下一步做什么
├─ 状态面：什么被持久化、生命周期多长
├─ 计算面：真正干活的那一层
├─ 资源面：受什么约束
├─ 平台面：适配了哪些后端
└─ 产物面：交出什么
```

**这一棵树本身就是可复用资产。**下次学同类系统，可以直接拿来改。

**产出**：统一框架树 + 一句话的"根本区别"。

> 判断"根本区别"的句式：**不是"支持哪些 X"，而是"把哪一层当作自己的核心抽象"。**
> 例："四个项目的根本区别，不是支持哪些模型，而是把哪一层当作自己的核心抽象。"

## S3 并排填表（N 列）

这是最耗时的一步，也是唯一无法省略的一步。

**动作**：对每一个面，建一张"面 × 项目"的表，每格填**可核查的具体事实**。

| | 项目 A | 项目 B | 项目 C |
| :--- | :--- | :--- | :--- |
| 面 1 · 接入 | `path/to/entry.py:120` | … | … |
| 面 2 · 控制 | … | … | … |

**两条硬纪律**：

1. **空格是信号，不是失败。** 某个项目在某个面上没有对应物，往往说明它少了一层——这本身是重大发现（例：llama.cpp 没有服务化调度器，因为"调用者拥有生成循环"）。
2. **每条断言必须有锚点。** 写 `vllm/v1/engine/core.py:630-656`，不写"在 engine 模块里"。不可核查的断言会让整张表失去价值——因为你下次无法验证自己是否理解对了。

**产出**：8–12 张对照表。

## S4 抽共性 → 领域不变量

**动作**：逐列向下读，找出**每一列都填满、且填法结构一致**的格子。

**产出格式**：

```text
领域不变量：<一句话>
证据：A 在 __，B 在 __，C 在 __，D 在 __（四家都做了这件事）
```

再往上再抽一层：这些不变量能不能收敛到少数几个根本问题？

推理框架的收敛结果：

```text
1. 语义正确性  2. 资源调度  3. 时间优化
```

**判据**：这些不变量是否可以脱离具体项目独立陈述？如果一句话里必须出现项目名，说明它还不是不变量。

## S5 读差异 → 设计空间

**动作**：逐行向右读，找出**同一面上各项目做法不同**的地方。

**每一条差异都要翻译成"设计选项 + tradeoff + 决定因素"**，而不是"甲这样、乙那样"。

模板：

```text
Q：<这一层由谁负责？>
  - 选项甲（<项目>）：<做法> —— 擅长 __，代价 __
  - 选项乙（<项目>）：<做法> —— 擅长 __，代价 __
  决定因素：___
```

**判据**：能否在不提项目名的情况下说出这个选项的适用条件？能，才算真的读懂了。

## S6 定位核心技术

**动作**：为每个项目单独列 8–12 条"它独有的、非平凡的技术点"。

注意和 S5 的分工：

| 步骤 | 视角 | 回答 |
| :--- | :--- | :--- |
| S5 差异 | 横向（同一面比各家） | 这个面上有哪些设计选项 |
| S6 核心技术 | 纵向（一家看自己） | 这一家凭什么跟别人不一样 |

**判据**：这条技术如果是所有同类项目都有的，它属于 S4（不变量），不该出现在这里。

## S7 横切验证：追踪一个最小单元

抽象建完之后必须验一遍，否则可能是一张漂亮的错表。

**动作**：设计一个"最小完整单元"，在每个项目里从头到尾追一遍。

```text
推理框架：一个最小请求   → 从 HTTP 进来到第一个 token 出去
kernel 编译器：一个最小 kernel → 从 Python 函数到机器码
```

每个项目只回答固定几问（问法必须完全一致，否则无法对照）：

```text
1. 外部输入在哪里进入？
2. 什么时候做第一次转换（tokenize / 降级成 IR）？
3. 内部表示对象是什么？
4. 谁决定下一次计算？
5. 谁调用最底层（模型 forward / nvcc）？
6. 结果在哪里变回外部形式？
```

**判据**：如果这六问在某项目上答不出来，说明 S1 划的面漏了一条，回去补。

**这一步的副产品极有价值**：它就是给新手的"最短上手路径"。

## S8 沉淀提问清单

把整张表压缩成一组**不依赖具体项目**的问题。这是最终交付物——下次遇到同类系统，拿着问题清单就能开工。

示例（推理框架版）：

```text
- 它管理什么状态？生命周期多长？谁能复用？
- 它把什么不稳定性隔离在了哪一层？
- 权重、缓存、请求、计算四者如何竞争同一种资源？
- 它是"运行时吸收复杂度"还是"离线工具吸收复杂度"？
- 同一份语义，它允许换几个后端？换后端的成本在哪？
```

# 验收标准

一张并行学习的表做完了，自检：

| # | 检查 | 不合格的样子 |
| :--- | :--- | :--- |
| 1 | 每张表有没有"其他 / 不适用"格 | 有 → 面划错了，或该项目缺这一层（那就该明说，而不是塞进"其他"） |
| 2 | 每条事实是否可核查 | 出现"大致在 xx 模块"、纯定性描述 |
| 3 | 共性是否脱离项目名也能陈述 | 一句话里必须带项目名 |
| 4 | 差异是否带 tradeoff 和决定因素 | 只写"A 用 X，B 用 Y" |
| 5 | 骨架能否套到下一类系统上 | 换领域后一条都用不上 → 学到的是细节不是结构 |
| 6 | 最小单元六问是否都答得出 | 某项目答不出 → 抽象有洞 |

# 反模式

| 反模式 | 表现 | 修正 |
| :--- | :--- | :--- |
| 写成 N 份 README 摘要 | 文档结构是"项目 A 介绍 / 项目 B 介绍" | 结构必须是"面 1 / 面 2 / 面 3" |
| 只写差异不写共性 | 全篇在比高下 | 先出共性表，共性往往比差异更有价值 |
| 概念混淆 | 把某项目的实现细节当成领域规律 | 问：换一家还会这样吗？ |
| 把入口当引擎 | 大篇幅写 HTTP 层、CLI 参数 | 入口可以替换，内部表示才稳定 |
| 无锚点断言 | "它应该是用 XX 实现的" | 每句话都要能点开看 |
| 一口气上 8 个项目 | 表填不完，半途而废 | N ∈ [2,5]，先小后大（curriculum） |
| 停在建表不前进一步 | 表很全，但说不出设计空间 | 必须走到 S5、S6，表格只是中间产物 |

# 两次实践复盘

## 案例一：四个推理框架

```text
对象：vLLM / SGLang / llama.cpp / stable-diffusion.cpp
共同问题：怎么把模型跑起来并服务化
产出：8 个面 × 4 列
抽取到的领域不变量骨架：
  接入 → 请求 → 控制 → 状态 → 数据 → 资源 → 平台 → 工件
```

**收获最大的一条**：四个项目的根本区别不是"支持哪些模型"，而是**把哪一层当作自己的核心抽象**——vLLM 是请求调度器，SGLang 是状态感知调度器，llama.cpp 是张量运行时，stable-diffusion.cpp 是管线编排器。

这句话是并排读了四家才可能得到的，读任何一家都得不到。

## 案例二：两个 kernel DSL

```text
对象：Triton / TileLang
共同问题：怎么用 Python 描述高性能 GPU kernel
产出：8 个面 × 2 列
抽取到的骨架：
  接入 → 前端语言 → 前端降级 → 编译控制 → 数据 → 平台 → 运行时 → 产物
```

**收获最大的一条**：

```text
Triton     → 看"一个块级语言如何被一步步降解成线程级指令"
TileLang   → 看"一条 tile 编译流水线长什么样"
```

以及一个可复用的判据：

> 这一步是谁决定的——用户显式声明，还是编译器推导？
> 这是 Triton 与 TileLang 全部分歧的源头。

## 两次对比的元结论

| | 案例一 | 案例二 |
| :--- | :--- | :--- |
| N | 4 | 2 |
| 面的名字 | 请求面 / 工件面 / 资源面 … | 前端语言层 / 编译控制面 / 产物面 … |
| 底层骨架 | 接入 → 表示 → 控制 → 状态 → 计算 → 资源 → 平台 → 产物 | **同一条** |

**骨架在跨领域复用，名字在领域内特化。** 这就是这套方法能沉淀下来的东西——你带走的不是四个推理框架的知识，而是一台"理解计算系统"的机器。

# 可迁移的提问清单（模板）

遇到任何一个新的计算系统／框架／中间件，先问这一组：

## 定位

- 它把**哪一层**当作自己的核心抽象？
- 用一句话说清"它不是别的什么"（例：不是模型前向 + API）
- 它的"根本区别"句式：不是"支持哪些 X"，而是"把哪一层当核心"

## 结构

- 接入面在哪？内部表示对象是什么？
- 谁决定下一步做什么？（调度器 / 编译器 / 调用者）
- 状态分别由谁拥有、生命周期多长、能否跨请求复用？
- 计算面最底层的调用是什么？谁发出它？
- 受什么资源约束？约束不足时怎么退化？
- 支持哪些平台，适配的三层（能力发现 / 统一运行接口 / kernel 构建）分别落在哪？
- 交出什么产物？

## 判据

- 哪些能力是**切面**（同时影响加载、调度、执行、缓存、输出）？
- 每处设计差异的**决定因素**是什么？
- 它把什么**不稳定性**隔离在了哪一层？
- 这个设计选项的**代价**是什么？

## 收口

- 这个领域**躲不掉的几件事**是什么？（通常能收敛到 3 条）
- 换一个新的同类系统，这套骨架还成立吗？
