# GROUPS

在 PostgreSQL 中，窗口函数的 `GROUPS` 是 **窗口框架（Window Frame）** 定义中的一种单位，用于指定当前行参与计算的行范围。

它是在 **PostgreSQL 11** 版本中引入的，与 `ROWS` 和 `RANGE` 并列。

为了让你彻底理解，我们从核心概念、语法、与 `ROWS` / `RANGE` 的区别，以及实战案例来拆解。

---

### 1. 核心概念：什么是 GROUPS？

在窗口函数中，`ORDER BY` 决定了行的排序。`GROUPS` 框架单位表示：**以“排序值相等的组”为单位**来计算偏移量。

- 每一组由 `ORDER BY` 表达式值相同的所有行组成。
- `GROUPS BETWEEN ...` 指的是**当前行所在的组**向前或向后移动多少个**组**。

---

### 2. 语法结构

```sql
SELECT 
    column,
    window_function() OVER (
        PARTITION BY partition_column 
        ORDER BY order_column 
        GROUPS BETWEEN frame_start AND frame_end
    )
FROM table;
```

**常用框架选项：**
- `GROUPS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`（默认）
- `GROUPS BETWEEN 1 PRECEDING AND 1 FOLLOWING`
- `GROUPS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING`
- `GROUPS BETWEEN 2 PRECEDING AND 2 FOLLOWING`

---

### 3. GROUPS 与 ROWS / RANGE 的本质区别

| 框架单位   | 定义依据               | 行数是否固定                       | 典型场景                                                |
| :--------- | :--------------------- | :--------------------------------- | :------------------------------------------------------ |
| **ROWS**   | 物理行数               | 固定（如前后 3 行）                | 移动平均、滑动计数                                      |
| **RANGE**  | 数值/日期差值          | 不固定（包含所有差值在范围内的行） | 过去 7 天内的所有订单                                   |
| **GROUPS** | **排序字段值相同的组** | 不固定（按组偏移）                 | 按排名/等级进行分组统计（如：当前等级与前两个等级对比） |

---

### 4. 实战举例（让你秒懂）

假设有如下销售表 `sales`：

| id   | salesperson | year | amount |
| :--- | :---------- | :--- | :----- |
| 1    | Alice       | 2020 | 100    |
| 2    | Alice       | 2021 | 150    |
| 3    | Alice       | 2022 | 200    |
| 4    | Bob         | 2020 | 80     |
| 5    | Bob         | 2021 | 120    |
| 6    | Bob         | 2022 | 180    |
| 7    | Carol       | 2021 | 90     |
| 8    | Carol       | 2022 | 110    |

**需求**：按年份排序，计算**当前年份**以及**前一个年份组**和**后一个年份组**的平均销售额。

```sql
SELECT 
    salesperson,
    year,
    amount,
    AVG(amount) OVER (
        ORDER BY year 
        GROUPS BETWEEN 1 PRECEDING AND 1 FOLLOWING
    ) AS avg_neighbor_groups
FROM sales
ORDER BY year, salesperson;
```

**执行过程解析：**
- `ORDER BY year` 将数据分为组：2020 组（2 行）、2021 组（3 行）、2022 组（3 行）。
- 对于 **2020 年** 的行：框架包含前 1 组（无）+ 当前组（2020）+ 后 1 组（2021） = 共 5 行，平均值为 `(100+80+150+120+90)/5 = 108`。
- 对于 **2021 年** 的行：框架包含 2020 + 2021 + 2022 = 全部 8 行，平均值为 `(100+80+150+120+90+200+180+110)/8 = 128.75`。
- 对于 **2022 年** 的行：框架包含 2021 + 2022 = 6 行，平均值为 `(150+120+90+200+180+110)/6 = 141.67`。

# FILTER

在 PostgreSQL 中，`FILTER` 是用于**聚合函数**的一个非常强大的子句，它允许你在进行聚合计算时**有条件地过滤参与计算的行**，而不会影响整体的结果集行数。

很多初学者容易混淆 `FILTER` 和 `WHERE`，以及 `FILTER` 和 `CASE WHEN`，下面我帮你彻底理清。

---

## 1. 核心概念：FILTER 是什么？

`FILTER` 子句跟在聚合函数（如 `SUM`, `AVG`, `COUNT`, `MAX`, `MIN`, `STRING_AGG` 等）后面，语法如下：

```sql
aggregate_function(expression) FILTER (WHERE condition)
```

**关键点：**
- 只有**满足 `WHERE` 条件**的行才会参与该聚合函数的计算。
- 不满足条件的行会被**忽略**（就像被过滤掉了一样）。
- **结果集的行数不会改变**（这是与 `WHERE` 最大的区别）。

---

## 2. FILTER 与 WHERE 的区别（最重要！）

| 特性 | `WHERE` 子句 | `FILTER` 子句 |
| :--- | :--- | :--- |
| **作用范围** | 过滤**整个查询**的行 | 仅过滤**某个特定聚合函数**的行 |
| **结果集行数** | **会减少**（不满足条件的行被丢弃） | **不会减少**（所有行依然返回） |
| **使用位置** | 在 `FROM` 之后，`GROUP BY` 之前 | 在聚合函数内部 |
| **能否多个条件** | 一个查询只能有一个 `WHERE` | 可以在多个聚合函数上使用不同的 `FILTER` |

### 直观对比示例

假设有订单表 `orders`：

| id | product | category | amount |
| :--- | :--- | :--- | :--- |
| 1 | A | 电子产品 | 100 |
| 2 | B | 电子产品 | 200 |
| 3 | C | 图书 | 50 |
| 4 | D | 图书 | 80 |

**需求**：按产品类别分组，同时统计**总销售额**和**仅电子产品的销售额**。

```sql
SELECT 
    category,
    SUM(amount) AS total_sales,                      -- 所有订单
    SUM(amount) FILTER (WHERE category = '电子产品') AS electronic_sales  -- 只统计电子产品
FROM orders
GROUP BY category;
```

**结果：**

| category | total_sales | electronic_sales |
| :--- | :--- | :--- |
| 电子产品 | 300 | 300 |
| 图书 | 130 | NULL（因为图书类没有电子产品） |

**如果用 `WHERE` 会怎样？**
```sql
SELECT category, SUM(amount) 
FROM orders 
WHERE category = '电子产品' 
GROUP BY category;
```
结果只有一行（电子产品），图书类直接消失了。这就是区别！

---

## 3. FILTER 与 CASE WHEN 的区别

在没有 `FILTER` 的年代，我们通常用 `CASE WHEN` 模拟条件聚合：

```sql
-- 使用 CASE WHEN（传统方式）
SUM(CASE WHEN category = '电子产品' THEN amount ELSE 0 END)

-- 使用 FILTER（更优雅的方式）
SUM(amount) FILTER (WHERE category = '电子产品')
```

**区别：**
- `CASE WHEN` 会将不满足条件的值设为 `0`（或 `NULL`），这会影响计算（比如 `AVG` 会把 0 算进去）。
- `FILTER` 是**直接忽略**不满足条件的行，语义更清晰，性能也更好（优化器可以更好地处理）。

---

## 4. 实战场景举例

### 场景 1：统计不同维度的指标（最常用）

统计每个部门的**总工资**、**男性工资总和**、**女性工资总和**：

```sql
SELECT 
    department,
    SUM(salary) AS total_salary,
    SUM(salary) FILTER (WHERE gender = 'M') AS male_salary,
    SUM(salary) FILTER (WHERE gender = 'F') AS female_salary,
    COUNT(*) FILTER (WHERE gender = 'M') AS male_count,
    COUNT(*) FILTER (WHERE gender = 'F') AS female_count
FROM employees
GROUP BY department;
```

### 场景 2：计算百分比/占比

计算每个产品的**总销量**和**高价值订单（金额 > 100）的占比**：

```sql
SELECT 
    product_id,
    COUNT(*) AS total_orders,
    COUNT(*) FILTER (WHERE amount > 100) AS high_value_orders,
    ROUND(
        100.0 * COUNT(*) FILTER (WHERE amount > 100) / COUNT(*), 
        2
    ) AS high_value_percentage
FROM orders
GROUP BY product_id;
```

### 场景 3：与窗口函数结合使用

统计每个销售人员的**总销售额**以及** 2023 年的销售额**：

```sql
SELECT 
    salesperson,
    SUM(amount) AS total_sales,
    SUM(amount) FILTER (WHERE year = 2023) AS sales_2023,
    SUM(amount) FILTER (WHERE year = 2024) AS sales_2024,
    -- 计算同比增长率（需要处理除零）
    CASE 
        WHEN SUM(amount) FILTER (WHERE year = 2023) = 0 THEN NULL
        ELSE (SUM(amount) FILTER (WHERE year = 2024) - SUM(amount) FILTER (WHERE year = 2023)) 
             / SUM(amount) FILTER (WHERE year = 2023) * 100
    END AS growth_rate
FROM sales
GROUP BY salesperson;
```

### 场景 4：多条件 FILTER（使用 AND/OR）

统计**已发货**且**金额大于 500** 的订单数：

```sql
SELECT 
    customer_id,
    COUNT(*) FILTER (WHERE status = 'shipped' AND amount > 500) AS large_shipped_orders
FROM orders
GROUP BY customer_id;
```

---

## 5. FILTER 的限制与注意事项

1. **只能用于聚合函数**  
   `FILTER` 不能用于普通窗口函数（如 `ROW_NUMBER()`、`RANK()`）。  
   ❌ `ROW_NUMBER() FILTER (WHERE ...)` 是**不允许**的。  
   但可以与部分聚合窗口函数结合（如 `SUM() OVER()`）。

2. **不能与 `DISTINCT` 同时使用？**  
   实际上可以，但要小心顺序：  
   ```sql
   COUNT(DISTINCT user_id) FILTER (WHERE active = true)
   ```

3. **性能考虑**  
   `FILTER` 通常比 `CASE WHEN` 更高效，因为优化器可以将其转换为更简单的条件聚合计划。

# NTILE

`NTILE()` 是 MySQL 8.0 引入的一个窗口函数，它的核心功能是将一个数据集**尽可能均匀地**划分为指定数量的“桶”（bucket），并为每一行分配其所属的桶编号。

## 核心语法

它的基本用法如下：

```sql
NTILE(n) OVER (
    [PARTITION BY 分组字段]
    ORDER BY 排序字段 [ASC|DESC]
)
```

- ** `n` **：一个**正整数**，指定了要划分的桶的数量。比如 `NTILE(4)` 表示分成 4 个桶。
- ** `PARTITION BY` **：可选。如果使用，`NTILE()` 会在每个分区内独立地分桶，否则就在整个结果集上操作。
- ** `ORDER BY` **：**必需**。它决定了数据分桶的顺序。例如 `ORDER BY salary DESC` 会按薪资从高到低排序，然后把最高的一部分人分到第 1桶。

## 工作原理：如何做到“尽可能均匀”？

`NTILE()` 的精髓在于“尽可能均匀”地分配行数，而不是按值的大小区间划分。

假设总行数为 `R`，要分成 `N` 个桶：
1.  它会计算每个桶的基本行数：`R / N`。
2.  如果 `R` 不能被 `N` 整除，多出来的行（`R % N` 行）会**从第 1 个桶开始，每个桶多分配 1 行**。

**举个例子**：如果有 9 行数据，执行 `NTILE(4)`。
- 9 ÷ 4 = 2 余 1。
- 结果就是：第 1 个桶有 3 行（2+1），第 2、3、4 个桶各有 2 行。

## 典型使用场景

`NTILE()` 非常适用于数据分析和分组的场景：

1.  **百分位分析**：用 `NTILE(4)` 快速计算**四分位数**，`NTILE(10)` 计算**十分位数**，`NTILE(100)` 计算**百分位数**。
2.  **数据抽样**：比如你想随机抽取 10% 的用户进行测试，可以用 `NTILE(10)` 给用户编号，然后筛选出编号为 1 的用户群。
3.  **数据均匀分片**：在需要将大量数据均匀分发给多个并行任务处理时，`NTILE()` 是一个理想的工具。

## ⚠️ 关键注意事项

1.  **MySQL 版本要求**：`NTILE()` 是 MySQL 8.0 及更高版本才有的功能。如果你的数据库是 5.7 或更早版本，需要通过用户变量等方式手动模拟。
2.  **ORDER BY 必须唯一**：如果 `ORDER BY` 的字段有重复值，数据的顺序不稳定，每次查询 `NTILE()` 的结果可能不同，导致“切片漂移”。**建议在 `ORDER BY` 中加上一个唯一键（如 `id`）来保证结果稳定**。
3.  **与 GROUP BY 的搭配**：`NTILE()` 是窗口函数，执行顺序在 `GROUP BY` 之后。如果你想统计每个桶的平均值，需要先用子查询或 CTE 计算出桶编号，再在外层用 `GROUP BY` 聚合。

# 稠密索引和稀疏索引

- 稠密索引：每个记录一个索引
- 稀疏索引：部分记录一个索引

# 聚集索引和非聚集索引

| 索引类型      | 核心定义                                                                    |
| --------- | ----------------------------------------------------------------------- |
| **聚集索引**  | 索引的**叶子节点**存储的是**完整的数据行记录**。也就是说，**索引树本身就是数据表本身**，数据按索引键的顺序物理存储。        |
| **非聚集索引** | 索引的**叶子节点**存储的是**索引列的值 + 指向数据行的指针**（在 InnoDB 中是指向聚集索引键，即主键）。索引树和数据是分离的。 |

# 默认窗口陷阱

## 陷阱 1 省略 ORDER BY

### 错误写法

```sql
SELECT 
    salesperson,
    amount,
    SUM(amount) OVER() AS total_sum  -- ❌ 没有 ORDER BY
FROM sales;
```

### 你以为的结果

你可能以为 `SUM()` 会按照某种逻辑（比如按 `amount` 排序）逐行累计。

### 实际结果

**所有行的 `total_sum` 都等于全表的总和！**

因为在窗口函数中：

- **没有 `ORDER BY` ** 时，窗口框架的默认值是：`RANGE BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`（整个分区所有行）。
- 也就是说，`SUM()` 计算的是**整个表的总额**，而不是你想要的累计和。

### ✅ 正确写法（想要累计和）
```sql
SELECT 
    salesperson,
    amount,
    SUM(amount) OVER(ORDER BY salesperson) AS running_sum  -- ✅ 有 ORDER BY
FROM sales;
```

---

## 陷阱 2：默认窗口框架的规则（ORDER BY 存在时）

即使你写了 `ORDER BY`，也可能会踩坑，因为**默认窗口框架会随 `ORDER BY` 的存在而变化**。

### 默认框架规则（SQL 标准）

| 是否包含 `ORDER BY` | 默认窗口框架                                                 |
| :------------------ | :----------------------------------------------------------- |
| **没有 `ORDER BY` ** | `RANGE BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`（整个分区） |
| **有 `ORDER BY` **   | `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`（从分区开始到当前行） |

看起来合理，但 `RANGE` 的“当前行”定义会导致问题。

---

## 陷阱 3：RANGE 与 ROWS 的混淆（经典坑）

当 `ORDER BY` 列有**重复值**时，`RANGE` 和 `ROWS` 的行为完全不同。

### 示例数据
| id   | category | score |
| :--- | :------- | :---- |
| 1    | A        | 80    |
| 2    | A        | 80    |
| 3    | A        | 90    |
| 4    | A        | 100   |

### 查询 1：使用默认 RANGE
```sql
SELECT 
    id,
    score,
    SUM(score) OVER(ORDER BY score) AS range_sum  -- 默认 RANGE
FROM scores;
```

**结果：**

| id   | score | range_sum                                     |
| :--- | :---- | :-------------------------------------------- |
| 1    | 80    | **160**  ← 包含了两行 80                      |
| 2    | 80    | **160**  ← 同上（因为排序值相同，属于同一组） |
| 3    | 90    | **250**  ← 80+80+90                           |
| 4    | 100   | **350**  ← 全部相加                           |

- 因为 `ORDER BY score` 有重复值（80 出现两次），`RANGE` 会将所有 `score=80` 的行**视为同一个“逻辑行”**，所以累计和时一次性加上所有 80。

### 查询 2：显式使用 ROWS
```sql
SELECT 
    id,
    score,
    SUM(score) OVER(ORDER BY score ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS rows_sum
FROM scores;
```

**结果：**

| id   | score | rows_sum               |
| :--- | :---- | :--------------------- |
| 1    | 80    | **80**    ← 只加第一行 |
| 2    | 80    | **160**   ← 80+80      |
| 3    | 90    | **250**   ← 80+80+90   |
| 4    | 100   | **350**   ← 全部相加   |

- `ROWS` 按照**物理行**逐行累加，即使是相同值也会分开计算。

### 💡 核心陷阱
**很多人以为默认是 `ROWS`，但实际上是 `RANGE`！** 如果 `ORDER BY` 列有重复值，使用 `RANGE` 会让相同值的行共享同一个累计值，这通常不是你想要的结果。

---

## 陷阱 4：与 GROUPS 的关系（复习你之前的问题）

还记得你问过的 `GROUPS` 吗？它的默认框架也是 `RANGE` 风格：

```sql
-- 这三个是等价的
SUM(x) OVER(ORDER BY y)                          -- 默认 RANGE
SUM(x) OVER(ORDER BY y RANGE UNBOUNDED PRECEDING)
SUM(x) OVER(ORDER BY y GROUPS UNBOUNDED PRECEDING)  -- PostgreSQL 11+ 默认
```

- 如果 `ORDER BY y` 有重复值，`RANGE` 和 `GROUPS` 都会把重复值当成一个组来处理。
- 如果你想要逐行累计（不管值是否重复），请**显式写成 `ROWS` **。

---

## 陷阱 5：PARTITION BY 与 ORDER BY 的误用

```sql
-- ❌ 错误：只在分区内排序，但没指定排序顺序
SELECT 
    salesperson,
    amount,
    ROW_NUMBER() OVER(PARTITION BY salesperson)  -- 缺少 ORDER BY
FROM sales;
```

**结果**：`ROW_NUMBER()` 的编号顺序是**不确定的**（取决于存储顺序），每次执行可能不同。

✅ **正确做法**：总是明确指定 `ORDER BY`
```sql
ROW_NUMBER() OVER(PARTITION BY salesperson ORDER BY amount DESC)
```

---

## 如何避免默认窗口陷阱？（最佳实践清单）

| 检查项                       | 建议                                                         |
| :--------------------------- | :----------------------------------------------------------- |
| **总是显式写 `ORDER BY` **    | 不要依赖默认值，明确排序意图。                               |
| **显式指定框架（Frame）**    | 如果你想要累计和：`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` <br> 如果你想要整个分区：`ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` |
| **处理重复值时小心 `RANGE` ** | 如果有重复的排序键，考虑改用 `ROWS` 或 `GROUPS`。            |
| **用 `EXPLAIN` 验证**        | 查看执行计划，确认窗口函数的实际处理范围。                   |
| **单元测试**                 | 用少量数据验证窗口函数的结果是否符合预期。                   |

# RLS 策略

同一张表，不同用户执行同一个查询，看到的结果可能不同。

# GROUPING

- GROUPING(字段)=0：该行是常规分组行（字段有具体值）
- GROUPING(字段)=1：该行是 ROLLUP 汇总行（该字段被聚合，值为 NULL）。
# BCNF 和 2 NF

都是消除部分函数依赖，区别在于：
- 2 NF 消除非主属性。
- BCNF 消除主属性。

更深一点：
- 主属性在候选键中。
- 非主属性不在候选键中。

# ROWS 和 RANGE

在数据库中，** `RANGE` ** 和 ** `ROWS` ** 是用于定义**窗口函数（Window Function）**中“窗口框架”（Window Frame）边界的关键字。它们都跟在 `ORDER BY` 后面，用来指定当前行参与计算的数据范围，但两者的**逻辑完全不同**。

最核心的区别是：** `ROWS` 按物理行数定位，`RANGE` 按逻辑值定位。**

---

### 1. 核心区别（一句话总结）
- **ROWS**：根据**当前行向上/向下固定的行数**来确定窗口（物理偏移）。
- **RANGE**：根据**当前行的值**，在 `ORDER BY` 列上取**与当前行值差值在指定范围内的所有行**（逻辑偏移）。

---

### 2. 详细对比

| 维度                         | **ROWS**                                   | **RANGE**                                   |
| :--------------------------- | :----------------------------------------- | :------------------------------------------ |
| **定位依据**                 | 物理行号（第几行）                         | 列的值（数据内容）                          |
| **受 ORDER BY 列重复值影响** | 不受影响，严格按行数截取                   | **受影响**，若值相同，会全部包含在框架内    |
| **常用语法**                 | `ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING` | `RANGE BETWEEN 1 PRECEDING AND 1 FOLLOWING` |
| **适用场景**                 | 移动平均、固定窗口大小的计算               | 按数值范围汇总（如过去 7 天的销售额）       |

---

### 3. 典型示例说明

假设有如下成绩表 `score_table`：

| student | score |
| :------ | :---- |
| A       | 80    |
| B       | 80    |
| C       | 85    |
| D       | 90    |
| E       | 90    |
| F       | 90    |

执行查询（按 `score` 排序）：
```sql
SELECT student, score,
       COUNT(*) OVER (ORDER BY score ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING) AS rows_count,
       COUNT(*) OVER (ORDER BY score RANGE BETWEEN 1 PRECEDING AND 1 FOLLOWING) AS range_count
FROM score_table;
```

#### 结果分析：

- **ROWS 结果**：严格看当前行的前 1 行和后 1 行（物理位置）。
  - 对于第 3 行的 C（85）：前一行是 B（80），后一行是 D（90）→ 计数 = **3**。

- **RANGE 结果**：看 `score` 值在 `[当前值-1, 当前值+1]` 内的所有行。
  - 对于 C（85）：取分数在 `[84, 86]` 的行 → 只有 C 自己 → 计数 = **1**。
  - 对于 D（90）：取分数在 `[89, 91]` 的行 → D、E、F 都是 90 → 计数 = **3**。
