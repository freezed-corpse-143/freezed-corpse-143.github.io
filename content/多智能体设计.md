# 设计环节

## 环节 1：需求判断——要不要多智能体？

三大动因：

| 动因    | 说明                                                                 |
| ----- | ------------------------------------------------------------------ |
| 上下文管理 | 提供专门知识而不撑爆模型的上下文窗口——若上下文无限、延迟为零，把知识全塞进单一提示词即可，正因不行才需要模式化地选择性呈现相关信息 |
| 分布式开发 | 不同团队独立开发维护各自能力，再组合成大系统（有清晰边界）                                      |
| 并行化   | 为子任务生成专门 worker 并并发执行，提速                                           |

## 环节 2：架构模式选择

以下是五种多智能体协作模式的 Markdown 表格总结：

| 模式                          | 工作机制                                                        | 适用场景                     |
| :-------------------------- | :---------------------------------------------------------- | :----------------------- |
| **Subagents（子代理）**          | 主 agent 把子 agent 当工具调用；所有路由经过主 agent，由它决定何时/如何调用            | 需要集中控制、分布式开发、并行、多跳       |
| **Handoffs（移交）**            | 行为随状态动态变化：工具调用更新状态变量→触发路由/配置变化→切换 agent 或调整当前 agent 的工具与提示词 | 多轮对话、子 agent 直接面向用户      |
| **Skills（技能）**              | 专门提示词与知识按需加载；单个 agent 保持控制，需要时加载技能上下文                       | 简单聚焦任务、直接用户交互            |
| **Router（路由器）**             | 一个路由步骤对输入分类，分发给一个或多个专门 agent，结果再合成                          | 多个独立知识域（vertical）、并行查询多源 |
| **Custom workflow（自定义工作流）** | 用 LangGraph 定制执行流，确定性逻辑与 agentic 行为混排，把其他模式作为节点嵌入           | 需要精确控制/可审计的复杂流程          |

## 环节 3：上下文工程设计

以下是五种上下文管理方案的 Markdown 表格总结：

| 方案                             | 要点                                                                        |
| :----------------------------- | :------------------------------------------------------------------------ |
| **选择性呈现（selective surfacing）** | 按需把相关上下文注入对应 agent，而非全量倾倒                                                 |
| **上下文隔离**                      | Subagents 每次调用都是全新上下文（stateless），隔离强但重复完整流程                               |
| **技能按需加载**                     | Skills 模式：需要时才加载专门知识，单 agent 保持控制                                         |
| **有状态的历史裁剪**                   | Stateful Router：从持久化状态取历史消息、选择性纳入 agent 上下文——官方称这是上下文工程的一个调节杠杆 [Router 页] |
| **动态提示词/工具**                   | Handoffs：状态变量驱动，切换 agent 时更换其提示词与工具集                                      |

## 环节 4：状态与数据流设计


| 方案 | 要点 |
| :--- | :--- |
| **State（共享状态）** | 所有节点操作同一共享状态；定义输入/输出 schema |
| **Nodes / Edges** | 节点=函数（同步/异步），边=路由与停止逻辑 |
| **Conditional edges** | 条件分支路由 |
| **Reducers** | 状态更新合并规则（追加/覆盖消息等） |
| **Command** | 单 agent 路由用 `Command(goto=...)`；多 agent handoff 用 `Command(PARENT)` 跳回父图 |
| **Send** | 并行 fan-out 到多个 agent |
| **API 二选一** | Graph API（声明式图，推荐用于显式共享状态）vs Functional API（函数式入口点，更轻量） |
## 环节 5：持久化

| 方案 | 层级 | 用途 |
| :--- | :--- | :--- |
| **Checkpointer（检查点）** | 短时记忆、线程作用域 | 对话连续性、human-in-the-loop 工作流、时间旅行（回滚/重放）、容错恢复 |
| **Store（存储）** | 长期记忆、跨线程 | 跨会话共享任意信息；可加密序列化 |
| **后端选型** | – | InMemorySaver（内存/测试）→ SQLite/Postgres（生产）；checkpoint 需支持按 (thread_id, checkpoint_ns, checkpoint_id) O(1) 直查 |
## 环节 6：控制流机制


| 方案                    | 要点                                                                        |
| :-------------------- | :------------------------------------------------------------------------ |
| **确定性 × agentic 混排**  | LangGraph 核心优势：需要可靠可审计的地方用手写确定性逻辑，需要灵活的地方用 LLM 决策，同一图中精确控制 [LangGraph 概览] |
| **Human-in-the-loop** | 任意检查点中断、检查并修改 agent 状态后继续 [LangGraph 概览]                                  |
| **Streaming**         | 流式输出；Deep Agents 提供 `stream.subagents` 投影，UI 直接暴露子代理概念 [Deep Agents 文档]   |
| **终止/护栏**             | 图边定义何时停止；最大迭代、中断点                                                         |
| **并发执行**              | `asyncio.gather` / Send 并行                                                |

## 环节 7：可观测性与评估

| 方案 | 要点 |
| :--- | :--- |
| **Tracing** | LangSmith 全链路 trace，跨 agent 协调流程可视化；"跟踪多智能体的完整协调流" [多智能体页] |
| **自动问题检测** | LangSmith Engine 监控 trace、检测问题并直接提出修复 PR |
| **Evals** | 数据集 + 评估 + 提示词工程（Test 阶段） |
| **调试** | LangGraph 可视化执行路径、状态转换、运行时指标 [LangGraph 概览] |
