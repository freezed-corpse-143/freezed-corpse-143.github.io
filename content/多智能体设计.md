# 设计环节

## 环节 1：需求判断——要不要多智能体？

三大动因：

| 动因    | 说明                                                                 |
| ----- | ------------------------------------------------------------------ |
| 上下文管理 | 提供专门知识而不撑爆模型的上下文窗口——若上下文无限、延迟为零，把知识全塞进单一提示词即可，正因不行才需要模式化地选择性呈现相关信息 |
| 分布式开发 | 不同团队独立开发维护各自能力，再组合成大系统（有清晰边界）                                      |
| 并行化   | 为子任务生成专门 worker 并并发执行，提速                                           |

## 环节 2：架构模式选择

以下是五种多智能体协作模式的 Markdown 表格总结：

| 模式                          | 工作机制                                                        | 适用场景                     |
| :-------------------------- | :---------------------------------------------------------- | :----------------------- |
| **Subagents（子代理）**          | 主 agent 把子 agent 当工具调用；所有路由经过主 agent，由它决定何时/如何调用            | 需要集中控制、分布式开发、并行、多跳       |
| **Handoffs（移交）**            | 行为随状态动态变化：工具调用更新状态变量→触发路由/配置变化→切换 agent 或调整当前 agent 的工具与提示词 | 多轮对话、子 agent 直接面向用户      |
| **Skills（技能）**              | 专门提示词与知识按需加载；单个 agent 保持控制，需要时加载技能上下文                       | 简单聚焦任务、直接用户交互            |
| **Router（路由器）**             | 一个路由步骤对输入分类，分发给一个或多个专门 agent，结果再合成                          | 多个独立知识域（vertical）、并行查询多源 |
| **Custom workflow（自定义工作流）** | 用 LangGraph 定制执行流，确定性逻辑与 agentic 行为混排，把其他模式作为节点嵌入           | 需要精确控制/可审计的复杂流程          |
