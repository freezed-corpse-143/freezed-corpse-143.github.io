# 任务模型

一个完整的任务模型扩展成下面的各部分：

| 部分              | PM 需要明确的内容                        | 缺失后容易出现什么问题           |
| ----------------- | ---------------------------------------- | -------------------------------- |
| **1. 价值与目标** | 为什么做？它支持哪个上层目标？           | 完成了很多工作，却没有推进项目   |
| **2. 范围与边界** | 本任务包含什么？明确排除什么？           | 工作不断膨胀，迟迟无法结束       |
| **3. 交付与验收** | 产物是什么？质量门槛是什么？谁验收？     | 执行者说完成，使用者说不能用     |
| **4. 输入与依赖** | 需要哪些资料、前置成果、接口和决定？     | 任务已启动，却一直在等待         |
| **5. 资源与权限** | 谁执行？需要哪些工具、预算、环境和授权？ | 知道怎么做，但没有执行条件       |
| **6. 推进与估算** | 准备怎么做？工作量多大？何时检查进展？   | 只能到截止时间才发现延期         |
| **7. 风险与异常** | 哪些假设可能不成立？失败后怎么办？       | 一次意外就阻塞整个计划           |
| **8. 交接与整合** | 结果交给谁？如何接入上层成果？           | 子任务都完成了，项目仍然不能交付 |

# 分解的时机

分解不是越早越好，也不是越细越好。判断依据只有一条：**当前任务是否已经无法在有限步骤内完成**。“有限步骤”指执行者能在不丢失上下文的前提下，一次连续做完并自检。

出现下面任一信号，就应该停止硬做、转入分解：

| 信号                 | 具体表现                               | 说明                               |
| -------------------- | -------------------------------------- | ---------------------------------- |
| 步骤不可枚举         | 说不清第 3 步做什么，只能边做边看      | 后续路径依赖尚未知的结果           |
| 单步含多个未知       | 一步里同时包含选型、实现、验证         | 失败原因无法归因，只能靠猜         |
| 超出一次能保持的范围 | 需要同时记住的前提、接口、约定多到会漏 | 上下文一旦滑出，前面的工作等于重做 |
| 需要并行才能赶上时间 | 前后端、数据与界面只能串行推进         | 不拆无法并行                       |
| 需要中途被人检查     | 关键决策要先确认再继续                 | 没有检查点，返工量随步骤数累积     |
| 结果需要分别验收     | 部分成果要单独交给别人使用             | 不拆就无法单独交付、单独回滚       |

反过来，能在有限步骤内完成、且中途不需要外部检查的任务不应拆开。拆分本身有代价：

- **接口成本**：拆开后要约定输入输出，约定不完整就产生返工。
- **整合成本**：子任务都完成，仍需一次整合与联调，这部分最常被漏算。
- **上下文成本**：交接要让接收者重建背景，可能比一个人做到底更慢。
- **协调成本**：并行意味着等待，最慢的子任务决定整体完成时间。

所以问题不是“能不能拆”，而是“拆开换来的并行、可验证、可回滚，是否大于以上四项成本”。收益说不清时先不拆，等出现第一个信号再拆，通常更省。

**决定粒度的是未知量，不是工作量。** 工作量大但步骤确定的活，按顺序做即可；未知量多的活，才需要在每个未知处切开。

# 资源注入

| 类型       | 例子                         | 管理方式           |
| ---------- | ---------------------------- | ------------------ |
| 信息输入   | 需求说明、样本数据、业务规则 | 补充、澄清、核实   |
| 前置依赖   | 另一个任务产出的 API         | 协调顺序、约定接口 |
| 执行资源   | 人员、算力、预算、时间       | 分配、采购、排期   |
| 工具与环境 | 编译器、测试环境、MCP 服务   | 配置、验证可用性   |
| 权限与决策 | 数据访问许可、方案批准       | 找到有权决定的人   |
| 外部协作   | 供应商、客户反馈、专家支持   | 约定响应时间和责任 |

例如，“等主管确认”“等测试服务器”“等接口开发完”都表现为等待，但它们分别属于**决策、资源、依赖**，不能用同一种办法解决。

# 独立沙盒

有一类子任务的结果事先无法知道：选型对比、可行性验证、性能上限摸底、复现一个陌生故障。这类**探索类子任务不应在主环境里做**，而应新开一个隔离环境（沙盒）来跑。

不隔离会同时坏两头：

| 污染方向       | 后果                                                                     |
| -------------- | ------------------------------------------------------------------------ |
| 探索污染主环境 | 试验性改动、临时依赖、半成品配置留在主环境，结论还没出来，主环境已不可信 |
| 主环境污染探索 | 历史改动、遗留配置、缺失权限混进实验，看到的现象无法归因到真正的变量     |

另外两个理由：

- **降低环境复杂度**：沙盒里只放这次实验必需的输入，噪音少，异常更容易定位。
- **控制变量**：一次只改一个因子，基线固定（版本、数据快照、参数、随机种子），结论才可比较、可复现。

建沙盒的最低要求：

1. **可丢弃**：能整体删掉重建，不依赖手工恢复。容器、临时目录、独立分支、独立数据库都算。
2. **最小**：只复制这次实验需要的那部分输入，不复制整个环境。
3. **基线固定**：记录初始版本、数据快照与参数，先跑一次基线再动变量。
4. **带回结论，不带回环境**：验证完成后只把结论、参数与复现步骤带回主环境；临时依赖要么按结论进正式依赖，要么随沙盒一起销毁。
5. **有销毁条件**：结论出来即关闭，否则沙盒会慢慢变成第二个主环境，反而增加长期维护量。

沙盒的代价是重建环境、重复准备输入，因此只对**结果未知**的子任务使用；步骤确定、结果可预期的子任务仍在主环境按顺序完成。

# 任务之间的关系

再进一步，**任务之间的关系，和任务本身一样重要**。PM 至少需要维护两种结构：

- **分解树**：父目标由哪些子成果组成，用来检查有没有遗漏。
- **依赖图**：哪些任务必须等待其他任务，用来安排执行顺序和并行工作。

例如，“完成登录功能”可以分解成界面、认证接口、会话管理、测试等工作；但测试需要哪些前置成果、界面能否先用模拟接口开发，则属于依赖关系。仅有分解树，还不能形成可执行的计划。

可以用一个具体任务看出区别：

| 字段       | 示例：实现邮箱密码登录                                               |
| ---------- | -------------------------------------------------------------------- |
| 上层目标   | 让已注册用户进入个人工作区                                           |
| 范围       | 邮箱密码登录；本次不包含注册、找回密码、第三方登录                   |
| 交付物     | 登录页面、认证接口、验证记录                                         |
| 验收条件   | 正确凭据可进入工作区；错误凭据有明确提示；未登录访问受限页面会被拦截 |
| 输入与依赖 | 用户数据结构、接口约定、页面设计                                     |
| 资源与权限 | 开发人员、测试账号、测试环境访问权限                                 |
| 推进方式   | 先确认接口约定，再允许前后端并行开发，最后联调验收                   |
| 风险与处理 | 认证服务未就绪时，用模拟接口验证页面；正式验收仍需连接真实服务       |
| 交接与整合 | 接入应用导航和部署环境，由指定负责人验收                             |

最后，PM 还需要给“是否继续拆分”设置停止条件。一个任务满足下面这些条件，通常就已经足够细：

1. **负责人能解释清楚如何开始。**
2. **必要输入已经具备，或有明确的到位安排。**
3. **能在合理时间内观察到结果或获得反馈。**
4. **完成与否有明确判据。**
5. **异常能及时暴露，并知道由谁处理。**
6. **成果能够交接，并推进上层目标。**

一条完整的管理逻辑：

**为什么做 → 做到哪里 → 交付什么 → 如何验收 → 依靠什么 → 谁来推进 → 异常怎么办 → 如何汇入整体。**

其中最容易被忽略、也最有 PM 特征的一点是：**局部任务完成，不等于整体目标完成；任务分解必须同时设计最后如何整合。**
