
可以把“环境”统一理解为：**执行任务所依赖的资源、能力、约束和状态的集合。** 这样，开发环境、Agent 环境、Skill、MCP 就能放进同一个分析框架。

但需要区分：**声明存在的能力、当前可调用的能力，以及实际验证有效的能力，是三个不同层次。** 环境自检就是把它们对齐。

|检查层面|传统开发环境|Agent / Skill / MCP 环境|
|---|---|---|
|**能力发现**|有哪些编译器、解释器、命令|有哪些工具、Skill、MCP 服务|
|**接口契约**|参数、返回值、ABI、文件格式|工具参数 schema、结果结构、Skill 执行规则|
|**依赖关系**|库、运行时、系统组件|Skill 依赖的工具、账号、服务、其他 Skill|
|**权限边界**|文件权限、网络权限、进程权限|工具授权、账号作用域、允许执行的操作|
|**当前状态**|工作目录、环境变量、运行中的服务|登录状态、连接状态、会话上下文、当前选中对象|
|**兼容性**|版本、架构、平台|工具接口版本、客户端支持、Skill 与工具是否匹配|
|**实际可用性**|能否编译、运行、访问依赖|能否完成一次最小调用，返回结果是否符合预期|
|**结果验证**|测试、退出码、产物检查|操作是否生效、产物是否可访问、外部状态是否改变|

这里最值得深入的是：**Agent 环境不仅影响“能不能执行”，还影响“如何选择执行方案”。**

例如，任务是“修改一份文档”：

- 有专用文档接口，就可以直接读取并编辑。
- 只有本地文件工具，就需要下载、修改、验证、上传。
- 有浏览器操作能力，就可能通过页面完成。
- 只有读取权限，就应交付可供应用的修改稿。
- 有 Skill 但缺少其依赖工具，说明这条执行路径尚不完整。

所以，**环境自检应该发生在制定具体执行方案之前，并贯穿执行过程。**

可以把它设计成三个阶段：

|阶段|要回答的问题|检查方式|
|---|---|---|
|**启动时：建立能力概况**|我处于什么环境？有哪些基本能力和限制？|读取环境声明、工具目录、工作区规则|
|**任务前：验证相关依赖**|完成这个任务需要什么？这些条件当前成立吗？|按需读取 Skill，检查权限、连接和目标对象|
|**执行中：更新环境判断**|刚才的结果是否推翻了原来的假设？|检查返回值，遇到失效、冲突或状态变化时重新探测|

不必每次检查所有东西。更合理的是：**基础检查一次，任务依赖按需检查，易变状态在关键操作前重新确认。** 比如工具参数结构通常比较稳定，而登录状态、文件版本、当前页面、剩余额度随时可能变化。

还有一个容易忽略的区别：**自检本身也有副作用。** 查询版本、读取元数据通常很轻；发送测试邮件、创建测试订单就已经改变了外部世界。因此，“验证工具可用”不能自动等同于“执行一次真实业务操作”，应优先使用只读查询、预览或 dry-run。

如果把它纳入系统设计，环境自检最终应输出一份可供规划器使用的状态：

```
任务：编辑并保存文档

所需能力：读取、编辑、保存、验证
已验证：读取、编辑
缺失条件：保存接口尚未授权
不确定项：目标文档是否已被其他人更新
可行路径：生成修改稿；授权后保存
重新检查时机：写入前确认目标版本
```

**这使环境从一组隐含假设，变成执行计划的显式输入。** 对传统程序，这能减少“在我机器上能跑”的问题；对 Agent，还能减少凭空假设工具存在、误判权限，以及操作完成却没有验证结果的问题。
