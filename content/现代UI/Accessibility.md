# Semantic HTML

核心思想：**用正确的标签做正确的事**，而不是全用 `div` + `span` 加样式。

浏览器和屏幕阅读器（screen reader）会依据标签类型决定：

- 能不能被键盘聚焦
- 被读出来是什么角色（role）
- 交互行为是什么

清单里的元素：

| 元素        | 语义/作用                           |
| --------- | ------------------------------- |
| `button`  | 可点击操作，天然可聚焦、支持 Enter/Space 触发   |
| `a`       | 链接，用于跳转（有 href 才可聚焦）            |
| `input`   | 输入控件，配合 `type` 决定行为             |
| `label`   | 与 input 关联，点击文字能聚焦输入框，屏幕阅读器读出名称 |
| `form`    | 表单容器，支持提交、校验语义                  |
| `nav`     | 导航区域地标（landmark）                |
| `main`    | 主内容地标，一页通常只有一个                  |
| `section` | 主题性分区，通常配标题                     |
| `dialog`  | 对话框，自带模态语义、焦点管理等                |

**为什么重要**：语义标签免费带来键盘支持、屏幕阅读器支持、SEO 和可维护性。用 `div` 模拟按钮，就要手动补一大堆 ARIA 和键盘事件，还容易漏。

# Keyboard Navigation

不用鼠标也能操作所有功能。

| 按键         | 典型行为                                       |
| ------------ | ---------------------------------------------- |
| `Tab`        | 焦点向前移动                                   |
| `Shift+Tab`  | 焦点向后移动                                   |
| `Enter`      | 激活链接、提交、触发按钮                       |
| `Space`      | 激活按钮、勾选复选框、翻页                     |
| `Escape`     | 关闭弹窗/菜单/下拉                             |
| `Arrow Keys` | 在组件内部移动（菜单项、选项卡、单选组、树等） |

关键区别：

- `button`：Enter 和 Space 都能触发
- `a[href]`：只有 Enter 触发（Space 是滚动页面）
- 复合组件（如 tabs、menu）：Tab 进入组件，**Arrow 在内部移动**，这是 WAI-ARIA 的约定模式

# Focus Management

让焦点"跟着用户的注意力走"。

- ** `focus-visible` **：CSS 伪类，只在"键盘操作"时显示焦点轮廓，鼠标点击时不显示。既保留可访问性又不破坏视觉设计。
  ```css
  :focus-visible { outline: 2px solid blue; }
  ```
- **Focus Trap（焦点陷阱）**：模态框打开时，把 Tab 循环限制在弹窗内部，防止焦点跑到背后的页面。
- **Focus Return（焦点归还）**：关闭弹窗后，焦点回到当初触发它的那个元素，否则用户会"迷失"在页面里。

这三者通常一起出现在 `dialog`、抽屉、下拉菜单里。

# ARIA

当原生 HTML 无法表达语义时，用 ARIA 补充。原则：**能用原生标签就别用 ARIA**（"No ARIA is better than bad ARIA"）。

| 属性            | 作用                                                         |
| --------------- | ------------------------------------------------------------ |
| `role`          | 声明元素角色，如 `role="tab"`、`role="dialog"`               |
| `aria-label`    | 给元素一个可访问名称（无可见文字时用）                       |
| `aria-expanded` | 展开/收起状态，如手风琴、下拉菜单                            |
| `aria-selected` | 选中状态，如 tabs、列表项                                    |
| `aria-controls` | 指向被控制的元素 id（如按钮控制的面板）                      |
| `aria-live`     | 动态区域，内容变化时屏幕阅读器自动播报（`polite` / `assertive`） |

`aria-live` 常用于：表单错误提示、Toast 通知、加载状态、搜索结果数量更新。

# `@media (prefers-reduced-motion: reduce)`

用户系统开启了"减少动态效果"时生效。前庭功能障碍、眩晕症用户对此敏感。

```css
@media (prefers-reduced-motion: reduce) {
  * { animation: none; transition: none; }
}
```

工程实践中不是简单全禁，而是把大幅位移、视差、自动播放动画替换成淡入淡出或直接静态呈现。

# 最终习惯

> **任何组件都问一句：不用鼠标能不能完整操作？**

这是把上述知识内化成"条件反射"。做一个下拉菜单时，自动检查：

1. Tab 能不能进入？
2. Arrow 能不能选项？
3. Enter/Space 能不能确认？
4. Escape 能不能关闭？
5. 关闭后焦点回到触发按钮了吗？
6. 屏幕阅读器读出角色和状态了吗？
7. 有没有可见的焦点样式？

---

**整体逻辑链**：语义 HTML 打地基 → 键盘操作保证可用 → 焦点管理保证不迷失 → ARIA 补充语义和状态 → 尊重用户动效偏好 → 形成"键盘优先"的工程直觉。
