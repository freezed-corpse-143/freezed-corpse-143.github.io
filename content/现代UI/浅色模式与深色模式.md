深色模式／浅色模式难，主要因为：**它改变的是整套视觉关系，而不仅是背景颜色。** 一个页面改起来容易；整个产品长期保持一致，就需要系统设计。

可以从下面几个层面理解。

**1. 颜色表达的是语义，不能直接反转**

例如浅色模式中：

- 白色代表页面背景；
- 浅灰色代表次级区域；
- 深色代表主要文字；
- 蓝色代表可操作；
- 红色代表错误。

换成深色后，必须保留这些含义，同时重新调整亮度、饱和度和对比度。简单把黑白交换，容易出现按钮刺眼、边框过强、次要文字看不清等问题。

因此，组件最好使用**语义颜色变量**：

```
/* 浅色主题 */
:root {
  --bg-page: #ffffff;
  --bg-panel: #f4f4f5;
  --text-primary: #18181b;
  --text-secondary: #52525b;
  --border-default: #d4d4d8;
}

/* 深色主题 */
[data-theme="dark"] {
  --bg-page: #18181b;
  --bg-panel: #27272a;
  --text-primary: #fafafa;
  --text-secondary: #a1a1aa;
  --border-default: #3f3f46;
}

.card {
  background: var(--bg-panel);
  color: var(--text-primary);
  border: 1px solid var(--border-default);
}
```

难点在于：**这些变量如何划分，才能让不同组件都正确表达自己的含义。**

**2. 空间层次需要重新建立**

浅色模式中，卡片经常依靠阴影从背景中“浮起来”。但在深色背景上，黑色阴影很难被看见。

于是需要综合调整：

|视觉任务|浅色模式常见手段|深色模式常见手段|
|---|---|---|
|区分页面与卡片|背景差异、阴影|不同亮度的表面|
|强调弹窗|阴影、遮罩|表面亮度、边框、遮罩|
|表达选中|浅色填充|调整后的深色填充与强调色|
|分隔区域|浅灰边框|低对比度边框|

这意味着，颜色改对了，页面仍然可能显得扁平或杂乱。

**3. 一个组件往往有很多状态**

一个输入框至少可能有：

`默认、悬停、聚焦、禁用、错误、只读`

而错误状态还能同时处于聚焦状态。按钮、下拉菜单、表格也都有类似组合。

**每个主题都需要覆盖这些状态，并保持状态之间的差别清晰。** 所以工作量往往藏在细节里，而不是首页截图里。

**4. 很多内容不受主题变量控制**

CSS 变量可以管理自己写的组件，却无法自动解决所有资源：

- Logo、插画可能带白色底；
- 图片里的文字可能只有深色版本；
- SVG 可能写死了填充颜色；
- 图表、代码高亮有自己的配色；
- 第三方组件、嵌入页面可能采用独立主题。

这部分通常需要单独适配。给整个页面加 `filter: invert()` 会连照片、品牌色一起改变，很难作为完整方案。

**5. 主题切换还涉及应用启动过程**

一般需要支持三种选择：

|用户选择|实际行为|
|---|---|
|浅色|始终使用浅色|
|深色|始终使用深色|
|跟随系统|随系统偏好变化|

这里有两个不同的状态：

```
用户偏好：light / dark / system
实际主题：light / dark
```

还需要处理保存设置、系统变化，以及**首次打开时的闪白**：如果浏览器先绘制浅色页面，随后 JavaScript 才读取深色偏好，用户就会看到一次闪烁。服务端渲染时，还可能涉及服务端与浏览器初始主题的一致性。

**6. 旧项目的成本尤其高**

如果项目一开始就使用语义变量，主题切换通常比较可控。

如果几百个组件里散落着：

```
color: #333;
background: white;
border-color: #ddd;
```

你就必须逐个判断：这个白色究竟是页面背景、卡片背景，还是按钮文字？**相同色值可能承担不同职责，不能全局替换。**

所以，深浅模式的难度可以概括为：

> **切换开关很简单；建立一套能覆盖颜色、层次、状态、资源和启动流程的主题系统，才是主要工作。**

它也是前端从“把组件画出来”走向“维护完整设计系统”的一个典型问题。
