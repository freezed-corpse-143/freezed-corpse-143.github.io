# 组件检查清单

可以把它整理为一套 **“组件状态 × 事件 × 过渡动画”** 的检查框架。你列出的进入、常驻、悬浮、点击等，分别涉及组件生命周期、交互状态和事件来源，拆开后会更完整。

**关键是先定义组件有哪些状态、什么事件会改变状态，再决定哪些变化需要动画。** 同一个按钮被鼠标点击和键盘激活，通常应产生一致的业务反馈，同时保留各自需要的交互提示。

下面这张表可以作为逐个组件检查的清单：

| 维度          | 要考虑的情况              | 常见动画或视觉反馈        | 设计时要回答的问题              |
| ----------- | ------------------- | ---------------- | ---------------------- |
| **首次呈现**    | 进入页面、滚动到可视区域、首次挂载   | 淡入、轻微位移、分组依次出现   | 是否需要引导视线？每次出现都播放吗？     |
| **显示与隐藏**   | 展开、收起、打开、关闭、移除      | 淡入淡出、高度变化、缩放、滑动  | 隐藏后是否保留空间？退出动画结束后再移除吗？ |
| **常驻状态**    | 待机、等待、持续运行          | 呼吸、闪烁、循环旋转       | 持续运动是否传递必要信息？会不会干扰阅读？  |
| **鼠标悬浮**    | 移入、移出               | 背景、边框、阴影、提示浮层变化  | 能否看出可操作性？移出如何恢复？       |
| **按压与释放**   | 按下、松开、拖出后松开、取消      | 颜色加深、轻微下压或缩放     | 是否立即响应按下？取消操作如何恢复？     |
| **键盘焦点**    | Tab 进入、离开、键盘激活      | 清晰焦点环、激活反馈       | 焦点在哪里？键盘操作能否完成同一任务？    |
| **触摸与手势**   | 轻触、长按、滑动、拖动、取消      | 按压反馈、跟手位移、回弹     | 没有悬浮时如何发现功能？是否与页面滚动冲突？ |
| **值与选择变化**  | 开关、勾选、切换选项、修改数值     | 滑块移动、选中标记、指示线移动  | 能否看出旧值如何变为新值？          |
| **异步过程**    | 请求开始、处理中、成功、失败、重试   | 加载指示、进度、状态图标切换   | 操作是否已接收？能否继续操作或取消？     |
| **校验与异常**   | 输入错误、权限不足、操作不可用     | 错误文本出现、边框变化、原因提示 | 用户是否知道原因，以及下一步怎么做？     |
| **布局与内容更新** | 列表插入删除、排序、文本变长、容器变化 | 位置过渡、尺寸过渡、内容替换   | 用户能否追踪原来的对象？是否造成跳动？    |
| **拖放过程**    | 拾起、拖动、进入目标、放下、拒绝    | 抬升、占位、目标高亮、落位或回位 | 当前拖的是谁？可以放在哪里？         |
| **注意力提示**   | 新消息、未读、状态更新         | 徽标出现、短暂强调        | 值得打断用户吗？提示何时停止？        |

注意，**视觉反馈不一定需要运动**。焦点环、禁用状态、错误提示等，直接清晰地显示，往往就足够了。

以一个“提交按钮”为例，不需要给它安排所有动画，而是先列出状态和转换：

|状态转换|触发原因|应有反馈|
|---|---|---|
|默认 → 悬浮|鼠标移入|背景或边框轻微变化|
|默认 → 获得焦点|Tab 导航|显示清晰焦点环|
|可操作 → 按压|鼠标按下或键盘激活|即时按压反馈|
|按压 → 默认|取消按压|恢复外观，不提交|
|可操作 → 提交中|确认激活|显示加载状态，处理重复提交|
|提交中 → 成功|请求成功|明确成功结果|
|提交中 → 失败|请求失败|显示失败原因，允许重试|
|禁用 → 可操作|条件满足|清晰恢复可操作外观，通常无需额外动画|

其中，**悬浮、焦点、按压和加载可能同时存在**，所以不能只把组件定义成一个简单的 `default / hover / loading` 枚举；需要考虑这些状态如何组合，以及谁覆盖谁。

每一条需要动画的转换，还应补齐下面几项：

|动画规格|需要明确的内容|
|---|---|
|**目的**|表示操作已接收、解释位置变化，还是引导注意力|
|**变化属性**|透明度、位置、尺寸、颜色、阴影等|
|**时间行为**|时长、延迟、缓动、是否循环|
|**中断规则**|动画中再次点击、反向操作、快速移入移出时怎么办|
|**交互时机**|动画期间能否点击？何时可聚焦？何时移除元素？|
|**布局影响**|是否占空间、推动其他内容、保留占位|
|**降级方式**|用户要求减少动态效果时如何简化；关闭动画后是否仍能理解状态|

你可以把每个组件的设计记录成一句模板：

> **当【事件】发生，组件从【状态 A】转为【状态 B】，通过【视觉变化】表达【目的】；如果期间发生【中断事件】，则【处理方式】。**

例如：“侧栏正在展开时再次点击折叠按钮，从当前宽度反向收起。”这种描述比单独写“侧栏添加展开动画”，更接近可以直接开发的需求。

# 设计顺序

可以按照 **“业务流程 → 页面结构 → 静态布局 → 状态与交互 → 动画 → 性能验证”** 逐步推进。不过，实际开发时，最好先做通一条核心流程，再扩展其他页面。

你列出的三个步骤可以稍作调整：

1. **先明确用户任务，再推导页面种类和数量。**
2. **建立页面导航图，同时为复杂流程建立状态机。**
3. **先确定页面区域和信息层级，再拆分具体组件。**

其中，页面导航图描述“用户在哪里、能去哪里”；状态机描述“当前处于什么状态、什么条件下允许变化”。一个页面内部也可能包含多个状态机。

下面是一套从粗到细的设计开发顺序。

|阶段|核心问题|主要工作|完成标志|
|---|---|---|---|
|**1. 业务与用户任务**|谁来用？要完成什么？|明确角色、目标、核心任务、业务规则与范围|能描述一条完整任务，例如“查找商品并完成购买”|
|**2. 业务流程**|完成任务需要哪些步骤？|画主流程、分支、失败与恢复流程；标出权限和前置条件|正常路径和关键异常都有去向|
|**3. 信息架构与页面清单**|信息怎么组织？需要哪些页面？|划分导航、页面、弹窗、抽屉；确定 URL 与入口|每个页面都有明确职责，能解释为何存在|
|**4. 导航与流程状态**|页面如何连接？操作何时允许？|建立导航图；为登录、支付、审批等复杂流程建状态机|进入、返回、刷新、直接访问都有明确行为|
|**5. 页面线框与布局**|用户先看什么、在哪里操作？|确定区域、内容顺序、主次操作、滚动方式和响应式布局|不依赖精细配色，也能理解和完成任务|
|**6. 组件与视觉规则**|哪些结构复用？如何保持一致？|定义字体、颜色、间距；拆分基础组件和业务组件|相同语义具有一致的外观与行为|
|**7. 静态页面实现**|布局能否真实落地？|使用模拟数据搭建页面，检查长文本、多内容和不同尺寸|主要布局稳定，内容变化不会轻易破坏页面|
|**8. 功能与数据接入**|页面能否完成业务？|接入接口、表单、权限、校验、提交和恢复逻辑|一条核心业务链可以端到端完成|
|**9. 状态与交互完善**|等待、失败、中断时会发生什么？|完善加载、空数据、错误、禁用、焦点、键盘与触摸交互|用户在关键状态下都知道当前情况和下一步|
|**10. 动效设计与实现**|哪些状态变化需要被看见？|为显示隐藏、布局变化、操作反馈等添加动画，处理打断与反向操作|动画能解释变化，快速连续操作也正常|
|**11. 性能与质量验证**|实际环境下是否顺畅可靠？|测量加载、交互、滚动、资源和渲染开销；验证兼容性与可访问性|达到预先约定的验收指标|

**这里的顺序表示工作重心，不表示前面完全不考虑后面的事情。** 例如，长列表的数据规模在布局阶段就要了解；错误状态在流程阶段就要设计；到了后期再集中验证和优化。

**第一步：从任务推导页面，而不是先凑页面数量**

例如做一个文件管理系统，先列出任务：

- 查找与浏览文件。
- 上传文件并查看结果。
- 预览、下载、重命名。
- 删除文件并恢复。

然后再决定承载方式：

|用户任务|可能的界面承载|
|---|---|
|浏览文件|文件列表页|
|查看文件内容|预览页或侧边抽屉|
|重命名|行内编辑或小弹窗|
|查看上传进度|页面中的任务面板|
|恢复已删除文件|回收站页|

**一个任务不一定对应一个页面，一个页面也可以承载多个相关任务。** 页面数量是组织任务后的结果。

**第二步：分开描述导航、业务状态和组件状态**

这三层相互关联，但职责不同：

|层级|描述对象|文件管理示例|
|---|---|---|
|**页面导航**|页面之间如何到达|文件列表、预览、回收站之间的跳转|
|**业务状态**|业务对象经历什么过程|文件上传：排队、上传中、成功、失败、已取消|
|**组件状态**|用户如何操作界面|上传按钮：可操作、悬浮、聚焦、按压、禁用|

例如，“上传中”不一定要跳到新页面，它可以只更新当前页面的进度组件。也不必把整个系统塞进一个巨大状态机：**为有明确规则的流程分别建模即可。**

**第三步：静态页面要验证真实内容边界**

静态阶段除了“正常效果图”，还要准备几类模拟数据：

|内容条件|要验证的布局问题|
|---|---|
|没有内容|空状态是否清楚，是否有下一步入口|
|内容很少|页面是否出现不合理的空白|
|内容很多|如何滚动、分页，操作区是否仍然可用|
|文本很长|换行、截断、提示和容器尺寸是否合理|
|图片缺失或比例不同|占位与布局是否稳定|
|窄屏、宽屏|内容如何重排，哪些操作需要收纳|

这样，静态页面已经具备承受真实数据的能力，后续接接口时返工会少很多。

**第四步：让功能、反馈和动画分层落地**

以“删除文件”为例，可以分三轮完成：

|轮次|实现内容|
|---|---|
|**业务可用**|选择文件、确认删除、发送请求、更新列表|
|**交互完整**|提交中反馈、防重复操作、失败提示、焦点处理、必要的撤销入口|
|**动效完善**|条目退出、剩余条目补位、提示出现；处理动画期间再次操作|

按钮按下反馈等基础效果可以随组件一起实现；复杂的页面编排动画适合在结构和交互稳定后添加。

**第五步：性能约束前置，具体优化依据测量**

|时机|要做的事情|
|---|---|
|**需求阶段**|明确设备、网络、数据规模，以及关键体验指标|
|**设计阶段**|考虑大列表、大图片、复杂图表和持续动画的成本|
|**实现阶段**|保持资源尺寸合理，避免重复请求、资源泄漏和明显多余的渲染|
|**验证阶段**|用接近真实的数据与设备测量，定位瓶颈后优化|
|**优化之后**|复测，并确认功能和视觉没有退化|

不要等所有动画完成后，才发现页面需要展示几万条数据；也不必在只有十条数据时，提前搭建复杂的虚拟列表系统。

实际推进项目时，推荐采用 **“全局先粗，核心流程先通，随后逐步扩展”** 的方式：

1. 先画完整业务流程、页面地图和粗线框。
2. 选一条最重要的任务链，贯通静态布局、接口、异常处理和基本交互。
3. 用这条任务链检验页面划分和组件设计。
4. 将验证过的组件与规则推广到其他页面。
5. 完善动效，再根据实际测量优化性能。

每个页面都可以维护一张简短的设计卡：**页面目的、入口与出口、区域布局、组件、数据、状态、交互、动效、验收条件**。随着项目推进逐项补齐，就能把设计稿持续细化为可开发、可验证的需求。
