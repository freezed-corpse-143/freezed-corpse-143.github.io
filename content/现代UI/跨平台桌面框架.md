# 统一框架

```text
跨平台桌面应用框架
├─ 接入面：怎么描述一个应用、怎么把它跑起来（pubspec.yaml + flutter run / tauri.conf.json + cargo / package.json + GN）
├─ 表示面：UI 在框架内部被表示成什么（Widget→Element→RenderObject 三棵树 / 无表示，只有 WebView 宿主句柄 / content::WebContents + gin 包装）
├─ 渲染面：像素从哪来、谁拥有提交（自绘 Impeller/Skia / 系统 WebView / 打包 Chromium）
├─ 控制面：谁拥有消息循环、谁决定下一帧（4 个 TaskRunner + Animator / tao EventLoop + 单一 Message 收件箱 / Chromium BrowserMainLoop + 泵入的 uv）
├─ 状态面：框架自己存什么、活多久（Element 树 + State + Binding / TypeId 作 key 的 insert-only StateManager / g_browser_process + 每进程一份 Node env）
├─ 通信面：前端 ↔ 原生怎么说话、怎么序列化（MethodChannel + StandardMethodCodec 自有二进制 / ipc://localhost 自定义 scheme + serde_json / mojo + V8 结构化克隆）
├─ 资源面：运行时从哪来、能不能共享（每引擎一份 VM，可 FlutterEngineGroup 共享 / 不打包运行时、用系统 WebView / 每个应用各带一份完整 Chromium）
├─ 平台面：适配的三层落在哪（能力发现 defaultTargetPlatform / 统一接口 embedder C ABI / 各平台 shell/platform/* / 编译期 cfg_alias / Runtime trait / runtime-wry / 五个 Client 工厂 / content+mojo / views + 平台子目录）
├─ 产物面：交出什么、谁签名、谁更新（flutter_tools 调原生工具链 / Rust bundler 直出 msi·dmg·deb / GN dist.zip + default_app.asar）
└─ 切面层：安全边界、插件、原生互操作、开发期状态保留（无内建权限系统 / 编译期能力清单 + 每次 IPC 强制 / 进程沙箱 + context bridge；热重载 / dev 重建 / 前端工具自己 HMR）
```

三个项目的根本区别，不是"支持哪些平台"，而是**把哪一层当作自己的核心抽象**：

- **Flutter**：以 **「不可变 Widget 配置 → 可变 Element 树（Element 持 State、下挂 RenderObject）」+ 自研渲染引擎**为核心抽象。框架只认这棵树：其上不关心平台，其下不关心 GPU 后端，平台被压成一组 embedder 回调。
- **Tauri**：以 **「WebView 宿主句柄 + 可替换的 Runtime 接缝」**为核心抽象。它没有 UI 模型，也没有渲染引擎；`Webview`/`Window` 是宿主句柄，`Runtime` trait 是唯一允许换掉的接缝（默认实现是 wry）。
- **Electron**：以 **「content::WebContents（浏览器进程手里的一棵帧树）+ 每进程固定注入一份 JS init bundle」**为核心抽象。它不发明窗口/文档模型，只用 gin 把别人的对象包成 JS 对象。

一句话记法：

```text
Flutter  → 自绘引擎 + 三棵树（拥有像素，把平台压成 embedder 回调）
Tauri    → 系统 WebView + Rust 后端（不拥有像素，把平台压成一个 Runtime trait）
Electron → 打包 Chromium + Node（拥有整个浏览器，把平台压成 content 之上的一层 gin 绑定）
```

## 先看三条根本问题（领域不变量收敛到 3 条）

| # | 根本问题 | 三个项目都必须回答的问题 |
| :--- | :--- | :--- |
| 1 | **语义正确性** | 用户写的 UI 描述（Widget 配置 / HTML / DOM）怎么变成确定性的一帧，输入事件怎么回到正确的处理者 |
| 2 | **载体归属** | 像素由谁产生、运行时由谁提供——自绘引擎、宿主系统 WebView，还是随包分发的浏览器 |
| 3 | **跨界最小化** | 每一次跨语境调用（Dart↔C++、JS↔Rust、JS↔C++）与每一帧怎么少算、少搬、少卡 |

第 2 条是这套骨架里"落到物理"那个槽位在本领域的特化：推理框架填的是"资源调度"、kernel 编译器填的是"硬件映射"、桌面框架填的是**执行与像素载体的归属**。它也是三家全部分歧的源头——先看这一条，其余八格基本都能推出来。

# 接入面

三家把"声明"和"启动"分开的方式完全不同：工具链用什么语言写、谁去拉起谁。

| | Flutter（`53d381d9067`） | Tauri（`61285f6fa`） | Electron（`df79406cec` / Chromium 156） |
| :--- | :--- | :--- | :--- |
| 工程清单 | `pubspec.yaml`（`packages/flutter/pubspec.yaml:1`） | `tauri.conf.json`（schema: `crates/tauri-utils/src/config.rs:4063`）+ `Cargo.toml` | `package.json`（`main` 字段即入口，`lib/browser/init.ts:120`） |
| CLI 入口 | `bin/flutter` → `bin/internal/shared.sh:273` exec Dart snapshot | `crates/tauri-cli/src/lib.rs:145` `enum Commands{Init,Dev,Build,Bundle,…}` | `npm/cli.js:7`（三行，只 `spawn` 转发） |
| 谁拉起谁 | Dart 工具链跑在 Dart VM 上，经 devfs 与设备通信；`flutter_tools.dart:7` → `commands/run.dart:709` | CLI 是 `cargo` 的包装：`interface/rust/desktop.rs:239` `runner` 默认 `"cargo"` | 构建入口是 GN 不是 npm：`BUILD.gn:1689` `executable("electron_app")` |
| 到第一个窗口 | `runApp`（`widgets/binding.dart:1890`） | `tauri::Builder::default().run(generate_context!())`（`Builder` 在 `crates/tauri/src/app.rs:1555`） | `electron_main_win.cc:228` `content::ContentMain` |
| 平台宿主工程 | 模板生成的（`templates/app/`），不是手写的 | 无（Cargo 原生） | 无（Chromium 构建体系） |

**要点**：入口不是引擎。

- Flutter 的入口把一整套 Dart 工具链带了进来——`bin/flutter` 本身就是 Dart 程序的 launcher，工具与框架同语言，所以 `flutter run/devtools/hot reload` 都能深达 VM。
- Tauri 的入口刻意薄：`tauri dev` 的全部实质是"读配置 → 设环境变量 → `cargo run`"。真正的应用逻辑入口是用户自己的 `main.rs`。
- Electron 的 npm 包只是分发壳（`npm/install.js:40` 下载预编译产物并写 `path.txt`），开发者真正会碰的构建入口是 GN/Chromium 那一侧。


# 表示面

这一面三家分成三类，是本领域差异最刺眼的地方。

| | Flutter | Tauri | Electron |
| :--- | :--- | :--- | :--- |
| 有 UI 表示对象吗 | 三棵树 | **无** | 借用别人的树 |
| 具体对象 | `Widget`(immutable 配置, `packages/flutter/lib/src/widgets/framework.dart:314`) → `Element`(`:3575`) → `RenderObject`(`rendering/object.dart:2010`) | `Webview`(`crates/tauri/src/webview/mod.rs:1428`) / `Window`(`window/mod.rs:996`) —— 宿主句柄，非 UI 模型 | `api::BrowserWindow`(`shell/browser/api/electron_api_browser_window.h:19`) → `api::BaseWindow`(`electron_api_base_window.h:46`) → `NativeWindow`(`native_window.h:62`, `views::Widget` @ `:522`) → `api::WebContents`(`electron_api_web_contents.h:124`) |
| 转换点 | `Widget.createElement`(`framework.dart:351`) / `Element.mount`(`:4346`) | 编译期一次性：`html2` 解析出 DOM 只为注入 CSP nonce（`crates/tauri-codegen/src/context.rs:28,80`） | JS `new BrowserWindow` → `electron_api_browser_window.cc:424` 的 `electron_browser_window` 绑定 |
| 真实状态载体 | `Element`（持 `State`，`framework.dart:918`） | 系统 WebView 内部的文档树（框架看不见） | `content::WebContents`（源码自述见下） |

`electron_api_web_contents.h:124` 的注释就是结论：

```cpp
// Wrapper around the content::WebContents.
class WebContents final : public gin::Wrappable<WebContents>, …
```

**要点**：这一格决定了各自的能力上限。

- **Flutter 有三棵自有树**，所以能做布局期介入（`RenderObject` 的 constraints）、能做局部重建（`Element` diff）、能做层栅格缓存（`RasterCache`）、能保留状态热重载（`Element.reassemble`）。
- **Electron 用别人的树**，所以能白拿 Blink 的全部能力（DOM/CSS/事件/DevTools），但也意味着"Electron 的 UI 模型"这个说法不成立——要研究 UI 得去研究 Chromium。
- **Tauri 没有树**，所以它对 UI 做的事只有三件：开窗口、塞 URL/HTML、接 IPC。想在 Tauri 里做"框架级布局优化"是没有接口的。

# 渲染面

| | Flutter | Tauri | Electron |
| :--- | :--- | :--- | :--- |
| 像素来源 | 自绘引擎（Impeller 或 Skia） | 系统 WebView | 随包分发的 Chromium |
| 提交链路 | `RendererBinding.drawFrame`(`rendering/binding.dart:691`) → `RenderView.compositeFrame`(`rendering/view.dart:346`) → `SceneBuilder`(`engine/src/flutter/lib/ui/compositing.dart:259`) → `View.render`(`lib/ui/window.dart:380`) → `Rasterizer::Draw`(`shell/common/rasterizer.cc:248`) → `LayerTree::Paint`(`flow/layers/layer_tree.cc:96`) | `runtime-wry/src/lib.rs:4737` `WebViewBuilder` → `:5166-5180` 分平台 `build_gtk(vbox)` / `build_as_child(&window)` → 交给 wry → WebView2 / WKWebView / WebKitGTK | `BUILD.gn:561` 直接依赖 `//third_party/blink/public:blink`、`:532-533` viz、`:581` ui/compositor、`:560` skia |
| 双后端 | 是：`flow/compositor_context.cc:183` Impeller / `:157` Skia | 否（后端由平台的 WebView 决定） | 否（就一个 Chromium，版本随框架走） |
| GPU 归属 | 引擎自己持有（GLES/Metal/Vulkan + 自有着色器编译器） | 宿主 | Chromium GPU 进程（Electron 只给空壳 `ElectronGpuClient`，`electron_main_delegate.cc:448`） |

**要点**：把"像素所有权"画成一条链，三家的能力与代价立刻对齐。

```text
Flutter : 框架 ──▶ 引擎 ──▶ GPU                    （全程自有，代价=引擎体积与维护）
Tauri   : 框架 ──▶ wry ──▶ 系统 WebView ──▶ 宿主合成器 （只在宿主之上贴一层，代价=跨平台不一致）
Electron: 框架 ─(不参与)─▶ Chromium ──▶ GPU          （把整条链打包进来，代价=分发体积）
```

# 控制面

| | Flutter | Tauri | Electron |
| :--- | :--- | :--- | :--- |
| 循环归谁 | 引擎的 `Animator` + 4 个 TaskRunner | 主线程的 tao `EventLoop` | Chromium 的 `BrowserMainLoop`（Node 的 uv 被泵进去） |
| 关键锚点 | `common/task_runners.h:15`（platform/UI/Raster/IO）；`Animator::RequestFrame`(`shell/common/animator.cc:239`) → `Engine::BeginFrame`(`shell/common/engine.cc:296`) | `runtime-wry/src/lib.rs:3091` `run` → `:3093` `event_loop.run(event_handler)`；`run_iteration`(`:3036`) 用 `ControlFlow::Wait`(`:3051`) | `ElectronBrowserMainParts : content::BrowserMainParts`(`electron_browser_main_parts.h:76`)；`node_bindings.cc:1137` `uv_run(uv_loop_, UV_RUN_ONCE)` |
| 跨线程约束 | 任务投递到对应 TaskRunner；UI 与 Raster 线程可合并(`rasterizer.cc:250`) | 一律封成消息：`run_on_main_thread`(`:2626`) → `send_user_message(Message::Task)`；收件箱 `enum Message`(`:1497`)；异步 command 另走 tokio(`crates/tauri/src/async_runtime.rs:29`) | 双循环合流：另开 embed thread 阻塞 `PollEvents`(`:1204-1213`)，`WakeupMainThread` 投回 MessageLoop；`uv_task_runner.cc:18` 反向投递 |

**要点**：三家都躲不掉"平台 UI 线程只允许被一个循环驱动"这条硬约束，区别只在**把约束收敛到几个地方**。

Flutter 把它收敛成四个 TaskRunner（embedder 必须提供，`embedder.h` 里有 `custom_task_runners`）；Tauri 收敛成一个收件箱；Electron 则完全继承 Chromium 的循环，并额外把 Node 的循环"挂"上去——这也是 Electron 里最容易出微妙 bug 的一块（`JoinAppCode` 抽干 uv，`electron_browser_main_parts.cc:379,382`）。

# 状态面

| | Flutter | Tauri | Electron |
| :--- | :--- | :--- | :--- |
| 框架自持状态 | `Element` 树 + `State`(`framework.dart:918`) + `RenderObject` + Binding 缓存 | `StateManager` = `TypeId` 作 key 的 insert-only 表（`crates/tauri/src/state.rs:102,107`），`State<'r,T>` 本质是 `&'r T`（`:20`） | `g_browser_process`(`browser_process_impl.cc:123`) + `node_bindings_`/`node_env_`(`electron_browser_main_parts.h:165,174`) + `KeyWeakMap`(`key_weak_map.h:19`) |
| 生命周期 | 跟随 Element 树；`State` 可跨重建存活 | 进程级；**插入后不可变更/移动**（`state.rs:100` 注释原文），唯一移除是 `unsafe fn unmanage`(`:131`) | 进程级；Node env 每进程一份且全局去重（`node_bindings.cc:187`） |
| 拥有者 | `WidgetsBinding` / `RendererBinding` 等 | `AppManager`（`manager/mod.rs:195` `Arc<StateManager>`） | `ElectronBrowserMainParts` + JS 侧 gin 单例（`app`/`session`） |
| 会话级缓存 | `RestorationManager`(`services/restoration.dart:158`) | `WebContextStore`(`runtime-wry/src/lib.rs:175`，按 `data_directory` 去重) | preload V8 code cache(`preload_code_cache.cc:181`) |
| 开发期状态保留 | **是框架职责**：`Element.reassemble`(`framework.dart:3772`) | 否 | 否（HMR 属 Vite/webpack） |

**要点**：Tauri 的 `StateManager` 是本领域里少见的一种明确取舍——**insert-only + 类型即 key**：

```rust
/// - Once you insert a value, you can't remove/mutated/move it anymore
type TypeIdMap = HashMap<TypeId, Box<dyn Any + Sync + Send>, BuildHasherDefault<IdentHash>>;
```

换来的是 `State<'r, T>` 零拷贝共享（不需要 `Mutex` 就能并发只读），代价是"运行期可变全局状态"这条路被主动堵死——你要可变就用 `Mutex` 或 channel，不要塞进来。

# 通信面

三家给出了三种完全不同的序列化与通道形态。

| | Flutter | Tauri | Electron |
| :--- | :--- | :--- | :--- |
| 通道 | MethodChannel → BinaryMessenger → PlatformDispatcher | 自定义 URI scheme `ipc://localhost` | mojo |
| 序列化 | `StandardMethodCodec` 自有二进制(`packages/flutter/lib/src/services/message_codecs.dart:580`) | `serde_json`，body 二态 `InvokeBody::Json/Raw`(`crates/tauri/src/ipc/protocol.rs:112-124`) | V8 结构化克隆 → `blink::CloneableMessage`(`shell/common/v8_util.cc:331,337`) |
| 完整链路 | `invokeMethod`(`platform_channel.dart:537`) → `_invokeMethod`(`:350`) → `BinaryMessenger.send`(`services/binding.dart:612`) → `Engine::HandlePlatformMessage`(`shell/common/engine.cc:548`) | JS `invoke`(`packages/api/src/core.ts`) → `scripts/core.js:81` → `scripts/ipc.js:145` → 响应带 `Tauri-Response: ok\|error` 头(`protocol.rs:29,126`) | `api.mojom:100` `ElectronApiIPC{Message/Invoke/MessageSync[Sync]/…}`，渲染侧绑定 `electron_api_ipc_renderer.cc:533` |
| 大 payload 优化 | 无特殊分流 | channel 双阈值：小包直接 eval、大包 `FETCH_CHANNEL_DATA_COMMAND` 回读(`ipc/channel.rs:31,319`) | `SerializedValue{BigBuffer buffer; uint64 size}`(`api.mojom:37`) |
| 中转税优化 | — | — | 主进程去掉 JS 蹦床，C++ 直接 emit(`electron_api_ipc_dispatch.h:36`；JS 只注册 `lib/browser/ipc-dispatch.ts:7`) |

**要点**：把三者并排看，能读出一条清晰的设计轴——**通道要不要复用已有语义**。

```text
Flutter : 不复用任何外部语义，自造二进制 codec        （最省，最封闭，多语言需同步实现）
Tauri   : 复用 HTTP 语义（方法/头/body/状态码）        （统一可拦截，代价=自己补 CORS/头语义）
Electron: 复用 Chromium 内部通道（mojo + 结构化克隆）   （最富表达能力，代价=与 Blink 强耦合）
```

Tauri 选 HTTP 语义的好处不只是"好读"：它让 ACL 与 isolation 有了**单一可拦截点**。这正是下一面（切面）的前置条件。

# 资源面

这一格的分歧最大——数量和倍数级差异全部来自"运行时从哪来"。

| | Flutter | Tauri | Electron |
| :--- | :--- | :--- | :--- |
| 运行时 | 引擎库（应用内嵌一份） | **不打包运行时**，用系统 WebView | 每个应用各带一份完整 Chromium + Node |
| 载体锚点 | 每 engine 一份 DartVM；`FlutterEngineGroup` 让同组引擎共享 VM/snapshot/字体缓存(`shell/platform/android/io/flutter/embedding/engine/FlutterEngineGroup.java:29`) | `crates/tauri-codegen/src/embedded_assets.rs:78,290`：前端资产 Brotli 压进二进制（档位源码注释称 hand-picked） | `npm/install.js:40` `downloadArtifact` 把整份 zip 解进每个应用的 `node_modules/electron/dist`；清单见 `script/zip_manifests/dist_zip.win.x64.manifest` |
| 多应用/多窗口共享 | 引擎内多 View 共享；跨应用不共享 | 同 app 内按 `data_directory` 复用 `WebContext`(`runtime-wry/src/lib.rs:175`，引用计数 `:4710-4735`) | 跨应用不共享 |
| 约束不足时退化 | 不共享则每 engine 一份 VM | WebView2 缺席 → 安装器下载 bootstrapper(`bundle/windows/nsis/installer.nsi:547`、`msi/main.wxs:294`)；运行期探针 `webview_version()`(`runtime-wry/src/lib.rs:2783`) | `ELECTRON_RUN_AS_NODE` → 同一二进制变纯 Node(`shell/app/node_main.cc:126`) |
| 裁剪手段 | —（引擎基本整体带） | 编译期（不需要的东西不编进） | 双时机：编译期 `buildflags/buildflags.gni`，打包期 `fuses`(`build/fuses/fuses.json5`) |

**要点**：这一格不是"谁更好"，是"复杂度在时间轴上的位置不同"。

```text
Tauri   : 复杂度推给用户机器（要有 WebView2/WKWebView/WebKitGTK，且版本各异）
Flutter : 复杂度推给开发者（把引擎塞进包，接受体积与启动成本）
Electron: 复杂度全部买断（体积/内存换确定性与 Node 全能力）
```

> 注：三者体积/内存的绝对数字**本仓库内均无实测数据**，此处不给数字。要数字必须自己构建后测。

# 平台面

三家都把平台适配切成三层，但"统一接口"那一层的位置完全不同。

| 层 | Flutter | Tauri | Electron |
| :--- | :--- | :--- | :--- |
| 能力发现 | 运行期：`defaultTargetPlatform`/`kIsWeb`(`packages/flutter/lib/src/foundation/platform.dart:51`，实现在 `_platform_io.dart:15`) | **编译期**：`tauri-build/src/lib.rs:660-661` 打 `cfg_alias("desktop"/"mobile")`；`tauri-utils/src/platform.rs:35` `enum Target` | 运行期 + 编译期混合：`ElectronMainDelegate::Create{Content,ContentBrowser,ContentGpu,ContentRenderer,ContentUtility}Client`(`shell/app/electron_main_delegate.cc:437-470`) |
| 统一运行接口 | **C ABI**：`FlutterEngineRun`(`shell/platform/embedder/embedder.h:2965`) + 嵌入方提供的 TaskRunner/渲染/平台消息回调 | **Rust trait**：`Runtime`(`crates/tauri-runtime/src/lib.rs:418`，另有 `RuntimeHandle:289`/`WebviewDispatch:545`/`WindowDispatch:675`) | Chromium 的 `content/public/*` + mojo |
| 各平台实现 | `engine/src/flutter/shell/platform/{windows,macos,linux,android,ios,fuchsia,glfw}/` | `crates/tauri-runtime-wry/src/lib.rs:2508` `Wry<T>`（包 wry + tao）；移动另见 `crates/tauri/src/plugin/mobile.rs`、`ios.rs:26` | `shell/browser/ui/{cocoa,gtk,win,x,views}` + `native_window_views.h:51` |

**要点**：这一层直接决定了"新增一个平台要动多少东西"。

- Flutter 的接口是**跨语言契约**（`embedder.h`，C ABI）：新平台 = 写一个 embedder，不需要改框架。
- Tauri 的接口是**同语言 trait**：新平台 = 加一个 `impl Runtime`（默认给 wry），但 `cfg(...)` 分支仍会散布在 `runtime-wry/src/lib.rs` 这个 5416 行的单文件里。
- Electron 的接口**不是自己定义的**：它是 Chromium 的 `content` 层。新平台 = 让 Chromium 先支持那个平台。这既是它最强的护城河，也是它最大的天花板。

# 切面层

安全边界画在哪，是三家姿态差异最大的地方。

| | Flutter | Tauri | Electron |
| :--- | :--- | :--- | :--- |
| 权限/能力模型 | **无**（交给宿主平台：macOS 模板 entitlements `templates/app/macos.tmpl/Runner/DebugProfile.entitlements:5`、Android Manifest；Dart 侧只有 isolate） | **有，且是核心**：编译期解析 capability→permission→resolved ACL(`tauri-build/src/acl.rs:404`、`acl/capability.rs:110`)，运行期**每次 IPC** 强制 `resolve_access` 并默认拒绝(`crates/tauri/src/webview/mod.rs:2052,2080`，"Command {} not allowed by ACL") | 进程沙箱 + 桥：`contextIsolation` 默认开且由 contextBridge 在调用点强制(`shell/renderer/api/electron_api_context_bridge.cc:1159`)；`sandbox` 由命令行门控(`command_line_args.cc:57`) |
| 前端信任假设 | 前端就是你的 Dart 代码，可信 | **前端不可信**：每次启动生成随机 128-bit Z85 invoke key(`crates/tauri/src/lib.rs:1281`)，Rust 侧逐请求比对(`webview/mod.rs:2011`) | **按世界分信任**：隔离世界之间靠递归代理 + 深冻结，递归上限 1000(`context_bridge.cc:62`) |

| 插件系统 | pub 插件 + 生成的 `GeneratedPluginRegistrant`(`packages/flutter_tools/lib/src/flutter_plugins.dart:1041,1047`) + MethodChannel | `trait Plugin`(`crates/tauri/src/plugin.rs:37`)，命令命名空间 `plugin:<name>|<cmd>` | **不定义插件 ABI**：原生走 Node N-API（`process.dlopen` 被 asar 层改写，`lib/node/asar-fs-wrapper.ts:2451`）；Chrome 扩展为编译期可选项 |

| 不可逆裁剪 | — | 编译期 cfg | **fuses**：把开关烧进二进制位，签名后 OS 保证改不回来(`build/fuses/fuses.json5`) |

**要点**：三种安全姿态，对应三种前端信任假设。

```text

Tauri    : 前端不可信 → 静态能力清单 + 每次调用强制 + 抗同机伪造的密钥
Electron : 前端半信半疑 → 按"世界"隔离，桥是唯一开口，能力开关烧进二进制
```

# 领域不变量（每一列都填满、且填法结构一致）

抽共性时要小心：抽出来的是"**任何一类框架都躲不掉的事**"，所以句子里不该出现项目名。

```text
不变量 1：必须定义"UI 描述 → 一帧"的确定性路径，并让输入事件回到正确的处理者。

不变量 3：必须把"平台 UI 线程/消息循环"这条硬约束收敛到一个受控点。

不变量 4：必须解决"前端语境 ↔ 原生语境"的跨界调用，并承担序列化与信任代价。
证据：Flutter（message_codecs.dart:580 + engine.cc:548）、Tauri（ipc/protocol.rs:38,112 + webview/mod.rs:2080）、
      Electron（api.mojom:100 + v8_util.cc:331 + context_bridge.cc:1159）。

不变量 5：必须交出"用户机器上能装的东西"，并把签名/更新的责任显式交给某一层。
证据：Flutter（build_ios.dart:561、无应用更新器）、Tauri（bundle.rs:191 + updater_bundle.rs:29 + 插件）、
      Electron（BUILD.gn:1909 dist.zip + auto-updater.md:13-14 + 外部 builder）。

不变量 6：必须显式处理"平台能力不齐"，并有降级路径。
证据：Tauri 逐条标注各后端权限支持情况（tauri-runtime/src/webview_permissions.rs:18-99，macOS 多项 "not yet supported by platform backends"）；
      Electron 用 views 统一 + shell/browser/ui/{cocoa,gtk,win,x} 分派；Flutter 用 shell/platform/* 分实现 + embedder 回调能力协商。
```

再抽一层，收敛到三条（见篇首）：**语义正确性 / 载体归属 / 跨界最小化**。

自检不变量 6 的判据：把上面任何一条句子里的项目名删掉，话还成立——成立了，才是领域不变量。

# 设计空间（差异 → 选项 + 代价 + 决定因素）

## Q1 执行与像素载体从哪来？

```text
- 选项甲（Flutter）：自绘引擎 —— 擅长像素级一致与性能可控；代价=引擎体积、启动成本、无法复用系统控件
- 选项乙（Tauri）：宿主系统 WebView —— 擅长体积小、无运行时维护；代价=跨平台渲染/API 不一致、能力被 WebView 版本卡住
- 选项丙（Electron）：随包分发 Chromium —— 擅长确定性行为 + 完整 Node 能力；代价=体积/内存数倍、升级必须整体发版
决定因素：能不能接受"用户机器上的渲染行为不由你决定"（能 → 乙；不能且要跨平台一致 → 甲；不能且要 Web 生态+Node → 丙）
```

## Q2 UI 在框架内部有没有表示对象？

```text
- 选项甲（Flutter）：三棵自有树（Widget/Element/RenderObject）—— 擅长介入布局/绘制/局部重建；代价=要维护一整套 UI 框架与语言绑定
- 选项乙（Tauri）：没有 —— 擅长极薄、语义零阻抗；代价=框架层面无法做任何 UI 优化，只剩"开窗口 + 塞内容"
- 选项丙（Electron）：复用 content 的树 —— 擅长白拿 Blink 全部能力；代价=框架自身没有 UI 抽象，能力被 Chromium 版本绑定
决定因素：你要在 UI 层做"框架级"的事吗？（要 → 甲；只要壳 → 乙；只要 Web 的全部能力 → 丙）
```

## Q3 跨语境通道用什么形态？

```text
- 选项甲（Flutter）：自有二进制 codec —— 擅长高频小消息；代价=多语言需同步实现、类型受 codec 限制
- 选项乙（Tauri）：自定义 URI scheme + HTTP 语义 + JSON —— 擅长统一可拦截、可审计；代价=自己补头/CORS 语义、JSON 有开销
- 选项丙（Electron）：mojo + V8 结构化克隆 —— 擅长传富对象（Blob/ArrayBuffer/MessagePort）与保序；代价=与 Blink 强耦合、序列化面大
决定因素：通道上要不要做统一鉴权？（要 → 乙；只追求吞吐 → 甲；要传结构化对象 → 丙）
```

## Q4 平台差异在编译期还是运行期吸收？

```text
- 选项甲（Tauri）：编译期为主 —— 擅长零运行期开销、死代码可裁剪；代价=平台组合爆炸（runtime-wry 单文件 5416 行）、新平台要改核心文件
- 选项乙（Flutter）：运行期能力发现 + 编译期各平台分实现 —— 擅长一套引擎盖住 5+ 平台；代价=嵌入方要实现大量回调与线程契约
- 选项丙（Electron）：继承上游（Chromium 决定支持谁）—— 擅长几乎零适配成本；代价=平台集合不由自己决定
决定因素：平台集合是"固定且体积敏感"还是"可能动态扩展"（前者 → 甲；后者 → 乙）
```

## Q5 安全边界画在哪？

```text
- 选项甲（Flutter）：不画（人写的前端就是可信的）—— 擅长简单；代价=前端一旦注入不可信内容，框架不提供任何兜底
- 选项乙（Tauri）：静态能力清单 + 每次调用强制 + 抗伪造密钥 —— 擅长默认拒绝、清单可静态审计；代价=每次 IPC 要过 ACL、扩能力要走构建期
- 选项丙（Electron）：进程沙箱 + 按世界分信任的桥 —— 擅长默认隔离；代价=preload 要拆成最小暴露面、跨世界传值要服代理语义
决定因素：会不会加载不可信/远程内容？（不会 → 甲；会且要可审计 → 乙；会且依赖 Web 生态 → 丙）
```

## Q6 开发期状态保留谁来负责？

```text
- 选项甲（Flutter）：框架负责（VM 换类 + Element.reassemble 遍历，State 实例不丢）—— 擅长迭代快、状态不丢；代价=代码必须可重入、State 需处理 reassemble
- 选项乙/丙（Tauri/Electron）：前端工具负责（Vite/webpack HMR），框架只负责重建进程 —— 擅长职责清晰；代价=框架层面的状态（Rust State / 主进程 Node 状态）重启即丢
决定因素：框架是否拥有 UI 树（拥有才可能做到"保留实例树的热重载"）
```

> 这一条是本表里**唯一只有一家填满的格子**，也是"三家骨架相同但能力不同"的典型证据。

**"取系统信息"这一步的差别最值得注意**：

- Tauri：Rust command 直接执行——**没有跨界**，后端本来就是原生。
- Flutter：走 MethodChannel 跨到平台代码（或 `dart:ffi`）——**一次跨界 + 一次编解码**。
- Electron：主进程 Node 直接执行——**没有跨界**，但主进程本身跑在 Chromium 里。

"后端是不是原生"是 Tauri 与另两家的另一条分界线：Tauri 的原生不是"额外能力"，而是它的全部后端。

# 并排学习的关注点（怎么用这张表继续往下钻）

## 只研究"渲染所有权"

```text
沿同一条链追踪：UI 描述 → 中间表示 → 图层 → GPU 提交 → 窗口
对照结论：
  Flutter 在"中间表示"处有自有资产（DisplayList/Layer 树/RasterCache），所以能做层复用与后端切换；
  Tauri   在"图层"处就交出去了，只剩一句 build_xxx；
  Electron 连"UI 描述"都不在自己手里（Blink 所有）。
问：这个框架在渲染链上"最靠上"的那个自有对象是什么？（Flutter: Layer 树；Tauri: 无；Electron: 无）
```

## 只研究"平台差异税"

```text
1. 平台分支写在哪？（单文件 match / 独立目录 / patch 上游）
2. 新平台是"加实现"还是"改核心"？（Flutter 加 embedder；Tauri 加 impl 但 cfg 散布；Electron 等 Chromium）
3. 能力不齐时是显式降级还是隐式不支持？（Tauri: webview_permissions.rs:18-99 逐条标注；Flutter: 回调协商；Electron: views 抽象）
```

## 只研究"信任边界"

```text
1. 框架认为"前端可信"还是"前端不可信"？（可信 / 不可信 / 分世界）
2. 强制点在哪一次调用上？（无 / 每次 IPC 的 resolve_access / 每次跨世界传值）
3. 能不能在装好之后被关掉？（Flutter: 无此概念；Tauri: 能力清单在构建期；Electron: fuses 烧进二进制并由签名保护）
```

## 只研究"打包与体积"

```text
1. 运行时谁来提供？（框架自带 / 系统自带 / 用户机器补装）
2. 裁剪发生在哪个时机？（编译期 buildflags / 打包期 fuses / 无）
3. 更新协议归谁？（商店 / 插件 / 只有 mac+win）
```

# 最终的认知

三个框架本质上都在解决同样三件事：

1. **语义正确性**：把用户写的 UI 描述正确落到一帧上，并让输入回到正确的处理者。三家的差别在于"这一帧是否由框架自己算出来"。
2. **载体归属**：像素与运行时由谁提供。这一条决定了另外八格里的大部分后果——体积、跨平台一致性、能介入到多深、平台适配要付多少税。
3. **跨界最小化**：每次跨语境调用与每一帧都要少算少搬。序列化格式、帧调度、启动快照、热重载、IPC 分流，全部属于这一条。

三个框架分别提供了三个最佳观察窗口：

```text
Flutter
  → 看"一个完整 UI 栈（语言 + 树 + 渲染器 + 工具链）如何被设计成跨平台一致的"
    以及"拥有像素"这件事换来了什么、又必须自己维护什么

Tauri
  → 看"一个应用外壳的最小抽象边界在哪里"
    一个 trait、一个 StateManager、一套 ACL —— 渲染、运行时全部推给宿主

Electron
  → 看"把上游大工程的某一层（content）直接当成自己的核心抽象"是什么后果
    强的部分是别人的，贵的部分（补丁债、体积）是自己的
```

对桌面应用框架再补一问（这一领域特有的）：

> **它认为"运行时"是它的问题、宿主的问题，还是用户机器的问题？**
> 这一问决定了它的体积、启动成本、崩溃面、以及升级策略。
