
# 可拔插插件系统

核心目标：在不修改主程序代码的前提下，让主程序动态感知并加载外部功能模块

### 1. 插件契约（Contract / SPI）

主程序需要定义一套稳定的接口规范，所有插件必须实现该接口。这是插件与宿主之间唯一的耦合点。例如 Java 的 `java.util.ServiceLoader`、Eclipse 的扩展点机制、VS Code 的 Extension API 都属于此类契约。契约一旦发布，需要保持向后兼容，否则已有插件将失效。

### 2. 插件发现（Discovery）

宿主程序启动时或运行中，需要知道“有哪些插件可用”。常见发现方式包括：

- **目录扫描**：约定插件目录（如 `plugins/`），宿主扫描该目录下的动态库或包；
- **配置文件声明**：宿主读取一个 manifest 文件，其中列出已安装插件的路径与元信息；
- **注册中心**：在分布式系统中，插件本身可能作为服务注册到注册中心，宿主通过服务发现机制获取可用插件列表。

### 3. 插件隔离与加载（Loading & Isolation）

插件加载的核心挑战是**类加载器隔离**。如果所有插件共享宿主的类加载器，插件之间的依赖冲突将无法解决（例如两个插件依赖同一个库的不同版本）。因此，成熟插件系统通常为每个插件创建独立的类加载器，仅将宿主暴露的 API 类传递给插件。OSGi 是这一领域的经典实践。

### 4. 生命周期管理

插件需要经历安装、启动、运行、停止、卸载等状态。宿主需要提供生命周期钩子（如 `onLoad`、`onEnable`、`onDisable`），并处理插件热部署场景下的资源释放问题。

# 服务注册与发现

服务注册与发现本质上是**注册表模式（Registry Pattern）** 在分布式环境下的应用。

### 核心结构

注册表模式包含三个角色：

- **服务提供者（Provider）**：启动时将自己的网络地址（IP:Port）、服务名、元数据写入注册表；
- **注册表（Registry）**：一个高可用的数据库，存储所有服务的实例信息，并通过心跳机制感知实例的存活状态；
- **服务消费者（Consumer）**：启动时从注册表拉取目标服务的实例列表，缓存到本地，并在注册表推送变更时更新缓存。

### 两种实现拓扑

**客户端发现**：消费者直接从注册表拉取实例列表，自己决定调用哪个实例（负载均衡逻辑在客户端）。Dubbo、Eureka + Ribbon 属于此类。优点是少一次网络跳转，且客户端可以缓存并容忍注册表短暂不可用。

**服务端发现**：消费者只调用一个固定的负载均衡器地址，由负载均衡器查询注册表并将请求转发到具体实例。Kubernetes 的 Service、AWS ELB 属于此类。优点是客户端简单、语言无关，但负载均衡器可能成为瓶颈。

### 与微服务的配合

在微服务架构中，服务注册与发现使得服务的位置不再静态绑定。每个服务只需要知道目标服务的**逻辑名称**，具体的网络位置由注册表在运行时动态解析。这是实现弹性伸缩、故障转移和蓝绿部署的基础设施。

# 冷启动优化

冷启动的核心矛盾是：**启动阶段需要完成的工作量（配置解析、依赖初始化、类加载、序列化）与用户对响应速度的期望之间的冲突**。优化手段可以从不同层次切入。

### 1. 减少启动时读取的文件数量与随机 I/O

启动时读取大量零碎配置文件是常见性能陷阱。机械硬盘的随机读取性能极差，即使是 SSD，多次文件打开与系统调用也有开销。优化策略是**合并配置文件为单一文件**，启动时一次顺序读取完成，然后内存中解析。

Chrome 的配置存储策略即遵循此原则：将历史记录、密码等零碎数据合并，避免启动时的大量随机 I/O。

### 2. 序列化格式选择

配置数据的序列化格式直接影响反序列化速度。实测数据表明：

- **JSON**：读取约 183 ms，写入约 165 ms（1000 条 key-value）；
- **ProtoBuf**：读取约 92 ms，写入约 119 ms；
- **自定义简单格式**（如一行 value 一行 key）：读取约 1 ms，写入约 7 ms。

对于启动场景，**配置结构简单且可控时，自定义序列化往往远快于通用库**。但如果配置结构复杂或需要跨语言，ProtoBuf 是更平衡的选择。注意：使用第三方序列化库本身会引入 DLL/动态库加载开销，这部分可能抵消序列化收益。

### 3. 减少启动时加载的库

动态库的加载（尤其是大型第三方库）可能占据启动时间的主要部分。一个不到 100 KB 的配置文件，如果用到的序列化库本身加载就需要数百毫秒，收益为负。原则是：**启动阶段只加载必需的最小依赖集**，非关键库延迟到实际使用时再加载。

### 4. 快照与预初始化技术

**AWS SnapStart（Java）**：Lambda 函数初始化阶段完成后，将整个 JVM 堆快照保存。后续冷启动直接从快照恢复，跳过初始化代码执行。但需要注意：快照中的静态初始化块中如果使用了 `currentTimeMillis`，恢复时会得到快照创建时的时间而非当前时间；基于时间的缓存也会失效。

**GraalVM Native Image**：通过 Ahead-of-Time 编译，将应用编译为原生可执行文件。启动时没有 JIT 编译和类加载开销，启动时间和内存占用都显著低于 JVM 模式。代价是构建时间长，且需要依赖库支持 AOT（反射、动态代理等需要配置）。
